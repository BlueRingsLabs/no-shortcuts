# 43.1 Building eval suites

*About 10 hours. Prerequisites: 39.1 (evaluating models), 18.3 (classifier error rates), 05.1 (the bootstrap). Lab: [`lab_43_1_eval_suites.py`](labs/lab_43_1_eval_suites.py).*

Here's how most LLM features ship: someone writes a prompt, tries it on five inputs they thought of, likes the outputs, and merges.
Two weeks later someone else "improves" the prompt, tries it on five different inputs, likes those too, and merges. Nobody knows whether
the product got better or worse, and the first sign is a customer screenshot on social media. That's vibes-based engineering, and it's
the default.

The fix is the same one software engineering found decades ago: tests, run on every change. An **eval suite** is a test suite for
behavior that can't be fully specified: a set of cases, checks on the outputs, and a report comparing the current version with the
last one. 39.1 was about judging models in general. This lesson is about judging *your* system on *your* task, which is the only
evaluation that tells you whether to ship.

The lab evaluates a small question-answering system over this course (BM25 retrieval, 41.1, with the best passage's first sentences as the
answer, plus a citation) on 672 exercise questions from the course, whose correct source lesson is known. It compares two versions that differ
only in chunking.

## The cases

A good eval set is built from reality, not imagination:

- **Real inputs**: sampled from production traffic (anonymized), or, before launch, from the people who will use it. Your
  imagination produces clean, typical inputs; users produce the rest.
- **Every failure you've seen**: each bug report, bad trace (43.2) and red-team finding (44.2) becomes a case. This is where the value
  compounds: the suite remembers every mistake so the system doesn't repeat it.
- **Coverage of the hard parts**: edge cases, each category of request, adversarial inputs, and inputs that should be refused or
  answered with "I don't know".
- **Enough of them** to detect the differences you care about (below). Dozens for a smoke test, hundreds to thousands for decisions.

Each case records the input, what a good output must satisfy (a reference answer, required facts, a source), and metadata (category,
where it came from). Version the set with the code (48.2), and keep a held-out part you don't look at while iterating on prompts, or
you'll overfit the prompt to your tests (18.1).

## The checks

Check as much as possible **in code**. Code checks are fast, free, deterministic and never drift:

- format and schema (40.2): parses, validates, required fields;
- constraints: length, language, no forbidden content, required disclaimers;
- grounding: citations exist and point to retrieved sources (41.3); numbers in the answer appear in the sources;
- task-specific correctness when there's a reference: the right label, the right source, the right tool called with the right
  arguments, a SQL query that returns the expected rows, code that passes tests.

The lab's checks are all code: non-empty, has a citation, the cited lesson exists, under 90 words, the citation appears in the text, and
the cited lesson is the right one. Every failure is named, which makes the report readable:

| version | pass rate | wrong source | too long |
|---|---|---|---|
| v1, plain chunks | 0.682 | 204 | 16 |
| v2, chunks with title and heading | 0.717 | 181 | 15 |

And the most useful line in the report isn't the pass rate. It's this: **v2 fixed 34 cases and broke 10.** A single number hides that
every change moves cases in both directions. The broken list is what you read before shipping, because one of those 10 might be a case
that matters more than all 34 fixes put together.

What code can't check (helpfulness, tone, whether an explanation is correct), people or models judge. Both need the treatment below.

## Is the difference real?

The lab's comparison: v2 − v1 = +3.6 points, paired bootstrap 95% interval [+1.6, +5.5], so the improvement is real. Now the same
comparison on subsets, as if the suite were smaller:

| cases | difference | 95% interval |
|---|---|---|
| 672 | +0.036 | [+0.016, +0.055] |
| 200 | +0.040 | [+0.005, +0.075] |
| 50 | +0.040 | [−0.060, +0.140] |

With 50 cases, the suite can't tell a 4-point improvement from a 6-point regression; with 200 it barely can. The versions disagree on only 6.5% of cases, and in a
paired comparison those disagreements are all the evidence there is (39.1). So:

- Compare versions **paired**, on the same cases, and report the interval.
- **Size the suite** for the effect you need to detect. Roughly, you need tens of disagreements in the direction of the change before
  the difference is distinguishable from noise.
- For stochastic systems, run each case **several times** and look at the distribution (42.1). A case that passes 3 times in 5 is not
  "passing".

## LLM-as-judge

For qualities code can't check, teams use a model as a judge: give it the input, the output, a rubric (and a reference, if there is one),
and ask for a verdict. It's often the only way to evaluate at scale, and it's a classifier with errors like any other. So measure it
before trusting it.

The lab's judge sees 400 answers that people have labeled. It agrees with the people 83% of the time, which sounds good, but Cohen's
kappa, which discounts agreement expected by chance, is 0.595: moderate. It passes 86% of good answers and 24% of bad ones. Three
things to do with those numbers:

1. **Decide if it's good enough** for the decision you're using it for. A judge with 24% false passes is fine for tracking trends, and
   not fine for certifying a release.
2. **Correct aggregate rates.** If the judge passes good answers with rate $\text{TPR}$ and bad ones with rate $\text{FPR}$, an
   observed pass rate $o$ implies a true rate of $(o - \text{FPR}) / (\text{TPR} - \text{FPR})$ (the Rogan-Gladen estimator from
   epidemiology). On v1's 672 answers, which the judge hadn't been measured on, its raw pass rate is 0.662, the corrected rate 0.683
   (95% bootstrap interval 0.617 to 0.741), and the truth 0.682. The correction removes the bias and costs variance: dividing by
   $\text{TPR} - \text{FPR}$ amplifies the uncertainty of rates measured on 400 labels, and rates measured on one system's answers
   don't transfer exactly to another's (this judge likes long answers, and v1's are shorter). Report the interval.
3. **Test its biases.** Judges prefer longer answers, the first answer in a pairwise comparison, and outputs written in their own style.
   The lab's pairwise judge says v1 wins 43% of disagreements when v1 is shown first and 25% when it's shown second; the truth is 23%.
   Always run pairwise comparisons in both orders and average (or count only consistent verdicts).

Practices that make judges better: a specific rubric with examples of each grade rather than "rate helpfulness 1-10"; binary or
few-level verdicts rather than fine scales; asking for the reasoning before the verdict; a reference answer when one exists; a different
model family from the one being judged; and re-measuring agreement whenever the judge's model or prompt changes. The judge is a model in
production, and it drifts like one.

## Running it

- **On every change** to prompts, models, retrieval, tools or parsing code: a fast subset in CI (50.1), the full suite before
  release.
- **Report** pass rates per category, the fixed and broken lists, cost and latency per case, with intervals.
- **Gate releases** on no regression in critical categories and no significant regression overall, not on "the number went up".
- **Keep humans in the loop**: a person reads a sample of outputs for every release. Evals catch what you thought to check.

> **Scar tissue.** For a study group's Discord, I built a bot that answered questions about our course notes, and "improved" it for two
> weeks, judged by an LLM grader. When I finally read the outputs, the answers had become long, hedged and padded with restated questions.
> The judge preferred longer answers, every prompt change that made answers longer won the comparison, and I'd optimized the judge's taste
> instead of quality. Measure the judge against your own labels before you trust its scores, and look for length bias first.

## Things that will bite you

- **Five hand-picked examples** as the eval.
- **A single aggregate number** with no broken-cases list.
- **Too few cases** for the differences you're claiming.
- **Judges nobody measured**, used in one order, with a vague rubric.
- **Tuning prompts on the whole suite** until it passes, then being surprised in production.
- **Evals that never gain new cases** from production failures.

## Exercises

1. Write five code checks for a system that drafts replies to customer emails.
2. A change raises the pass rate from 81% to 83% on 150 cases. The versions disagree on 9 cases: 6 fixed, 3 broken. Ship it?
3. Your judge has TPR 0.9 and FPR 0.3. It passes 75% of this week's outputs. What's your estimate of the true pass rate? What if its FPR
   were measured on a different kind of output than this week's?
4. How would you detect a judge's preference for its own model family's outputs?
5. Where should an eval set's cases come from before a product has any users?
6. Why does a held-out part of the eval set matter when you iterate on prompts?

1. The reply parses into the expected structure (greeting, body, sign-off); it's under a length limit; it's in the customer's language; it

4. Take pairs of outputs from two model families that humans rated equal (or blind human preferences), and check whether the judge

5. From the people who will use it (ask them for real examples of what they'd ask), from existing channels (support tickets, search

   replace imagined cases with real ones as soon as traffic exists.

6. Every prompt change you keep because it improved the suite is a small fit to the suite. After many iterations the prompt is tuned to
   those cases, and the suite overstates quality (18.1). A held-out part, used only for final checks, estimates quality on cases the
