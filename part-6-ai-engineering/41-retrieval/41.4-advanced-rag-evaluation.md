# 41.4 Advanced RAG and evaluating retrieval

*About 8 hours. Prerequisites: 41.3, 05.1 (confidence intervals and the bootstrap). Lab: [`lab_41_4_advanced_rag_eval.py`](labs/lab_41_4_advanced_rag_eval.py).*

The RAG literature is full of techniques with good names: HyDE, query decomposition, GraphRAG, agentic retrieval, RAG-fusion. Each has
papers showing improvements, and each makes some systems worse. You can only know which by measuring on your own questions, carefully
enough that the measurement is worth more than the blog post that recommended the technique. So this lesson is half techniques and half
evaluation, and the evaluation half matters more.

The lab uses two query sets over this course: the exercise questions (the answer is in the lesson they belong to), and sentences from
lessons that cross-reference another lesson, with the reference removed (the answer is the referenced lesson, and the source lesson is
excluded from the results). The index is Parts 0 to V of the course, as in 41.1.

## Metrics, and what they reward

- **Recall@k**: is a relevant item in the top $k$? What matters when the generator reads the top $k$ anyway.
- **MRR** (mean reciprocal rank): $1/\text{rank}$ of the first relevant item. Rewards putting it first.
- **nDCG@k**: graded relevance, discounted by position: $\text{DCG} = \sum_i \text{gain}_i / \log_2(i + 1)$, normalized by the best
  possible ordering. Useful when "partly relevant" exists.
- **Precision@k**, for when the prompt is small and every irrelevant chunk displaces a relevant one (and can mislead the generator).

The lab grades relevance as 2 for the right lesson and 1 for another lesson of the same module:

| system | exercises recall@5 | exercises nDCG@10 | references recall@5 | references nDCG@10 |
|---|---|---|---|---|
| BM25 | 0.93 | 0.63 | 0.79 | 0.52 |
| dense | 0.48 | 0.33 | 0.41 | 0.27 |
| hybrid (RRF) | 0.78 | 0.53 | 0.70 | 0.45 |

The metrics agree on the order here, and they don't always: nDCG gives credit for "the right area", which a system that retrieves
neighbors of the answer can earn without ever retrieving the answer. **Choose the metric that matches what the generator needs**, and
write down why. The cross-reference queries are harder than the exercises for every system, which is typical: queries written by people
who know where the answer is are easier than real users' queries. Build the evaluation set from real queries when you can.

## Building an evaluation set

- **Real questions** from logs, tickets, search history, labeled with the passages that answer them. A few hundred is a start.
- **Synthetic questions**: an LLM writes questions for sampled passages. Cheap, and biased toward the passage's own wording, which flatters
  lexical retrieval. Use them for coverage, and keep a real set as the judge.
- **Unanswerable questions**, so abstention (41.3) gets measured.
- **Hard cases on purpose**: identifiers, negations, multi-part questions, questions that need two documents.
- **Freeze it and version it** (48.2), and add every production failure to it.

## Query rewriting

The query is often the weakest link: short, vague, in the user's words rather than the documents'.

- **Pseudo-relevance feedback** (Rocchio, 1971; RM3): assume the top few results are relevant, add their most distinctive terms to the
  query, search again.
- **HyDE** (Gao et al., 2022): have an LLM write a hypothetical answer, and search with that. The same idea as PRF, with an LLM as the
  expander: a fake answer looks more like a real document than a question does.
- **Decomposition**: split a multi-part question into sub-questions, retrieve for each, merge.
- **Multi-query / RAG-fusion**: several LLM paraphrases of the query, retrieve for each, fuse with RRF.

On this course, with BM25:

| query handling | exercises recall@5 | references recall@5 |
|---|---|---|
| BM25 | 0.930 | 0.792 |
| BM25 + PRF | 0.935 | 0.799 |
| BM25, decomposed into sentences + RRF | 0.878 | 0.792 |

PRF adds about half a point, which (next section) is inside the noise. Decomposition hurts: exercise questions have several sentences, but
they're about one lesson, and searching each sentence separately gives weight to sentences that are set-up, not substance. Rewriting helps
when the user's words differ from the documents' and the first results are decent; it drifts toward the wrong topic when they aren't. It
also costs an LLM call per query. Measure.

## Structure: graphs

Documents link to each other: citations, hyperlinks, a wiki's categories, this course's "(29.1)" references. A graph adds knowledge that
isn't in any single chunk's text: which documents belong together. The lab builds the cross-reference graph of the course (about 130
lessons, over 850 links) and lets each lesson's score borrow from its neighbors' scores, weighted by $\alpha$:

| hybrid + graph | exercises recall@5 | references recall@5 |
|---|---|---|
| $\alpha = 0$ (no graph) | 0.783 | 0.695 |
| $\alpha = 0.3$ | 0.784 | 0.715 |
| $\alpha = 1.0$ | 0.783 | 0.731 |

It helps only the reference queries (by 2 to 4 points), and leaves the exercises where they were. The reference queries are the ones about how lessons relate, and that's what the graph encodes. **GraphRAG**
(Edge et al., 2024) goes much further: an LLM extracts entities and relations into a knowledge graph, clusters it, and summarizes the
clusters, which helps "global" questions ("what are the main themes across these documents?") that no single chunk answers. It's
expensive to build and maintain; use it when your questions are of that kind.

## Is the difference real?

Every number above is an average over a few hundred queries, and averages over a few hundred queries have wide intervals. Compare systems
**on the same queries** and bootstrap the per-query differences (05.1):

| comparison | recall@5 difference | 95% CI | verdict |
|---|---|---|---|
| exercises: hybrid − BM25 | −0.147 | [−0.179, −0.118] | real |
| exercises: PRF − BM25 | +0.004 | [−0.004, +0.015] | could be noise |
| references: hybrid − BM25 | −0.097 | [−0.124, −0.069] | real |
| references: PRF − BM25 | +0.007 | [−0.012, +0.025] | could be noise |

The hybrid's loss is real (the dense retriever here is weak, 41.1). PRF's gain isn't established. That's a typical outcome for a
"technique that helps": a point or two, inside the noise, on a query set too small to tell. Decide before running the comparison what
difference would matter, and make the query set large enough to detect it.

## Evaluating the generation step

Retrieval metrics say whether the right sources reached the prompt. They don't say whether the answer used them correctly. The properties
to measure:

- **Faithfulness (groundedness)**: every claim in the answer is supported by the retrieved sources.
- **Answer relevance**: the answer addresses the question.
- **Correctness** against a reference answer, when you have one.
- **Citation accuracy**: the cited source supports the sentence (41.3).

The lab tests the cheapest faithfulness check, the share of an answer sentence's content words found in its source (a sentence passes at
0.6 or more), on four kinds of sentence:

| sentence | mean overlap | passes |
|---|---|---|
| copied from the source | 1.00 | 100% |
| source sentence with words dropped | 1.00 | 100% |
| from another lesson | 0.08 | 0% |
| source sentence with one fact changed | 0.94 | 100% |

It separates on-topic from off-topic perfectly, and it passes every sentence whose fact was changed, which is the error that matters most.
Catching "the source says 0.7 and the answer says 0.5" takes a model that reads for meaning: an NLI model (does the source entail the
sentence?) or an LLM judge. Frameworks such as RAGAS package these as scores; they're LLM judges, with judges' biases, and 43.1 shows how to
validate a judge against human labels before trusting its numbers. Use the lexical check as a cheap first filter, not as the metric.

## Other techniques worth knowing

- **Agentic retrieval**: the model decides when and what to search, possibly several times, using search as a tool (42.1). Better for
  multi-step questions, harder to evaluate and control, slower.
- **Long-context models instead of RAG**: when the corpus fits in the context window, just include it. For a small, stable corpus that's
  often simpler, with caching (45.1) making it affordable. RAG still wins on large or changing corpora, access control and cost per query.
- **Fine-tuning the retriever** on in-domain pairs (41.1): the most reliable improvement when you have the data.
- **Late interaction** (ColBERT): token-level embeddings matched at query time, between bi-encoders and cross-encoders in cost and quality.

## Things that will bite you

- **Adopting techniques from papers** without measuring them on your queries.
- **One metric** chosen after seeing the results.
- **Unpaired comparisons** and no intervals, on a hundred queries.
- **Synthetic-only evaluation sets** that flatter lexical overlap.
- **Lexical faithfulness scores** reported as faithfulness.
- **Evaluation sets that never grow** while the corpus and the users change.

## Exercises

1. When would nDCG and recall@5 rank two systems differently? Give a concrete example.
2. Why do synthetic questions generated from passages flatter BM25?
3. HyDE and pseudo-relevance feedback share an idea. What is it, and when does it backfire?
4. System B beats system A by 1.5 points of recall@5 on 300 queries. What do you do before switching?
5. Design a faithfulness check for a medical-information RAG system, and how you'd validate it.
6. Your corpus is 200 pages and changes monthly. RAG or long context? What would you measure to decide?

<summary>Answers</summary>

1. System A puts the right lesson at rank 4 and irrelevant ones elsewhere; system B puts four lessons of the right module in the top 4 and
   the right lesson at rank 7. Recall@5 prefers A; nDCG@10 may prefer B, because it credits the partial matches near the top.

2. The generator reads the passage and writes a question, usually reusing its distinctive words. Lexical retrieval matches those words
   exactly, so it looks better than it will on real users' questions, which use their own vocabulary.

3. Both expand the query with text that resembles relevant documents (PRF with terms from the top results, HyDE with an LLM-written
   answer). It backfires when the first results are wrong (PRF drifts toward them) or when the LLM's hypothetical answer is wrong or
   generic (HyDE retrieves documents similar to the hallucination).

4. Compute the paired difference with a bootstrap interval on the same queries; check it's consistent across query types; check latency
   and cost; and look at the queries where they disagree. If the interval includes zero, the switch isn't justified on this evidence;
   collect more queries if 1.5 points matters.

5. Split answers into atomic claims; check each against its cited sources with an NLI model or an LLM judge prompted for entailment, with
   numbers, dosages and negations checked explicitly; flag unsupported claims and block high-risk ones. Validate on a few hundred answers
   labeled by clinicians, including deliberately altered ones (changed dose, negation), and measure the check's recall on unsupported
   claims, which is the number that matters here.

6. 200 pages is roughly 100k to 150k tokens: long context is feasible, with prompt caching. Measure answer quality both ways on the same
   evaluation set (long context avoids retrieval misses; RAG avoids distraction), cost and latency per query, and whether access control
   differs by page. Monthly changes are easy either way.
