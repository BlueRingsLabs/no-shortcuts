# 41.3 RAG done properly

*About 9 hours. Prerequisites: 41.1, 41.2, 40.2 (prompting and structured outputs). Lab: [`lab_41_3_rag.py`](labs/lab_41_3_rag.py).*

Retrieval-augmented generation is the most deployed LLM pattern there is, and the most often deployed badly. The demo takes an afternoon:
split documents into chunks, embed them, retrieve the top five for each question, paste them into a prompt, ship. Then the questions
arrive that the demo never saw: the answer spans two chunks, the answer isn't in the documents at all, the question uses an error code the
embedding has never heard of, the model cites source 3 for something source 3 doesn't say. Most RAG failures turn out to be retrieval failures or a
missing "I don't know", not model failures. This lesson covers the pipeline stage by stage, with numbers
from a RAG system over this course, using its exercise questions as test queries.

The index is Parts 0 to V of this course, fixed so that these numbers don't move as later lessons are written. If you edit those
lessons, expect the third decimal to change; the patterns won't.

## The pipeline

1. **Ingest**: parse documents (the unglamorous part: PDFs, tables, HTML boilerplate, scanned pages), keep their structure and metadata.
2. **Chunk**: split into retrievable units.
3. **Index**: lexical (BM25) and dense (41.1), in a vector index (41.2), with metadata for filtering (source, date, access rights).
4. **Retrieve**: candidates from each index, merged.
5. **Rerank**: a more expensive model orders the candidates.
6. **Decide**: is anything here relevant enough to answer from?
7. **Assemble**: a prompt with the question, the sources, and instructions, within a token budget.
8. **Generate** with citations, and **check** them.

Each stage can fail independently, which is why you evaluate them separately (41.4) as well as end to end.

## Chunking

Chunks are what the retriever sees and what the model reads, and the two want different things: small chunks give precise matches; large
chunks give the model context. The lab compares strategies by lesson-level recall with the top 5 chunks, and with a fixed prompt budget
of 600 words filled in rank order:

| chunking | recall@5 | words in the top 5 | recall within 600 words |
|---|---|---|---|
| fixed windows, 60 words | 0.92 | 298 | 0.94 |
| fixed windows, 120 words | 0.93 | 590 | 0.92 |
| fixed 120, overlap 30 | 0.94 | 593 | 0.91 |
| fixed windows, 300 words | 0.95 | 1,450 | 0.85 |
| sections, paragraphs packed to 120 words | 0.92 | 486 | 0.91 |
| same, with lesson title and heading on each chunk | 0.93 | 530 | 0.92 |
| whole sections, with header | 0.95 | 1,183 | 0.82 |

With a fixed number of chunks, bigger chunks look better, because they carry more text into the prompt. With a fixed budget, which is
what you actually pay for in tokens and in the model's attention, it reverses: small chunks spend the budget on the parts that match. So
**compare chunking strategies at equal prompt cost**, or you're comparing prompt sizes.

Structure-aware chunking (by section and paragraph) doesn't win on this metric, and I'd still use it. Its benefit is invisible to a
retrieval metric: a chunk that starts mid-sentence, splits a table from its header or separates a code block from its explanation is
harder for the model to *use*. Putting the document title and section heading on each chunk ("contextual" chunk headers) helps retrieval
a little, even after paying for the words it adds; Anthropic's contextual retrieval write-up pushes the same idea further, with an LLM writing a sentence
of context per chunk.

Practical defaults: split on structure first (headings, paragraphs), pack to a few hundred tokens, add the title and heading, keep tables
and code blocks whole, and store a pointer to the parent section so you can expand a hit into its surroundings at assembly time
("small to big" retrieval).

## Two stages: recall, then precision

The first stage must not miss: it retrieves generously (tens to hundreds of candidates) from several cheap retrievers. The second stage
orders them with a model that can afford to be expensive because it sees only the candidates. The standard reranker is a **cross-encoder**:
a transformer that reads the query and the chunk *together* and outputs a relevance score, far more accurate than comparing two separately
computed vectors, and far too slow to run over a whole corpus.

The lab can't afford a real cross-encoder, so it trains gradient-boosted trees on features of each candidate (the three retrievers' scores
and ranks, overlap with the heading, length) on the questions from even-numbered lessons, and tests on the odd ones:

| system | recall@1 | recall@3 | MRR@10 |
|---|---|---|---|
| BM25 | 0.715 | 0.887 | 0.809 |
| dense (the small encoder of 41.1) | 0.225 | 0.406 | 0.337 |
| LSA | 0.649 | 0.866 | 0.767 |
| hybrid (RRF of all three) | 0.542 | 0.809 | 0.692 |
| hybrid + reranker | 0.681 | 0.877 | 0.792 |

Two honest lessons in that table. **Fusion with a weak retriever hurts**: reciprocal rank fusion gives the dense retriever's top results
real weight, and here they're mostly wrong (41.1 explained why this encoder is weak). And **a reranker built from the same weak signals
recovers most of the loss but doesn't beat BM25 at the top**: it can only reweight what the first stage measured. A cross-encoder reads the
text; that's the difference that makes rerankers worth their latency in production. With a strong embedding model and a real
cross-encoder, the usual published result is hybrid plus reranking beating either retriever alone. Check it on your own questions; this
table is a reminder that "usually" isn't "always".

## Knowing when not to answer

Retrieval always returns something. If the answer isn't in the index, the top chunks are the least irrelevant ones, and a model told to
answer from them will produce a fluent, cited, wrong answer. The lab removes a fifth of the lessons from the index, so their questions
become unanswerable, and abstains when the reranker's best probability is below a threshold:

| abstain below | answered from the right source | answered from a wrong source | unanswerable questions correctly declined |
|---|---|---|---|
| 0.0 (never abstain) | 0.61 | 0.39 | 0.00 |
| 0.2 | 0.61 | 0.38 | 0.05 |
| 0.4 | 0.60 | 0.31 | 0.33 |
| 0.6 | 0.55 | 0.23 | 0.65 |

Raising the threshold from 0 to 0.6 cuts the wrong-source answers by 40% and declines two thirds of the unanswerable questions, at
the cost of about 6 points of good answers. Where to set it is a product decision: in a support bot, "I don't know, here's how to reach a person"
is cheap; in a search tool for lawyers, a confidently wrong answer is expensive. It needs a relevance score that means something, which
raw cosine similarities and BM25 scores don't (their scale varies by query); a reranker's probability, calibrated on labeled data (18.3),
does. Also tell the model it may say the sources don't contain the answer, and test that it does.

## Assembling the prompt

- **A token budget**, filled in rank order. More context isn't free: cost, latency, and models use information in the middle of long
  contexts less reliably than at the ends (Liu et al., 2023, "lost in the middle"). Put the best sources first.
- **Delimited, numbered sources** (`<source id="3" lesson="41.2">...</source>`), so the model can cite them and code can check the citations.
- **Deduplicate** near-identical chunks, and consider grouping chunks from the same document in document order.
- **Instructions**: answer only from the sources, cite them, say so when they don't contain the answer. The sources are data, not
  instructions: a retrieved document can contain text that tries to steer the model, and 44.1 covers how to keep it in its place.
- **Access control at retrieval time**: filter by what the asking user may read *before* ranking. A RAG system that retrieves from
  documents the user can't open is a data leak with a chat interface.

## Citations that something checks

Citations are only worth their tokens if something verifies them. The lab's checker parses `[n]` markers, checks that each number exists,
and checks that each cited sentence shares most of its content words with its source. It flags a sentence copied from another lesson
("shares only 0% of the sentence's words") and a citation to a source that doesn't exist. That catches invented and misattributed
citations, which are common. It doesn't catch a sentence that uses the source's words to say something the source doesn't: 41.4 measures
exactly how badly a lexical check misses that, and 43.1 covers the model-based judges that can catch it.

> **Scar tissue.** The first RAG system I built answered questions about my university's academic regulations, and it answered a
> surprising number of them with "Page 3 of 212". The PDF extraction kept headers and footers, which appeared on every page, and after
> chunking they were the most common text in the index. For vague questions, the footer was the best match. Look at your chunks, with your
> own eyes, before you tune anything else. Parsing is the least glamorous and most decisive stage.

## Things that will bite you

- **Evaluating only end to end**, so you can't tell a retrieval miss from a generation error.
- **Comparing chunkers at different prompt sizes.**
- **No abstention path**, so unanswerable questions get confident answers.
- **Stale indexes**: documents updated or deleted in the source, still served from the index. Index freshness is a pipeline (Part II), not
  a one-off script.
- **Permissions ignored** at retrieval.
- **Parsing garbage**: headers, footers, navigation menus and broken tables indexed as content. Look at your chunks.
- **Top-k fixed at 5 forever**: tune k and the budget on your evaluation set.

## Exercises

4. Design the abstention logic for an internal HR policy assistant. What threshold, and who decides?
5. A user asks a question whose answer is spread across three sections of a long document. What in the pipeline helps, and what fails?
6. Write the checks you'd run on every answer before showing it to the user, cheapest first.

<summary>Answers</summary>

1. Recall@5 lets bigger chunks carry more text: five 300-word chunks cover 1,500 words of lessons, so they hit more often. At a fixed word
   budget, large chunks fit only two or three, mostly text that doesn't match the question; small chunks fit ten, each chosen for matching.
   Recall@k is only comparable across chunkers at equal prompt size.

2. A cross-encoder attends across query and passage jointly, so it can match specific terms, negations and relations between them; a
   bi-encoder compresses each into a vector separately and compares them, losing detail. But a cross-encoder must run once per (query,
   passage) pair at query time, which is impossible over millions of passages; the bi-encoder's passage vectors are precomputed.

3. Weighted fusion (lower weight for the weak retriever, tuned on validation queries), or a learned reranker over the union of candidates
   (the lab's second stage), or dropping the weak retriever. Choose on a held-out query set with paired comparisons (41.4), considering
   latency and maintenance.

4. Abstain when the calibrated relevance of the best source is below a threshold chosen on labeled questions, including unanswerable ones,
   so that wrong-source answers stay below an agreed rate; on abstention, link the HR portal and a contact. The HR policy owners decide the
   trade-off (a wrong answer about leave entitlement is costly), and it's revisited with production data.

5. Helps: chunk headers and parent-section pointers (retrieve a chunk, expand to its section), retrieving more candidates and grouping by
   document, a larger budget for such queries, query decomposition (41.4). Fails: fixed top-k of small chunks, which may return one of the
   three parts; ranking that treats the parts as competitors rather than complements.

6. Citation format valid and numbers in range; each cited sentence overlaps its source (lexical, cheap); no claims without citations when
   the policy requires them; abstention correctly triggered when relevance was low; then, sampled or for high-stakes answers, a model-based
   faithfulness check (NLI or an LLM judge validated against people, 43.1). Log everything for evaluation (43.2).
