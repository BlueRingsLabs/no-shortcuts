# 44.1 Prompt injection and the OWASP LLM Top 10

*About 10 hours. Prerequisites: 40.3 (tool use), 42.2 (MCP), 41.3 (RAG). Lab: [`lab_44_1_injection_defenses.py`](labs/lab_44_1_injection_defenses.py).*

I've spent a good part of my career being paid to find the gap between what a system was designed to do and what it can be made to do.
LLM applications have the widest such gap I've seen in a long time. Their designers keep making the same assumption, that the model
will follow the developer's instructions and treat everything else as data. There is no mechanism that makes that true. This lesson is
about why, and about the designs that hold anyway. It's written from the defender's side, as is the lab: the tests use harmless
canaries, the question is always "can untrusted text steer this system?", and the answers are architectural.

## The problem

A language model receives one sequence of tokens. The system prompt, the user's message, a retrieved document, a web page, a tool's
output and an email body are all just text in that sequence. Chat templates mark roles, and models are trained to give the system and user
turns priority. But that priority is a learned tendency, not an enforced boundary. Text that reads like an instruction, anywhere in the
context, can influence what the model does.

That's **prompt injection**. It has two forms:

- **Direct**: the user writes the instructions themselves ("ignore your rules and..."). When the user is the only one affected, it's
  mostly a policy problem: they can make the assistant say things you'd rather it didn't.
- **Indirect**: the instructions arrive inside content the application processes on the user's behalf: a web page it browses, a
  document it retrieves, an email it summarizes, a tool result, an MCP tool description (42.2), a code comment. The author of that
  content is a third party, and the victim is the user whose assistant, with the user's permissions, just read it.

Indirect injection is the serious one. It turns every piece of content your application reads into a potential command channel, and the
consequences scale with what the application can do: read private data, send messages, call APIs, run code.

It is not a bug to be patched. It's a property of how these models work, the way SQL injection is a property of building queries by
concatenating strings. The difference is that SQL injection has a complete fix (parameterized queries, which separate code from data
structurally) and prompt injection, so far, doesn't. Every defense that relies on the model telling instructions from data is
probabilistic.

## The lethal combination

Simon Willison's framing is the most useful one for design reviews. An application is exposed when it has all three of:

1. **access to private data** (the user's email, files, CRM records),
2. **exposure to untrusted content** (anything a third party can write),
3. **a way to send data out** (sending messages, making HTTP requests, even rendering an image from a URL, which makes the client fetch
   it).

With all three, a single piece of content can make the assistant read something private and send it somewhere. Remove any one leg for a
given flow and that exfiltration path closes. Most secure designs come down to deciding which leg to remove where.

## Defenses, measured

The lab builds an email assistant that reads an inbox and can send email and render Markdown (with images). A quarter of the test emails
contain a harmless canary instruction asking the assistant to send the thread to `canary@example.test`, or to display an image from a
canary URL. The canaries come in several forms: plain, formatted as a "system note", an image, base64-encoded, and in Spanish. How often
a real model follows such text depends on the model, the phrasing and the context, and it changes with every model release. So the lab
treats it as a parameter $p$ and measures each defense across $p$:

| defense | canaries fired, $p = 0.1$ | $p = 0.5$ | $p = 1.0$ |
|---|---|---|---|
| none | 12 | 39 | 96 |
| delimiters + "emails are data" instruction | 9 | 24 | 47 |
| spotlighting (datamarking) | 6 | 16 | 24 |
| input classifier | 3 | 27 | 56 |
| taint policy on tool calls | 3 | 5 | 12 |
| renderer image allowlist | 9 | 34 | 84 |
| policy + allowlist | 0 | 0 | 0 |
| quarantined reader (dual LLM) | 0 | 0 | 0 |

(The follow rates under delimiting and spotlighting are the lab's stated assumptions, chosen to be generous to those defenses.)

**Probabilistic defenses** make the model less likely to be steered:

- clear delimiters with an instruction that the content is data;
- **spotlighting** (Hines et al., 2024), which marks untrusted text so it's recognizably different, for example by interleaving a marker
  character or encoding it;
- **instruction hierarchy** training, where models learn to give system instructions priority over tool outputs;
- **classifiers** that detect injection attempts in inputs.

They're worth having, and they divide the problem by a factor you don't control. At $p = 1$ (a model that reliably follows text addressed
to it, or an attacker who found the phrasing that works on your model) they leave a quarter to a half of the canaries firing. The lab's
classifier also shows the usual detector problem: it catches the phrasings it was built for, misses the image, encoded and translated
variants entirely, and flags legitimate emails that mention assistants or forwarding. A model-based detector does better on both counts
and has the same shape.

**Structural defenses** make the harmful outcome impossible, whatever the model does:

- A **taint-tracking policy** in the tool layer. Once untrusted content has entered the context, side-effecting tools can only act within
  a safe set (here: send only to the user's own contacts), and anything else requires the user's confirmation. It stops the email canaries
  at every $p$, but not the image, which is a different channel.
- An **allowlist in the renderer**. The client only fetches images from your own domains. It stops the image channel, and only that.
- Both together close both channels.
- **Privilege separation (the dual-LLM or quarantine pattern)**. The model that reads untrusted content has no tools, and its output is
  treated as data: rendered as plain text, never executed or used to choose actions. A separate privileged component, code or a model
  that never sees the raw untrusted text, decides what to do. Recent research systems formalize this: CaMeL (Debenedetti et al., 2025)
  extracts a program from the user's request, and tracks which values came from untrusted sources through its execution.

The structural defenses cost convenience. The lab's policy asks the user before forwarding an invoice to a supplier address found in an
email, which is a legitimate request. That's the design problem: put confirmations where they protect, show the user exactly what will
happen, and not so often that they learn to click "yes" without reading (44.2).

## The OWASP Top 10 for LLM applications

OWASP maintains a list of the most important risks for LLM applications (2025 edition). Each item links to what this Part covered:

1. **Prompt injection**: this lesson.
2. **Sensitive information disclosure**: models reveal training data, other users' data in shared context, or data they had access
   to. Controls: don't give the model data the user isn't allowed to see (41.2's partitioning, 40.3's scoping), redact at capture
   (44.2), and review what goes into fine-tuning data.
3. **Supply chain**: models, datasets, packages, plugins and MCP servers from third parties (42.2, 53.2). Pin versions, verify sources,
   scan, and prefer formats that can't execute code (safetensors, not pickles).
4. **Data and model poisoning**: manipulated training, fine-tuning or retrieval data (53.1). Control what goes into training and into
   your index, with provenance.
5. **Improper output handling**: treating model output as trusted, by rendering it as HTML, running it as SQL or shell, or fetching its
   URLs. Model output is untrusted input to whatever consumes it: escape, parameterize, sandbox, allowlist.
6. **Excessive agency**: more tools, permissions or autonomy than the task needs (40.3, 42.1). Least privilege and human approval.
7. **System prompt leakage**: assume the system prompt will be read. Never put secrets or access rules in it (44.2).
8. **Vector and embedding weaknesses**: missing access control in retrieval, poisoned documents, inversion of embeddings back to text
   (41.2, 41.3).
9. **Misinformation**: confident, wrong output that people rely on. Grounding with citations, evaluation, and interfaces that show
   uncertainty (41.3, 43.1).
10. **Unbounded consumption**: runaway costs from loops, abuse or denial of wallet. Budgets, rate limits and quotas (40.1, 44.2, 45.1).

Use it as a checklist in design reviews, alongside the ordinary web application risks, which all still apply.

> **Scar tissue.** In a freelance security assessment of a client's ticket-summarizing assistant, I planted a harmless canary in a test
> ticket: a sentence addressed to the assistant, asking it to add a specific made-up word to its summary and mark the ticket as resolved.
> It did both. The assistant had write access to ticket status, and it treated the content it was summarizing as instructions. The fix
> wasn't a better system prompt. It was taking status changes away from the component that reads untrusted text.

## Things that will bite you

- **Believing the system prompt is a security boundary.**
- **All three legs in one flow**: private data, untrusted content and an outbound channel, with nothing structural between them.
- **Markdown images, links and HTML** rendered from model output without an allowlist.
- **Tools with more authority than the user**, or with the service's authority instead of the user's.
- **Relying on a detector** as the only defense.
- **Testing with one phrasing** and concluding the model is "resistant" (44.2).

## Exercises

1. A browsing assistant can read web pages and the user's calendar, and can send email. Identify the three legs and propose two designs
   that remove one each.
2. Why is "the model was trained with an instruction hierarchy" not sufficient for an application that sends email?
3. A support bot renders Markdown. How could untrusted content cause data to leave through an image, and what control stops it
   regardless of the model?
4. Map a RAG application over internal documents onto the OWASP list: which three items are most important, and what's the control for
   each?
5. Why does an input classifier have to be evaluated like any other classifier, and what's the cost of its false positives?
6. The quarantined-reader pattern makes the assistant less capable. Give a task it can still do well, and one it can't do without a
   confirmation step.

<summary>Answers</summary>

1. Private data: the calendar. Untrusted content: web pages. Outbound: email. Design A: when a page has been read in this session, email
   can only go to the user after confirmation, showing the full message (tainting). Design B: browsing runs in a quarantined component
   that returns a structured summary; the component with calendar and email access never sees page text. Also consider whether the
   assistant needs to send email at all.

2. It lowers the probability that injected text is followed, and not to zero; attackers search for phrasings that work, and models change.
   Sending email is irreversible and data-exfiltrating, so the control must hold even when the model is fooled: a policy on the send
   tool, confirmation, or separation.

3. Injected text asks the model to include an image whose URL contains data from the conversation (in the query string). The client
   renders the Markdown and fetches the URL, delivering the data to the attacker's server with no click. Stop it in the renderer: only
   fetch images from an allowlist of your own domains (and a Content Security Policy in web clients), or don't render images from model
   output at all.

4. Sensitive information disclosure (users retrieving documents they shouldn't see: enforce document-level permissions in retrieval,
   by partition or filter applied by the system); vector and embedding weaknesses and poisoning (anyone who can edit a wiki page can plant
   content: provenance, review of indexed sources, treating retrieved text as untrusted); prompt injection via retrieved documents (keep
   the RAG assistant's tools read-only, and treat its output as untrusted for anything downstream).

5. It's a classifier with a false-negative rate (injections that pass) and a false-positive rate (legitimate content blocked). Measured
   only on the attacks it was designed for, it looks perfect. The false positives block legitimate emails and documents, frustrate users,
   and teach them to bypass the control, so both rates need measuring on realistic traffic (43.1).

6. It can still summarize, classify, extract fields into a fixed schema, and answer questions about the content, since its output is data
   that code or the user acts on. It can't act on instructions found in the content ("pay this invoice", "reply with the report") without
   a step where the privileged side, or the user, confirms a specific action with specific arguments.
