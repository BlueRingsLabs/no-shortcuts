# 42.1 The agent loop: ReAct, planning and memory

*About 10 hours. Prerequisites: 40.3 (tool use), 40.1 (cost and latency). Lab: [`lab_42_1_agent_loop.py`](labs/lab_42_1_agent_loop.py).*

An agent is a language model in a loop: it looks at the goal and what has happened so far, decides on an action (usually a tool call),
sees the result, and repeats until it decides it's done. That's all. The word has been stretched to cover everything from a chatbot with
a search tool to autonomous systems that run for hours. The engineering questions are the same across that range: how reliable is each
step, what does the loop cost, how does it stop, and would a plain program have done the job better?

That last question comes first, because the answer is often yes.

## Workflows and agents

Anthropic's "Building effective agents" (2024) draws the line usefully:

- A **workflow** is a program you wrote that calls a model at fixed points: extract, then classify, then draft. The control flow is
  code.
- An **agent** decides its own control flow: which tool next, how many steps, when to stop. The control flow is the model's.

Workflows are predictable, testable, cheaper and easier to debug. Agents handle tasks whose steps depend on what's found along the way:
debugging an unfamiliar codebase, researching a question whose answer is spread across unknown sources. The lab's task, "what are the
titles of the prerequisites of lesson X?", is deliberately one that *doesn't* need an agent: two lines of code solve all 95 instances
exactly, with no model calls. Everything the agent does in the rest of the lab (between 2 and 6 model calls per task, with occasional
failures) is the price of using an agent where a workflow would do. That price is common in production, and it's a design error.

Use an agent when you can't write the steps down. When you can write down some of them, write those down and let the model decide only the
rest (42.3).

## ReAct

The pattern nearly every agent uses descends from **ReAct** (Yao et al., 2022): interleave reasoning ("I need the prerequisites, so I'll
read the lesson's header first") with actions (a tool call) and observations (its result), all in the context, so each decision can use
everything seen so far. Modern APIs make this native: the model emits thinking and tool calls, your code runs the tools and appends the
results (40.3). The lab's traced run for lesson 04.4:

```
[0] act: read_lesson(04.4) -> {"title": "Maximum likelihood and MAP", "prerequisites": ["04.1", "04.3", "03.1"]}
[1] act: read_lesson(04.1) -> {"title": "Random variables and distributions", ...}
[2] act: read_lesson(04.3) -> {"title": "Expectation, variance and the limit theorems", ...}
[3] act: read_lesson(03.1) -> {"title": "Derivatives, gradients and the chain rule", ...}
[4] answer: Random variables and distributions | Expectation, variance and ... | Derivatives, gradients and ...
```

Five model calls, each re-reading the whole history.

**Planning** variants make the model write a plan first and then execute it (plan-and-execute), or revise it as results arrive. A written
plan helps on long tasks: it gives the model something to check progress against, and gives *you* something to inspect. It doesn't remove
the need to adapt, and a plan followed rigidly after the world has contradicted it is worse than no plan.

## Reliability compounds

If each step succeeds with probability $1 - \varepsilon$ independently, a task of $n$ steps succeeds with probability $(1-\varepsilon)^n$.
At 95% per step, a 20-step task succeeds a third of the time. The lab injects the mistakes models make (answering from "memory" instead of
looking something up, repeating an action) with probability $\varepsilon$ per step:

| $\varepsilon$ | checks | 1 prerequisite | 2 | 3 | 4 |
|---|---|---|---|---|---|
| 0.05 | none | 0.94 | 0.93 | 0.87 | 0.79 |
| 0.05 | loop guard + verifier | 1.00 | 1.00 | 1.00 | 1.00 |
| 0.15 | none | 0.83 | 0.78 | 0.55 | 0.49 |
| 0.15 | loop guard + verifier | 1.00 | 1.00 | 1.00 | 1.00 |

Success falls with the length of the task, a little less steeply than $(1-\varepsilon)^n$ because some mistakes are harmless. The checks
change the picture entirely. A **verifier** rejects any answer containing a title that no tool returned in this conversation, and sends the
model back to look it up. A **loop guard** refuses a repeated identical call, with a message saying so. Together they turn fatal mistakes
into retries.

The lab's verifier is perfect only because its mistakes are easy to detect: an invented title is either in the tool results or not. Real
verification is harder and partial. But the principle carries over: **put checks between steps**. Check that answers cite what tools
returned, that intermediate results parse and validate (40.2), that a code change compiles and passes its tests, that a number is within
range. Every check you can write in code makes the agent's effective $\varepsilon$ smaller, and $n$ matters less.

## Memory and context

Every observation stays in the context and is re-sent on every later call. The input tokens of a task therefore grow roughly with the
square of its length (40.3, exercise 4). The lab runs the same 15 four-prerequisite tasks with two designs of the same tool:

| tool returns | correct | input tokens per task |
|---|---|---|
| the first 1,500 characters of the lesson file | 1.00 | 11,435 |
| title and prerequisite IDs only | 1.00 | 2,500 |

Same answers, 5× less input. Tool design is the first lever on an agent's cost. Others:

- **Drop or truncate old observations** once used. Keep a short running summary or notes list ("found: 04.1 = Random variables...")
  instead of full results.
- **External memory**: write notes, plans and intermediate results to files or a store, and read back what's needed, instead of keeping
  everything in context. Long-running coding agents rely on this.
- **Prompt caching** of the stable prefix (40.1). The growing history can be cached incrementally too.
- **Sub-agents** with their own clean context for sub-tasks, returning only a summary (42.3).

Long-term memory across sessions (user preferences, facts learned) is retrieval (Module 41) over what the agent chose to save,
and inherits retrieval's problems, plus a new one: whatever gets written into memory can influence every future session. That includes
text an attacker managed to get the agent to save (44.1).

## Stopping

An agent must stop, and it can't be trusted to decide alone when. Put these in code, where the model can't argue with them:

- **Budgets**: steps, tokens, money and wall-clock time.
- **Loop detection**: the same call with the same arguments, or no new information in the last few steps.
- **A defined outcome at the limit**: hand off to a human, return a partial result with an honest status, or ask the user.

In the lab, with a model that makes a mistake 30% of the time and tends to stay stuck once it starts repeating itself, 18% of runs hit
the 8-step budget without a loop guard. With the guard, none do, and accuracy rises from 0.42 to 0.58. The budget stopped the bleeding;
the guard fixed the cause.

> **Scar tissue.** An agent I prototyped to reconcile my own freelance invoices against bank statements hit a tool that returned an error
> message it couldn't parse, and it tried the same call again. And again. Four hundred times, overnight, each attempt re-sending the
> growing conversation. Nothing broke except the token budget and my faith in "it'll figure it out". Step limits, token limits and
> repeated-call detection are not optional extras. They're the difference between an agent and a very expensive loop.

## Things that will bite you

- **Agents for fixed procedures**: paying for non-determinism you don't need.
- **No checks between steps**, so one early mistake poisons everything after it.
- **Verbose tools** filling the context with what the agent doesn't need.
- **No budget, no loop detection**, or no plan for what happens at the limit.
- **Trusting the agent's own report** of what it did instead of your logs (43.2).
- **Evaluating on a handful of runs.** Agents are stochastic, so run each task many times and report the distribution (43.1).

## Exercises

1. A task needs 12 tool calls. Each step succeeds 97% of the time. What's the task success rate? What per-step rate would you need for
   90% task success?
2. Name three checks you could put between the steps of an agent that fixes failing unit tests.
3. An agent's cost per task grew 4× when tasks grew 2× longer. Explain, and propose two fixes.
4. Rewrite the lab's task as a workflow with one model call that adds value. What would the model do?
5. Your agent sometimes loops forever calling a search tool with slightly different queries. Why doesn't an exact-duplicate loop guard
   catch it, and what would?
6. When is a plan-and-execute agent better than a pure ReAct one, and when worse?

<details>
<summary>Answers</summary>

1. $0.97^{12} \approx 0.69$. For 90%: $(1-\varepsilon)^{12} = 0.9$, so $1 - \varepsilon = 0.9^{1/12} \approx 0.9913$, which means per-step
   errors below 0.9%. That's why long tasks need checks that catch and correct errors, not just a better model.

2. After an edit: the code parses and type-checks. After running tests: the targeted test now passes and no previously passing test
   fails. Before finishing: the diff touches only files related to the failure, contains no disabled tests or deleted assertions, and
   stays within a size limit. Each can be enforced by code, with the failure message sent back to the model.

3. Each step re-sends the whole history, so input tokens grow roughly with the square of the number of steps: twice as many steps,
   about four times the tokens. Fixes: make tools return less, summarize or drop old observations, cache the prefix, split the task into
   sub-agents with fresh contexts.

4. Code parses the prerequisites and looks up the titles (deterministic). One model call could then turn them into something useful,
   such as a short paragraph explaining what each prerequisite contributes, given their titles and first paragraphs. The model does
   the writing, the only step that needs it.

5. The calls differ in their arguments, so they aren't duplicates, but they make no progress. Detect lack of progress instead: the
   same tool called N times in a row, results that add no new documents or information (compare result IDs or hashes), or a step budget
   per tool. Then tell the model what's happening ("the last four searches returned nothing new") or stop.

6. Better when the task has a structure that can be foreseen (research with several known sub-questions, a migration across many
   files): the plan makes progress visible and lets you check or edit it before execution, and sub-tasks can run in parallel. Worse when
   early results change what needs doing (debugging), unless the plan is revised as results arrive; a stale plan followed faithfully
   is worse than step-by-step decisions.
