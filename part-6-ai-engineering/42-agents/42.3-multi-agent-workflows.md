# 42.3 Multi-agent systems and workflow design

*About 8 hours. Prerequisites: 42.1, 42.2, 40.1. Lab: [`lab_42_3_workflows.py`](labs/lab_42_3_workflows.py).*

"Multi-agent" is the most over-sold idea in this Part. A diagram with five boxes labeled Researcher, Planner, Critic, Writer and Manager
looks like an organization, and it's tempting to believe it will behave like one. Usually it's one model called five times with five
system prompts, passing paraphrases of paraphrases to itself, at five times the cost. Sometimes that's exactly the right design. This lesson
is about telling the two cases apart, using a small set of patterns and the arithmetic of each.

## The patterns

From simplest to most autonomous (the vocabulary follows Anthropic's "Building effective agents", 2024):

- **Prompt chaining**: a fixed sequence of calls, each working on the previous one's output, with checks between them (42.1). Use it
  when a task splits cleanly into steps that are each easier than the whole.
- **Routing**: classify the request, then send it to a specialized prompt, model or pipeline. Use it when request types need
  different handling, or when cheap requests can go to a cheap model (45.1).
- **Parallelization**:
  - *sectioning* splits independent parts of a task across simultaneous calls;
  - *voting* runs the same task several times and aggregates the answers.
- **Orchestrator-workers**: a model plans sub-tasks at run time, dispatches them to workers, and synthesizes their results. Use it when
  the sub-tasks can't be known in advance: research across unknown sources, changes across an unknown set of files.
- **Evaluator-optimizer**: one call produces, another critiques against criteria, and the loop repeats until the critique passes or a
  budget runs out. Use it when there are clear criteria and iteration measurably helps (40.2's validate-and-retry is the simplest
  case).
- **Autonomous agents** (42.1): a single loop that decides everything.

Most production systems that work are the first three, with an agent inside one step if needed. Start from the simplest pattern that could
work and add autonomy only where the task demands it and your evaluation (43.1) shows it helps.

## Routing

A router is a classifier, and everything from Part III applies: it has an accuracy, a confusion matrix and a calibration. The lab trains
a simple router (TF-IDF and logistic regression) to send course questions to one of six "specialists", one per Part, and tests it on
questions from lessons it never saw:

| route when confidence ≥ | share routed | accuracy of routed requests |
|---|---|---|
| 0.0 (always) | 1.00 | 0.594 |
| 0.4 | 0.59 | 0.673 |
| 0.6 | 0.17 | 0.759 |
| 0.8 | 0.05 | 0.889 |

A misrouted request goes to a specialist that can't help it, and nothing raises an error: the specialist answers anyway, worse. So route
only when confident, send the rest to a generalist (or ask the user), log every routing decision, and measure routing accuracy separately
from end-to-end quality, so you know which part failed. An LLM can be the router, and often should be when categories are subtle, but it
needs the same measurement.

## Latency and cost of the patterns

The lab writes a four-section report (a 1,500-token prompt, 400 tokens of output per section) on the simulated API, where calls in parallel
take as long as the slowest:

| pattern | latency | cost |
|---|---|---|
| one call, everything at once | 40.7 s | $0.029 |
| chain, 4 sections in sequence | 43.0 s | $0.050 |
| 4 parallel sections | 10.7 s | $0.043 |
| orchestrator-workers (plan, 4 workers, synthesize) | 24.8 s | $0.067 |

Output tokens dominate latency (37.2), so splitting the output across parallel calls is the big latency lever: four times faster than one
call. Every pattern with more calls costs more, because each call re-sends a prompt. The orchestrator is slower than plain parallel
sections and costs the most, and it buys adaptivity: it decides the sections at run time. In published multi-agent research systems,
token usage several times that of a single agent is typical, and the extra spend is justified only for tasks valuable enough to pay for it.

## Handoffs lose information

Agents pass work to each other as text, and the text usually gets summarized to fit the next agent's context. The lab simulates handoffs
with an extractive summarizer (keep the 40% most central sentences) on 167 lesson sections, and measures what survives of their specific
facts, the numbers and code identifiers:

| handoffs | specific facts still present |
|---|---|
| 0 | 1.00 |
| 1 | 0.51 |
| 2 | 0.21 |
| 3 | 0.17 |

The gist survives; the specifics don't. And the next agent has no way to know what was dropped. An LLM summarizer is better than this
extractive one, but it fails the same way, and it can also add things. The design rules that follow:

- **Pass artifacts, not descriptions of them**: the data, the file, the query results, or a reference the next agent can read.
- **Give every agent the original task**, not the previous agent's paraphrase of it.
- **Share state explicitly**: a common store (a file, a database, a ticket) that each agent reads and writes, instead of a chain of
  messages.
- **Minimize handoffs.** One agent with good tools and a clean context usually beats three agents talking.

## Voting and "debate"

Voting is attractive: five answers, take the majority. The lab gives five agents a 70% chance each of answering a question right, in two
worlds with the same average:

| agents | single agent | majority of 5 |
|---|---|---|
| independent errors | 0.697 | 0.840 |
| same model, same prompt (errors correlated across questions) | 0.695 | 0.719 |

Condorcet's jury theorem, which promises that majorities of competent voters converge on the truth, assumes independent voters. Five copies
of one model are nearly one voter: they're hard on the same questions and agree when they're wrong. Voting helps with sampling noise
(self-consistency, 38.4) and helps more with genuinely different models, prompts or information. "Debate" between copies of one model
inherits the same limit, plus a new failure: the more confident agent tends to win, not the correct one.

## Evaluator-optimizer

A critic model reviewing a generator's output is only as good as its ability to tell good from bad on your task. A critic that approves
bad outputs 20% of the time sets a floor on your error rate no matter how many loops you run, and one that rejects good outputs burns
budget. Measure the critic like any classifier (43.1), prefer checks in code where possible (tests, validators, exact constraints), and
bound the loop.

## When multi-agent is right

- **Parallelizable, broad tasks**: research across many sources, where sub-agents explore independently with their own clean contexts
  and return condensed findings. Each sub-agent's context holds only its sub-task, which is the real benefit.
- **Different permissions or trust levels**: an agent that reads untrusted web content shouldn't be the one with access to your email.
  Splitting them, with a narrow interface between, is a security design (44.2).
- **Different models for different jobs**: a cheap model for triage, an expensive one for the hard cases.

And when it's wrong: tightly coupled tasks where every part depends on every other (most coding), tasks a single agent with good tools
handles, and anywhere the diagram exists mainly to look impressive.

## Things that will bite you

- **Five agents where one workflow would do.**
- **Routing without confidence thresholds**, or without measuring routing separately.
- **Summaries as the interface between agents.**
- **Voting among copies of one model** and calling it an ensemble.
- **Critics nobody has evaluated.**
- **Costs that multiply** with every agent, unmeasured.

## Exercises

1. Design a system that answers customer questions using docs, the customer's account data, and a human escalation path. Which patterns,
   and why?
2. Your router is 90% accurate over 5 routes, and each specialist answers 95% of correctly routed requests well but only 20% of misrouted
   ones. What's the end-to-end rate? What's the best improvement: a better router, better specialists, or a fallback?
3. Why does the orchestrator-workers pattern cost more than parallel sections, and when is that worth it?
4. A multi-agent research system's final reports contain numbers that appear in none of the sources. Where would you look first?
5. You run the same model 5 times and take the majority, and accuracy improves from 70% to 72%. A colleague proposes 25 runs. What do you
   expect, and what would help more?
6. Give an example where splitting one agent into two improves security.
