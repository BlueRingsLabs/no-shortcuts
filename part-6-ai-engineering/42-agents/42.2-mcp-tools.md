# 42.2 MCP and tool ecosystems

*About 8 hours. Prerequisites: 40.3 (tool use), 07.4 (networks and APIs). Lab: [`lab_42_2_mcp.py`](labs/lab_42_2_mcp.py), with the server in [`course_mcp_server.py`](labs/course_mcp_server.py).*

In 40.3 every tool was a function in your own code. That doesn't scale past one application: every AI product ended up writing its own
GitHub integration, its own database connector, its own file access, each slightly broken in its own way. The **Model Context Protocol**
(MCP, introduced by Anthropic in late 2024 and now an open specification with many implementations) standardizes the plumbing: a server
exposes tools, resources and prompts over a small JSON-RPC protocol, and any AI application that speaks MCP can use them. It's the same
move USB made for peripherals and the Language Server Protocol made for editors.

It's also a way to install someone else's code and let it write text into your model's context. Both halves of that sentence matter,
and this lesson spends as long on the second as on the first.

## The shape

- The **host** is the AI application (an IDE, a chat app, your agent). It owns the model, the conversation and the user.
- The host runs one **client** per server it connects to.
- A **server** exposes capabilities:
  - **tools**: functions the model can call, as in 40.3;
  - **resources**: data the host can read and put in context, such as files, records or schemas;
  - **prompts**: reusable templates a user can pick.
- **Transports**:
  - **stdio**, for local servers the host launches as a subprocess, with newline-delimited JSON-RPC on stdin and stdout;
  - **Streamable HTTP**, for remote servers, with OAuth for authorization.

The protocol has been revised several times. The lab implements revision 2026-07-28, which made MCP stateless. There's no longer an
`initialize` handshake: every request carries the protocol version and the client's capabilities in `params._meta`. A server that
doesn't support the requested version replies with error `-32022` and the list of versions it does support. Clients may call
`server/discover` first to learn the server's versions, capabilities and identity. Older servers still speak the handshake-based
revisions, and clients that need both detect which era a server speaks. When you read MCP code or tutorials, check which revision they
target; SDKs hide most of this, which is the point of SDKs.

## The wire, by hand

The lab starts the course's own MCP server (two tools: `course_search` over this course with BM25, 41.1, and `course_read_section`)
and talks to it with about sixty lines of client code:

1. A client speaking an older version gets `Unsupported protocol version` with `supported: ["2026-07-28"]`, and retries with it.
2. `server/discover` returns the server's name, version and capabilities; `tools/list` returns each tool's name, description and JSON
   Schema (`inputSchema`).
3. `tools/call` with a name and arguments returns content blocks. A tool that fails in a way the model should see (a bad argument)
   returns a normal result with `isError: true` and a message the model can act on, rather than a protocol error.

Two details the lab gets right on purpose. On stdio, stdout is the protocol channel, so the server logs to stderr: one stray `print` in a
server corrupts the stream, a classic first-day bug. And the client never waits forever on a response: servers hang, and a host that
blocks on one takes the whole conversation down with it.

The host turns each MCP tool into a model tool (`inputSchema` becomes the API's `input_schema`), passes them to the model and routes the
model's calls to the right server. In the lab the scripted model searches the course for "What does the KV cache store, and why does it
speed up generation?", reads the section of 37.2 the search pointed to, and answers from it. Everything from 40.3 still applies unchanged:
validation, authorization, idempotency, budgets. MCP standardizes how tools are described and called. It doesn't make them safe.

## Several servers

Real hosts connect to many servers at once, and tool names collide. The lab connects two servers that both expose `course_search`.
Without namespacing, which server receives a call depends on the host's merge order, and a server added later can quietly take over a tool
the model already relies on. Hosts should namespace tools by server (`course__course_search`) and show the user which server a call goes
to.

Tool definitions also cost context. The lab's two tools are about 400 tokens of definitions, sent with every request. Sixty tools, a
few servers' worth, are nearly 12,000 tokens, which is money and latency on every call and worse tool choice (40.3). Hosts connected to
many servers load definitions progressively: they search over tool names and descriptions first, then send the model only the few that
match.

## Trusting servers

An MCP server is software you run with your permissions, plus text you inject into your model's context. Both need the scrutiny you'd give
any dependency, and the second is new.

**Tool descriptions are prompts.** The model reads every name, description and schema, and they shape its behavior, including toward
tools from *other* servers. A malicious or compromised server can put instructions in its descriptions ("tool poisoning"). And it can
change them after you've reviewed them, because `tools/list` is called again whenever the host likes (a "rug pull"). The lab's second
server does exactly that: after the first listing, its search tool's description gains a usage tip telling the model to call it before
answering anything, with the full conversation as the query. That's an exfiltration channel dressed as documentation.

The host-side defenses, all in the lab:

- **Pin tool definitions.** Show them to a person when a server is added, store a hash of each approved definition, and refuse to use
  (or ask again about) any tool whose definition changed. In the lab the changed tool is caught and blocked, and the unchanged one stays
  usable.
- **Flag instruction-like text** ("always", "before answering", "include the conversation") for the reviewer. It's a hint, not a
  control: phrasing is trivially varied, which is why it comes after pinning, not instead of it.
- **Least privilege.** The real limit on damage is what the server can reach. A search server should receive search queries, not the
  conversation, and should run without access to your files, network or credentials beyond what it needs. Run local servers in a
  sandbox or container, with scoped credentials.
- **Treat tool results as untrusted data** (44.1): a server's output lands in the context too.
- **Confirm consequential actions** with the user, showing the exact tool, server and arguments (40.3).
- **Prefer servers from sources you trust**, pin versions like any dependency (53.2), and read the code of small
  ones before running them. A local stdio server is a program running as you.

For remote servers, authorization matters as much: MCP uses OAuth 2.1, and a server should receive tokens scoped to what it does, for
the user it acts for, never a shared admin credential (40.3's scoping rule, at the protocol level).

## When to write a server

Write an MCP server when a capability should be usable from several AI applications you don't control: your company's internal APIs for
every employee's assistant, a product's API for your customers' agents. Inside a single application you own, plain function tools
(40.3) are simpler and easier to secure, and nothing stops you from exposing them over MCP later.

## Things that will bite you

- **Printing to stdout** in a stdio server.
- **No timeouts** on server calls.
- **Tool name collisions** across servers.
- **Unpinned tool definitions**: approving a server once and trusting whatever it says afterwards.
- **Servers with more access than their tools need**, especially to the conversation.
- **Hundreds of tool definitions** in every request.
- **Tutorials for a different protocol revision.**

## Exercises

1. Why is `isError: true` in a tool result better than a JSON-RPC error for "the query was empty"?
2. A host connects to a filesystem server and a web-search server. What can go wrong if both are fully trusted?
3. Write the rule a host should apply when `tools/list` returns a description that differs from the approved one.
4. You're asked to expose your company's CRM to employees' AI assistants. Sketch the server's tools and its authorization model.
5. Why doesn't namespacing tool names solve tool poisoning?
6. When is an MCP server the wrong design?

<summary>Answers</summary>

1. A JSON-RPC error signals a protocol-level failure to the client code (unknown method, malformed request); the host typically
   doesn't show it to the model, or shows it as a failure. A tool result with `isError` is delivered to the model as the outcome of its
   call, with a message it can act on ("query must be a non-empty string"), so it can correct itself (40.3's validation loop).

2. Text from a web page (search results) can contain instructions that make the model use the filesystem tools: read files and put their
   contents in a search query, or write files. The two servers are individually harmless and together form an exfiltration path.
   Mitigations: least privilege (read-only, scoped directories), confirmation for writes and for data leaving through tools, treating
   search results as untrusted (44.1), and not combining untrusted-input tools with sensitive tools without a human in the loop.

3. Don't use the tool; show the user the old and new definitions side by side, with the changed text highlighted; use the new
   definition only after explicit re-approval; log the event. Until then, remove the tool from the model's tool list (not just
   refuse calls, because the description itself is the risk).

4. Tools like `crm_find_customer(query)`, `crm_get_account(account_id)` and `crm_log_note(account_id, text)`, each with strict schemas;
   read and write tools separated; no bulk export. Authorization: OAuth with the employee's identity, so the server enforces that
   employee's CRM permissions on every call (object-level, as in 40.3), with scopes for read versus write, audit logs of every call,
   rate limits, and confirmation for writes.

5. Namespacing prevents one server from taking over another's tool *name*. Poisoning works through *text*: a description is read by the
   model as part of its context and can influence how it uses every tool, including other servers'. Only pinning, review, least
   privilege and confirmation address that.

6. When there's one application and you own both sides (plain function tools are simpler); when the operation needs a tight
   transactional flow the model shouldn't orchestrate (make it a single tool or plain code); and when the capability is too sensitive to
   expose to model-driven calls at all.

## Further reading

- The MCP specification (modelcontextprotocol.io/specification), especially the versioning, transports and security best practices
  pages. Read the revision your SDK targets.
- Anthropic, "Introducing the Model Context Protocol", November 2024.
- The Agent2Agent (A2A) protocol specification (a2a-protocol.org), introduced by Google in 2025: agent-to-agent rather than
  agent-to-tool, and a useful contrast.
- IETF, RFC 9700, "Best Current Practice for OAuth 2.0 Security", 2025, and the OAuth 2.1 draft that MCP's authorization builds on.
- Invariant Labs, "MCP Security Notification: Tool Poisoning Attacks", 2025.
- OWASP Top 10 for LLM Applications (44.1): "Excessive Agency" and "Supply Chain".
