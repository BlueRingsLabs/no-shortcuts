# 45.2 Self-hosting open models

*About 10 hours. Prerequisites: 37.2 (KV cache and serving engines), 37.3 (quantization), 33.1 (GPU arithmetic), 45.1. Lab: [`lab_45_2_self_hosting.py`](labs/lab_45_2_self_hosting.py).*

Open-weight models (Llama, Mistral, Qwen, Gemma, DeepSeek and others) can be downloaded and run on your own hardware. Reasons to do it:
data that can't leave your network, latency you control, a fine-tuned small model that replaces a large API model for one task, predictable
cost at high volume, and independence from a provider's changes (43.2's silent model update can't happen to weights you hold). Reasons not
to: you now operate GPUs, serving software and model upgrades, and at low volume it's almost always more expensive. This lesson is the
arithmetic that decides, and the practicalities once you've decided.

## Memory: weights and the KV cache

Two things occupy GPU memory when serving (37.2, 37.3):

- **Weights**: parameters × bytes per parameter. 16-bit is 2 bytes, int8 is 1, 4-bit about 0.5 (plus a little for scales).
- **The KV cache**: for every token in every active sequence, a key and a value vector per layer and per KV head:
  $2 \times \text{layers} \times \text{KV heads} \times \text{head dim} \times \text{bytes}$ per token.

From the models' published configurations:

| model | weights bf16 | int8 | int4 | KV cache per token | per 8k-token sequence |
|---|---|---|---|---|---|
| Llama 3.1 8B | 16.0 GB | 8.0 GB | 4.0 GB | 131 kB | 1.07 GB |
| Mistral 7B | 14.4 GB | 7.2 GB | 3.6 GB | 131 kB | 1.07 GB |
| Llama 3.1 70B | 141 GB | 71 GB | 35 GB | 328 kB | 2.68 GB |

Concurrent 4,096-token sequences that fit, keeping 10% of memory for activations and the runtime:

| setup | sequences |
|---|---|
| Llama 3.1 8B, bf16, one L4 (24 GB) | 10 |
| Llama 3.1 8B, int4, one L4 | 32 |
| Llama 3.1 8B, bf16, one H100 (80 GB) | 104 |
| Llama 3.1 70B, bf16, one H100 | doesn't fit |
| Llama 3.1 70B, int4, one H100 | 27 |

Two conclusions. Grouped-query attention (8 KV heads instead of 32 or 64) is what keeps these caches affordable; models without it need
several times more cache memory per token. And long contexts eat concurrency: the cache, not the weights, usually limits how many users one
GPU serves. A 70B model in 16 bits needs at least two 80 GB GPUs with tensor parallelism; quantized to 4 bits it fits on one, at some cost
in quality that you measure on your evals (37.3, 43.1).

## Throughput: batching is the whole game

Decoding generates one token per sequence per step, and each step reads all the weights from memory. For one sequence, the GPU spends
almost all its time waiting for memory (the roofline, 33.1). Batching more sequences into each step amortizes that read. The lab measures
it on the course's tiny GPT on a 4-core CPU (timings from one quiet run; yours will differ, the shape won't):

| batch | tokens per second | vs batch 1 |
|---|---|---|
| 1 | 1,184 | 1.0× |
| 4 | 3,524 | 3.0× |
| 16 | 10,492 | 8.9× |
| 64 | 21,697 | 18.3× |

The same shape holds on GPUs, with larger numbers. The roofline estimate for Llama 3.1 8B in bf16 on one H100 (3.35 TB/s of memory bandwidth)
is about 209 tokens per second at batch 1, 13,400 at batch 64 and 53,600 at batch 256, ignoring KV-cache reads, which grow with batch and
context and take a real share. Serving engines exist to keep batches full as requests arrive and finish at different times: **continuous
batching**, **paged KV caches** (vLLM's PagedAttention), prefix caching, speculative decoding and chunked prefill (37.2).

The software:

- **vLLM** and **SGLang**: high-throughput serving on GPUs, with an OpenAI-compatible API.
- **TensorRT-LLM** (with Triton): NVIDIA's compiled path, the fastest on their hardware and the most work to set up.
- **llama.cpp** (and Ollama on top of it): CPU and consumer-GPU inference with quantized GGUF models; the way to run models on laptops
  and edge devices.
- **Hugging Face TGI**: a serving stack integrated with the Hub.

Whichever you use: apply the model's own chat template (40.2), set sampling defaults deliberately, and benchmark with your prompt and
output lengths, since throughput depends on both.

## The break-even

A GPU costs the same per hour whether it's busy or idle. With an illustrative $3.00 an hour for an H100-class GPU sustaining 5,000 output
tokens a second when busy (well below the roofline, as real mixed traffic is):

| utilization | cost per million tokens |
|---|---|
| 5% | $3.33 |
| 20% | $0.83 |
| 50% | $0.33 |
| 90% | $0.19 |

Against illustrative API prices of $0.50 per million for a small model and $5.00 for a mid-size one. At high, steady utilization,
self-hosting a small open model beats a small API model on cost. At low or bursty utilization it doesn't, and those figures leave out the
engineers who run it, redundancy (at least two replicas, 49.2), and the evaluation and upgrade work. The self-check answer: self-hosting is
cheaper than an API when traffic is high and steady enough to keep GPUs busy, or when a small fine-tuned model can replace a much larger API
model for your task. It's rarely cheaper at low volume. The non-cost reasons (data residency, control, latency) are often the real ones.

## Operating it

- **Evaluate before switching**: an open model's quality on your task, compared with the API model on your eval suite (43.1), in the
  quantization you'll serve.
- **Pin everything**: model weights by hash (53.2), the serving engine's version, the chat template and the sampling settings (48.2).
- **Load safely**: weights in safetensors, never pickles from unknown sources (53.2), and check the license (some open-weight licenses
  restrict use).
- **Monitor** throughput, time to first token, queue length, KV-cache utilization and GPU memory, besides the usual (43.2).
- **Scale** on queue length and KV-cache pressure, and plan for cold starts: loading 16 to 140 GB of weights takes minutes (49.2).

## Things that will bite you

- **Sizing by weights alone**, forgetting the KV cache.
- **Benchmarking with batch 1** or with prompt lengths unlike your traffic.
- **Comparing a GPU's cost** with API prices at 100% utilization you'll never have.
- **Quantizing without evaluating** the quantized model on your task.
- **The wrong chat template** (40.2).
- **One replica.**

## Exercises

1. Compute the KV cache per token for a model with 40 layers, 8 KV heads of dimension 128, in bf16. How many 32k-token sequences fit in 40 GB?
2. Why does batching barely increase the time per decoding step until a certain batch size?
3. Your traffic is 2 million output tokens a day, evenly spread. Estimate the utilization of one GPU at 5,000 tokens a second. Self-host?
4. A 70B model must serve 50 concurrent users with 8k contexts. Size the hardware in 16 bits and in 4 bits.
5. What would you check before replacing an API model with a fine-tuned 8B model for ticket classification?
6. Why can prefix caching matter more for self-hosted serving than for API calls?

<details>
<summary>Answers</summary>

1. $2 \times 40 \times 8 \times 128 \times 2 = 163{,}840$ bytes, about 164 kB per token. A 32k-token sequence needs about 5.4 GB, so 7
   sequences fit in 40 GB.

2. Each step must read all the weights once regardless of batch size, and at small batches that read dominates (memory-bound). Extra
   sequences add arithmetic that fits in the time the memory read takes anyway. Once arithmetic per step exceeds the memory time (and
   KV-cache reads grow), the step gets longer: compute-bound.

3. $2{,}000{,}000 / 86{,}400 \approx 23$ tokens a second, under 0.5% utilization. The GPU costs \$72 a day for 2 million tokens,
   \$36 per million, far above API prices. Don't self-host for cost; use an API, a much smaller machine, or serverless.

4. KV cache: 50 × 8,192 × 328 kB ≈ 134 GB. In 16 bits: 141 GB of weights plus 134 GB of cache plus overhead, about 300 GB: four 80 GB GPUs
   with tensor parallelism. In 4 bits: 35 GB plus 134 GB (unless the cache is also quantized, which halves it in 8 bits), about 180 GB: three
   80 GB GPUs, or two with an 8-bit KV cache. Then check throughput and quality.

5. Accuracy on the same held-out tickets, per category and on hard slices, with a paired comparison (43.1); calibration if downstream
   uses probabilities; behavior on unseen categories and inputs; latency and cost at your traffic; robustness to prompt-injection-like
   inputs in tickets (44.1); how it's retrained as categories change; and a rollback path to the API model (50.2).

6. With your own server, a shared prefix (system prompt, tools, documents) is computed once and reused across every request that shares
   it, saving prefill compute and time to first token on your hardware directly. With APIs, prompt caching is offered by the provider as a
   price discount; self-hosted, it's your throughput.
