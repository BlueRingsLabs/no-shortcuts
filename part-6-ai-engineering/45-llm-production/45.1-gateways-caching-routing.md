# 45.1 Gateways, caching, routing and cost control

*About 10 hours. Prerequisites: 40.1 (the LLM as an API), 43.2 (monitoring), 41.1 (embeddings). Lab: [`lab_45_1_gateway.py`](labs/lab_45_1_gateway.py).*

Every organization that ships a second LLM feature discovers, a few months later, that it has API keys in four repositories, three
different retry implementations, no idea which feature spends the money, and no way to switch providers when one has an outage. So once
more than one feature, team or model is involved, calls to LLM APIs should stop going directly from application code to providers,
and go through an **LLM gateway**: one service that every call passes through. It's the same idea as an API gateway, with LLM-specific jobs:

- one place for provider credentials, instead of keys in every service (44.2);
- routing between models and providers, and fallbacks when one fails;
- caching;
- rate limits, quotas and budgets per team, user and feature (40.1, 44.2);
- logging and tracing of every call (43.2), with redaction;
- a stable internal API, so changing providers is a configuration change.

You can use an open-source or hosted gateway (LiteLLM, Portkey, the cloud providers' own) or write a thin one. What matters is that it
exists before the tenth team integrates directly. The lab looks at the parts with the most engineering in them: caching, routing, and
surviving outages.

## Exact caching

Identical requests get identical answers from a cache instead of the model: no cost, near-zero latency. How much traffic repeats depends
on the product. The lab simulates 100,000 requests over 20,000 distinct questions with Zipf-distributed popularity (a few questions are very
common, as in support or search traffic) and gets an 86.9% hit rate. Open-ended chat has almost none.

Details that matter:

- **Normalize** before hashing (case, whitespace, trailing punctuation), so trivial variants share a key.
- **The key must include everything that changes the answer**: the model and its version, the system prompt, the parameters, the tools,
  and, if answers depend on data the user may see, the user's permissions. A cache shared across users that returns an answer built from
  one user's private data to another is a data leak. Scope it (per tenant, per permission set) or don't cache those requests.
- **Expire** entries when the underlying data or prompt changes.
- **Temperature**: caching a sampled answer makes it deterministic for everyone who asks. Usually fine, and occasionally not what the
  product wants.

(Provider-side *prompt caching*, 40.1, is different: it caches the processed prefix of a prompt, not the answer, and it's always worth
using.)

## Semantic caching

A semantic cache embeds each request and returns a cached answer when a previous request is close enough in embedding space, so paraphrases
hit too. That's the appeal. The risk is questions that are close in embedding space and different in meaning.

The lab tests it with the course's question templates, embedded by the encoder from 41.1. The cache holds 150 answered questions. The
incoming traffic has paraphrases of cached questions ("Tell me what lesson 18.2 covers" for a cached "What is lesson 18.2 about?"), which
should hit, and near-identical questions about a *different* lesson ("What is lesson 18.1 about?"), which must not:

| similarity threshold | hit rate | share of hits with the wrong answer |
|---|---|---|
| 0.5 and 0.7 | 1.000 | 0.42 |
| 0.8 to 0.95 | 0.495 | 0.16 |

At every threshold, a large share of hits return another lesson's answer. The embedding barely sees the difference between "18.1" and
"18.2" (41.1's lesson about identifiers), and no threshold separates the paraphrases from the wrong siblings. This lab's encoder is small,
and production embedding models are better at paraphrase, but numbers, names and IDs are exactly where all embedding models are weakest.
Semantic caching is only safe for FAQ-like traffic without near-duplicate questions, with a high threshold, exact-match checks on the
entities in the request (IDs, numbers, names, dates), and a measured wrong-hit rate on your traffic. A wrong cached answer is worse than a
slow right one, and nothing downstream will notice it.

## Routing and cascades

Most requests don't need the largest model. **Routing** sends each request to the cheapest model that can handle it: by request type,
by a classifier (42.3), or by the features of the request. A **cascade** tries the cheap model first and escalates when a check fails: a
validator (40.2), the small model's own confidence, a judge (43.1).

The lab's cascade, with stated assumptions (a small model correct 70% of the time and a large one 90%, the small one's mistakes concentrated
on hard requests), on 20,000 requests:

| strategy | correct | cost per 1,000 requests |
|---|---|---|
| always small | 0.698 | $0.88 |
| always large | 0.905 | $52.50 |
| cascade, check catches 60% of mistakes, 10% false alarms | 0.850 | $14.08 |
| cascade, check catches 90% of mistakes, 10% false alarms | 0.931 | $18.87 |

With a good check, the cascade matches the large model at about a third of the cost, and here beats it: requests the small model gets
right stay right, including some the large one would have missed (FrugalGPT, Chen et al., 2023, reported the same effect). With a weak check
it keeps many of the small model's errors. The check is the whole design, and it needs the same measurement as any classifier.

## Fallbacks and circuit breakers

Providers have outages. The lab simulates a day of traffic, one request a second, with the primary provider failing 1% of requests normally
and all of them during a 40-minute outage, each failure costing a 10-second timeout:

| strategy | failed requests | requests that waited for a timeout first |
|---|---|---|
| no fallback | 3,272 | 3,272 |
| fallback on every failure | 39 | 3,268 |
| fallback + circuit breaker | 40 | 947 |

A fallback turns failures into slow requests. A **circuit breaker** notices that the primary is failing (here, half of the last 20 calls),
stops sending it traffic for a while, and probes it again later, so most requests during the outage go straight to the fallback. Two
cautions: the fallback model behaves differently, so evaluate it on your suite (43.1) and keep its prompts tested; and the fallback provider
needs its own rate limits and quotas, or the outage becomes two.

## Cost control

The gateway is where cost control lives, because it sees every call:

- **Budgets and quotas** per team, feature, user and API key, with alerts before limits and hard stops at them.
- **Attribution**: every call tagged with its feature and team, so the monthly bill can be read.
- **Limits on output length** per feature (40.1), and on agent steps (42.1).
- **Model choice by default**: the cheap model unless a feature has shown, on its evals, that it needs a bigger one.
- **Batch APIs** for anything that isn't interactive.

> **Scar tissue.** A semantic cache I added, as a freelance job, in front of a small fintech app's support bot once answered a user's
> question about their balance with another user's answer. The cache was keyed on the embedding of the question alone, and "what's my
> balance?" is the same question for everyone. Cache keys must include everything the answer depends on: the user, the tenant, the
> permissions, the document versions. Or don't cache personalized answers at all, which is what we ended up doing, about an hour after I
> found out.

## Things that will bite you

- **Direct provider calls** from every service, each with its own key and no shared limits.
- **Cache keys missing the model version, prompt or permissions.**
- **Semantic caching** of questions that differ in a number or a name.
- **Cascades with unmeasured checks.**
- **Fallback models nobody evaluated**, or that share the primary's failure.
- **No per-feature cost attribution.**

## Exercises

1. What would you include in the cache key for a support assistant that answers questions using the customer's account data?
2. Your semantic cache has a 2% wrong-hit rate at the chosen threshold. How do you decide whether that's acceptable, and what can reduce it?
3. Design a cascade for classifying support tickets into 30 categories, with a small and a large model. What's the check?
4. Why does a circuit breaker reduce latency during an outage but not the number of failed requests?
5. A feature's cost tripled after a prompt change. Where in the gateway's data do you look?
6. When should a team not route to the cheaper model, even if it's accurate enough on average?

<details>
<summary>Answers</summary>

1. The normalized question, the model and version, the system prompt version, the tool definitions, the generation parameters, and the
   customer ID (or the exact set of account data the answer used). Answers that depend on account data are per-customer; only generic
   answers (help-center content, no personal data) can be shared across customers.

2. Estimate the cost of a wrong cached answer (a wrong refund policy, a wrong medical dosage, a wrong lesson title) against the savings.
   Measure the wrong-hit rate by category. Reduce it: raise the threshold, require exact matches on extracted entities, exclude categories
   where wrong answers are costly, add a cheap verification step (does the cached answer mention the entities in the new question?), and
   expire entries sooner.

3. The small model classifies and returns its probability for the top category (or the margin between the top two). The check: escalate
   when the top probability is below a threshold calibrated on a labeled set (18.3) so that escalated tickets contain most of the small
   model's errors; also escalate categories where errors are costly (legal, security) regardless. Measure the cascade's accuracy and cost
   on held-out tickets for several thresholds and pick the operating point.

4. During the outage, every request fails on the primary anyway; with a fallback, they're served by the fallback either way. The circuit
   breaker stops the primary attempts, so requests don't wait for a timeout before falling back: same success count, much lower latency.

5. Per-feature token counts before and after the change: input tokens per call (a longer prompt, or a broken prompt cache from variable
   content at the start, 40.1), output tokens per call (a prompt that invites longer answers), calls per request (retries, agent steps),
   and the model distribution (a change in routing).

6. When the cheaper model fails on a segment that matters (a language, a customer tier, a category with high stakes), even if average
   accuracy is fine; when its failures are harder to detect; when latency or consistency requirements differ; and when switching changes
   behavior users rely on. Route on evaluated slices, not averages.
