# 40.2 Prompting as programming and structured outputs

*About 8 hours. Prerequisites: 40.1, 38.1 (chat templates), 37.1 (constrained decoding), 10.3 (validation with schemas). Lab: [`lab_40_2_structured_outputs.py`](labs/lab_40_2_structured_outputs.py).*

"Prompt engineering" got its reputation from people collecting magic phrases. Ignore the phrases. A prompt in a product is code: it
has inputs, it has a specification (the output you need), it has bugs, it regresses when someone "improves" it, and it runs millions of
times on inputs its author never imagined. Treat it like code, with version control, review and tests, and most of the mystique goes
away. What's left is a small set of techniques that work, and a larger set of engineering around the model's output, because the output is
text and your program needs data.

## What goes into a prompt

A prompt that works in production usually has the same parts, in roughly this order:

1. **Role and context** (system prompt): who the model is working for, what the product does, who the user is. Short.
2. **The task**, stated as you would to a competent new colleague who has no context: what to do, what the output is for, what good
   looks like. Most bad prompts are underspecified, not badly worded.
3. **Constraints and policies**: what not to do, how to handle the cases you already know are hard ("if the ticket mentions legal
   action, set priority to high and category to legal").
4. **The data**, clearly delimited from the instructions (XML-style tags work well: `<ticket>...</ticket>`). Everything inside the
   tags is data to process, never instructions to follow; say so, and see 44.1 for why saying so is not enough.
5. **The output format**, as a schema, not as prose.
6. **Examples** (few-shot), when the task has a format or judgment that's easier to show than to describe.

Stable parts go first and variable parts last, which is also what makes prompt caching work (40.1).

Some things that reliably help: being specific about the edge cases; giving the reason behind a rule ("the summary is shown in a
200-pixel column", not "be concise"), because models generalize from reasons; asking for the reasoning before the answer on tasks that need
it (or using a reasoning model, 38.4); and splitting a complicated task into several calls with simple prompts, each testable on its own
(42.1). Things that don't: threats, bribes, capital letters, and phrases copied from a thread about someone else's model. When a phrase
seems to help, it's a hypothesis, and 43.1 is how you test it.

**Examples work, and they leak.** Models copy the examples' length, tone, vocabulary and sometimes their content. Use several examples
that differ from each other in the ways real inputs differ, don't use examples that resemble a real answer, and check outputs for text
copied from them. One of the lab's twelve outputs is a model that echoed its example before giving the answer, and a parser that took
the first JSON object in the text returned the example, validated.

## Prompts are code

- **Version them** in the repository, next to the code that fills them, not in a dashboard nobody reviews. Templates with named
  variables, rendered by one function, logged with their version on every call (43.2).
- **Test them**: a set of inputs with checks on the outputs, run on every change to the prompt, the model version or the parsing code.
  43.1 is the full treatment; the minimum is a few dozen real inputs, including the ones that failed in production.
- **Review changes** like code changes, with the test results attached. A "small wording fix" is a behavior change.
- **Pin the model version** the prompt was tested against (40.1). Prompts tuned for one model are often worse on the next.

Tools that optimize prompts automatically against a metric (DSPy, Khattab et al., 2023, and its descendants) treat the prompt as a
parameter to fit, which is the logical end of this view. They need what any fitting needs: a metric you trust and data held out from
the optimization, or they overfit to your test set like anything else (18.1).

## The string the model actually sees

A chat API takes a list of messages; the model sees one token sequence, built by the model's **chat template** (38.1). With a hosted API
the provider applies it. When you self-host (45.2), fine-tune, or build prompts as raw strings, it's your job, and it's a classic silent
bug: the model still answers, just worse.

The lab asks the course's fine-tuned model (38.1) the same 120 questions it was trained on, changing only the prompt string:

| prompt | exact match |
|---|---|
| the template it was trained with | 0.667 |
| the same, with the trailing space stripped | 0.017 |
| "Please answer briefly." prepended to the question | 0.150 |
| a hand-written "User: / Assistant:" template | 0.000 |

The model is the same in every row. The trained template ends in the tokens `|`, `>`, `" "`; stripping the trailing space makes the
prompt end in `ant`, `|`, `>`, a sequence the model never saw followed by an answer, and accuracy collapses from two thirds to under
two percent. A polite instruction costs more than three quarters of the accuracy, because the question no longer looks like the training questions.
A tiny model fine-tuned on one narrow format is an extreme case, and large instruction-tuned models are far more tolerant. But the
failure mode is identical, it's silent (the model still answers, fluently and wrongly), and it's common when people self-host models
and write the template by hand.

Use the tokenizer's own template (`tokenizer.apply_chat_template` in Hugging Face) rather than reproducing it by hand, never let user
text contain the template's special tokens (35.1), and when outputs look strangely worse after a migration, diff the token IDs of the
prompt, not the text.

## Getting data out: structured outputs

Your program needs a priority, a category and a boolean, not prose. Four approaches, from worst to best:

1. **Ask for JSON in the prompt and parse the text.** Works most of the time, which is the problem.
2. **Ask, then extract, repair and validate.** Where most codebases end up. Robust against formatting noise, and it moves the failures
   from loud to quiet.
3. **Tool calling with a schema**: define a "tool" whose input schema is your output schema and require the model to call it (40.3).
   Providers train models heavily on tool calls, so arguments are much more reliably well-formed.
4. **Constrained decoding against the schema** ("structured outputs" or "JSON mode with a schema" at the major providers; Outlines,
   XGrammar or llguidance when you self-host). The decoder masks every token that would violate the schema (37.1), so the output
   parses and matches the schema by construction.

Whatever the approach, **validate** the result with a real schema (pydantic, JSON Schema): types, enums, required fields, ranges, and
the cross-field rules no schema language expresses well ("if refund_requested, category must be billing"). Constrained decoding
guarantees the shape, never the content.

### What the lab's twelve outputs show

Twelve outputs of the kinds models return when a prompt asks for JSON: clean, wrapped in a markdown fence, with a chatty preamble, a
trailing comma, Python syntax, a comment, cut off by `max_tokens`, an invented enum value (`"urgent"`), a boolean as `"yes"`, a missing
field, an echoed example, and an extra field. Three parsers, and pydantic in its default and strict modes:

| parser | correct | passed validation with wrong content |
|---|---|---|
| `json.loads` | 3 | 0 |
| extract the first `{...}` | 5 | 1 |
| lenient repair (comments, trailing commas, Python literals, close what's open) | 8 | 2 |
| lenient repair, strict validation | 7 | 2 |

The lenient parser rescues the most outputs, and that's exactly what makes it dangerous: it closed the quote and the brace of a truncated
answer and handed back a schema-valid object whose summary is "Charged tw". Pydantic's default ("lax") mode then converted the string
`"yes"` to `True`, which is convenient right up until the model writes `"no, but maybe"` somewhere a boolean belongs. The rules that fall
out:

- **Check `stop_reason` before parsing.** A truncated output is a failure, never something to repair.
- **Validate strictly**, and decide deliberately what to do with extra fields (ignore, or forbid to catch schema drift).
- **Repair only syntax you understand** (a fence, a preamble), and count how often you had to: a rising repair rate is a model or prompt
  regression, visible in your metrics before it's visible to users.
- **Prefer constrained decoding**, which makes the whole left side of the table disappear and leaves only content errors, the ones you
  have to evaluate for (43.1).

### Retrying, and when it doesn't help

The standard loop: call, check the stop reason, parse, validate, and on failure send the validation error back as a message and ask for a
corrected answer, a bounded number of times (the lab's `structured_call`). Each retry costs a full call's tokens and latency, so a loop
that retries 5% of requests adds 5% to the cost and much more to the tail latency (p99 is now two or three calls).

The arithmetic that justifies retries assumes failures are independent: at a 10% failure rate, three attempts fail $0.1^3 = 0.1\%$ of the
time. The lab tests that with 10,000 tickets, the same 10% average failure rate and at most three attempts, in two worlds: every ticket
equally likely to fail, or a few tickets hard (failing almost every time) and most easy. With independent failures, 0.07% of tickets still
fail after three attempts (0.1% predicted). With concentrated failures, 4.0% do, about 40 times the prediction, for the same average. Real failures
are concentrated: the inputs that confuse a model once confuse it again, because they're the unusual ones. So:

- Retries fix noise (a sampling accident, a formatting slip), not difficulty.
- Log the inputs that exhaust their retries (43.2); they're your best test cases and your best evidence for a prompt or model change.
- Have a fallback that isn't the same model with the same prompt: a stronger model, a simpler task, or a human queue.

### Does a format cost accuracy?

The lab asks the same model the same 120 questions two ways: answer normally and build `{"title": ...}` in code, or prefill the answer
with `{"title": "` and let the model write the value inside the JSON (the cheapest form of forcing a format). Answering normally:
0.667. Inside the JSON: 0.000, with outputs like `Adg.tttttes`. The model had never seen its answers inside JSON,
and the unfamiliar context knocked it off the task entirely. The format was valid; the content was gone.

The literature disagrees on how much this matters for large models (Tam et al., 2024, found format restrictions can hurt reasoning
tasks; follow-ups found much of the effect came from how the prompts and parsers were set up). The engineering answer doesn't depend on
who's right: measure your task with and without the format on your own evaluation set, and if the format costs accuracy, answer first and
format second, or put a free-text reasoning field before the answer fields so the model gets its room to think before committing.

## Things that will bite you

- **Parsing without checking `stop_reason`**, and repairing truncated JSON into a valid, wrong object.
- **Lax validation** that coerces strings into booleans and numbers.
- **Few-shot examples copied into outputs**, or extracted as the answer.
- **Hand-built chat templates** when self-hosting; a stripped trailing space.
- **Unversioned prompts** edited in a dashboard, with no tests.
- **Retry loops without a bound**, or with the assumption that failures are independent.
- **Untrusted text concatenated into instructions** (44.1).

3. A model fails 10% of requests with invalid output. You allow up to three attempts. Give the final failure rate if failures are
   independent, and explain why it will be higher in practice.
4. Why is lenient JSON repair of a `max_tokens`-truncated output worse than failing?
5. You move from a hosted API to a self-hosted open model with the same prompts, and quality drops. Name three things to check before
   blaming the model.
6. When does forcing structured output hurt accuracy, and what are two ways around it?
