# 40.1 The LLM as an API: tokens, latency and money

*About 6 hours. Prerequisites: 35.1 (tokens), 37.1 and 37.2 (decoding, prefill vs decode, prompt caching), 07.4 (networks and APIs). Lab: [`lab_40_1_llm_as_api.py`](labs/lab_40_1_llm_as_api.py).*

Part VI is about building products on models you didn't train, usually through an API. The first thing to internalize is that an LLM
API call is not a function call. It's a remote, metered, rate-limited, slow, occasionally failing, nondeterministic service whose price
depends on how much text you send and receive, and whose latency depends on it too. Everything a backend engineer knows about calling a
flaky third-party service applies, plus three LLM-specific facts: you pay per token, time scales with tokens, and the output can be wrong in
ways no status code reports.

The lab runs against a simulated API (in `part-6-ai-engineering/_shared/fakellm.py`): offline, deterministic, with virtual time, so it can
be rate-limited, flaky and slow on command. That's also how you should test your own LLM code.

## The call

The shape is the same across providers: a list of messages with roles, an optional system prompt, generation parameters, and a response with content, a stop reason and token usage. With Anthropic's Python SDK:

```python
import anthropic
client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY; retries and timeouts are configurable
resp = client.messages.create(
    model=MODEL,                        # a pinned, dated model ID from your config (see below)
    max_tokens=500,
    system="You are a support triage assistant...",
    messages=[{"role": "user", "content": ticket_text}],
)
print(resp.content[0].text, resp.stop_reason, resp.usage.input_tokens, resp.usage.output_tokens)
```

OpenAI-compatible APIs (which many open-model servers also expose, 45.2) differ in field names, not in substance. Keep the provider behind a thin interface of your own so you can swap models, add a fake for tests, and route between providers (45.1).

## Tokens are the unit of everything

You're billed per input token and per output token (output typically 3 to 5 times more expensive), limits are in tokens per minute, context windows are in tokens, and latency grows with tokens. Count them with the provider's tokenizer or token-counting endpoint, not by characters; and remember 35.1: the same text costs different numbers of tokens in different languages and with different tokenizers.

The lab prices a realistic workload, triaging a million support tickets (a 446-token system prompt, a 316-token ticket, a 60-token answer), at three illustrative price tiers:

| model tier | plain | with prompt caching | + batch API |
|---|---|---|---|
| small | $266 | $165 | $83 |
| medium | $3,186 | $1,982 | $991 |
| large | $15,930 | $9,909 | $4,954 |

Three levers, in order of size:

1. **Model choice**: a factor of 60 between the tiers. Most applications need the large model for a minority of requests at most; which ones is an evaluation question (43.1) and a routing problem (45.1).
2. **Prompt caching**: the stable prefix (system prompt, tool definitions, few-shot examples, a long document) is billed at a steep discount when reused within the cache lifetime (37.2 explains why it's cheaper for the provider). Put stable content first and variable content last.
3. **Batch APIs**: asynchronous jobs (results within hours) at about half price. Anything that doesn't need an answer now (nightly classification, backfills, evaluations) belongs there.

Then the smaller levers: shorter prompts (every instruction is paid on every call), `max_tokens` set to what the task needs, and asking for concise output formats.

## Latency

Two numbers, from 37.2: **time to first token** grows with the prompt (prefill), and **time per output token** multiplies the output length (decode). In the lab's medium tier, TTFT goes from 0.27 s for a 200-token prompt to 2.65 s for 20,000, while going from 100 to 1,000 output tokens takes the total from 3 s to 25 s. So:

- **Long outputs are slow**; a verbose model is a slow model. Ask for less.
- **Streaming** doesn't make the answer faster; it shows the first words after TTFT instead of after the whole response, which is what users perceive in a chat interface. It complicates everything downstream that needs the complete output (validation, 40.2).
- **Parallelize** independent calls instead of chaining them; every sequential step adds its full latency.
- Measure p50 and p95, per request type, in production (43.2). Provider latency varies by time of day and load.

## Calling it robustly

What goes wrong, and what to do:

- **Rate limits** (HTTP 429): requests or tokens per minute exceeded. Wait for the `Retry-After` the server sends, and put a shared rate limiter in front of all your workers so they don't exceed the limit collectively.
- **Transient server errors** (5xx, "overloaded") and **timeouts**: retry with **exponential backoff and jitter**. Don't retry client errors (400s): a malformed request stays malformed.
- **Timeouts**: set them, sized to the expected output length (a 2,000-token answer legitimately takes a minute), and treat a timeout as "unknown outcome" for anything with side effects.
- **Truncation**: `stop_reason == "max_tokens"` means the answer was cut off. The lab's client flags it; using a truncated JSON object or half an answer is a classic silent bug.
- **Idempotency**: a retried request may have been processed the first time. For LLM calls that's usually just cost, but for tool calls with side effects (40.3) it's a real problem: design them to be safe to repeat.

In the lab, with an 8% server error rate, 3% timeouts and a 30-requests-per-minute limit, a client that fires as fast as it can gets 25 of 200 tickets through; the robust client gets all 200, at exactly the rate limit.

**The thundering herd**: when many clients are rejected at the same moment and retry after the same delay, they collide again. The lab's simulation (50 clients, a server that takes one request per 100 ms): fixed one-second retries finish after 49 s with 1,225 rejections; exponential backoff *without* jitter never desynchronizes and takes over 20 minutes; exponential backoff with **full jitter** (a random wait between zero and the backoff) finishes in 10 s with 122 rejections. The official SDKs retry with jittered backoff by default; if you write your own loop, add the jitter.

## Nondeterminism and versions

Even at temperature 0, hosted models can return different outputs for the same input (batching effects, 37.2; routing between replicas). Build for it: validate outputs (40.2), evaluate on distributions of runs, not single samples (43.1). And **pin model versions** (dated model identifiers rather than floating aliases) in production, with an explicit upgrade process that reruns your evaluation suite: a silent model update is a deployment you didn't review.

## Data and security basics

Everything you send goes to a third party: check the provider's data retention and training terms, your contracts, and regulation (54.2, 54.3) before sending customer data. Don't put secrets in prompts, and assume anything in the context can end up in the output (44.1). Keep API keys in a secrets manager, rotate them, scope them per service, and set spending limits and alerts: a leaked key or a loop bug is a bill.

> **Scar tissue.** A script I wrote to classify a few thousand forum posts with an LLM API retried on any error, including a JSON
> validation failure that was deterministic for a handful of malformed posts. No backoff, no retry limit, no budget. I ran it before going
> to sleep. In the morning it had classified everything, several times over, and that night's bill was larger than what I'd spent on the
> API in the previous three months. Retries need limits, and a job that spends money needs a budget that stops it.

## Things that will bite you

- **Estimating cost in words or characters** instead of tokens, or forgetting that output tokens cost several times more.
- **No retries, or retries without jitter.**
- **No timeouts**, or timeouts shorter than a legitimate long answer.
- **Ignoring `stop_reason`** and using truncated output.
- **Variable content at the start of the prompt**, defeating prompt caching.
- **Floating model aliases** in production.
- **Unbounded loops** of LLM calls with no budget (42.1).

## Exercises

1. A request has a 1,200-token system prompt (cached), a 400-token user message and a 250-token answer, on a model priced at \$3 / \$0.30 (cached) / \$15 per million input, cached input and output tokens. What does it cost? How many such requests does \$100 buy?
2. Why do output tokens cost more than input tokens?
3. Write the wait time for retry attempt $k$ with full jitter, base 1 s and cap 30 s.
4. Your summarization feature takes 12 s. Users complain. List four changes, in the order you'd try them.
5. A worker pool of 20 processes hits a 600 requests/minute limit and gets many 429s. Why doesn't per-process retrying fix it, and what does?
6. A retry of a "send email to customer" tool call results in two emails. How do you prevent it?

<details>
<summary>Answers</summary>

1. Cached input: $1{,}200 \times 0.30/10^6 = \$0.00036$; input: $400 \times 3/10^6 = \$0.0012$; output: $250 \times 15/10^6 = \$0.00375$. Total $\$0.00531$. $100 buys about 18,800 requests. (Output is 70% of the cost.)

2. Input tokens are processed in parallel in one prefill pass (compute-bound, efficient); output tokens are generated one at a time, each a memory-bound decode step that occupies GPU memory (the growing KV cache) and a batch slot for its duration (37.2). Per token, generation costs the provider much more.

3. $\text{wait}_k = \text{Uniform}(0, \min(30, 1 \cdot 2^k))$ seconds, or the server's `Retry-After` if larger.

4. Stream the output so users see text after the time to first token; shorten the output (ask for a shorter summary, lower `max_tokens`); try a smaller or faster model, checking quality on your evaluation set; shorten or cache the input (prompt caching, less context); split long documents and summarize chunks in parallel. Measure which part is prefill and which is decode first.

5. Each process only sees its own retries; together they still exceed the global limit, and their retries add load. A shared rate limiter (a token bucket in Redis, or a gateway, 45.1) keeps the aggregate under the limit, with jittered backoff for what still gets rejected, and a queue in front so bursts wait instead of failing.

6. Make the tool idempotent: attach an idempotency key (for example, derived from the conversation and tool-call ID) that the email service stores, so a repeated request with the same key is a no-op. Record side effects before acknowledging, and treat timeouts as "unknown" by checking state rather than blindly retrying. For irreversible actions, require confirmation (40.3).
