# 40.3 Tool use and function calling

*About 8 hours. Prerequisites: 40.1, 40.2, 07.4 (networks and APIs). Lab: [`lab_40_3_tool_use.py`](labs/lab_40_3_tool_use.py).*

Tool use is where an LLM stops being a text generator and starts doing things: looking up an order, running a query, issuing a refund,
sending an email. It's also where the consequences of a wrong answer stop being a bad paragraph and start being a refund to the wrong
customer. I've spent enough years on the offensive side of security reviews to have a simple rule for this: whatever the model can call,
assume it will eventually call with the worst arguments you can think of, and a few you can't. The model is not your security boundary.
The code around it is.

## What function calling is

The model never executes anything. You describe tools (a name, a description, a JSON Schema for the arguments); the model, when it
decides a tool would help, stops generating text and emits a structured request: this tool, these arguments. Your code decides whether
to run it, runs it, and sends the result back as a message. The model continues, possibly calling more tools, until it produces a final
answer. That's the whole mechanism; "agents" (42.1) are this loop with more autonomy.

With Anthropic's SDK:

```python
tools = [{
    "name": "lookup_order",
    "description": "Get an order by ID: items, amount paid in cents, status. Use before any refund.",
    "input_schema": {"type": "object",
                     "properties": {"order_id": {"type": "string", "pattern": "^A[0-9]{4}$"}},
                     "required": ["order_id"]},
}]
messages = [{"role": "user", "content": request}]
for _ in range(MAX_STEPS):
    resp = client.messages.create(model=MODEL, max_tokens=1024, tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break
    results = []
    for block in resp.content:
        if block.type == "tool_use":
            output, is_error = execute(block.name, block.input, user=current_user)   # validate, authorize, run
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": output, "is_error": is_error})
    messages.append({"role": "user", "content": results})
```

Note what's in `execute`: validation, authorization and the actual call, with `current_user` coming from your authentication, not from
anything the model wrote. A response can contain several tool calls, which you can run in parallel when they're independent. `tool_choice`
lets you force a specific tool (the structured-output trick from 40.2) or require some tool call. Other providers differ in field names,
not in the loop.

The lab runs this loop against the simulated API with a scripted "model" that makes the mistakes real models make: a garbled order ID
now and then, an amount sent as `"$49.99"` instead of `4999`, and occasionally getting stuck re-reading the same order. Its trace of one
conversation is worth reading line by line: wrong ID, error, correct ID, wrong type, validation error, correct call, email, done. Six
model calls for a task that needs four, which is normal, and which is why every error message you return matters.

## Designing tools

Tool definitions are prompts. The model chooses a tool, and fills its arguments, from the name, the description and the schema, so
write them for a reader who has nothing else:

- **Few, distinct tools** with clear names. Two tools whose descriptions overlap will be confused. Selection accuracy drops as the
  number of tools grows; with dozens, retrieve the relevant tools per request (42.2) or split the work between specialized calls.
- **Descriptions that say when to use the tool**, what it returns and what it can't do ("Irreversible", "Use once, to confirm the
  outcome", "Use before any refund").
- **Tight schemas**: enums instead of free strings, integer cents instead of floating dollars, patterns for IDs, required fields. Each
  constraint is both an instruction and a check.
- **Results the model can use**: concise, relevant fields, not a 40 kB API response (it's context you pay for, 40.1, and it dilutes
  attention). Paginate or summarize big results.
- **Errors that say what to do next**: "order A1043 not found" gets a different next move than "500". The lab's model recovers from
  every error it's given a precise message for.
- **Higher-level tools over low-level ones** when the sequence is always the same: a `refund_order` that does the lookup, the check and
  the refund in code is more reliable than trusting the model to call three tools in the right order every time. Code is for what you
  know; the model is for what you don't.

## The tool layer is the security boundary

Everything the model sends you is untrusted input, as much as a form field on a public website, because it's derived from text you don't
control: user messages, retrieved documents, previous tool results (44.1). So the tool layer does what any API handling untrusted input
does.

**Validate arguments strictly, before anything runs.** In the lab's 300 conversations, without validation the `"$49.99"` string reached
glue code that "helpfully" converted it to an integer and refunded 49 cents: the call succeeded, the model reported success, and 24
customers got the wrong amount. With a strict schema check, the model got "Input should be a valid integer" and fixed its own call every
time.

**Authorize in the tool, from the session, never from the model.** A garbled order ID is often another customer's valid ID. The lookup
succeeds, the model has no reason to doubt it, and the refund goes to a stranger. No schema can catch that. The lab's results:

| checks in the tool layer | refunded correctly (of 300) | wrong amount | refunded to other customers |
|---|---|---|---|
| none | 245 | 24 | $3,116.74 |
| argument validation | 273 | 0 | $2,580.85 |
| validation + tools scoped to the authenticated customer | 300 | 0 | $0.00 |

The scoped version answers "not found" for other customers' orders (the same answer as for a missing one, so the tool doesn't become an
oracle for which order numbers exist), and the model, told the order doesn't exist, re-reads the request and uses the right ID. That's
ordinary object-level authorization, the most common flaw in web APIs, and LLM tools reintroduce it with enthusiasm, because it's
tempting to let the model pass whatever IDs it likes to a tool running with a service account's privileges. Give each tool the permissions
of the user it acts for, and no more.

**Make side effects safe to repeat.** A timeout is an unknown outcome: the work may or may not have happened. The lab's payment service
times out 5% of the time before refunding and 10% after. Results over 1,000 partial refunds:

| client | correct | refunded twice |
|---|---|---|
| never retry tool calls in code | 891 | 109 |
| retry, no idempotency key | 891 | 109 |
| retry with an idempotency key | 1,000 | 0 |

The first row is the surprise: not retrying in your code changed nothing, because the *model* saw an error and called the tool again.
You can't stop that retry, so you have to make it harmless. An idempotency key (derived by your code from the conversation and the
operation, never generated by the model) lets the service recognize the repeat and return the original result. Payment APIs support
them; for your own services, build it in.

**Require approval for what's irreversible or expensive**, enforced in the tool layer where the model can't talk its way around it. In
the lab, refunds above $200 go to a human queue (83 of 300), and the model tells the customer so. Approval requests should show a human
exactly what will happen (the tool and its arguments), not the model's summary of it.

**Budget every loop**: steps, tokens, money and wall time, with a defined outcome when the budget runs out (hand off to a human, return a
partial result). The lab's model gets stuck re-reading the order in 30% of its steps; with a budget of 8 steps, 10 of 300 conversations
hit it and were handed off, instead of looping until someone noticed the bill.

**Log everything**: every tool call, its arguments, the result and the user it ran for (43.2). When something goes wrong, the question
will be "what did it do, for whom, and why", and the answer must not depend on the model's own account.

## Latency and cost

Each tool round trip is a full model call plus the tool's own latency, and the context grows with every result, so the cost of a
conversation grows faster than linearly in its steps (the whole history is re-sent each time; prompt caching helps, 40.1). Fewer, more
capable tools; parallel calls when independent; concise results; and deterministic code for fixed sequences all shorten the loop.

## Things that will bite you

- **Trusting model-supplied IDs** with a service account behind the tool.
- **Lax argument handling** that coerces bad input into a valid-looking action.
- **Retrying side effects without idempotency keys**, or assuming no retries happen because your code doesn't retry.
- **No step, token or cost budget** on the loop.
- **Irreversible actions without human approval.**
- **Huge tool results** stuffed into the context.
- **Tool results treated as trusted instructions**: a document or web page returned by a tool can contain text that reads like
  instructions (44.1).

## Exercises

1. Write the tool definition (name, description, schema) for "cancel a subscription". What goes in the description?
2. A tool `get_invoice(invoice_id)` runs with a database role that can read all invoices. What's the vulnerability, and how do you fix
   it without relying on the prompt?
3. Why doesn't "the model only retries if we tell it to" protect you from duplicate side effects?
4. A conversation averages 6 model calls; each re-sends the growing history. The system prompt and tools are 3,000 tokens; each step
   adds 400 tokens of results. Estimate the input tokens for the conversation, with and without prompt caching of the prefix.
5. Your agent can send emails. List four controls you'd put in the tool layer.
6. When should a sequence of tool calls be replaced by a single tool?

1. `cancel_subscription`, arguments `subscription_id` (pattern-constrained) and `reason` (enum). Description: what it does, that it's

2. Broken object-level authorization: any invoice ID the model produces (from a user's request, a prompt injection or a typo) is

   control.

3. The model decides to call a tool again when it sees an error or an unclear result, and any intermediate layer (SDK, gateway,

4. Step $k$ (1 to 6) sends $3{,}000 + 400(k-1)$ tokens: in total $6 \times 3{,}000 + 400 \times (0+1+\dots+5) = 18{,}000 + 6{,}000 =

5. Recipients restricted to the session's customer (or an allowlist), rate limits per conversation and per user, content checks (no

6. When the sequence is always the same and its correctness can be checked in code (look up, check, act), when the intermediate
