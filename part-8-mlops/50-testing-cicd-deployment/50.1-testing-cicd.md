# 50.1 Testing ML systems and CI/CD/CT

*About 10 hours. Prerequisites: 48.1, 48.2, 43.1 (eval suites), 10.3 (data quality). Lab: [`lab_50_1_testing_ml.py`](labs/lab_50_1_testing_ml.py).*

Software engineers test code. ML systems have three things that change and break: the code, the data and the model, and each fails in
ways the others' tests don't see. A model trained by correct code on correct-looking data can still be worse than the one it replaces; a
model that's better offline can be broken in production by a feature computed differently at serving time. This lesson is about the test
suite that stands between a retrained model and your users, and the pipeline that runs it automatically.

The lab builds that suite for a loan-default model and runs it on two candidate releases. One is simply retrained on fresh data. The other
was retrained after someone "cleaned up" the feature code, which now computes income in thousands during training while the serving path
still sends dollars. Its offline numbers look fine.

## Tests of code

The feature functions, preprocessing, postprocessing and glue are ordinary code, and get ordinary tests:

- **Unit tests** on known inputs, including the edge cases (zero income, missing fields, extreme values).
- **Property-based tests** (hypothesis): state properties that must hold for *any* valid input and let the library search for
  counterexamples. The lab's: outputs are finite for any income, debt and age, and the debt ratio never decreases when debt increases.
  Property tests find the inputs you didn't think of, which is where features produce NaN or infinity at 3 a.m.
- **Tests of the training code** on tiny data: it runs end to end, the loss decreases, the model overfits a handful of examples (if it
  can't, something's broken), and outputs have the right shapes.

## Tests of data

Data changes without a commit. Test every batch before it's used for training or scoring (10.3):

- **Schema**: fields present, types right.
- **Ranges and domains**: ages between 18 and 100, amounts non-negative, categories from the known set.
- **Missingness**: rates within expected bounds.
- **Distribution**: compared with the last training data (51.1 has the statistics).

The lab's data tests pass on a normal batch and fail on one where an upstream system started sending ages in months: the range test and
the distribution test both catch it, before a model trains on it. Great Expectations, Pandera and dbt tests are the common tools.

## Tests of the model

- **A quality gate against the current champion**: on the same test set, compare the candidate paired with the champion (43.1) and
  require it to be no worse beyond noise, using the bootstrap lower bound of the difference, not a single number.
- **Slices**: the gate applies per segment too (regions, customer types, protected groups, 54.1). An average can improve while a slice
  collapses (50.2 shows it).
- **Behavioral tests** (Ribeiro et al., 2020, "CheckList"):
  - *invariance*: a change that shouldn't matter doesn't change the prediction (here, the region, which policy says must not affect the
    score);
  - *directional expectations*: a change with a known direction moves the prediction that way (more late payments shouldn't lower the
    predicted risk);
  - *minimum functionality*: simple cases every acceptable model must get right.
- **Operational tests**: latency, memory, model size and serialization round trip, within budget.

## The test that caught the bug

| test | good | broken |
|---|---|---|
| quality gate vs champion (offline) | pass | pass |
| no slice below 0.60 AUC | pass | pass |
| invariance to region | pass | pass |
| directional: more late payments means higher risk | pass | pass |
| train/serve consistency | pass | **fail** |

The broken model passes every offline test, because its evaluation used its own (wrong) feature code consistently. In production, where
income arrives in dollars, its AUC is 0.637 against the good model's 0.657: quietly worse, with no error anywhere. Only one test catches it:
push the same raw records through the training path and the serving path, and require identical predictions. **Training/serving skew** is
among the most common production ML bugs (Google's "Rules of Machine Learning" devotes several rules to it). The structural fix is to compute features in one
place (a shared library, or a feature store with one definition for offline and online, 22.1); the test makes sure it stays fixed.

## CI, CD and CT

- **Continuous integration**: on every code change, run code tests, a small end-to-end training run on sample data, and linters (49.2).
  Fast: minutes.
- **Continuous training**: on a schedule or a trigger (new data, drift alarms, 51.1), the pipeline (48.2) validates data, trains,
  evaluates, runs the model tests, and registers the candidate with its report (48.1).
- **Continuous delivery**: a candidate that passes goes into a staged rollout (shadow, then canary, 50.2), with automatic rollback. A
  human approves promotion for high-stakes systems. The approval should be a click on a report, not a manual procedure.

Google's "ML Test Score" rubric (Breck et al., 2017) is a useful checklist: 28 tests across data, model, infrastructure and monitoring,
scored by whether they're manual or automated. Most teams, measured honestly, score low; each point gained is an incident avoided.

## Things that will bite you

- **Features computed twice**, in training and in serving, by different code.
- **Data changes nobody tests**, because data doesn't go through code review.
- **A quality gate on one aggregate number**, with no slices and no uncertainty.
- **No behavioral tests**, so a model that learned a forbidden shortcut passes.
- **Retraining pipelines that promote automatically** with no human-readable report.
- **Flaky tests from nondeterministic training**, "fixed" by loosening thresholds until they mean nothing (48.2).

## Exercises

1. Write three property-based tests for a function that normalizes free-text addresses.
2. Your data test fails on Monday's batch: 4% of transactions have negative amounts. What do you do, and what should the pipeline do
   automatically?
3. Design the quality gate for replacing a fraud model: metrics, slices, thresholds and the statistical test.
4. Give an invariance test and a directional test for a sentiment classifier, and for a house-price model.
5. How would you test for training/serving skew when the serving path is a Java service and training is Python?
6. What does a retraining pipeline need before it's safe to run without a human looking at each model?

1. Idempotence: normalizing twice equals normalizing once. Preservation: the house number and postal code survive normalization.
   Robustness: extra whitespace, case changes and trailing punctuation don't change the output. (And no exceptions on arbitrary Unicode.)

4. Sentiment: invariance to changing a person's name or a location ("I loved my stay in Paris/Lagos"); directional: adding "not" before

5. Build a golden set of raw records; run them through the Python training pipeline and, in CI, through the Java service (a container

   periodically compare them with a recomputation offline.

6. Data validation that fails closed; a quality gate with slices and uncertainty; behavioral and operational tests; a staged rollout with
   automatic rollback on guardrail metrics; monitoring (51.1); lineage for every model (48.1); and a human-readable report stored with
