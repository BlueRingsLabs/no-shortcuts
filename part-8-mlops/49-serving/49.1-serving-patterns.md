# 49.1 Serving patterns: batch, online, streaming

*About 8 hours. Prerequisites: 48.1 (registries), 14.1 (Kafka and event-driven architecture), 33.3 (profiling). Lab: [`lab_49_1_serving_patterns.py`](labs/lab_49_1_serving_patterns.py).*

A trained model is a file. Serving is everything that turns that file into predictions someone uses: when they're computed, where they
live, how fast they arrive, and what happens at 3 a.m. when traffic triples. The first decision is the one teams most often get wrong by
default: they build an online service with a latency budget for predictions that could have been computed last night and put in a table.
This lesson covers the three patterns, how to choose, what an online service looks like, and where its latency actually comes from.

## Three patterns

**Batch (offline) inference**: a scheduled job scores everything that might need a prediction and writes the results to a table or a
key-value store; the application looks them up. Nightly churn scores, weekly demand forecasts, recommendations refreshed every hour.

- Cheapest per prediction by far (the lab: 9 µs per row in a batch against 82 µs one at a time, in the same process, before any
  network), no latency budget, easy to retry and backfill (13.1), easy to inspect before anyone sees the results.
- Predictions are as stale as the last run, and you score entities nobody asks about.

**Online (real-time) inference**: a service computes a prediction per request. Fraud checks at payment time, search ranking, anything whose
inputs only exist at request time (the basket, the query, the last three clicks).

- Fresh inputs, no wasted predictions.
- A latency budget, an availability requirement, capacity planning, and a service to operate (49.2).

**Streaming inference**: a consumer reads events from a log (14.1), scores them, and writes the results to another topic or store. Fraud
signals on card transactions, anomaly detection on sensor data, updating a user's features and scores as they act.

- Fresh within seconds, decoupled from any request path, naturally buffered (a slow consumer lags instead of failing requests).
- Stream processing's complexity: ordering, late events, state, exactly-once (14.2).

Hybrids are common and usually right: precompute the heavy parts in batch (embeddings, candidate lists, aggregates), keep fresh features
updated by a stream, and do a small final computation online. Ask, for each prediction: **when are its inputs known, and how stale can the
result be?** If the inputs are known the day before and staleness of a day is fine, it's batch, however modern online serving looks.

## An online service

The skeleton is small. With FastAPI (the lab uses the standard library, to avoid a dependency, but this is what you'd write):

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI
from pydantic import BaseModel, Field

class Request(BaseModel):
    features: list[float] = Field(min_length=64, max_length=64)      # validate at the edge

class Response(BaseModel):
    score: float
    model_version: str

@asynccontextmanager
async def lifespan(app):
    app.state.model = load_model("models:/fraud/production")       # once, at startup (48.1)
    yield

app = FastAPI(lifespan=lifespan)

@app.post("/predict")
def predict(req: Request) -> Response:                           # sync def: FastAPI runs it in a thread pool
    return Response(score=app.state.model.score(req.features), model_version=app.state.model.version)

@app.get("/healthz")
def health():                                                    # liveness and readiness probes (49.2)
    return {"ok": True}
```

What makes it production-grade isn't in that file: input validation with useful errors, the model version in every response and log line
(for 43.2's traces and 51.1's monitoring), timeouts on every downstream call (a feature store, another model), a fallback when the model
or a feature is unavailable (a default score, a rule, the last known value), graceful shutdown that finishes in-flight requests, and the
same feature code as training, or you get train/serve skew (50.1).

## Where latency comes from

The lab runs a real HTTP server (in its own process) and a load generator, and measures latency percentiles as the number of concurrent
clients grows. Its small model takes 82 µs per prediction. A single client waits **1.6 ms** per request: the other 95% is connection
handling, HTTP parsing, JSON, and Python threads. That's typical. Before making a model faster (49.3), measure what share of the request it is.

Then load, one request at a time:

| concurrent clients | req/s | p50 ms | p95 ms | p99 ms |
|---|---|---|---|---|
| 1 | 556 | 1.6 | 2.4 | 8.2 |
| 4 | 166 | 24 | 48 | 60 |
| 16 | 147 | 108 | 194 | 225 |
| 32 | 169 | 187 | 310 | 394 |

The server is one process with one model, and requests take turns. Once they arrive faster than it serves them, they **queue**, and
latency becomes mostly waiting. By Little's law (in-flight requests = throughput × latency), with throughput fixed, doubling the clients
doubles the latency. Here throughput doesn't even stay fixed: it drops from 556 to about 170 requests per second as soon as there's more
than one client, because Python threads contending for one interpreter and a lock cost more than the work they do. How much that
contention costs depends on the machine: on a 2-core cloud runner, the same lab went from 1,000 requests per second at one client to
1,400 at 32, with the same queueing shape. Timings like these move with the hardware and with whatever else runs on it; the shapes are
what to read. The **tail** grows fastest: p99 is where queueing, garbage collection, a noisy neighbor and an unlucky scheduling decision
add up, and at 32 clients it's about 0.4 seconds for an 82 µs model.

This is why capacity planning targets a utilization well below 100%: in a queue, latency grows without bound as utilization approaches 1
(with random arrivals, waiting time scales like $\rho / (1 - \rho)$). A service at 80% utilization has a p99 that a service at 50% doesn't.

## Dynamic batching

The server holds each request for up to 2 ms, collects whatever else arrives, and runs them through the model together (what Triton,
TorchServe and every LLM server do). It pays when the model's cost per call is large and grows slowly with the batch size. For the small
model above it can't help much, since the model is 5% of each request; my first version of this lab demonstrated batching on that model,
and it "won" on my machine only because the unbatched server's thread contention was so bad, and lost on a cloud runner where it wasn't.
So the lab uses a larger network (17M parameters) whose one-row forward pass is dominated by reading its weights: 2.8 ms for one row,
15 ms for 32 (0.47 ms per row).

| concurrent clients | one at a time: req/s | p50 ms | p99 ms | dynamic batching: req/s | p50 ms | p99 ms |
|---|---|---|---|---|---|---|
| 1 | 395 | 2.2 | 10 | 231 | 4.0 | 8.2 |
| 4 | 125 | 31 | 68 | 465 | 7.3 | 20 |
| 16 | 134 | 114 | 281 | 625 | 25 | 36 |
| 32 | 140 | 228 | 517 | 901 | 34 | 53 |

Without batching, throughput is capped near one request per model call. With it, one call serves many requests: 6 times the throughput
at 32 clients, and because the queue drains faster, a tenth of the p99. At one client batching is slower, since every request waits for
companions that never come. Tune the window and the maximum batch size on your own traffic: the window is a latency cost at low load, and
the gain depends on how much the model benefits from batching (a lot on GPUs, where one call's cost is mostly fixed overhead and weight
reads; little for a small model that is a sliver of each request).

For LLMs this becomes **continuous batching** (45.2): requests join and leave the batch at every generated token, because they finish at
different lengths.

## Scaling out

One process has a ceiling. Beyond it: several worker processes per machine (sidestepping Python's interpreter lock), several replicas
behind a load balancer, autoscaling on queue length or latency rather than CPU (49.2), and for expensive models, GPU servers with batching.
Keep every replica stateless, so any request can go anywhere and a replica can die without losing anything.

> **Scar tissue.** A friend's startup asked me to speed up a model API with a median latency of about 400 ms, for a gradient-boosted model
> that scored in under a millisecond. The handler downloaded the model from object storage on every request, so that a new model file
> would be picked up "automatically". It was, along with 399 ms of network I/O per request. Load once at startup, and reload deliberately
> when a new version is registered.

## Things that will bite you

- **Online serving by default** for predictions that could be batch.
- **Benchmarking with one client** and reporting that as the latency.
- **Mean latency** instead of percentiles; p99 is what your users complain about and what your timeouts must cover.
- **Running at high utilization** and wondering where the tail came from.
- **No timeouts or fallbacks** on downstream calls: one slow feature store takes the whole service down.
- **Load tests from the same machine** as the server, which then competes with its own load (the lab runs the server in a separate
  process for this reason, and still shares the machine's cores).
- **Different feature code** online and in training.

## Exercises

1. For each, choose batch, online or streaming, and justify: product recommendations on the home page; a credit decision during an
   application; flagging suspicious logins; forecasting next week's inventory; a spam filter for incoming email.
2. Using Little's law: a service handles 400 requests per second with a mean latency of 50 ms. How many requests are in flight? What
   happens to latency if traffic rises to 500 per second and throughput can't grow?
3. In the lab, dynamic batching is slower at one client. By how much would you expect it to be slower, and why?
4. Your p50 is 20 ms and your p99 is 900 ms. List five causes to investigate, and how you'd tell them apart.
5. Design the fallback behavior of a fraud model service when the feature store times out.
6. Why does the lab run the server in a separate process from the load generator?

1. Home-page recommendations: batch (precompute per user hourly or daily), with an online reranking step if context matters. Credit

2. In flight = 400 × 0.05 = 20. If arrivals exceed capacity, the queue grows without bound: latency keeps increasing for as long as the

3. Up to the batching window (2 ms) plus the batching thread's overhead, since a lone request waits for companions that never come; the
   lab shows more than that because the batching thread and the queues add their own delays. Adaptive windows (dispatch immediately when
   the queue is empty) remove most of it.

4. Queueing near saturation (check utilization and whether p99 rises with load); garbage collection or memory pressure (correlate with

5. Short timeout on the feature store (well inside the budget); on timeout, score with the features available using a model trained to
   handle missing values, or fall back to rules; mark the response as degraded, log it, alert on the degraded rate; never block the
   payment indefinitely; decide with the business whether degraded means approve, decline or review for high amounts.

6. So the load generator's threads don't compete with the server's for the same Python interpreter lock, which would inflate the
   measured latency with the client's own overhead. They still share the machine's CPU cores, which is why production load tests run from
