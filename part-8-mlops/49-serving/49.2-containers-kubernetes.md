# 49.2 Containers and Kubernetes for ML

*About 10 hours. Prerequisites: 49.1, 00.2 (Docker basics), 07.4 (Linux processes and networking). Lab: [`lab_49_2_containers_k8s.py`](labs/lab_49_2_containers_k8s.py).*

A model server is a program with an unusual amount of baggage: a specific Python, specific versions of numerical libraries compiled against
specific system libraries, sometimes a specific CUDA, and a model file of hundreds of megabytes to hundreds of gigabytes. Containers package
all of it into one immutable artifact that runs the same on a laptop, in CI and in production. Kubernetes runs many copies of it, restarts
them when they die, routes traffic to the healthy ones and adds more when load grows. Together they're the default way ML services are
deployed. Most of their incidents come from a short list of configuration mistakes, which this lesson and its lab are about.

## Images

A **container image** is a stack of filesystem layers plus metadata (the command to run, the user, the ports). A **Dockerfile** builds it
step by step, each instruction a cached layer. The lab lints two Dockerfiles for the same model server. The naive one:

```dockerfile
FROM python:latest
COPY . /app
RUN pip install -r /app/requirements.txt
CMD python /app/serve.py
```

It has seven problems, each of which has caused real outages:

- **`latest`, and no digest**: the base image changes under you, and the build that worked yesterday doesn't today. Pin a version *and*
  a digest (`python:3.12-slim@sha256:...`); tags are mutable, digests aren't.
- **`COPY .`** copies the whole build context into the image: `.git`, local data, notebooks, `.env` files with credentials. Copy exactly
  what's needed, and keep a `.dockerignore`.
- **Unpinned dependencies**: `requirements.txt` without pinned transitive versions and hashes rebuilds differently every time (48.2).
- **Root**: a compromised process owns the container. Create a user and switch to it.
- **Shell-form `CMD`**: the server runs as a child of `/bin/sh`, which doesn't forward `SIGTERM`, so it never gets to finish in-flight
  requests on shutdown and is killed after the grace period. Use the exec form (`CMD ["python", "serve.py"]`).
- **No health check.**
- And, implied: a single stage, so compilers, caches and build tools ship to production. **Multi-stage builds** install in one stage and
  copy only the results into a slim runtime stage.

**Where does the model go?** Three options:

1. **Baked into the image**: simplest, immutable, and the image is the whole deployment. But multi-gigabyte images are slow to push and
   pull, and a model update means a new image.
2. **Downloaded at startup** from the registry (48.1) or object storage: small images, models versioned separately, but every new replica
   pays the download, and startup depends on storage being up.
3. **Mounted** from a shared volume or a node-local cache: fast starts, more infrastructure.

For small models, bake them in. For large ones, cache on nodes. The lab's autoscaling section shows why start time matters so much.

## Kubernetes, the parts that matter for serving

- A **Pod** runs one or more containers together; a **Deployment** keeps N replicas of a pod running and replaces them during updates; a
  **Service** gives them one stable address and load-balances across the ready ones.
- **Resource requests** tell the scheduler what a pod needs (it places pods where requests fit). **Limits** cap usage: exceeding the memory
  limit gets the container killed (OOMKilled), and CPU limits throttle it. Set memory requests equal to limits for predictable serving, and
  be careful with CPU limits on latency-sensitive services, since throttling shows up as p99 spikes (49.1).
- **Probes**: the *startup* probe gives a slow-loading container time before other checks begin; *readiness* says whether to send it
  traffic (not until the model is loaded and warm); *liveness* says whether to restart it. A liveness probe without a startup probe on a
  server that takes three minutes to load its model restarts it forever: a classic ML crash loop.
- **Rolling updates** with `maxUnavailable: 0` replace pods one at a time without losing capacity.
- **Secrets** come from Secret objects or an external secrets manager, never plain `env` values in a manifest that gets committed.
- **GPUs** are requested as extended resources (`nvidia.com/gpu: 1`), whole devices by default; sharing them needs MIG or time-slicing.

The lab's naive Deployment has eight issues: a single replica, an image by mutable tag, no requests, no memory limit, no readiness or
liveness probe, a plain-text API key, and root. The good one fixes all of them. Real linters (hadolint for Dockerfiles, kube-linter or
Checkov for manifests, Trivy for image vulnerabilities) check hundreds of rules; run them in CI (50.1).

## Autoscaling and cold starts

The **Horizontal Pod Autoscaler** adjusts the replica count to keep a metric near a target:
$\text{desired} = \lceil \text{current} \times \text{observed} / \text{target} \rceil$, evaluated every 15 seconds or so. The lab simulates a
traffic jump from 150 to 600 requests a second, with replicas that each serve 50 a second and a target of 35 per replica:

| setup | dropped requests | p99 latency during the spike | seconds to recover |
|---|---|---|---|
| minimum 5 replicas, 20 s start (model in the image) | 5,000 | 8.0 s | 22 |
| minimum 5 replicas, 180 s start (model downloaded) | 61,000 | 8.0 s | 182 |
| minimum 12 replicas (headroom), 180 s start | 0 | 0.02 s | 0 |

Autoscaling reacts to load it has already failed to serve, then waits for new replicas to become ready. With a three-minute cold start, the
spike is over, or the users have gone, before help arrives. So:

- **Make starts fast**: small images, models cached on nodes, lazy or memory-mapped loading, pre-pulled images.
- **Keep headroom** for known peaks (scheduled scaling before the morning rush, marketing emails, launches).
- **Scale on leading signals**: queue length or in-flight requests react faster than CPU. KEDA scales on queue depth and custom metrics.
- **Shed load gracefully**: reject early with a clear error (and a retry-after, 40.1) rather than letting queues grow until everything
  times out.
- For GPU inference, scale-to-zero saves money and costs a cold start of minutes: a product decision, not a default.

## Things that will bite you

- **Mutable image tags** in production.
- **Secrets in images or manifests.**
- **Liveness probes that kill slow-loading model servers.**
- **No memory limit**, or a limit below the model's peak memory (OOMKilled under load).
- **CPU throttling** from tight CPU limits, visible only in p99.
- **Cold starts** longer than the spikes you need to absorb.
- **Shell-form entrypoints** that swallow `SIGTERM`.

## Exercises

1. Write a Dockerfile for a scikit-learn model server with a pinned, non-root, multi-stage build. Where does the model file come from?
2. A server takes 90 seconds to load its model. Write the startup, readiness and liveness probes.
3. Your pods get OOMKilled only under peak load. What's happening, and what do you change?
4. Estimate the replicas needed for 1,200 requests a second at a p99 target of 100 ms, if one replica sustains 80 requests a second
   with p99 under 100 ms. What headroom would you add, and why?
5. Why do rolling updates need readiness probes to be correct?
6. When is scale-to-zero a good idea for a model service?

1. Build stage: `FROM python:3.12-slim@sha256:...`, copy `requirements.lock`, `pip install --require-hashes --target /deps`. Runtime stage:
   the same base by digest, create a user, copy `/deps` and `serve.py`, `USER app`, exec-form `CMD`. The model: small ones copied into
   the image at build time from the registry by version (so the image is the whole deployment); record the model version as an image
   label.

2. Startup: `httpGet /healthz`, `periodSeconds: 5`, `failureThreshold: 30` (up to 150 s to start). Readiness: `/ready`, which returns
   200 only once the model is loaded and a warm-up prediction succeeded, every 5 s. Liveness: `/healthz` (the process responds), every 10 s,
   `failureThreshold: 3`. Liveness only begins after startup succeeds.

3. Memory grows with concurrent requests (batches, per-request buffers, a memory leak or unbounded caches) and exceeds the limit at peak.
   Measure peak memory under realistic load; raise the limit (and request) to peak plus margin; bound concurrency per pod (fewer workers or
   a smaller max batch); fix leaks; scale out earlier.

4. $1200/80 = 15$ replicas at exactly capacity, which is too tight: at capacity, queues grow and p99 blows up (49.1). Run at 60 to 70%
   utilization: $1200/(0.65 \times 80) \approx 23$ replicas. Add enough to survive the loss of one node or zone, and to cover the time
   the autoscaler takes to react to growth.

5. During a rolling update, old pods are removed once new ones are "ready". If readiness means only "the process started", traffic reaches
   pods that are still loading the model, and requests fail while capacity looks fine. Readiness must mean "can serve now".

6. When traffic is rare and latency on the first request after idle can be seconds or minutes (internal tools, batch-like endpoints,
   development environments), and the idle cost (especially GPUs) is significant. Not for user-facing, latency-sensitive traffic, unless
   cold starts are made very fast.
