# 53.2 The ML supply chain

*About 10 hours. Prerequisites: 48.1 (registries), 48.2 (pinned environments), 49.2 (images). Lab: [`lab_53_2_supply_chain.py`](labs/lab_53_2_supply_chain.py).*

An ML system is assembled from other people's work: Python packages by the hundred, pretrained models from hubs, datasets from wherever,
container base images, notebooks copied from a blog. Each is code or data you didn't write, running with your permissions and touching your
data. Software security learned this the hard way, with compromised build systems and packages that made the news; ML adds its own
artifacts, and one of them, the pickled model file, is a program disguised as data. This lesson covers the chain and its controls. The self-check
question, why `torch.load` on an untrusted file is a remote code execution vulnerability, is where it starts.

## Pickle is code

Python's pickle format doesn't store data; it stores instructions for rebuilding objects, and rebuilding can mean calling any importable
function with any arguments. A class can define `__reduce__` to say "to rebuild me, call this function with these arguments", and
`pickle.loads` will do it. The lab demonstrates this harmlessly: the "payload" appends a message to a list, and after `pickle.loads` the list
contains it. A real malicious file calls something else, with your permissions, the moment you load it.

Formats built on pickle include `.pkl`, `.joblib`, PyTorch's `.pt` and `.bin` (a zip archive with a pickle inside), and many older model
files on hubs. Treat any of them from an untrusted source as an executable.

The controls, in order of strength:

1. **Don't load pickles from untrusted sources.** Use formats that can't execute code: **safetensors** (a JSON header with names,
   dtypes, shapes and offsets, then raw bytes), ONNX, or plain arrays. The lab implements the safetensors idea in 30 lines and round-trips a
   model exactly; loading it only parses JSON and copies numbers. It's the default on the Hugging Face Hub.
2. **Restricted loading.** `torch.load(..., weights_only=True)` (the default in recent PyTorch) uses an unpickler that only allows
   tensor-related types. In the lab it loads a plain state_dict and refuses the file with a callable, before calling anything.
3. **Scanning.** Tools like picklescan (and hub-side scanners) list the imports a pickle would perform, without executing it, and flag ones
   outside an allowlist. The lab's scanner sees `collections.OrderedDict` and `torch._utils._rebuild_tensor_v2` in a state_dict, and
   `__main__.record_event` in the demonstration file. Scanning catches known-bad patterns and can be evaded; it's a safety net, not the
   control.
4. **Isolation.** If you must load an untrusted pickle (to convert it to safetensors, say), do it in a sandbox with no network, no
   credentials and nothing of value.

## Integrity: hashes and signatures

Knowing *what* you load matters as much as its format:

- **Pin hashes.** Record the SHA-256 of every artifact you depend on (model weights, datasets, packages via `--require-hashes`, images by
  digest, 49.2) and verify before use. In the lab, flipping one bit in one weight changes the hash, and the check fails.
- **Sign.** A hash says the file is the one you recorded; a signature says who produced it. Sigstore (cosign) signs artifacts and images with
  short-lived keys tied to an identity (a CI workflow, a person), with a public transparency log. Then a deployment can require "signed by
  our training pipeline" before anything runs. The lab uses an HMAC as a stand-in to show the mechanics: the tampered file's signature doesn't
  verify.
- **Provenance attestations** (SLSA, in-toto) record how an artifact was built: from which source, by which builder, with which inputs.
  For models, this is 48.1's lineage, made verifiable.

## Knowing what you run

- **A software bill of materials (SBOM)** lists every component with its version (CycloneDX and SPDX are the formats). The lab generates one
  for its own environment: 171 Python packages, most of which nobody chose directly. Scan it against vulnerability databases (OSV, GitHub
  advisories) on every build with pip-audit, Trivy or similar, and keep it with the release so you can answer "are we affected?" when the
  next advisory lands. ML-BOMs extend the idea to models and datasets.
- **Typo-squatting and dependency confusion.** Attackers publish packages named one typo away from popular ones (`reqeusts`), or with the
  same name as your internal packages on the public index. The lab's check flags `reqeusts`, `transfomers` and `safetensor` against an
  allowlist. The controls: install from a curated internal index or proxy, pin with hashes, and review new dependencies like code, because
  they are code.
- **Pretrained models and datasets** from hubs: check the publisher, the license, the format, the model card, and evaluate the model
  yourself (53.1 on backdoors). A popular download count is not a security review.
- **Notebooks and snippets**: a notebook that runs `pip install` from an unfamiliar URL, or `curl | bash`, is supply chain too.

## The pipeline is part of the chain

Build and training systems are high-value targets: whoever controls them controls every artifact they produce. Protect them like
production (52.1): least-privilege credentials scoped to each job, no long-lived secrets, isolated build environments, protected branches
and required reviews for pipeline changes, and signed outputs. The strongest attacks on software supply chains have gone through build
systems, not through the code people reviewed.

> **Scar tissue.** In a freelance security review of a small ML startup, the most worrying thing I found wasn't in their API. They
> downloaded pretrained models from public hubs and shared drives and loaded them with `pickle`, which runs whatever code the file
> contains. Nobody checked where the files came from, and the training machines had credentials for their production data. We scanned what
> was there (it was clean, that time), moved to a safe tensor format, pinned hashes, and loaded third-party files in a sandbox with no
> credentials.

## Things that will bite you

- **`pickle.load`, `joblib.load` or `torch.load` without `weights_only`** on files from the internet, a user upload, or a shared drive.
- **Models referenced by mutable names** ("latest" on a hub) instead of pinned revisions and hashes.
- **Unpinned, unhashed dependencies** and installs from the public index straight into production images.
- **No SBOM**, so "are we affected?" takes days.
- **Build and training pipelines** with broad credentials and no review of changes.
- **Trusting scanners** as the primary control.

## Exercises

1. Explain to a colleague, in three sentences, why loading a `.pt` file from a stranger is dangerous and what to do instead.
2. Your team downloads a model from a hub by name in the training script. List everything you'd change.
3. A vulnerability advisory names a package version. How do you find every deployed model service that includes it?
4. Why does `--require-hashes` protect against more than version pinning alone?
5. What does a signature on a model add over a pinned hash?
6. Design the controls for a training pipeline that fine-tunes on customer-uploaded documents.

<details>
<summary>Answers</summary>

1. A `.pt` file contains a pickle, and loading a pickle can call any function the file names, so loading it runs the author's code with
   your permissions. Ask for the weights in safetensors (or convert them in a sandbox), load with `weights_only=True` if you must use the
   PyTorch format, and verify where the file came from.

2. Pin the model revision (a commit hash, not a branch name), record and verify the file hashes, prefer safetensors weights, mirror the
   model into your own registry (48.1) after evaluating it, record its license and provenance, and load it in the pipeline from your
   registry, not from the internet, with network access for training jobs restricted.

3. Query the SBOMs stored with each release (or the image scans in your registry) for the package and version, then map images to the
   services and model versions running them (49.2's digests and 48.1's registry). Without SBOMs, you'd be inspecting images one by one.

4. A version number can be republished or served differently by a compromised or confused index (or resolved from a different index
   entirely in dependency confusion); a hash pins the exact bytes, so any substitute fails installation. It also covers transitive
   dependencies in the lock file, not just the ones you named.

5. A hash only says "these are the bytes I recorded", and whoever can change the file may be able to change the recorded hash too if it's
   stored alongside. A signature binds the artifact to an identity (your CI pipeline, a person) with a key the attacker doesn't hold, so
   it proves origin, and verification policies can require specific signers.

6. Uploaded documents are untrusted data: scan and sanitize them (file types, sizes, malware scanning for office formats), parse in an
   isolated environment, store them in a separate bucket with provenance per customer, keep one customer's documents out of others'
   models (per-tenant fine-tunes or strict data agreements), audit training data for poisoning and privacy (53.1, 54.2), run training with
   least-privilege credentials and no general network access, sign the outputs, and evaluate each fine-tuned model before serving it.
