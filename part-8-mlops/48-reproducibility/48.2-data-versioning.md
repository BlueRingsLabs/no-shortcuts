# 48.2 Data versioning, pipelines and environments

*About 8 hours. Prerequisites: 48.1, 00.2 (environments), 13.1 (orchestration). Lab: [`lab_48_2_data_pipelines.py`](labs/lab_48_2_data_pipelines.py).*

A model is a function of three things: code, data and environment. Git versions the first. This lesson is about the other two, and about
the pipeline that ties them together, because "reproducible" means someone else can rerun your training, get the same result, and know
why.

## Versioning data by content

Git is built for small text files that change line by line. Training data is large and binary, and changes by whole files. The trick used by
DVC, git-lfs and most data versioning tools is **content addressing**:

1. Hash the data file (SHA-256).
2. Store it in a cache, local or in object storage, under its hash.
3. Commit a small **pointer file** (hash, size, path) to git instead of the data.

The lab does exactly this. After adding v1, then v2 (with new rows), then a regenerated v1 identical to the first, the cache holds 2
objects, not 3: identical content is stored once, whatever it's called. Checking out a commit gives you the pointer; fetching the pointer
gives you the exact bytes, verified by their hash. A commit now pins code *and* data.

With DVC:

```
dvc add data/transactions.parquet        # writes data/transactions.parquet.dvc (the pointer), caches the file
git add data/transactions.parquet.dvc .gitignore && git commit -m "Data: March snapshot"
dvc push                                  # upload the cache to remote storage (S3, GCS, Azure, SSH...)
git checkout v1.2 && dvc pull             # the code and the data of v1.2
```

For data that lives in tables rather than files, the same ideas appear as warehouse snapshots and time travel (Delta Lake, Iceberg; 11.2):
query the table as of a version or timestamp, and record that version with the run. Whatever the mechanism, the requirement is the same:
from a model version, you can get back the exact training data.

## Pipelines with stage caching

A training pipeline is a DAG of stages (prepare, featurize, train, evaluate), each with declared inputs, parameters and outputs. A
pipeline tool records a hash of each stage's code, parameters and input contents, and reruns a stage only when that hash changes. The lab's
five scenarios:

| change | prepare | featurize | train |
|---|---|---|---|
| first run | ran | ran | ran |
| nothing | cached | cached | cached |
| a training parameter | cached | cached | ran |
| the raw data | ran | ran | ran |
| a parameter "changed" to its old value | cached | cached | cached |

Everything downstream of a change reruns, nothing else does. That makes a three-hour pipeline cheap to iterate on, and it makes "which data
and which parameters produced this model?" a lookup in the lock file. DVC pipelines (`dvc.yaml`, `dvc repro`), Make and most orchestrators
(13.1) implement this. Two rules keep it honest: stages must be pure functions of their declared inputs (no reading a table that isn't
declared, no "latest" data), and parameters live in files, not in someone's shell history.

## Environments

The environment is the third input, and the one people forget until a library update changes their results. The layers, from most to
least often broken:

- **Python packages**: pin exact versions with a lock file (`uv.lock`, `poetry.lock`, `pip-compile` output), including transitive
  dependencies. A `requirements.txt` with `torch>=2` isn't a pin.
- **The Python version and system libraries**: a container image (49.2), referenced by digest, not by a mutable tag like `latest`.
- **Hardware and drivers**: GPU model, CUDA and cuDNN versions, which change numerical results.

Record all of it with every run (48.1), and build training and serving from the same lock file, or test the difference.

## Bit-identical or statistically identical?

The lab trains the same small network four times:

| run | weights hash | final loss |
|---|---|---|
| seed 0, 4 threads | e40eb26d… | 0.47956428 |
| seed 0, 4 threads, again | e40eb26d… (identical) | 0.47956428 |
| seed 1, 4 threads | ba1750db… | 0.48481083 |
| seed 0, 1 thread | bf0f5da6… (different) | 0.47956428 |

Same seed and same setup give bit-identical weights. Changing only the thread count changes the bits, while the loss agrees to eight
digits. Floating-point addition isn't associative, so anything that changes the order of a sum (thread count, a BLAS library, a GPU
kernel choice, batch composition in distributed training) changes the last bits, and training can amplify them.

So aim for two levels:

- **Bit-identical** on the same hardware and software: seeds everywhere (Python, NumPy, framework, data loader workers),
  deterministic algorithms (`torch.use_deterministic_algorithms(True)`, at some speed cost), fixed thread counts, pinned versions. Useful
  for debugging and for audits.
- **Statistically identical** everywhere else: the same metrics within seed variance (48.1). That's the standard that matters for
  science and for decisions.

> **Scar tissue.** A reviewer on a paper I co-authored at university asked us to rerun an experiment eight months after we'd submitted,
> and we couldn't reproduce our own numbers. The data had been re-downloaded from a source that had since corrected and extended it, and
> the library versions weren't pinned, so even the code gave different results. We had the model file, and no way to show where it came
> from. Content-addressed data snapshots and locked environments feel like overhead right up until someone asks "why".

## Things that will bite you

- **Data overwritten in place**, so the training set no longer exists.
- **Pipelines reading undeclared inputs** ("the latest table"), so caching and lineage silently lie.
- **Unpinned dependencies**, or training and serving environments built separately.
- **`latest` image tags.**
- **Expecting bitwise reproducibility** across hardware, or accepting results that don't even reproduce statistically.
- **Personal data in versioned datasets** that must later be deleted (54.2): design for deletion, since immutable history and the right
  to erasure pull in opposite directions.

## Exercises

1. Why does content addressing deduplicate automatically? What does it cost when a 50 GB file changes by one row?
2. A pipeline stage reads a config file that isn't declared as a dependency. What goes wrong?
3. Your model's metrics changed after a rebuild of the training container with "the same" requirements. Where do you look?
4. Make a small PyTorch training loop as reproducible as possible on one machine. List the steps.
5. A user asks for their data to be deleted, and it's in 40 versioned snapshots used by 12 models. What are your options?
6. What would you store to be able to reproduce a model trained on a warehouse table that's updated daily?

<details>
<summary>Answers</summary>

1. The storage key is the hash of the content, so identical content maps to the same key and is stored once, whatever its name or
   version. The cost: any change produces a new hash, so a one-row change to a monolithic 50 GB file stores a new 50 GB object.
   Chunking (splitting files into content-addressed chunks) or partitioned formats (one file per day or per partition) limit this.

2. Changes to that file don't change the stage's hash, so the stage stays "cached" with stale outputs, and the lock file records a
   lineage that doesn't include the real input. Results become irreproducible in a way nothing reports. Declare every input.

3. Transitive dependencies that weren't pinned (`requirements.txt` pins direct dependencies only), a newer base image under the same
   tag, a different BLAS or CUDA build of the same library version, and changed default arguments in a library. Diff the full package
   list (`pip freeze`) and the image digests of the two builds.

4. Seed Python's `random`, NumPy and torch (`torch.manual_seed`, which also seeds CUDA); seed data loader workers and use a
   seeded generator for shuffling; set `torch.use_deterministic_algorithms(True)` (and the cuBLAS workspace variable on GPU); fix the
   thread count; pin library versions and record hardware; avoid nondeterministic operations or accept their documented tolerance.

5. Delete the user's records from the source and from every snapshot (rewrite the affected files, which breaks old hashes, so record the
   deletion), or keep personal data out of versioned snapshots in the first place (pseudonymize, reference by ID into a deletable
   store). For the models: assess whether retraining without the data is required (it depends on the law, the data, and whether the
   model could reveal it, 54.2), and document the decision. Machine unlearning methods exist but are immature.

6. The table version or snapshot ID (with time travel, 11.2) or an exported immutable snapshot with its hash; the exact query and its
   parameters (including the date range); the pipeline code version; and ideally the row count and a checksum of the extracted data, to
   verify later.
