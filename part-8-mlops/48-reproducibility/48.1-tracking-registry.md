# 48.1 Experiment tracking and model registries

*About 7 hours. Prerequisites: 18.1 (honest evaluation), 08.1 (SQL). Lab: [`lab_48_1_tracking_registry.py`](labs/lab_48_1_tracking_registry.py).*

Six months from now someone will ask which data trained the model in production, with which parameters, from which code, and why it was
chosen over the other candidates. If the answer lives in a notebook called `final_v3_REAL.ipynb` on a laptop that's since been
reimaged, you don't have an answer. Experiment tracking and a model registry are the boring infrastructure that makes that question
answerable in a minute, and they cost almost nothing to adopt on day one. Retrofitting them after the incident costs a lot more.

The lab builds both on SQLite in about a hundred lines, so that when you use MLflow (or Weights & Biases, or your cloud's equivalent),
you know exactly what it's doing for you.

## Tracking

A **run** is one execution of training. For each, record:

- **parameters**: every hyperparameter and configuration value, including the seed;
- **metrics**: evaluation results, and training curves as metrics with steps;
- **tags**: the code version (git commit), a hash of the training data, the environment (Python and library versions, hardware),
  who ran it and why;
- **artifacts**: the model file, plots, the evaluation report, the exact config, stored by content hash.

With MLflow the same thing is a few lines:

```python
import mlflow
mlflow.set_experiment("fraud-gbm")
with mlflow.start_run():
    mlflow.log_params(params | {"seed": seed})
    mlflow.set_tags({"git_commit": commit, "data_sha256": data_hash})
    model.fit(X_train, y_train)
    mlflow.log_metric("val_auc", val_auc)
    mlflow.sklearn.log_model(model, name="model")
```

The lab logs a 9-configuration sweep and queries it with SQL for the top runs. Two things the tracker can't do for you. First, if you
select the best of 9 by *test* AUC, the winner's test score is optimistically biased (18.1): select on validation, report on a test set used
once. Second, "best" may be noise.

## Seed variance

The lab reruns the top two configurations with 8 seeds each (the seed changes the early-stopping split and the binning sample):

| configuration | mean AUC | sd | range |
|---|---|---|---|
| "best" (by its seed-0 run) | 0.9564 | 0.0012 | 0.9543 to 0.9585 |
| "second" | 0.9567 | 0.0007 | 0.9558 to 0.9579 |

With seed 0, "best" led by 0.0006. Over 8 seeds, it's slightly *behind*. The ranking of single runs was ranking seeds. The practice:
log the seed, run the finalists several times, and compare distributions. A difference smaller than the seed-to-seed spread isn't a
finding, however it looks on the leaderboard (43.1 made the same point for evals).

## The registry

A **model registry** is the list of models that matter, separate from the thousands of runs that don't. Each registered **version** points
to the run that produced it, which gives it **lineage**: data hash, code commit, parameters, metrics, environment. **Aliases** (MLflow's
term; older systems used "stages") name the versions that play roles: `champion` is what production serves, `challenger` is what's being
tested against it.

In the lab, version 1 is registered as champion and version 2 as challenger, each resolving to its artifact and lineage. Promotion moves
the alias; rollback moves it back. Nothing is rebuilt, nothing is overwritten, and it takes a second, which is the property you want at 3
a.m. Serving code asks for `fraud-scorer@champion`, never a file path, so a deploy is a registry change that can be audited and reverted.

Two details the lab's content-addressed artifact store shows. Of 27 logged artifacts, 23 are distinct: identical models (same
configuration, same seed, deterministic training) are stored once. And an artifact's hash is its identity, so "the model in production"
is a checkable fact, not a filename that might have been overwritten.

## What to record so a model can be reproduced

The self-check question: what do you need to store to reproduce a model exactly six months from now?

- **Code**: the commit, with no uncommitted changes (record a "dirty" flag and refuse to register from a dirty tree).
- **Data**: an immutable snapshot or a content hash with a way to retrieve those exact bytes (48.2), including the query or pipeline
  version that produced it.
- **Configuration**: every parameter and the seed.
- **Environment**: pinned package versions (a lock file), the Python version, the container image digest, and hardware and driver
  versions for GPU work (48.2).
- **The procedure**: the pipeline that runs training and evaluation, as code, not as a person's memory.
- **The artifacts**: the model and its evaluation report, stored immutably.

With all of that, reproduction is a command. Without any one of them, it's archaeology.

## Things that will bite you

- **Untracked runs**: the good result came from the run nobody logged.
- **No data version**: the table was overwritten; the model's training data no longer exists.
- **Selecting on the test set** across many runs.
- **Single-seed comparisons.**
- **Models loaded by file path** in serving, overwritten in place.
- **Pickled models** loaded from untrusted sources (53.2).

## Exercises

1. List the tags you'd attach to every training run in your team, and the ones you'd refuse to register a model without.
2. Why does selecting the best of 50 runs by test score bias that score upward? How large can the bias be?
3. A colleague's new model beats the champion by 0.3 AUC points in one run. What do you ask for?
4. Design the promotion process from challenger to champion: who, what checks, what's recorded.
5. How would you find every production model that was trained on a dataset later found to contain corrupted rows?
6. What does an alias-based deployment give you that copying a model file to a server doesn't?

<details>
<summary>Answers</summary>

1. Always: git commit and dirty flag, data hash and data snapshot ID, config file hash, seed, library versions, container image digest,
   hardware, user, purpose. Required for registration: a clean commit, a data snapshot that can be retrieved, a linked evaluation report
   on the agreed test set, and the environment lock.

2. Each run's test score is the true score plus noise. The maximum of 50 noisy scores sits in the upper tail of that noise: roughly
   2.2 noise standard deviations above the mean if the configurations are similar. With a test-score standard deviation of 0.003,
   that's a 0.007 optimistic bias, often larger than the real differences being claimed.

3. The seed-to-seed spread of both models (several seeds each), evaluation on the same validation and test sets with a paired
   comparison and an interval, whether any tuning used the test set, and whether the improvement holds on the slices that matter.

4. The challenger must pass the offline evaluation suite (no regression in critical slices, and improvement beyond seed variance), the
   behavioral tests (50.1), and a shadow or canary period in production (50.2) with metrics within guardrails. An owner approves, the
   alias moves, and the registry records who, when, why, and the evaluation evidence. Rollback is the same alias move, pre-approved.

5. Query the registry and tracker for all model versions whose run's data tag matches the corrupted snapshot, or any snapshot derived
   from it (data lineage, 15.2), then filter to those with a production alias. This only works if data hashes and lineage were
   recorded at training time.

6. Atomic, auditable, instantly reversible deploys; lineage from the serving system to the training run; several consumers can resolve
   the same alias consistently; and there's no ambiguity about which bytes are in production, because the version is immutable and
   the file isn't overwritten.
