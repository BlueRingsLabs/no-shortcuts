# 14.2 Stream processing: time, windows, state and exactly-once

*About 13 hours. Prerequisites: 14.1, 08.2 (windows, sessionization), 13.1. Lab: [`lab_14_2_stream_processing.py`](labs/lab_14_2_stream_processing.py).*

Batch processing has a luxury that stream processing doesn't: when the batch job for March 14 runs, March 14 is over. All the
data is there (more or less). A stream processor computing "orders per minute" has to decide, at some point, that the minute
13:05 is finished and emit a result, while knowing perfectly well that a phone that lost signal in a tunnel might send an order
from 13:05 at 13:20. Everything difficult about streaming comes from that: **time**, and the fact that the data about the past
keeps arriving in the present.

This lesson covers the concepts that every stream processor (Apache Flink, Spark Structured Streaming, Kafka Streams, Beam/
Dataflow) implements in its own vocabulary: event time, windows, watermarks, state, and end-to-end correctness. The lab
implements a small event-time window processor so you can watch late data being handled, or dropped.

## Two clocks

- **Event time**: when the thing happened, stamped by the device or system where it happened.
- **Processing time**: when your processor sees it.

In a perfect world they'd differ by a constant small delay. In the real world the gap varies wildly: network delays, mobile devices offline for hours,
batch uploads from IoT gateways, retries (14.1), a consumer that was down and is now catching up on two hours of lag, clock skew between devices. Events
arrive **out of order**.

If you aggregate by processing time ("orders that *arrived* in this minute"), results depend on network conditions and on your consumer's health: a
consumer that catches up after an outage reports a huge spike that never happened. If you aggregate by event time ("orders that *happened* in this
minute"), results are meaningful, but you have to decide how long to wait for stragglers. The lab measures both on the same out-of-order stream.

For business metrics and ML features, **use event time**. Processing time is for operational metrics about the pipeline itself (throughput, lag).

## Windows

Unbounded streams are aggregated over **windows**:

- **Tumbling**: fixed-size, non-overlapping (every 1 minute). Each event belongs to exactly one window.
- **Hopping / sliding**: fixed size with a smaller step (a 10-minute window every 1 minute): each event belongs to several windows. "Transactions for this
  card in the last 10 minutes" is a sliding window, and it's one of the most common real-time fraud features.
- **Session**: dynamic, per key, closed after a gap of inactivity (30 minutes). The streaming version of 08.2's sessionization: sessions can **merge** when a
  late event fills the gap between two of them.
- **Global windows** with custom triggers, for special cases.

## Watermarks: deciding the past is over

A **watermark** is the processor's estimate of event-time progress: "I believe I've now seen all events with event time ≤ W". When the watermark passes the end
of a window, the window can be finalized and emitted.

A common heuristic: `watermark = max event time seen so far - allowed delay` (say, 5 minutes). The delay is a trade-off:

- **Short delay**: low latency, but more events arrive after their window was closed (**late events**).
- **Long delay**: complete results, but everything is emitted later, and the processor must keep more windows open in memory.

What to do with late events is a policy decision:

1. **Drop** them (and count them: the late-drop rate is a metric to monitor, 15.3).
2. **Update** the window's result and emit a correction (allowed lateness): downstream must handle updates (upserts by window key), not just appends.
3. **Side output** them to a separate stream for later reconciliation, often by a batch job that recomputes with complete data.

The last one points to an important architectural idea: streaming results are often **provisional**, and a later batch computation over the complete data
provides the final numbers. (The "Lambda architecture" formalized this with separate batch and streaming code paths, which doubled the work; the "Kappa
architecture" uses one streaming code path and reprocesses from the log when needed. Modern engines let you run the same code in batch and streaming modes,
which mostly dissolves the debate.)

## State

Anything beyond stateless filtering and mapping needs **state**: running counts per window, the last seen event per key for deduplication, open sessions, the
current version of each row for CDC. Stream processors keep state in memory or in an embedded store (RocksDB in Flink and Kafka Streams), partitioned by key
so it scales with the stream's partitions.

State must be:

- **Fault tolerant**: periodically **checkpointed** to durable storage together with the input offsets, so after a crash the processor restores state and
  rewinds the input to the matching offsets. That consistent pairing (state + offsets) is what makes exactly-once state updates possible inside the processor.
- **Bounded**: state that grows forever (dedup sets of every event ID ever seen, sessions never closed) eventually kills the job. Use **TTLs** (forget event IDs
  after the maximum plausible redelivery delay) and watermarks to expire windows.
- **Evolvable**: changing your processing logic may require migrating state, or reprocessing from the log.

## Stream joins

- **Stream-table (enrichment)**: join each event with the current value of a lookup table (the customer's segment, the product's category), often maintained as
  a local table from a compacted topic or CDC stream. Beware of the temporal subtlety from 09.2: you usually want the value *as of the event time*, not "now",
  especially when reprocessing history.
- **Stream-stream**: join two event streams within a time window (an ad impression and a click on it within 30 minutes). Both sides must be buffered in state
  for the window's duration.

## Change data capture streams

CDC (13.1, 14.1) delivers a stream of row changes: `insert(row)`, `update(before, after)`, `delete(key)`. Applying it to a target means **upserting by primary
key and applying deletes**, in commit order per key. Replaying the same change events must be idempotent. With that, a warehouse or search index can mirror an
operational database with seconds of latency, including deletes (which watermark-based extraction can't see). The lab applies a CDC stream with retries and
duplicates and checks that the mirror ends up identical to the source.

## The engines

- **Apache Flink**: the reference for low-latency, stateful, event-time stream processing with exactly-once state and large state (RocksDB); SQL and DataStream
  APIs.
- **Spark Structured Streaming**: streams as unbounded DataFrames, micro-batches by default, same API as batch Spark (Module 12). Natural if you're already on Spark and
  seconds of latency are fine.
- **Kafka Streams / ksqlDB**: a library (not a cluster) for processing Kafka topics inside your own services, with state stores backed by Kafka.
- **Apache Beam** (Google Dataflow): a unified model for batch and streaming, from the people who wrote the definitive papers on watermarks.

For small volumes, a plain consumer in Python with careful idempotency (14.1) is often enough. Don't deploy Flink to count 50 events per second.

## Streaming for ML

- **Real-time features**: sliding-window aggregates per entity, written to an online feature store for low-latency serving (22.1, 49.1). The same features must
  be computable **point-in-time correctly** for training (09.2): the value the model would have seen at prediction time, not the value computed later with
  late events included. Training/serving skew from streaming features is a classic source of models that are great offline and bad online.
- **Online inference** on events (fraud scoring), with predictions and features logged as events for monitoring and for building training data later (51.1).

> **Scar tissue.** During a CTF we organized, the live chart of solves per hour dropped by a few percent at the same time every night, and
> the players in the chat built a whole theory about a secret curfew. The real cause: the consumer lagged while a nightly backup ran on
> the same box, and the windows closed on processing time, so late events landed in the next hour or were dropped. Event time, a watermark
> and a sensible allowed lateness, and the nightly dip vanished. So did the curfew theory, which was more interesting than the truth.

## Things that will bite you

- **Processing-time aggregation** for business metrics.
- **Watermarks too aggressive** (silently dropping late data) or too lax (unbounded state, late results).
- **Unbounded state**: dedup sets and sessions without TTLs.
- **Non-idempotent sinks** under at-least-once delivery (14.1).
- **Enrichment with current values** when reprocessing history.
- **Streaming as a default** when an hourly batch job would do.

## Exercises

1. Events for minute 13:05 arrive at processing times ranging from 13:05:01 to 13:21. With a watermark of "max event time - 5 minutes", which of them are late? What
   options do you have for them?
2. Design the "number of transactions per card in the last 10 minutes" feature: window type, key, state, and how to make the training data point-in-time correct.
3. Your streaming dedup keeps every event ID it has ever seen. Estimate the state size after a year at 5,000 events per second with 16-byte IDs, and propose a fix.
4. A consumer applies a CDC stream to a warehouse table with plain `INSERT`s. What goes wrong with updates, deletes and redeliveries?
5. When is Spark Structured Streaming a better choice than Flink, and vice versa?

1. The window 13:05-13:06 closes when the watermark passes 13:06, i.e. when an event with event time ≥ 13:11 has been seen. Events from 13:05 arriving after that

5. Spark Structured Streaming: your platform already runs Spark, latency of seconds is fine, and you want one code base for batch and streaming. Flink: low latency
