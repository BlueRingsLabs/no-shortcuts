# 12.2 Spark in practice: partitions, shuffles, skew

*About 13 hours. Prerequisites: 12.1. Lab: [`lab_12_2_spark_practice.py`](labs/lab_12_2_spark_practice.py).*

Every slow Spark job I've been asked to look at had one of about six problems, and I could usually tell which one from
the stage timeline in the Spark UI within a couple of minutes: one task running for forty minutes while the other 199
finished in ten seconds (skew), a join shuffling two huge tables when one of them could have been broadcast, a Python UDF
serializing every row, two hundred partitions of 2 MB each, twelve thousand output files, or the same expensive DataFrame
recomputed five times. This lesson is about those six, how to recognize them, and how to fix them.

The DataFrame API used here is PySpark's, and it maps almost one to one to Spark SQL, so everything applies to SQL jobs too.

## Partitions: how many, how big

A partition is the unit of parallelism: one task per partition per stage. Rules of thumb:

- **Input partitions** come from the files: roughly one per file block/row group, controlled by `spark.sql.files.maxPartitionBytes` (128 MB by default).
  Many small files mean many tiny partitions (11.2's small files problem, in another costume).
- **Shuffle partitions** come from `spark.sql.shuffle.partitions` (200 by default, a number chosen long ago for clusters of a certain size). Too few:
  huge tasks that spill to disk and leave cores idle. Too many: thousands of tiny tasks where scheduling overhead dominates. A good target is partitions of
  100-200 MB, and at least 2-3 times the number of cores.
- **Adaptive Query Execution (AQE)**, on by default since Spark 3.2, re-optimizes at runtime using real shuffle statistics: it **coalesces** small shuffle
  partitions, **switches join strategies** (to broadcast, if a side turns out small), and **splits skewed partitions**. It fixes a lot of bad defaults
  automatically. Know it's there, and read the final plan (AQE plans show `isFinalPlan=true`).

`repartition(n)` does a full shuffle into `n` partitions (optionally by columns); `coalesce(n)` merges partitions without a shuffle (only to reduce). Use
`repartition` by key before a heavy operation on that key; use `coalesce` to reduce output files.

## Joins: shuffle vs broadcast

Spark's main join strategies:

- **Sort-merge join** (the default for two big tables): shuffle both sides by the join key, sort, merge. Two shuffles.
- **Broadcast hash join**: if one side is small (below `spark.sql.autoBroadcastJoinThreshold`, 10 MB by default; AQE can decide at runtime), send a full copy
  of it to every executor, and join each partition of the big side locally. **No shuffle of the big side at all.** The typical fact-to-dimension join (09.2)
  should almost always be a broadcast.

You can hint it: `big.join(F.broadcast(small), "key")`. Don't broadcast things that aren't small: every executor must hold the whole table in memory, and the
driver collects it first.

## Skew

**Skew** means a few keys have far more rows than the rest. After a shuffle by key, one partition gets all the rows of the giant key, one task processes it, and
the whole stage waits for that task. You see it in the UI as a stage where the max task duration is 100x the median.

Where it comes from, in my experience: NULL or default keys (`customer_id = 0` for all guest checkouts, `country = 'unknown'`), a few whale customers or popular
products (Zipf-distributed data, 04.1), and bot traffic concentrated on a few IDs.

Fixes:

1. **Filter or handle the hot keys separately.** NULL keys in a join can't match anything anyway: filter them out before the join, and union them back if needed.
2. **Broadcast** the other side if it's small: no shuffle, no skew problem.
3. **AQE skew join handling** (`spark.sql.adaptive.skewJoin.enabled`, on by default): splits oversized partitions into several tasks, replicating the matching
   rows of the other side.
4. **Salting**: append a random suffix (0..k-1) to the hot key on the big side, and replicate each row of the other side k times with every suffix. The hot key
   is now spread across k partitions. For aggregations, aggregate by (key, salt) first, then by key: a two-stage aggregation.

The lab builds a skewed join, measures it, and fixes it with salting.

## UDFs: the hidden serialization tax

Built-in functions (`F.when`, `F.regexp_extract`, `F.date_trunc`, hundreds more) run inside the JVM on Tungsten's binary format and benefit from code generation.
A **Python UDF** forces every row to be serialized, sent to a Python worker process, processed one row at a time, and sent back. It's often several times to
100x slower than the equivalent built-in, and it's opaque to the optimizer (no pushdown through it). Spark 4 softened the blow by moving the data to Python in Arrow
batches by default, but your function is still called once per row, in another process.

Order of preference:

1. **Built-in functions** (check the docs; the function you want probably exists).
2. **Spark SQL expressions** (`F.expr("...")`).
3. **Pandas UDFs** (`@pandas_udf`): vectorized, data moves in Arrow batches, and your function operates on pandas Series. Much faster than row-by-row UDFs when
   you truly need Python (a model's `predict`, a library call).
4. Row-at-a-time Python UDFs: last resort.

## Caching

`df.cache()` keeps a DataFrame in executor memory (spilling to disk if needed) after its first computation. Use it when a DataFrame is **reused by several actions**
and is expensive to recompute (12.1, exercise 4). Don't cache everything: cached data competes with execution memory, and caching something used once only adds
cost. `unpersist()` when done.

## Writing output

- `df.write.partitionBy("date")` creates Hive-style partitions (11.2). Each task writes one file **per partition value it contains**: with 200 tasks and 365 dates,
  you can get 73,000 files. Repartition by the partition column first (`df.repartition("date").write.partitionBy("date")`) so each date is written by one task, or
  set `maxRecordsPerFile`.
- Target files of hundreds of MB. `coalesce` or `repartition` before writing to control the count.
- Write to a table format (Delta, Iceberg) rather than raw directories to get atomic commits (11.2); raw `overwrite` of a directory is not atomic, and a failed job
  leaves a half-written directory.

## Memory and spills

Executors split memory between **execution** (shuffles, joins, sorts, aggregations) and **storage** (cache). When execution memory runs out, Spark **spills** to
local disk: slower but correct. When it can't spill (a single huge record, a massive broadcast, `collect` to the driver), you get `OutOfMemoryError`. Typical causes:
skew (one partition too big), broadcasting something big, too few shuffle partitions, `collect()`/`toPandas()` on large data, and Python workers using memory outside
the JVM's accounting (pandas UDFs on huge batches).

## Reading the Spark UI (and plans)

When a job is slow, look in this order:

1. **Jobs and stages**: which stage takes the time?
2. **Task duration distribution** in that stage: max vs median (skew?), number of tasks (too few/many partitions?).
3. **Shuffle read/write sizes** and **spill** per stage.
4. **The SQL tab / `df.explain("formatted")`**: `Exchange` (shuffles), `BroadcastHashJoin` vs `SortMergeJoin`, `BatchEvalPython` / `ArrowEvalPython` (Python UDFs),
   pushed filters in the scan node.

## Cost

On a cloud cluster, cost ≈ number of machines × time. Levers: right-size the cluster (autoscaling, 52.1), use spot/preemptible instances for fault-tolerant batch
work, avoid unnecessary shuffles, read less data (partition pruning, column pruning, 11.1), and question whether the job needs Spark at all (12.1).

> **Scar tissue.** For a course project on a public clickstream dataset, my Spark job on the university cluster took forty minutes for 199
> of its 200 tasks and six hours for the last one. The join key was `user_id`, and anonymous events all had the same `user_id`: an empty
> string. About a third of the data landed in a single partition, on a single core, while the rest of a shared cluster idled and other
> students queued behind me. Routing the anonymous rows through their own path (and salting the key for the rest) cut it to twenty-five
> minutes. The Spark UI showed the skew the whole time. I just never opened the stage view.

## Things that will bite you

- **The default 200 shuffle partitions** on data that's 200 MB or 20 TB.
- **Skewed keys** (NULLs, defaults, whales).
- **Sort-merge joins against small dimension tables.**
- **Python UDFs** where a built-in exists.
- **Recomputing** uncached DataFrames across multiple actions.
- **Output file explosions** from `partitionBy` without repartitioning.
- **`collect()` and `toPandas()`** on big results.

4. A job writes `partitionBy("event_date")` and produces 50,000 tiny files per run. Explain why and fix it.

<summary>Answers</summary>

1. Skew: one key (or a few) holds a huge share of the rows after a shuffle. Confirm in the UI (task duration and shuffle read size of the slow task vs the median) and
   by counting rows per key (`groupBy(key).count().orderBy(desc)`). Fixes: filter/handle NULL or default keys separately; broadcast the other side if it's small;
   enable/tune AQE skew join; salt the hot keys.

2. The dimension table is broadcast: a full copy goes to every executor, and each partition of the fact table joins locally against it. Look for
   `BroadcastHashJoin` (and a `BroadcastExchange` on the small side only) instead of `SortMergeJoin` with two `Exchange hashpartitioning` nodes.

3. ```python
   df.withColumn("bucket", F.when(F.col("amount") > 1000, "high").when(F.col("amount") < 10, "low").otherwise("mid")) \
     .withColumn("domain", F.regexp_extract("email", r"@(.+)$", 1))
   ```

4. Each of the N tasks writes one file for every `event_date` value present in its partition; with data spread randomly, every task has rows for every date: N ×
   dates files. Fix: `df.repartition("event_date").write.partitionBy("event_date")` (one task per date; add a second column or `maxRecordsPerFile` if some dates are
   huge), or cluster/compact via the table format.

5. Stage 1: add `salt = floor(rand() * k)` and aggregate by `(user_id, salt)`: the hot user's rows are spread over k tasks, each producing a partial count. Stage 2:
   aggregate the partial counts by `user_id` (at most k rows per user, so it's cheap). The result is identical; the work for the hot key is parallelized.
