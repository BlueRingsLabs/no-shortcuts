# 12.1 From MapReduce to Spark: the distributed model

*About 12 hours. Prerequisites: 07.1, 07.3, 08.3, 10.2. Lab: [`lab_12_1_distributed_model.py`](labs/lab_12_1_distributed_model.py).*

Before you distribute anything, one question: does it actually need distributing? In 10.2 you aggregated data several times
larger than a 64 MB memory limit on a single core. A single modern server with 64 cores and half a terabyte of RAM, running
DuckDB or Polars, handles more than most companies will ever have. Distributed systems buy you scale at the price of
complexity, network overhead, partial failures, and a whole new category of bugs. I've seen people run Spark clusters on 5 GB
of data because "that's what data engineers use", and spend more on the cluster and on debugging it than the problem was
worth.

That said, some data genuinely doesn't fit on one machine, many companies run their platforms on Spark regardless of size,
and the ideas (partitioning, shuffles, lazy evaluation, lineage) show up in every distributed system you'll touch, including
distributed training in 33.2. So let's learn how it works, starting from the idea that started it all.

## MapReduce

In 2004, Jeffrey Dean and Sanjay Ghemawat at Google published MapReduce: a programming model where you write two functions and
the framework handles distribution, scheduling and failures.

1. **Map**: process each input record independently, emitting (key, value) pairs.
2. **Shuffle**: the framework groups all pairs by key, moving data across the network so that every value for a given key lands on the
   same machine. Partitioning is by hash: `partition = hash(key) % n_reducers`.
3. **Reduce**: for each key, combine its values into a result.

Word count, the "hello world" of big data:

```
map("the cat sat on the mat")  ->  (the,1) (cat,1) (sat,1) (on,1) (the,1) (mat,1)
shuffle                         ->  the: [1,1,...]   cat: [1,...]   ...
reduce("the", [1,1,...])        ->  (the, 2)
```

Why it scaled: map tasks are **embarrassingly parallel** (no communication), and a **combiner** can pre-aggregate on each mapper (summing
the 1s locally) before the shuffle, reducing network traffic. Why it hurt: every job wrote its output to disk (HDFS) and complex pipelines
were chains of jobs, each reading the previous one's output from disk, which made iterative algorithms (like ML training) painfully slow.

The deep idea that survived: **computation expressed as transformations over partitioned data, with a shuffle wherever data must be
regrouped by key.** A SQL `GROUP BY`, a join, a `DISTINCT`, a window function with `PARTITION BY`: on a distributed engine, every one of them is
a map, a shuffle and a reduce. Understanding that is understanding distributed performance.

## Spark

Apache Spark (Zaharia et al., Berkeley, 2010) kept the model and fixed the pain:

- **In-memory** intermediate results instead of disk between every step.
- A general **DAG** of operations instead of rigid map-then-reduce pairs.
- **Lazy evaluation**: transformations build a plan; nothing runs until an **action** needs a result.
- **Lineage-based fault tolerance**: instead of replicating intermediate data, Spark remembers how each partition was computed, and recomputes
  lost partitions from their inputs if a machine dies.
- High-level APIs: DataFrames and SQL, optimized by the **Catalyst** optimizer (predicate pushdown, column pruning, join reordering, constant
  folding, the same ideas as 08.3) and executed by **Tungsten** (compact binary memory layout, code generation). The old RDD API still exists
  underneath; you should rarely need it.

### Architecture

- The **driver** runs your program, builds the plan, and schedules work.
- **Executors** (processes on worker machines) run **tasks** and hold cached data.
- A **cluster manager** (Kubernetes, YARN, standalone, or `local[*]` on your laptop, which is what the lab uses) allocates executors.

Data is split into **partitions**. One **task** processes one partition. Parallelism = number of partitions being processed at once, bounded
by the total number of executor cores.

### Transformations, actions, stages

- **Transformations** (`select`, `filter`, `withColumn`, `join`, `groupBy().agg()`) return a new DataFrame and do nothing yet.
- **Actions** (`count`, `collect`, `show`, `write`, `toPandas`) trigger execution.

Transformations come in two kinds, and this distinction is the key to Spark performance:

- **Narrow**: each output partition depends on a single input partition (`select`, `filter`, `withColumn`, `map`). No data moves between
  machines. Spark pipelines consecutive narrow transformations into one pass.
- **Wide**: an output partition depends on many input partitions (`groupBy`, `join`, `distinct`, `orderBy`, `repartition`, window functions).
  Requires a **shuffle**: every executor writes its data partitioned by key to local disk, and every executor then fetches its share from every
  other executor over the network.

A **job** (one action) is divided into **stages** at shuffle boundaries. Within a stage, tasks run independently in parallel. Between stages,
there's a shuffle, and the next stage can't start until the shuffle data is ready (a barrier).

```
read parquet -> filter -> withColumn        (stage 1: narrow, pipelined, one task per input partition)
      ----------------- shuffle by customer_id ------------------
groupBy(customer_id).agg(sum)               (stage 2: one task per shuffle partition)
```

`df.explain()` shows the physical plan: look for `Exchange` operators, which are shuffles. Minimizing the number and size of shuffles is most of
Spark tuning (12.2).

### Why shuffles are expensive

A shuffle serializes data, writes it to local disk, sends it across the network (every executor to every executor: $O(n^2)$ connections in the
number of executors), deserializes it, and often sorts it. It's the one place where a distributed job pays for being distributed. And it's the
place where things go wrong: skewed keys make one task take forever (12.2), large shuffles spill to disk, and lost executors force re-computation
of the map outputs they held.

## Amdahl's law: the limits of scaling out

If a fraction $s$ of a job is inherently serial (driver work, a final single-partition step, a skewed key), then with $N$ workers the best
speedup is

$$\text{speedup}(N) = \frac{1}{s + \frac{1 - s}{N}} \le \frac{1}{s}$$

With 5% serial work, no number of machines gets you past 20x. Add coordination and shuffle overhead that *grows* with $N$, and there's an optimal
cluster size beyond which adding machines makes things slower. The lab measures this, on one machine with a varying number of cores, which is
enough to see the curve bend.

This is also why "distribute it" isn't free: a job that takes 10 minutes on one machine might take 3 on a cluster of 10, not 1, and cost more in
total.

## When to reach for Spark

Reasonable reasons: data that doesn't fit on one machine even with streaming and spilling (many terabytes), shuffles bigger than one machine's
memory and disk, an existing platform (Databricks, EMR, Dataproc) where the data and governance already live, Spark Structured Streaming for
large-scale stream processing (14.2), and ecosystem integrations (Delta Lake started in Spark).

Unreasonable reasons: "big data" that's 10 GB, CV-driven architecture, and "we might need it someday". Start with DuckDB or Polars; move when you
measure a need.

## Things that will bite you

- **`collect()` on a big DataFrame**: pulls everything into the driver's memory. The driver dies.
- **Forgetting laziness**: timing a transformation measures nothing; the work happens at the action. And calling several actions on an uncached
  DataFrame recomputes it from scratch each time.
- **Too few or too many partitions**: too few and cores sit idle (or tasks are huge and spill); too many and scheduling overhead dominates (12.2).
- **Python UDFs**: data is serialized between the JVM and Python per row; they're dramatically slower than built-in functions (12.2).
- **Distributed systems for small data.**

## Exercises

1. Write word count as map and reduce functions in plain Python, including a combiner. How much data crosses the "network" with and without the
   combiner for a text of 1,000 words with 200 distinct words, split across 4 mappers?
2. For each operation, say narrow or wide: `filter`, `groupBy.agg`, `withColumn`, `join` (in general), `union`, `distinct`, `orderBy`, `sample`.
3. A job has 10% serial work. What's the maximum speedup with 4, 16 and 1,000 workers?
4. You call `df.count()` and then `df.write.parquet(...)` on the same expensive DataFrame. What happens, and how do you avoid it?
5. Why can Spark recover from a lost executor without having replicated its data?

<summary>Answers</summary>

1. The lab implements it. Without a combiner, every word occurrence crosses the network: 1,000 pairs. With a combiner, each mapper sends at most
   one pair per distinct word it saw: at most 4 × 200 = 800 pairs, typically far fewer if each mapper sees only a subset of words; in natural text
   with a heavy-tailed word distribution, the reduction is large for frequent words ("the" appears once per mapper instead of dozens of times).

2. Narrow: `filter`, `withColumn`, `union`, `sample`. Wide: `groupBy.agg`, `distinct`, `orderBy`, `join` (unless it's a broadcast join, where the
   small side is copied to every executor and the big side isn't shuffled, 12.2).

3. $1/(0.1 + 0.9/N)$: 4 workers → 3.08x, 16 → 6.4x, 1,000 → 9.9x. Never more than 10x.

4. Two actions, two full computations of `df` from the source, because nothing is kept by default. Use `df.cache()` (or `persist`) before the first
   action if you'll reuse it (and `unpersist` afterwards), or restructure so there's one action (for example, write first and count from the written
   files).

5. Lineage: each partition of each DataFrame knows which transformations, applied to which parent partitions, produce it. If an executor dies, the
   driver re-runs the tasks needed to recompute exactly the lost partitions from their inputs (going back as far as needed, possibly to the source files
   or to shuffle outputs that survived).
