# 10.2 Polars and DuckDB: the modern single-node stack

*About 10 hours. Prerequisites: 10.1, Module 08. Lab: [`lab_10_2_polars_duckdb.py`](labs/lab_10_2_polars_duckdb.py).*

For about ten years, the standard advice was: pandas until the data doesn't fit in memory, then Spark. There was nothing
in between, so people spun up clusters for 20 GB of data, paid for them, waited for them, and debugged them. Meanwhile,
laptops got 16 cores, 64 GB of RAM and NVMe disks that read several GB per second. A single modern machine can chew
through hundreds of gigabytes if the software uses it properly.

That software now exists. **DuckDB** is an in-process analytical SQL database (think "SQLite for analytics"): columnar,
vectorized, multi-threaded, able to spill to disk and to query Parquet and CSV files directly. **Polars** is a DataFrame
library written in Rust with a lazy query engine, the same ideas behind a DataFrame API. Both are often 10 to 100 times
faster than pandas on analytical workloads, and both handle data larger than RAM. I've replaced more than one Spark job with
a DuckDB query running on a single VM, with a fraction of the cost and none of the cluster babysitting. This lesson is about
when and how.

## Why they're fast

The ideas from 07.3 and 08.3, applied:

- **Columnar storage and execution**: operate on column chunks (vectors) that fit in cache, using SIMD.
- **All the cores**: parallel scans, aggregations and joins. pandas mostly uses one.
- **Query optimization**: because they see the whole query before running it (SQL for DuckDB, lazy mode for Polars), they can push filters down to
  the scan, read only needed columns, reorder joins, and avoid materializing intermediate results. pandas executes each line eagerly, exactly as
  written, including your inefficiencies.
- **Out-of-core execution**: streaming through data in chunks and spilling to disk when an aggregation or join doesn't fit in memory.
- **Apache Arrow** as the in-memory format: a standard columnar layout that pandas (with Arrow dtypes), Polars, DuckDB, Spark and many others can
  share **without copying**. Moving a table from DuckDB to Polars to pandas can be nearly free.

## DuckDB

```python
import duckdb
con = duckdb.connect()                     # in-memory; or duckdb.connect("warehouse.duckdb") for a persistent file

# Query files directly, with globs; only needed columns and row groups are read
con.sql("""
    SELECT country, date_trunc('month', order_ts) AS month, SUM(amount) AS revenue
    FROM 'data/orders/*.parquet'
    WHERE order_ts >= '2025-01-01'
    GROUP BY ALL ORDER BY ALL
""").df()                                  # -> pandas; .pl() -> Polars; .arrow() -> Arrow

# Query in-memory DataFrames by variable name
con.sql("SELECT * FROM my_pandas_df WHERE x > 0")
```

Useful features: `GROUP BY ALL` / `ORDER BY ALL`, `QUALIFY`, `ASOF JOIN`, `SUMMARIZE table` (a quick profile), reading remote files over HTTP/S3 with
the `httpfs` extension, and `COPY ... TO 'out.parquet' (FORMAT parquet, PARTITION_BY (year, month))` for writing partitioned datasets (11.2). Settings like
`SET memory_limit = '4GB'` and `SET threads = 8` control resources.

DuckDB is excellent for: exploratory analysis on big files, local development of warehouse transformations (dbt-duckdb, 13.3), data quality checks,
feature computation, and the "medium data" pipelines that don't need a cluster.

## Polars

Polars has two modes. **Eager** looks like pandas. **Lazy** builds a query plan and optimizes it before running, and it's the one you should use for
anything non-trivial.

```python
import polars as pl

result = (
    pl.scan_parquet("data/orders/*.parquet")            # lazy: nothing is read yet
      .filter(pl.col("order_ts") >= pl.datetime(2025, 1, 1))
      .join(pl.scan_parquet("data/customers.parquet"), on="customer_id", how="left")
      .group_by("country", pl.col("order_ts").dt.truncate("1mo").alias("month"))
      .agg(pl.col("amount").sum().alias("revenue"), pl.len().alias("orders"))
      .sort("country", "month")
      .collect()                                         # optimize, then execute (engine="streaming" for larger-than-RAM)
)
```

The **expression API** is the heart of Polars: `pl.col("x")`, arithmetic, `.when().then().otherwise()`, `.over("group")` for window functions, `.str` and
`.dt` namespaces. Expressions inside one `select`/`with_columns`/`agg` run in parallel. There's no index (which removes a whole class of alignment bugs
from 10.1) and no chained-assignment ambiguity: DataFrames are immutable, every operation returns a new one.

`lazy_frame.explain()` prints the optimized plan, where you can see the filter pushed into the Parquet scan and the projection reduced to the columns
actually used.

## pandas, Polars, DuckDB: which one?

My working rule, not a law:

- **pandas**: small data, the long tail of library integrations (plotting, scikit-learn, statsmodels all speak pandas), and teams that already know it.
  Fine up to a few million rows.
- **Polars**: DataFrame-style pipelines on medium-to-large data, feature engineering, anything you'd otherwise write in pandas but is slow. Great in
  production Python services because it's fast and has no hidden mutability.
- **DuckDB**: when the natural language is SQL, when data lives in files (Parquet/CSV/JSON) you want to query in place, when you want a local warehouse,
  and for larger-than-memory joins and aggregations.
- **Spark** (Module 12): when the data truly doesn't fit on one machine (many terabytes), when you need the cluster for other reasons (an existing
  platform, streaming at scale), or when the data is already in a distributed lakehouse and the compute sits next to it.

They interoperate cheaply via Arrow, so mixing them is normal: DuckDB to join and aggregate the raw files, Polars for feature logic, pandas at the end for
the plotting library that insists on it.

## Larger than memory, in practice

Both engines stream through data when they can. Operations that need to see everything at once (a global sort, a hash join where the build side is huge,
an aggregation with billions of groups) have to spill to disk, which works but slows down. Ways to help them:

- **Filter early and select few columns** (they do this automatically when they can see the whole query, but not across Python-level steps you force to
  materialize).
- **Store data as Parquet, partitioned** by the columns you filter on (11.1, 11.2). CSV has no column pruning, no statistics for skipping, and must be
  parsed.
- **Pre-aggregate** before joining.
- **Watch memory limits** in containers: an engine that thinks it has the whole machine's RAM inside a 4 GB container gets killed by the OOM killer. Set
  limits explicitly.

## Things that will bite you

- **Eager pipelines** in Polars (`read_parquet` + many steps) instead of lazy scans: you lose the optimizer.
- **Converting back to pandas too early**, then doing the heavy work in pandas anyway.
- **CSV as the storage format** for anything big or repeatedly queried.
- **Container memory limits** vs engine defaults.
- **Assuming identical semantics**: NULL handling, integer division, sorting of NULLs and string collation differ slightly between pandas, Polars and SQL.
  Test the edge cases when you port logic.
