# 10.1 pandas without the pain

*About 10 hours. Prerequisites: 01.3, Module 08. Lab: [`lab_10_1_pandas.py`](labs/lab_10_1_pandas.py).*

pandas is the tool that everybody uses and almost nobody uses well. Its API is enormous, it offers five ways to do each
thing (four of them slow), and a lot of the advice floating around the internet was written for versions that no longer
exist. In particular, pandas 3.0 (released in 2026) changed some behaviour that a decade of tutorials relied on: copy-on-write
is now always on, and strings have a real dtype. If you learned pandas from old notebooks, some of your muscle memory is now
wrong, and some of it now silently does nothing.

This lesson is the subset of pandas I actually use, the traps that produce wrong numbers without errors, and the patterns
that keep pandas code fast and readable. The next lesson covers when to leave pandas for Polars or DuckDB, which is more often
than people think.

## The data model

- A **Series** is a 1-D array with an **index** (labels). A **DataFrame** is a dict of Series sharing the same index. Each column has one dtype.
- The **index** aligns data. Arithmetic between two Series aligns on labels, not positions: `s1 + s2` matches rows by index label and produces
  NaN where a label is missing from either side. It's powerful and it's a trap: after filtering or sorting, your index is no longer `0..n-1`,
  and combining with a NumPy array or a list assumes positions. When the index carries no meaning, `reset_index(drop=True)`.
- Underneath, columns are NumPy arrays or Arrow arrays (01.3's vectorization applies: operate on whole columns).

### Dtypes matter

| Kind | Dtype | Notes |
|---|---|---|
| integers | `int64`, nullable `Int64` | classic `int64` can't hold missing values; a NaN turns the column into `float64` (and IDs into `1.2345e+06`). `Int64` (capital I) is nullable |
| floats | `float64`, `float32` | NaN is the missing marker |
| strings | `str` (pandas 3 default, Arrow-backed) | before 3.0 strings were `object` columns of Python objects: slow and memory-hungry |
| booleans | `bool`, nullable `boolean` | |
| categories | `category` | low-cardinality strings stored as integer codes: huge memory and speed savings for things like country or status |
| datetimes | `datetime64[us]`, `datetime64[us, UTC]` | pandas 3 defaults to microsecond resolution (older versions: nanoseconds). Use tz-aware UTC for anything that crosses systems (08.1) |

Always check `df.dtypes` and `df.info(memory_usage="deep")` after loading. When reading CSVs, **specify dtypes** (`dtype={"customer_id": "Int64",
"country": "category"}`, `parse_dates=[...]`) instead of letting pandas guess from the first chunk of rows. Type guessing is how ZIP codes lose their
leading zeros and IDs become floats.

## Selecting and modifying data

```python
df.loc[row_labels, col_labels]     # by label (and boolean masks)
df.iloc[row_positions, col_positions]
df[df["status"] == "delivered"]    # boolean mask
df.query("status == 'delivered' and quantity > 1")
```

### Copy-on-write, and the death of chained assignment

In pandas 3, **every indexing operation behaves as if it returned a copy**. Modifying the result never modifies the original DataFrame. (Under the hood,
data is shared until one side is written to, so it's still cheap.) Consequences:

```python
df[df["status"] == "returned"]["refund"] = True     # does NOTHING to df (pandas 3 warns with ChainedAssignmentError)
df.loc[df["status"] == "returned", "refund"] = True  # the correct way: one .loc call

sub = df[df["country"] == "AR"]
sub["vip"] = True                                   # modifies sub only; df is untouched, and that's fine now
```

In old pandas, the first line sometimes worked and sometimes didn't, with the famous `SettingWithCopyWarning`. Now the rule is simple: **to modify a
DataFrame, index it once with `.loc`/`.iloc` on the left side of the assignment**, or build a new column with `assign`. Code written for old pandas that
relied on chained assignment silently stops working after an upgrade, which is exactly the kind of change that deserves a test suite (01.2).

## Method chaining

Readable pandas code looks like a pipeline, each step a method returning a new DataFrame:

```python
revenue_by_country = (
    orders
    .query("status == 'delivered'")
    .merge(items, on="order_id", how="inner", validate="one_to_many")
    .assign(amount=lambda d: d["quantity"] * d["unit_price"])
    .merge(customers[["customer_id", "country"]], on="customer_id", validate="many_to_one")
    .groupby("country", as_index=False)
    .agg(revenue=("amount", "sum"), orders=("order_id", "nunique"))
    .sort_values("revenue", ascending=False)
)
```

`assign` with a lambda refers to the DataFrame *at that point in the chain*. `pipe(f)` lets you insert your own function. The chain reads top to bottom
like the SQL CTEs from 08.1, and each step can be inspected by cutting the chain there.

## Joins: `merge`, with seatbelts

`df.merge(other, on=..., how="inner" | "left" | "right" | "outer")` is SQL's join, with the same fan-out risk (08.2). pandas gives you two seatbelts that
I use on every merge:

- **`validate=`**: `"one_to_one"`, `"one_to_many"`, `"many_to_one"`. If the data violates the declared cardinality (a "unique" key that isn't),
  `merge` raises instead of silently multiplying rows. This single argument would have prevented a large share of the wrong numbers I've seen in
  notebooks.
- **`indicator=True`**: adds a `_merge` column saying whether each row came from `left_only`, `right_only` or `both`. Great for finding orphans
  (orders whose customer doesn't exist).

And check row counts before and after, as in SQL.

## groupby: aggregate, transform, filter

```python
g = items.groupby("order_id")
g["quantity"].sum()                                             # one row per group
g.agg(lines=("product_id", "size"), qty=("quantity", "sum"))   # named aggregations
items["order_qty"] = g["quantity"].transform("sum")            # broadcast back to rows (a window function, 08.2)
items["rank_in_order"] = g["unit_price"].rank(ascending=False)
g.filter(lambda d: len(d) >= 3)                                # keep groups meeting a condition
```

`transform` is the pandas equivalent of `SUM(...) OVER (PARTITION BY ...)`: it returns a result aligned with the original rows. Use it for "share of
group total", "difference from group mean", "latest per group" and similar.

**Avoid `groupby(...).apply(custom_function)` and row-wise `df.apply(f, axis=1)`** when a vectorized or built-in aggregation exists. `apply` calls a Python
function per group or per row, losing all of 01.3's vectorization. The lab measures a 100x+ difference on a simple conditional column. `iterrows` is even
slower. When you catch yourself writing a loop over rows, there's almost always `np.where`, `np.select`, `.map`, `.clip`, `.str` or `.dt` methods that do it.

## Reshaping

- **Wide ↔ long**: `pivot_table(index=..., columns=..., values=..., aggfunc=...)` goes long to wide (with aggregation, so duplicates are handled);
  `melt` goes wide to long. Long format is what databases, plotting libraries and most ML pipelines want; wide format is what humans want in reports.
- `stack`/`unstack` move index levels to columns and back.
- `explode` turns a column of lists into one row per element.

## Time series

With a `DatetimeIndex` (or a datetime column and `on=`):

```python
daily = orders.set_index("order_ts").resample("D")["order_id"].count()     # event counts per day (empty days = 0)
weekly_ma = daily.rolling(7).mean()                                         # 7-row moving average (rows = days here)
orders["order_ts"].dt.tz_localize("UTC").dt.tz_convert("America/Argentina/Buenos_Aires")
```

`resample` fills in empty periods, which avoids the calendar-join problem from 08.2. `rolling("7D")` with a time-based window works correctly even on irregular
timestamps.

## Performance and memory

- Vectorize (01.3). Avoid `apply`, `iterrows`, and Python loops.
- Use `category` for low-cardinality strings and the right numeric widths (`int32`, `float32` when precision allows).
- Read only the columns you need (`usecols=`, and Parquet instead of CSV, 11.1).
- pandas is single-threaded for most operations and holds everything in memory. A rule of thumb: you need 5 to 10 times the dataset's size in RAM for
  comfortable work, because intermediate results pile up. When data approaches that, move to Polars or DuckDB (10.2), not to a bigger laptop.

> **Scar tissue.** In a competition project I once fed a model features that were shifted by one row for about a third of the examples. A
> `sort_values` had reordered one frame, a later assignment went by position through `.values` for one column and by index for another,
> and pandas did exactly what I told it to. The model trained, the metrics looked fine, and the predictions were for the neighbor. Now I
> assert on keys after every merge, and I don't mix positional and label-based access in the same function. Pandas isn't the bug. The bug
> is trusting that it read your mind.

## Things that will bite you

- **Chained assignment** (now silently does nothing, with a warning).
- **Index alignment** when combining Series from different sources.
- **Silent dtype changes**: ints to floats on NaN, strings to object, dates left as strings.
- **Fan-out merges**: use `validate=`.
- **`apply` everywhere.**
- **NaN semantics**: `NaN != NaN`, `groupby` drops NaN keys by default (`dropna=False` to keep them), `sum()` of all-NaN is 0 (unlike SQL's NULL).

2. Add a column with each order line's share of its order's total amount, without a loop and without `apply`.
3. A merge of `orders` with `customers` on `customer_id` increases the row count. Which `validate=` value would have caught it, and what's the likely cause?
4. Replace this with a vectorized expression: `df["bucket"] = df.apply(lambda r: "big" if r.amount > 1000 else ("mid" if r.amount > 100 else "small"), axis=1)`.
5. Load a CSV with columns `zip`, `customer_id` (with some missing values) and `signup` (dates) so that none of them is mangled.

<summary>Answers</summary>

1. It filters `df` into a temporary copy, sets `y` on the copy, and throws the copy away. `df` is unchanged (pandas 3 emits a `ChainedAssignmentError` warning).
   Correct: `df.loc[df["x"] > 0, "y"] = 1`.

2. ```python
   items = items.assign(amount=items["quantity"] * items["unit_price"])
   items["share"] = items["amount"] / items.groupby("order_id")["amount"].transform("sum")
   ```

3. `validate="many_to_one"` (many orders per customer, but each customer_id must appear once in `customers`). The likely cause: duplicated customers
   (the same customer_id twice, from a double load or a bad dedup), which the dirty shop in 10.3 contains.

4. ```python
   df["bucket"] = np.select([df["amount"] > 1000, df["amount"] > 100], ["big", "mid"], default="small")
   ```
   or `pd.cut(df["amount"], [-np.inf, 100, 1000, np.inf], labels=["small", "mid", "big"])` (careful with the boundary conventions: `cut` intervals are
   right-closed by default).

5. ```python
   pd.read_csv(path, dtype={"zip": "str", "customer_id": "Int64"}, parse_dates=["signup"])
   ```
   `zip` as a string keeps leading zeros; `Int64` keeps IDs as integers despite missing values; `parse_dates` turns the dates into `datetime64`. Check
   `df.dtypes` afterwards anyway.
