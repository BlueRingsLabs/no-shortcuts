# 10.3 Data cleaning and data quality

*About 10 hours. Prerequisites: 10.1, 10.2. Lab: [`lab_10_3_data_quality.py`](labs/lab_10_3_data_quality.py).*

Here's the unglamorous truth about this profession: models are rarely the problem. Data is. The label that's wrong 8% of
the time, the join key with trailing spaces, the "country" column that contains `AR`, `Argentina`, `ar` and `ARG`, the
timestamp that's in UTC for web orders and in local time for app orders because two teams wrote the ingestion, the
customer who exists three times with three emails. None of those throw an error. All of them corrupt every number computed
downstream.

The industry keeps rediscovering this. There's a whole movement called "data-centric AI" whose central insight is, and I say
this with affection, that the quality of the data matters more than the cleverness of the model. Every experienced engineer I
know nodded at that and went back to writing validation checks, which is what this lesson is about: how to find problems
systematically, fix them without making new ones, and encode your expectations as tests so the same problem never sneaks
back in silently.

The lab uses the "dirty" version of the shop dataset (`make_shop(dirty=True)`), which has nine documented kinds of garbage
injected. Your job is to find all of them before reading the generator's source. Cheating is possible, and pointless.

## A taxonomy of data problems

Having names for things helps you check for all of them, not just the ones you thought of:

| Dimension | Question | Examples |
|---|---|---|
| **Completeness** | is anything missing? | NULL emails, missing days in a time series, a partition that didn't load |
| **Validity** | do values follow the rules? | negative quantities, malformed emails, dates in 2099, a price stored as `"EUR 129.99"` |
| **Uniqueness** | are entities duplicated? | the same order loaded twice, a customer registered with two IDs |
| **Consistency** | do representations agree? | `AR` vs `Argentina`, `shipped` vs `SHIPPED `, UTC vs local time |
| **Integrity** | do references resolve? | orders pointing to customers that don't exist (orphans) |
| **Timeliness** | is it fresh? | yesterday's partition still missing at 9 AM (15.3) |
| **Accuracy** | does it match reality? | a price that's valid-looking but wrong. The hardest one: no check inside the data can prove it |

## Profile before you trust

The first thing to do with any new dataset, before modeling anything:

- Shape, dtypes, memory (`df.info()`), and whether dtypes are what they should be (a numeric column read as strings is a clue).
- Per column: null fraction, number of distinct values, min/max, most frequent values. DuckDB's `SUMMARIZE` and `df.describe(include="all")` do this in one
  line.
- Keys: are the supposed primary keys unique? Do foreign keys resolve?
- Distributions: histograms of numeric columns (on log scales for skewed ones, 04.1), bar charts of categorical ones. Spikes at suspicious values (0,
  -1, 999, 9999, 1970-01-01, 1900-01-01) are almost always sentinel values meaning "missing" or "unknown", from some system that couldn't store NULL.
- Time: row counts per day. Gaps and sudden jumps are pipeline incidents or tracking changes, and they'll show up as fake "trends" in any model trained on
  them.

## Missing data

How to handle missing values depends on **why** they're missing (Rubin's classification):

- **MCAR** (missing completely at random): the missingness is unrelated to anything. Dropping rows loses data but doesn't bias results. Rare in practice.
- **MAR** (missing at random): missingness depends on *observed* variables (income is missing more often for younger customers, and you know their age).
  Imputation using those variables can correct for it.
- **MNAR** (missing not at random): missingness depends on the missing value itself (people with very high incomes decline to answer). No method using only
  the observed data can fully fix this; you need assumptions or external information.

Practical options:

- **Drop** rows or columns: fine when few are affected and MCAR is plausible. Know how many rows you drop and report it.
- **Impute**: a constant, the median, a model-based estimate. For ML, always fit imputers on training data only (18.4) and consider adding a **missing
  indicator** column, because the fact that a value is missing is often predictive by itself (a missing "last login" means "never logged in").
- **Leave it**: gradient boosting libraries (20.4) handle NaN natively and learn which side of a split missing values should go to. Sometimes the best
  cleaning is none.

What you must never do is fill with 0 or -1 silently in a numeric column where 0 is a legitimate value. That creates a fake spike, a fake relationship, and a
bug that will be very hard to find later.

## Duplicates

- **Exact duplicates**: identical rows, often from a retried load (a pipeline that ran twice, 13.1). Easy to find (`duplicated()`), but first ask whether they're
  really duplicates: two identical order lines might be two legitimate purchases. That's why events need an ID.
- **Key duplicates**: the same primary key twice with different values. Something upstream is broken; decide which version wins (the latest `updated_at`,
  08.2's latest-row pattern) and fix the source.
- **Entity duplicates** (record linkage): the same real-world entity with different keys: a customer who signed up twice, with `ana.garcia@x.com` and
  ` ANA.GARCIA@X.COM `. Normalize (trim, lowercase, remove punctuation, canonical formats) and match on normalized keys; for fuzzier cases, blocking plus a
  similarity measure (edit distance from 07.1, token overlap) and a threshold, ideally reviewed by a human for the ambiguous pairs. At scale, this is its own
  discipline (entity resolution), and it's an area where small ML models and even LLMs are genuinely useful, with human review.

## Standardization

Make equal things look equal: trim whitespace, normalize case, map synonyms to canonical codes (`Argentina` → `AR`, using ISO standards where they exist),
parse numbers out of strings (and decide what to do with the currency), convert units, and put all timestamps in UTC with explicit time zones. Do it in **one
place**, early in the pipeline (the "silver" layer of 11.2), with mapping tables that are version-controlled, not in ad-hoc fixes scattered across notebooks.

## Outliers

An outlier is either an error or the most interesting data point in your dataset, and your job is to find out which. A quantity of 9999 in an order line is
almost certainly a test order or a typo. A single customer who spends 100x the median might be your best enterprise client. Techniques:

- Domain rules (quantity must be between 1 and 100; latency can't be negative).
- Robust statistics: flag values beyond, say, 5 median absolute deviations from the median, or outside Tukey's fences (Q1 - 3·IQR, Q3 + 3·IQR). Robust because,
  unlike mean and standard deviation, they aren't dragged by the outliers themselves.
- For multivariate outliers, the methods in 23.3.

Then decide per case: fix, cap (winsorize), drop, or keep and flag. And document the decision.

## Expectations as code

The most important idea of this lesson: **every assumption you make about the data should be an executable check.** Not a comment, not a line in a wiki: a
test that runs every time the data is loaded and fails loudly (or quarantines bad rows) when violated.

```python
checks = [
    ("customers.customer_id unique",       customers["customer_id"].is_unique),
    ("customers.email valid or null",      customers["email"].isna() | customers["email"].str.match(EMAIL_RE)),
    ("order_items.quantity in [1, 100]",   order_items["quantity"].between(1, 100)),
    ("orders.customer_id exists",          orders["customer_id"].isin(customers["customer_id"])),
    ("signup_date not in the future",      customers["signup_date"] <= pd.Timestamp.now()),
]
```

Tools that formalize this: **Great Expectations** and **Soda** (declarative checks with reports), **pandera** (schemas for DataFrames, typed and
validated), **dbt tests** (13.3: `unique`, `not_null`, `accepted_values`, `relationships`, and custom SQL tests), and warehouse-native constraints where they're
enforced. The tool matters less than the habit.

Two policies for failures:

- **Fail the pipeline** (stop, alert, don't publish): for violations that make everything downstream untrustworthy (a primary key that's no longer unique, a
  missing partition, a schema change).
- **Quarantine** (route bad rows to a side table, continue with the good ones, alert): for row-level problems where partial data is better than none. Monitor
  the quarantine rate: a sudden jump is an incident even if the pipeline is "green".

## Cleaning without destroying evidence

Some rules I follow, learned the expensive way:

- **Never modify raw data in place.** Keep the raw layer immutable ("bronze", 11.2) and write cleaned data to a new layer. When a cleaning rule turns out to
  be wrong (and one will), you can re-run it.
- **Make cleaning deterministic and idempotent**: the same input gives the same output, and running it twice changes nothing (13.1).
- **Log what you changed**: counts of rows dropped, values imputed, duplicates merged, per rule, per run. A cleaning step that silently drops 30% of the data
  one day is a disaster disguised as a success.
- **Fix at the source when you can.** Every cleaning rule is a workaround for a bug somewhere upstream. Report it. Data contracts (15.2) formalize this.

> **Scar tissue.** A friend who sells used hardware asked me to automate his price lists, and one week the total value of his stock went
> up by a factor of a hundred. His new spreadsheet export wrote prices with a decimal comma and a thousands dot, `1.234,56`, and my
> parser, being helpful, read some rows as 1.234 and others as 123456. No error, because every value was a valid number. A range check on
> unit prices, the kind of test everybody agrees is obvious and nobody writes, would have stopped it at the door. I added it the next day.
> It has fired four times since.

## Things that will bite you

- **Sentinel values** (0, -1, 999, 1970-01-01) treated as real data.
- **Silent imputation** that creates fake patterns.
- **Deduplicating legitimate repeated events** because they happen to look identical.
- **Cleaning rules that drift** away from reality as the source system changes, with nobody checking the counts.
- **Checks that only run in notebooks**, once, and never again.
