# 11.2 Lakes, warehouses and lakehouses

*About 10 hours. Prerequisites: 11.1, 08.4. Lab: [`lab_11_2_lakehouse.py`](labs/lab_11_2_lakehouse.py).*

The history of analytical storage in three sentences: first we put everything in expensive, rigid **data warehouses**;
then we dumped everything as files into cheap, flexible **data lakes** and discovered they turn into swamps; then we
added a metadata layer on top of the lake files to get warehouse-like guarantees back, and called it a **lakehouse**.
Each step fixed the previous one's biggest problem and introduced a new one. Knowing why each exists lets you design a
platform instead of copying a vendor's architecture diagram.

The lab builds a toy table format from scratch (Parquet files plus a transaction log) so you can see exactly how Iceberg
and Delta Lake give you transactions on top of dumb object storage. It's the most enlightening hour in this part of the
course, I think, because it takes the air out of a lot of marketing.

## Object storage

Cloud data platforms sit on **object storage**: Amazon S3, Google Cloud Storage, Azure Blob Storage (and S3-compatible systems like MinIO). It's not a
filesystem, and the differences matter:

- You store **objects** (immutable blobs of bytes) under **keys** (strings that look like paths: `lake/orders/date=2025-03-01/part-0001.parquet`). There are
  no real directories; "folders" are key prefixes.
- **Objects are immutable.** You can't append to or modify an object; you replace it entirely.
- **No atomic rename** of a "directory". Renaming means copying every object and deleting the originals, non-atomically. Classic Hadoop-era tools relied on
  atomic directory renames to commit job outputs, and on object storage that assumption breaks, which is one of the reasons table formats exist.
- **Listing is slow and costs money** (paginated API calls). A table with a million small files takes a long time just to *list*.
- **Strong read-after-write consistency** is now standard on the major clouds (S3 since late 2020), but many tools were designed around the older eventual
  consistency, and their workarounds are still around.
- It's **cheap, durable** (eleven nines is the common claim) and **scales without limit**. That's why everything ends up there.

Security note from someone who's done cloud assessments: misconfigured buckets (public read, or "any authenticated AWS user", which means anyone on the
internet with an AWS account) are one of the most common causes of data breaches, full stop. Block public access at the account level, grant access by role
(15.1), encrypt, and log access.

## Data warehouses

A warehouse (Snowflake, BigQuery, Redshift, Synapse, and on-premises Teradata and friends) is a managed analytical database: you load data, it stores it in
its own optimized columnar format, and you query it with SQL. Strengths: fast, ACID, governance built in (permissions, auditing), easy for analysts. Modern
cloud warehouses **separate storage and compute**: data sits in object storage underneath, and compute clusters scale independently, even to zero.

Weaknesses: the data lives in the vendor's format (other engines can't read it directly, or only through export or special connectors), it can get expensive
at scale, and it's awkward for unstructured data (images, audio, raw logs) and for ML workloads that want to read training data with Python engines.

## Data lakes

A lake stores files (Parquet, JSON, CSV, images, anything) in object storage, organized by convention, and lets any engine (Spark, Presto/Trino, DuckDB,
Python) read them. Cheap, open, flexible, great for raw data and ML.

The problems, which every honest postmortem on the subject lists in roughly this order:

1. **No transactions.** A job that writes 200 files and crashes after 120 leaves a half-written table that readers happily read. Two jobs writing the same
   table at once corrupt it.
2. **No updates or deletes.** Files are immutable, so deleting one customer's data (a GDPR request, 15.2) means rewriting every file that contains them, by
   hand.
3. **No schema enforcement.** Someone writes a file with a different schema into the same folder, and every reader breaks, or worse, silently reads NULLs.
4. **Small files.** Streaming jobs and frequent small batches produce thousands of tiny files; listing and opening them dominates query time.
5. **No history.** You can't ask "what did this table look like yesterday?", or undo a bad write.
6. **Nobody knows what's in it.** Without a catalog and ownership, the lake becomes the famous swamp.

## Partitioning, and the small files problem

The lake's main performance tool is **partitioning**: organize files by the values of a column you commonly filter on, usually a date, in **Hive-style**
paths:

```
orders/order_date=2025-03-01/part-0.parquet
orders/order_date=2025-03-02/part-0.parquet
```

A query with `WHERE order_date >= '2025-03-02'` skips whole directories without opening them (**partition pruning**). Good partition columns have low to
moderate cardinality and appear in most filters. Bad ones: high-cardinality columns (`user_id` creates millions of tiny partitions), or columns nobody filters
on.

Rules of thumb: aim for files of a few hundred MB, partitions that each hold at least one decent-sized file, and a total number of files you can list in
seconds. When streaming or frequent appends create small files, run **compaction**: periodically rewrite many small files into fewer big ones. Within
partitions, **sort or cluster** by other common filter columns so Parquet statistics can skip row groups (11.1).

## Table formats: the lakehouse

**Apache Iceberg**, **Delta Lake** and **Apache Hudi** solve the lake's problems with the same core idea: keep the data files immutable in object storage, and
add a **metadata layer** that says exactly which files make up the table at each version.

How it works (simplified, and it's what the lab implements):

1. Data is written as new Parquet files. Existing files are **never modified**.
2. Each change to the table (append, delete, update, schema change, compaction) produces a new **snapshot**: a metadata file listing the data files that
   belong to the table in that version (plus schema, partition spec, statistics).
3. A commit is the **atomic swap of a single pointer** from the current snapshot to the new one. In Delta Lake, it's writing the next numbered JSON file in
   `_delta_log/` (the write fails if that number already exists: an atomic "put if absent"). In Iceberg, it's an atomic compare-and-swap of the table's
   current-metadata location in a **catalog** (Hive Metastore, AWS Glue, Nessie, Polaris, a REST catalog).
4. Readers read the current snapshot's file list. They never see half-written data, because files not referenced by a committed snapshot are invisible.

What falls out of this design:

- **ACID transactions** on object storage, with **optimistic concurrency**: two writers both try to commit version N+1; one wins, the other detects the
  conflict, checks whether the changes overlap, and retries on top of the new version (the same optimistic idea as 08.4's version column).
- **Updates and deletes**: rewrite only the affected files (copy-on-write), or write small "delete files" that mark rows as deleted and merge them at read
  time (merge-on-read). `DELETE FROM customers WHERE id = 42` becomes possible, which you need for the right to erasure.
- **Time travel**: old snapshots still point to old files, so you can query the table "as of" a version or timestamp, and roll back a bad write.
- **Schema evolution** (add, rename, drop columns via column IDs, not positions) and, in Iceberg, **partition evolution** (change the partitioning scheme
  without rewriting old data).
- **Statistics in metadata**: min/max per file lets engines skip files without opening them, even without Hive-style partition directories.
- **Maintenance**: old snapshots and unreferenced files accumulate, so you **expire snapshots** and **vacuum** orphan files periodically. Note the interaction
  with deletes: after `DELETE`, the deleted rows still exist in old files until those snapshots are expired and files vacuumed. For GDPR, the delete isn't done
  until the vacuum is.

The practical result: open file formats in cheap storage, readable by many engines, with most warehouse guarantees. Warehouses have responded by reading and
writing Iceberg natively, so the line keeps blurring.

## The medallion architecture

A common way to organize a lakehouse (the name comes from Databricks, the idea is older) is in layers of increasing quality:

- **Bronze (raw)**: data as it arrived, append-only, with ingestion metadata (source, load time, file name). Never modified. It's your insurance: any bug
  downstream can be fixed by reprocessing from bronze.
- **Silver (clean, conformed)**: validated, deduplicated, standardized, typed (10.3), with bad rows quarantined. Entities and events at their natural grain,
  joined to reference data.
- **Gold (business-level)**: aggregated and modeled for consumption: dimensional models (09.2), metrics tables, feature tables for ML, datasets for specific
  dashboards.

It's a useful convention, not a law. The principles underneath are what matter: keep raw data immutable, make each layer reproducible from the one before,
put quality checks between layers, and give consumers stable, documented tables in the top layer.

## Choosing, in practice

- Small team, analysts first, structured data: a cloud **warehouse** (or DuckDB/MotherDuck for small scale), with dbt (13.3). Least operational burden.
- Large or diverse data (logs, images, ML at scale), multiple engines, cost pressure: a **lakehouse** on object storage with Iceberg or Delta, a catalog, and
  Spark/Trino/DuckDB as engines.
- Many companies run both: lakehouse for raw and ML-heavy data, warehouse for curated business reporting, increasingly over the same Iceberg tables.

## Things that will bite you

- **Public or overly permissive buckets.**
- **Partitioning by high-cardinality columns** and the small files that follow.
- **Readers bypassing the table format** and listing files directly (they'll read uncommitted or deleted files).
- **Forgetting maintenance**: snapshots and orphan files pile up, costs grow, and deleted personal data lingers.
- **Treating bronze as mutable.**

## Exercises

1. Why can't a data lake of plain Parquet files give readers a consistent view while a job is writing to it? How does a table format fix it?
2. You partition an events table by `user_id` (5 million users) and by day. What happens to query performance and why? What would you do instead?
3. Two jobs append to the same Delta/Iceberg table at the same moment. Walk through what happens at commit time.
4. A customer invokes the right to erasure. You run `DELETE FROM events WHERE customer_id = 42` on an Iceberg table. When is their data actually gone from
   storage?
5. Describe what goes in bronze, silver and gold for the shop's clickstream.

<summary>Answers</summary>

1. Readers list the directory and read whatever files are there, including files from a job that has written some outputs but not finished (or failed). There's
   no notion of "committed". A table format makes the set of files that constitute the table explicit in a snapshot, and publishes a new snapshot atomically
   only after all files are written, so readers see either the old version or the new one, never a mix.

2. Millions of partitions, each with tiny files: listing and planning dominate, the metadata explodes, and each file is too small to read efficiently.
   Partition by day only (or by day and a small bucket of user_id, e.g. `hash(user_id) % 16`), and sort/cluster by `user_id` within partitions so file statistics
   can skip files for user lookups.

3. Both read snapshot N and write their data files. Both try to commit snapshot N+1. One succeeds (atomic put-if-absent or compare-and-swap). The other fails the
   commit, re-reads the new current snapshot (N+1), checks for conflicts (two appends don't conflict), and retries by committing N+2 including its files. For
   conflicting operations (both rewrote the same files, e.g. two updates of the same rows), the second one fails and must be re-run.

4. The DELETE creates a new snapshot without those rows (rewritten files or delete files). The old snapshots, still retained for time travel, reference files that
   contain the rows. The data is physically gone only after you expire the old snapshots (beyond your retention period) and remove the files no longer referenced
   (and after storage-level versioning/backups age out, if enabled). Your erasure process must include those steps and their timing.

5. Bronze: raw events as received (JSON), plus ingestion time and source, append-only. Silver: parsed, typed events (Parquet), deduplicated by event ID, bots
   filtered, timestamps in UTC, invalid events quarantined, product IDs validated against the products table; maybe sessionized (08.2). Gold: daily metrics
   (sessions, conversion funnel per channel), customer-level features (views in the last 7 days, last active time) for ML, and a funnel table for the product
   dashboard.
