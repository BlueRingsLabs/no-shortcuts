# 13.2 Orchestration with Airflow and Dagster

*About 10 hours. Prerequisites: 13.1, 07.1 (topological sort), 07.4. Lab: [`lab_13_2_orchestrator.py`](labs/lab_13_2_orchestrator.py).*

Cron can run a script at 2 AM. It can't tell you that the script failed, retry it with backoff, wait until the upstream
export has landed, run the forty downstream tasks in the right order and in parallel, skip the ones whose inputs failed,
re-run all of it for the last ninety days when the logic changes, and show you, the next morning, a picture of what happened
and why. That's what an **orchestrator** does, and every data platform above toy size has one.

The two you're most likely to meet are **Apache Airflow** (the incumbent, everywhere) and **Dagster** (asset-oriented, popular in
newer stacks), with Prefect and cloud-native options (AWS Step Functions, Google Cloud Composer, which is managed Airflow) around
them. The concepts transfer. The lab builds a small orchestrator from scratch, so that when Airflow does something surprising, you
know what it was trying to do.

## What an orchestrator does

1. **Dependencies as a DAG.** Tasks and the edges between them; execution follows a topological order (07.1), running independent tasks in parallel.
2. **Scheduling with logical dates.** Each run covers a **data interval** (for a daily DAG, "the day 2025-03-14"), passed to tasks as a parameter so
   that runs are reproducible and backfillable (13.1).
3. **Retries** with delays and backoff for transient failures, and **failure propagation**: tasks downstream of a failed task are marked "upstream
   failed" instead of running on missing inputs.
4. **Backfills and catch-up**: running the DAG for a range of past intervals, with limited concurrency.
5. **Sensors and triggers**: wait for a file, a partition, an external job, or an event before running.
6. **Resource control**: pools and concurrency limits, so a backfill doesn't open 500 connections to the production database.
7. **Observability**: a UI with the state of every task for every interval, logs, durations, SLAs and alerts (15.3).

What an orchestrator should **not** do: heavy computation inside the scheduler process. The orchestrator tells Spark, the warehouse, dbt or a container
to do the work, and waits. Airflow workers that load 10 GB DataFrames into memory are a classic anti-pattern that ends with an OOM-killed scheduler at
3 AM.

## Airflow

Core concepts:

- A **DAG** is defined in a Python file: tasks and dependencies, a schedule, a start date, default arguments (retries, owner).
- **Operators** are task templates: `BashOperator`, `PythonOperator`, `SQLExecuteQueryOperator`, provider operators for every cloud service, and
  `KubernetesPodOperator` (run any container: the most flexible and the most isolated option).
- The **TaskFlow API** (`@dag`, `@task`) lets you write Python tasks as decorated functions, passing small values between them via **XCom**.
- **Data intervals**: a daily DAG run for 2025-03-14 starts *after* that day ends, and templates like `{{ ds }}` or `data_interval_start` give tasks their
  logical date. (This off-by-one surprises everyone once.)
- **catchup**: when enabled, a DAG with a start date in the past runs once for every missed interval. Usually you want `catchup=False` and explicit
  backfills.
- **Executors** decide where tasks run: `LocalExecutor`, `CeleryExecutor` (worker pool), `KubernetesExecutor` (one pod per task).
- Recent versions add **datasets / assets** for data-aware scheduling (run this DAG when that table is updated).

```python
from datetime import datetime, timedelta
from airflow.decorators import dag, task


@dag(schedule="@daily", start_date=datetime(2025, 1, 1), catchup=False,
     default_args={"retries": 3, "retry_delay": timedelta(minutes=5), "retry_exponential_backoff": True},
     tags=["shop"])
def shop_daily():

    @task
    def extract_orders(ds=None):                 # ds: the logical date, injected by Airflow
        return run_extraction(date=ds)           # returns a small summary (paths, counts), NOT the data

    @task
    def validate(summary: dict):
        check_row_counts(summary)                # fail loudly (10.3)

    @task
    def build_marts(ds=None):
        run_dbt(select="marts", vars={"ds": ds}) # the heavy lifting happens in the warehouse

    summary = extract_orders()
    validate(summary) >> build_marts()


shop_daily()
```

Airflow habits that save pain:

- **Keep DAG files cheap to parse.** The scheduler re-parses them constantly; no database queries or heavy imports at module level.
- **XCom is for metadata, not data.** Pass paths and counts, not DataFrames.
- **Idempotent tasks, parameterized by the logical date** (13.1). Then retries and backfills just work.
- **Use pools** to limit concurrency against fragile systems.
- **Secrets from a secrets backend or connections**, not hard-coded in DAG files (15.1). DAG repositories are read by many people.

## Dagster and the asset view

Dagster flips the perspective from *tasks* to **assets**: you declare the tables, files and models your platform produces, and the code that computes each
from its upstream assets. The orchestrator derives the DAG from the asset dependencies.

```python
import dagster as dg

daily = dg.DailyPartitionsDefinition(start_date="2025-01-01")


@dg.asset(partitions_def=daily)
def raw_orders(context: dg.AssetExecutionContext) -> None:
    extract_orders(date=context.partition_key)


@dg.asset(partitions_def=daily, deps=[raw_orders])
def daily_revenue(context: dg.AssetExecutionContext) -> None:
    build_revenue(date=context.partition_key)
```

Why it's attractive: the thing you care about (is `daily_revenue` for March fresh and correct?) is the first-class object; lineage, freshness checks and
"materialize only what's stale" come naturally; partitions map directly to 13.1's logical dates; and assets can carry data quality checks. Airflow has been
moving toward similar ideas with its asset scheduling. Either way, think in assets: what data exists, what it depends on, and how fresh it must be.

## Choosing and operating

- **Airflow** if your company already runs it (likely), or you need its enormous library of integrations. Managed versions (Cloud Composer, Amazon MWAA,
  Astronomer) remove much of the operational burden.
- **Dagster** for new platforms that want asset lineage and data quality baked in.
- **Simpler options** (a managed scheduler that runs containers, GitHub Actions on a cron for tiny jobs, dbt Cloud's scheduler for pure-dbt shops) when
  the workflow is simple. Don't run an orchestrator you don't need.

Whatever you choose: version DAGs/assets in Git with code review and CI, test them (at least that they load and that the dependency graph is what you
think), and alert on failures and on **missed SLAs** (a DAG that silently didn't run is worse than one that failed loudly).

## Things that will bite you

- **The logical date off-by-one** (a daily run for day D runs after D ends).
- **Unintended catchup** creating hundreds of runs when you deploy a DAG with an old start date.
- **Heavy work in the orchestrator's workers or at DAG parse time.**
- **XCom used for data.**
- **Non-idempotent tasks**, turning automatic retries into duplicates.
- **Silent non-runs**: a paused DAG, a scheduler down. Monitor freshness of outputs, not only task failures (15.3).

## Exercises

1. Draw the DAG for: extract orders, extract customers, extract products (independent); validate each; build `fact_sales` (needs orders and products) and
   `dim_customer` (needs customers); build a revenue dashboard table (needs both). Which tasks can run in parallel?
2. A daily Airflow DAG has `start_date=2025-01-01`, `catchup=True`, and is deployed on 2025-09-01. What happens? What would you do instead?
3. `extract_orders` failed after three retries. What state do `validate`, `build_marts` and the independent `extract_products` end up in?
4. Rewrite exercise 1 as Dagster assets. What do you gain?
5. Why must a task use `ds` (the logical date) rather than `datetime.now()`?

<details>
<summary>Answers</summary>

1. Level 0: the three extracts, in parallel. Level 1: the three validations (each after its extract), in parallel. Level 2: `fact_sales` (after orders and
   products validations) and `dim_customer` (after customers validation), in parallel. Level 3: the dashboard table. The lab's orchestrator computes these levels.

2. Airflow schedules a run for every day from 2025-01-01 to 2025-08-31, about 243 runs, immediately (subject to concurrency limits). That can hammer sources and
   the warehouse. Instead: `catchup=False` (only the latest interval runs), and trigger an explicit, throttled backfill for the historical range if you need it.

3. `validate` and `build_marts` become `upstream_failed` and don't run. `extract_products` (and anything depending only on it) runs normally. The DAG run is
   marked failed.

4. Assets `raw_orders`, `raw_customers`, `raw_products` (maybe with asset checks for validation), `fact_sales` (deps orders, products), `dim_customer` (deps
   customers), `revenue_dashboard` (deps both). You gain: lineage and freshness per table, partitioned materialization (backfill "March of `fact_sales`" and
   see exactly which downstream partitions are stale), and checks attached to the data rather than to tasks.

5. With `now()`, the task's output depends on when it runs, so retries, delayed runs and backfills compute the wrong interval. With `ds`, every run for a given
   interval computes the same slice (13.1's idempotency and reproducibility).

</details>
