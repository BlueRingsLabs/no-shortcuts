# 13.1 ETL, ELT, idempotency and backfills

*About 10 hours. Prerequisites: Modules 08 to 11. Lab: [`lab_13_1_incremental_loads.py`](labs/lab_13_1_incremental_loads.py).*

The first data pipeline most people write is a script that reads from a database and appends to a table, scheduled with
cron at 2 AM. It works for three weeks. Then one night it fails halfway, someone re-runs it in the morning, and now half of
yesterday's data is in the table twice. Or the source database was slow, the extraction missed rows that were committed a
second too late, and nobody finds out until the monthly report is off by 0.3%. Or the business asks for last year's data to
be recomputed with a new rule, and there's no way to re-run the pipeline for a past date.

None of that is exotic. It's what happens to pipelines that weren't designed to be **re-run**. This lesson is about the
properties that make a pipeline safe to operate: idempotency, incremental processing done right, and backfills. They're the
difference between a data engineer who sleeps and one who doesn't.

## ETL vs ELT

- **ETL** (extract, transform, load): extract from sources, transform in a separate processing layer (a Spark job, a Python script), load the
  finished result into the warehouse. Traditional when warehouse compute was expensive and limited.
- **ELT** (extract, load, transform): load raw data into the warehouse or lakehouse first (bronze, 11.2), then transform it *inside* with SQL
  (dbt, 13.3). The modern default, because warehouse compute is elastic and SQL is the lingua franca, and because keeping the raw data lets you
  re-transform any time.

In practice you do both: light transformations on the way in (parsing, typing, PII masking before data lands anywhere, 15.2), heavier modeling
after loading. The principles below apply either way.

## Idempotency

A task is **idempotent** if running it once or several times with the same inputs produces the same result. You've seen the idea in HTTP (07.4)
and in retries (01.1). In pipelines it's the property that makes failures boring:

- A task failed halfway? Re-run it.
- Not sure whether it ran? Run it again.
- The orchestrator retried it automatically after a timeout, but the first attempt actually succeeded? No harm done.

How to build idempotent loads:

1. **Overwrite, don't append.** Each run writes a well-defined slice of the target (a date partition), replacing whatever was there. Running it
   twice writes the same slice twice. With table formats (11.2) or warehouses, `INSERT OVERWRITE ... PARTITION (date = ...)` or `DELETE WHERE date
   = ... ; INSERT ...` in one transaction.
2. **Upsert (MERGE) by key.** For entity tables, `MERGE INTO target USING staged ON target.id = staged.id WHEN MATCHED THEN UPDATE WHEN NOT MATCHED
   THEN INSERT`. Applying the same batch twice leaves the table unchanged.
3. **Deduplicate by event ID** on the way in, for event streams where the source may redeliver (Kafka's at-least-once delivery, 14.1).
4. **Parameterize runs by logical date**, not by "now". A task that processes "yesterday" computed from `datetime.now()` gives a different answer
   depending on when it runs, including when you re-run it next week. The run's **logical date** (Airflow calls it the data interval) must be an
   input.
5. **No side effects outside the target** that can't be repeated (sending emails, calling payment APIs), or guard them with idempotency keys.

## Incremental extraction

Full reloads (copy the whole source table every night) are simple and correct, and you should do them as long as they're cheap enough. When the
table gets too big, you extract only what changed. The options:

**Watermark on `updated_at`**: `SELECT * FROM orders WHERE updated_at > :last_watermark`. Simple, and full of traps:

- **Late commits and clock skew**: a transaction that started before your extraction, with an `updated_at` before the watermark, commits after
  it. Next run filters it out. Lost forever. Replica lag (08.4) causes the same problem.
- **Missing updates to `updated_at`**: some code path updates rows without touching `updated_at` (a bulk fix run by hand, a trigger that's missing).
- **Hard deletes are invisible**: a deleted row just stops appearing, and your target keeps it.

Mitigations: **overlap the window** (extract from `watermark - margin`, say one hour or one day) and deduplicate by key with MERGE, so re-extracting
rows is harmless; periodic full reconciliation (compare counts or checksums per partition between source and target, reload what differs); soft
deletes in the source.

**Change data capture (CDC)** reads the database's transaction log (PostgreSQL WAL, MySQL binlog) and emits every insert, update and delete in commit
order (Debezium is the common open-source tool). No missed updates, no invisible deletes, low load on the source. More infrastructure. It's the
right answer for important tables once you have streaming infrastructure (14.1, 14.2).

**Event data** (clickstreams, logs) is append-only by nature: incremental by event time or ingestion time, with deduplication by event ID and a policy
for late events (14.2).

## Backfills

A **backfill** re-runs a pipeline for past periods: because it's new, because logic changed, because a bug corrupted a range of dates, or because the
source re-delivered historical data. If your pipeline is idempotent and parameterized by logical date, a backfill is just "run it for each date in the
range", and orchestrators do exactly that (13.2).

Backfill hygiene:

- **Recompute downstream dependencies** too: if you fix `silver.orders` for March, every gold table built from March's orders is now stale.
  Orchestrators and dbt track dependencies to help (13.2, 13.3).
- **Mind the load on sources**: backfilling two years from a production database at full parallelism is a denial of service. Throttle.
- **Mind non-deterministic logic**: if a transformation uses "current" dimension values (09.2) or `now()`, a backfill today produces different results
  than the original run did. Sometimes that's what you want; decide consciously.
- **Keep raw data** (bronze): you can only backfill from data you still have.

## Designing a pipeline step

A checklist I use for every task:

- **Inputs and outputs**: exactly which slice of which tables it reads and writes, as a function of the logical date.
- **Idempotent write**: overwrite a partition or merge by key.
- **Atomic publish**: readers see the old data or the new data, never half (write to a staging location or table, then swap; or use a table format's
  transaction).
- **Validation before publish** (10.3): row counts, uniqueness, null rates, freshness; fail or quarantine.
- **Observability** (15.3): log rows read and written, duration, watermark used.
- **Retries** with backoff for transient errors, and a clear failure otherwise (07.4).

> **Scar tissue.** A side project of mine collected prices every day into a small database on a $5 VPS. One day the job failed halfway, I
> reran it, and doubled that day's volume in every chart. The load step appended. It had always appended; it had simply never been run
> twice for the same day. The fix was a delete-and-insert on the day's partition in one transaction, and a rule I've kept ever since:
> every job must be safe to run twice, because it will be, usually by a tired person, usually in a hurry. In my case, the tired person is
> always me.

## Things that will bite you

- **Appending on every run**, and duplicates after the first retry.
- **`now()` inside transformations** instead of the logical date.
- **Watermarks without overlap**, silently losing late-committed rows.
- **Invisible hard deletes** in incremental loads.
- **Backfills that don't propagate downstream**, leaving gold tables stale.
- **Publishing before validating.**

## Exercises

1. A task does `INSERT INTO daily_revenue SELECT date, SUM(amount) FROM orders WHERE date = '{ds}' GROUP BY date`. Make it idempotent in two different
   ways.
2. Your watermark-based extraction runs hourly with `updated_at > last_run_start`. Describe a concrete interleaving where a row is lost, and fix it.
3. The source deletes cancelled orders physically after 30 days. Your incremental pipeline never notices. How would you detect and handle it?
4. Marketing asks to recompute two years of attribution with a new rule. Your pipeline processes one day per run and takes 10 minutes. What do you check
   before launching the backfill, and how do you run it?
5. Why is "extract everything, then deduplicate by key keeping the latest `updated_at`" idempotent even if the extraction window overlaps previous runs?

<details>
<summary>Answers</summary>

1. (a) In one transaction: `DELETE FROM daily_revenue WHERE date = '{ds}'; INSERT ...`. (b) `MERGE INTO daily_revenue t USING (SELECT ...) s ON t.date = s.date
   WHEN MATCHED THEN UPDATE SET revenue = s.revenue WHEN NOT MATCHED THEN INSERT ...`. Or overwrite the partition for `{ds}` in a table format.

2. At 10:59:58 a long transaction updates row R, setting `updated_at = 10:59:58`, but commits at 11:00:05. The 11:00:00 run starts, doesn't see R (not
   committed), records `last_run_start = 11:00:00`. The 12:00 run looks for `updated_at > 11:00:00`: R's is 10:59:58, so it's skipped forever. Fix: overlap
   (extract `updated_at > last_watermark - 1 hour`), set the watermark from the maximum `updated_at` actually seen rather than the run's start time, and MERGE by
   key so re-extracted rows are harmless. Or use CDC.

3. Detect with periodic reconciliation: compare the set (or count, or checksum) of keys per partition between source and target; keys in the target but not in
   the source were deleted. Handle by applying deletes (or marking them `is_deleted`), or switch to CDC, which emits deletes. Better still, ask the source team
   for soft deletes or a deletion log.

4. Check: that the logic is parameterized by logical date and idempotent; that raw data for two years still exists; the load on sources and on the warehouse
   (throttle concurrency); cost; that downstream tables will be recomputed; that the new rule doesn't depend on current-state data that differs from the past;
   and communicate that numbers will change. Run it through the orchestrator's backfill command with limited parallelism (say 4-8 dates at a time), oldest first
   or newest first depending on what the business needs first, and validate a sample of dates against expectations.

5. The final state of each key depends only on the set of versions seen, not on how many times each was seen or in which run: "latest `updated_at` per key" is
   the same whether a version appears once or three times. Processing the same data again changes nothing, which is the definition of idempotent.
