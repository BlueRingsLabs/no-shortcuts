# 13.3 Transformations and tests with dbt

*About 10 hours. Prerequisites: Module 08, 09.2, 13.1. Lab: [`lab_13_3_dbt.py`](labs/lab_13_3_dbt.py).*

For years, the transformation layer of most data warehouses was a folder of SQL scripts with names like
`final_v2_FIXED_use_this.sql`, run in an order that lived in one person's head, with no tests, no documentation and no
version control. Then that person went on holiday. **dbt** (data build tool) became the standard not because it does
anything SQL can't, but because it brings software engineering to SQL: version control, modularity, dependency management,
testing, documentation, environments and code review. It's the "T" in ELT for most modern teams, and "dbt" appears in a
large fraction of Data Engineer and Analytics Engineer job postings.

## The idea

A dbt project is a folder of **models**: each model is a `SELECT` statement in a `.sql` file. dbt:

1. Resolves references between models (`{{ ref('stg_orders') }}`) and to raw tables (`{{ source('raw', 'orders') }}`) into real table names
   for the current environment.
2. Builds the **dependency graph** from those references (the same DAG idea as 13.2) and runs models in topological order, in parallel where
   possible.
3. **Materializes** each model as a view, a table, an incremental table or an ephemeral CTE, according to its configuration.
4. Runs **tests** on the results.
5. Generates **documentation** and **lineage** from the project.

You write `SELECT`s; dbt writes the `CREATE TABLE AS`, the `MERGE`, the drop-and-swap, the ordering. That's the whole trick, and it's enough to change
how teams work.

## Project structure

The layering convention (it's the medallion idea from 11.2 in SQL):

```
models/
├── sources.yml              # declares raw tables (the bronze layer), with freshness checks
├── staging/                 # one model per source table: rename, cast, clean, standardize (silver)
│   ├── stg_orders.sql
│   ├── stg_customers.sql
│   └── schema.yml           # tests and docs for staging models
├── intermediate/            # reusable joins and business logic (optional)
└── marts/                   # business-facing models: facts, dimensions, metrics (gold)
    ├── fct_orders.sql
    ├── dim_customers.sql
    └── schema.yml
```

Staging models are thin: one per source table, no joins, just making raw data usable (10.3's standardization, in one place). Marts implement the dimensional
model (09.2). A model should never read a raw table directly except through its staging model; that single rule keeps cleaning logic from being duplicated
across fifty queries.

```sql
-- models/marts/fct_orders.sql
-- grain: one row per order
select o.order_id, o.customer_id, o.order_ts, o.status,
       sum(i.amount) as order_total,
       count(*)      as n_lines
from {{ ref('stg_orders') }} o
join {{ ref('stg_order_items') }} i using (order_id)
group by all
```

Declare the grain in a comment at the top of every mart. Then test it.

## Materializations

- **view**: nothing stored; the query runs when someone reads it. Cheap to build, expensive to read. Good for staging.
- **table**: rebuilt from scratch on every run. Simple and always correct. Good default for marts until they get expensive.
- **incremental**: on the first run, a full build; on later runs, only new or changed rows are processed and merged by `unique_key`. The model's SQL uses
  `{% if is_incremental() %}` to filter to recent data, typically with an overlap window (13.1's late data problem, again). Much cheaper for big fact tables;
  harder to get right. When the logic changes, rebuild it fully (`--full-refresh`).
- **ephemeral**: inlined as a CTE into the models that reference it.
- **snapshot**: dbt's built-in implementation of **SCD type 2** (09.2): it compares a source table with its previous state and records changes with
  `dbt_valid_from` / `dbt_valid_to`.

## Tests

Tests are what make dbt worth it. **Generic tests** are declared in YAML:

```yaml
models:
  - name: stg_orders
    columns:
      - name: order_id
        data_tests: [unique, not_null]
      - name: customer_id
        data_tests:
          - relationships: {arguments: {to: ref('stg_customers'), field: customer_id}}
      - name: status
        data_tests:
          - accepted_values: {arguments: {values: ['delivered', 'shipped', 'cancelled', 'returned']}}
```

Every test is compiled into a query that returns the failing rows; zero rows means pass. So a **singular or custom test** is just a SQL query that should return
nothing ("revenue is never negative", "every order has at least one line", "daily totals match the source within 0.1%"). Packages like `dbt-expectations` add
dozens of ready-made checks in the Great Expectations style (10.3).

The minimum I put on every model: `unique` and `not_null` on the primary key (this single test catches fan-outs, 08.2, and duplicate loads), `relationships` on
foreign keys (orphans), and `accepted_values` on enumerations. Then specific tests for business rules and for the bugs you've actually had.

**`dbt build`** runs models and tests in DAG order and, most importantly, **skips everything downstream of a failed test**. Bad data stops at the first check instead of
flowing into the executive dashboard. The lab duplicates a customer and watches `dim_customers` and everything after it get skipped.

## Jinja, macros, and restraint

dbt SQL is templated with Jinja: variables (`{{ var('start_date') }}`), loops, conditionals, and **macros** (reusable SQL functions). Useful for genuinely repeated
patterns (a currency conversion used in 30 models, a standard set of audit columns). Dangerous when overused: SQL buried in three layers of macros is unreadable
and untestable. My rule: if a reviewer can't understand the compiled SQL from the source file, there's too much Jinja.

## Environments, CI and deployment

- **Targets** (in `profiles.yml`) point the same project at different schemas or databases: `dev` (your own sandbox schema), `ci`, `prod`. Everyone develops
  against their own schema, never against production.
- **CI on pull requests**: build and test the changed models and their downstream dependencies (`dbt build --select state:modified+`, comparing with the
  production manifest) in a temporary schema. Reviewers see test results before merging.
- **Production runs** are triggered by the orchestrator (13.2), usually after the extraction tasks, with the logical date passed as a variable.
- **Source freshness** checks (`dbt source freshness`) alert when raw tables stop being updated (15.3).
- **Contracts** on models (enforced column names and types) protect downstream consumers from accidental schema changes (15.2).

## Documentation and lineage

`dbt docs generate` produces a website with every model, its columns, descriptions, tests, and the lineage graph. The manifest (`target/manifest.json`) is a
machine-readable version of the whole project, which catalogs (15.2) and orchestrators (Dagster integrates dbt models as assets) consume. The lab reads it to
print each model's parents.

## Things that will bite you

- **Staging models skipped**, with marts reading raw tables and duplicating cleaning logic.
- **No uniqueness test on primary keys**: the fan-out goes straight to the dashboard.
- **Incremental models without an overlap or with a changed logic** and no full refresh: silently wrong history.
- **Everything materialized as views** in a warehouse that bills per query: every dashboard refresh recomputes the whole chain.
- **Macro soup.**
- **Developing against production.**

## Exercises

1. Write `stg_customers` for the dirty shop (10.3): trim and lowercase emails, map country names to ISO codes with a `case` or a seed table, cast types.
2. Write the YAML tests you'd put on `fct_orders` and `dim_customers`.
3. `fct_orders` is 2 billion rows and takes 40 minutes as a table. Convert it to incremental. What's the `unique_key`, what goes in the `is_incremental()` filter, and
   what overlap would you use?
4. A PR changes `stg_orders`. Which models should CI build and test, and with which dbt selector?
5. Write a singular test asserting that the sum of `order_total` in `fct_orders` equals the sum of line amounts in `stg_order_items`.

<summary>Answers</summary>

1. ```sql
   select customer_id,
          nullif(trim(lower(email)), '') as email,
          case upper(trim(country)) when 'ARGENTINA' then 'AR' when 'USA' then 'US' else upper(trim(country)) end as country,
          cast(signup_date as date) as signup_date,
          segment
   from {{ source('raw', 'customers') }}
   ```
   A seed (a small CSV of mappings versioned with the project, loaded with `dbt seed`) scales better than a growing `case`.

2. `fct_orders.order_id`: unique, not_null. `fct_orders.customer_id`: not_null, relationships to `dim_customers`. `fct_orders.status`: accepted_values.
   `fct_orders.order_total`: a custom test for `>= 0`. `dim_customers.customer_id`: unique, not_null. `dim_customers.country`: accepted_values.
   `dim_customers.email`: unique (where not null) if emails identify customers.

3. `unique_key = 'order_id'`; filter `where o.updated_at >= (select max(updated_at) from {{ this }}) - interval 3 days` (orders change status after
   creation, so filter on update time, not order time, with an overlap sized to your latest expected late updates). The `MERGE` on `order_id` makes the overlap
   harmless. Schedule periodic full refreshes (or a reconciliation test) to catch anything the window misses.

4. The changed model and everything downstream: `dbt build --select stg_orders+` (or `state:modified+` with the production manifest for `--state`, which
   detects the modified nodes automatically).

5. ```sql
   -- tests/order_totals_match_lines.sql
   with a as (select sum(order_total) as s from {{ ref('fct_orders') }}),
        b as (select sum(amount) as s from {{ ref('stg_order_items') }}
              where order_id in (select order_id from {{ ref('stg_orders') }}))
   select * from a, b where abs(a.s - b.s) > 0.01
   ```
