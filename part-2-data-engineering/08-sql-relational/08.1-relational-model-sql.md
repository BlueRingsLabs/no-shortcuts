Every few years someone announces that SQL is dead. NoSQL was going to kill it, then big data, then data lakes, then
"just ask the LLM". I've watched each of those waves arrive, and every single one ended with the new thing growing a SQL
interface. Spark has Spark SQL. Kafka has ksqlDB. Every lakehouse speaks SQL. The vector databases added SQL. The LLM
"text-to-SQL" tools generate... SQL, which you then need to be able to read to know if it's right.

SQL has survived fifty years because it's built on a solid mathematical idea (the relational model) and because it's
**declarative**: you say *what* you want, and the database figures out *how* to get it. That separation is why the same
query runs on SQLite on your laptop and on a warehouse scanning petabytes. It's the most valuable language in this
course, and in data jobs it's not optional: every Data Engineer, Data Scientist and ML Engineer posting I looked at while
designing this course asked for it.

All labs in this module use **DuckDB** (an in-process analytical database, no server needed) and **SQLite** (in Python's
standard library). The SQL is standard enough to carry over to PostgreSQL, BigQuery, Snowflake and Spark SQL, with small
dialect differences that I'll point out.

## The relational model

Edgar F. Codd proposed it in 1970, at IBM. The ideas:

- Data lives in **relations** (tables): sets of **tuples** (rows) with the same **attributes** (columns). Each attribute has a **type** (a
  domain).
- A relation is a *set*: no inherent order of rows, no duplicate rows (SQL relaxes this and allows duplicates, "bags", which is the source of
  a lot of subtle bugs).
- Rows are identified by **keys**, not by position. A **primary key** uniquely identifies a row. A **foreign key** in one table references
  the primary key of another, which is how relations connect.
- You query data with operations that take relations and return relations (**relational algebra**): selection (filter rows), projection
  (pick columns), join (combine relations), union, difference, aggregation. Because every operation returns a relation, they compose. A
  query is a pipeline of these operations.

That last point is why SQL is so expressive: the output of any query can be used as a table in another query.

## Defining tables

```sql
CREATE TABLE customers (
    customer_id  INTEGER PRIMARY KEY,
    name         VARCHAR NOT NULL,
    email        VARCHAR UNIQUE,
    country      CHAR(2),
    signup_date  DATE NOT NULL,
    segment      VARCHAR CHECK (segment IN ('consumer', 'pro', 'enterprise'))
);

CREATE TABLE orders (
    order_id     INTEGER PRIMARY KEY,
    customer_id  INTEGER NOT NULL REFERENCES customers(customer_id),
    order_ts     TIMESTAMP NOT NULL,
    status       VARCHAR NOT NULL,
    channel      VARCHAR
);
```

**Constraints are data quality you get for free.** `NOT NULL`, `UNIQUE`, `CHECK`, `PRIMARY KEY` and `REFERENCES` make the database reject bad
data at write time, instead of you discovering it at analysis time. Operational databases (PostgreSQL, MySQL) enforce them. Many analytical
warehouses *accept* the syntax but don't enforce all of it (for speed), so the guarantees you think you have may be decorative. Know which
kind you're talking to. Module 10.3 and 15.3 are about checking what the database won't.

## The shape of a query

```sql
SELECT   c.country, COUNT(*) AS n_orders, SUM(oi.quantity * oi.unit_price) AS revenue
FROM     orders o
JOIN     customers c    ON c.customer_id = o.customer_id
JOIN     order_items oi ON oi.order_id = o.order_id
WHERE    o.status = 'delivered'
GROUP BY c.country
HAVING   COUNT(*) > 100
ORDER BY revenue DESC
LIMIT    5;
```

The clauses are written in that order, but **logically evaluated in a different one**, and understanding this order explains most SQL error
messages:

1. `FROM` and `JOIN`: build the combined rows.
2. `WHERE`: filter rows (before grouping; can't use aggregates here).
3. `GROUP BY`: form groups.
4. `HAVING`: filter groups (can use aggregates).
5. `SELECT`: compute output columns (aliases are born here).
6. `DISTINCT`: remove duplicate output rows.
7. `ORDER BY`: sort (can use aliases, since SELECT already happened).
8. `LIMIT` / `OFFSET`: cut.

So you can't use a `SELECT` alias in `WHERE` (it doesn't exist yet), you can in `ORDER BY`, and "column must appear in GROUP BY or be used in
an aggregate" means you selected a column that has many values per group without saying which one you want. (Some databases, like DuckDB
and BigQuery, relax a few of these rules for convenience. Don't rely on it if the query must be portable.)

Also: **without `ORDER BY`, row order is undefined.** A query that "always" returns rows in insertion order will stop doing so the day the
table is repartitioned or the query runs in parallel. If order matters, say so.

## NULL: three-valued logic

`NULL` means "unknown" or "missing", and it's the single largest source of wrong SQL answers I've seen. SQL uses **three-valued logic**: a
comparison can be TRUE, FALSE or UNKNOWN.

- `NULL = NULL` is UNKNOWN, not TRUE. Use `IS NULL` / `IS NOT NULL` (or `IS NOT DISTINCT FROM` for null-safe equality).
- `WHERE` keeps only rows where the condition is TRUE, so rows where it's UNKNOWN silently disappear. `WHERE country <> 'AR'` does **not**
  return customers with a NULL country.
- `NOT IN` with a NULL in the list returns **nothing**: `x NOT IN (1, 2, NULL)` is `x <> 1 AND x <> 2 AND x <> NULL`, and the last part is
  UNKNOWN for every x. A subquery like `WHERE customer_id NOT IN (SELECT customer_id FROM blocked)` returns zero rows the day one NULL gets into
  `blocked`. Use `NOT EXISTS` instead, which handles NULLs sanely.
- Aggregates skip NULLs: `COUNT(col)` counts non-null values, `COUNT(*)` counts rows, `AVG(col)` is the average of the non-null values. If
  missing means zero in your business logic, `AVG(COALESCE(col, 0))` gives a different (and possibly correct) answer.
- Arithmetic with NULL gives NULL: `price * NULL` is NULL. `SUM` of a column that's all NULL is NULL, not 0.

`COALESCE(a, b, c)` returns the first non-null argument. `NULLIF(a, b)` returns NULL if `a = b`, which is the standard trick to avoid division
by zero: `revenue / NULLIF(n_orders, 0)`.

## Subqueries and CTEs

A **common table expression** (`WITH`) names an intermediate result. It's the single best tool for readable SQL:

```sql
WITH order_totals AS (
    SELECT o.order_id, o.customer_id, SUM(oi.quantity * oi.unit_price) AS total
    FROM orders o
    JOIN order_items oi USING (order_id)
    WHERE o.status NOT IN ('cancelled', 'returned')
    GROUP BY o.order_id, o.customer_id
),
customer_value AS (
    SELECT customer_id, COUNT(*) AS n_orders, SUM(total) AS lifetime_value
    FROM order_totals
    GROUP BY customer_id
)
SELECT c.segment, AVG(cv.lifetime_value) AS avg_ltv, MEDIAN(cv.lifetime_value) AS median_ltv
FROM customer_value cv
JOIN customers c USING (customer_id)
GROUP BY c.segment
ORDER BY avg_ltv DESC;
```

Each CTE is a named, testable step, which is the same idea as writing small functions. dbt (13.3) takes this to its logical conclusion: every
CTE-like step becomes a versioned, tested model.

Subqueries come in three flavors: scalar (`SELECT (SELECT MAX(price) FROM products)`), table (in `FROM`), and correlated (referencing the outer
row, like `EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id)`). Correlated subqueries read naturally for "exists" questions; for
anything heavier, a join or a window function (08.2) is usually clearer and faster.

## CASE, set operations, and the rest of the toolbox

```sql
SELECT order_id,
       CASE WHEN total >= 1000 THEN 'large'
            WHEN total >= 100  THEN 'medium'
            ELSE 'small' END AS size_bucket
FROM order_totals;
```

Set operations combine query results with the same columns: `UNION` (removes duplicates, which costs a sort or hash), `UNION ALL` (keeps them,
and is what you want 95% of the time), `INTERSECT`, `EXCEPT`. `EXCEPT` is great for data tests: "rows in the source that didn't make it to the
target".

Dates and times deserve a warning of their own: store timestamps in UTC (`TIMESTAMPTZ` where available), convert to local time only for
display, and be careful with `DATE_TRUNC('day', ts)` on UTC data when the business thinks in a local timezone. "Daily revenue" computed in UTC
and in Buenos Aires time are different numbers. I've seen dashboards disagree for exactly this reason, with two people each certain the other
was wrong.

## SQL injection: the oldest bug that still works

If you build queries by pasting user input into strings, you have a vulnerability:

```python
email = request.args["email"]
cur.execute(f"SELECT * FROM customers WHERE email = '{email}'")     # never do this
```

An "email" of `' OR '1'='1` returns every customer. Something like `'; DROP TABLE customers; --` does what it says on databases that allow
stacked queries. Injection has been at or near the top of the OWASP Top 10 for twenty years, and I still find it in internal tools, admin panels,
and, increasingly, in LLM applications that generate SQL from user text (44.1).

The fix is **parameterized queries**: the query text and the values travel separately, and the database never interprets the values as SQL.

```python
cur.execute("SELECT * FROM customers WHERE email = ?", (email,))    # SQLite / DuckDB style
cur.execute("SELECT * FROM customers WHERE email = %s", (email,))   # psycopg (PostgreSQL) style
```

Parameters work for values, not identifiers. If you must choose a column or table name dynamically, pick it from an allow-list in your code,
never from user input. And give the application's database user only the permissions it needs (no `DROP`, no access to other schemas): least
privilege turns a catastrophic injection into an annoying one. The lab exploits an injectable query and then fixes it.

## Things that will bite you

- **NULL semantics** in `WHERE`, `NOT IN`, `COUNT(col)` and arithmetic.
- **Missing `ORDER BY`** when order matters.
- **`UNION` instead of `UNION ALL`**, silently removing legitimate duplicate rows (two identical orders are still two orders).
- **Joins that multiply rows** (08.2 has a whole section on this).
- **Timezones.**
- **String-built queries.** Parameterize, always.

## Exercises

1. Write a query that returns, per channel, the number of delivered orders and the share of all delivered orders (as a percentage). Use a CTE.
2. Explain why `SELECT COUNT(*) FROM customers WHERE email <> 'not-an-email'` doesn't count customers with a NULL email, and write the version that
   does.
3. `SELECT * FROM customers WHERE customer_id NOT IN (SELECT customer_id FROM orders)` returns zero rows on a table with some NULL `customer_id`s in
   `orders`. Why? Rewrite it with `NOT EXISTS` and with a `LEFT JOIN`.
4. Write a query returning the top 3 categories by revenue from delivered orders, with revenue and number of distinct customers who bought in each.
5. Given `cur.execute(f"SELECT * FROM products WHERE category = '{cat}' ORDER BY {sort_col}")`, what can an attacker control, and how do you fix
   *both* injection points?

<summary>Answers</summary>

1. ```sql
   WITH d AS (SELECT channel, COUNT(*) AS n FROM orders WHERE status = 'delivered' GROUP BY channel)
   SELECT channel, n, ROUND(100.0 * n / SUM(n) OVER (), 2) AS pct
   FROM d ORDER BY n DESC;
   ```
   `SUM(n) OVER ()` is a window function (08.2) giving the grand total on every row. Without it: a second CTE with the total and a cross join.
   Note `100.0`: in some databases `100 * n / total` with integers does integer division and gives 0.

2. `NULL <> 'not-an-email'` is UNKNOWN, so those rows are filtered out. Version: `WHERE email IS NULL OR email <> 'not-an-email'`, or
   `WHERE email IS DISTINCT FROM 'not-an-email'`.

3. For a customer not in the list, `id NOT IN (..., NULL)` evaluates `id <> NULL` as UNKNOWN, so the whole predicate is UNKNOWN, and the row is dropped.
   ```sql
   SELECT * FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
   SELECT c.* FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id WHERE o.order_id IS NULL;
   ```

4. ```sql
   SELECT p.category,
          SUM(oi.quantity * oi.unit_price) AS revenue,
          COUNT(DISTINCT o.customer_id)   AS buyers
   FROM orders o
   JOIN order_items oi ON oi.order_id = o.order_id
   JOIN products p     ON p.product_id = oi.product_id
   WHERE o.status = 'delivered'
   GROUP BY p.category
   ORDER BY revenue DESC
   LIMIT 3;
   ```

5. The attacker controls a value (`cat`) and an identifier (`sort_col`). The value is fixed with a parameter (`WHERE category = ?`). The identifier can't
   be parameterized: validate it against an allow-list (`if sort_col not in {"price", "name"}: raise ValueError`) and then interpolate the validated
   constant. An `ORDER BY` injection can still leak data (via conditional sort orders), so the allow-list is not optional.
