# 08.4 Transactions, isolation and OLTP vs OLAP

*About 10 hours. Prerequisites: 08.1 to 08.3. Lab: [`lab_08_4_transactions.py`](labs/lab_08_4_transactions.py).*

A bank transfer takes money from one account and puts it in another. If the system crashes between the two steps, money
vanishes. If two transfers run at the same time on the same account, money can be created. Transactions exist to make
those impossible, and for fifty years they've been one of the quiet miracles of software engineering: most developers
never think about them, and most of the time that's fine.

Then you build a feature store that updates counters concurrently, or an inventory system, or a pipeline that writes to a
table other jobs are reading, and "most of the time" stops being good enough. This lesson covers what transactions
guarantee, the anomalies that appear when they guarantee less than you assumed, and the big architectural split between
databases built for transactions (OLTP) and databases built for analytics (OLAP), which is the reason data engineering exists
as a job.

## ACID

A **transaction** groups operations into one logical unit. The classic guarantees:

- **Atomicity**: all or nothing. If anything fails, everything is rolled back. No half-done transfers.
- **Consistency**: transactions move the database from one valid state to another, respecting constraints (the ones you declared, 08.1). This one
  is partly the application's job.
- **Isolation**: concurrent transactions don't see each other's intermediate states; the result is as if they ran in *some* order. How strongly
  this holds depends on the isolation level, and that's where the trouble is.
- **Durability**: once committed, it survives crashes. Implemented with a **write-ahead log** (WAL): changes are appended to a log on disk and flushed
  before the commit is acknowledged; after a crash, the log is replayed. The same idea (an append-only log as the source of truth) shows up again in
  Kafka (14.1), in table formats like Delta and Iceberg (11.2), and in change data capture.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- or ROLLBACK;
```

## Isolation anomalies

Full isolation (**serializable**: the outcome equals some serial execution) is expensive, so databases offer weaker levels, and each allows certain
anomalies:

- **Dirty read**: reading another transaction's uncommitted changes (which might be rolled back).
- **Non-repeatable read**: reading the same row twice in one transaction and getting different values, because another transaction committed in
  between.
- **Phantom read**: re-running a query with a `WHERE` and getting new rows that another transaction inserted.
- **Lost update**: two transactions read a value, both compute a new value from it, both write. One update disappears. The classic read-modify-write
  race (01.4 had its Python cousin).
- **Write skew**: two transactions each read an overlapping set, check a condition, and write *different* rows, and together they violate the
  condition. The textbook example: two on-call doctors each check "is someone else on call?", see yes, and both go off call. Nobody is on call.

The SQL standard levels, weakest to strongest:

| Level | Prevents |
|---|---|
| Read uncommitted | (almost nothing) |
| Read committed | dirty reads. The default in PostgreSQL, Oracle, SQL Server |
| Repeatable read | + non-repeatable reads (and in practice, with snapshot isolation, phantoms). MySQL/InnoDB default |
| Serializable | all anomalies, including write skew |

Real implementations don't map perfectly to this table, which is a well-known mess. Most modern databases implement **snapshot isolation** via **MVCC**
(multi-version concurrency control): each transaction sees a consistent snapshot of the database as of its start, writers create new versions of rows
instead of overwriting, and readers never block writers. Snapshot isolation prevents dirty reads, non-repeatable reads and most lost updates, but
**not write skew**. PostgreSQL's `SERIALIZABLE` adds detection of the dangerous patterns (serializable snapshot isolation) and aborts one of the
transactions, which your code must then **retry**.

The practical lesson: **know your database's default level, and don't assume it's serializable.** Most aren't by default.

### Preventing lost updates in application code

The bug:

```python
row = db.execute("SELECT stock FROM products WHERE id = ?", (pid,)).fetchone()
db.execute("UPDATE products SET stock = ? WHERE id = ?", (row[0] - qty, pid))   # stale if someone else wrote in between
```

Fixes, from simplest to most general:

1. **Atomic updates**: let the database do the arithmetic: `UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?`. Check the affected row count
   to know whether it succeeded.
2. **Pessimistic locking**: `SELECT ... FOR UPDATE` locks the row until the transaction ends; others wait. Watch out for **deadlocks** (A locks row 1 and
   waits for row 2, B locks row 2 and waits for row 1): databases detect them and kill one transaction. Always lock rows in a consistent order.
3. **Optimistic concurrency**: add a `version` column; update with `WHERE id = ? AND version = ?` and increment it; if zero rows were updated, someone
   else won, so re-read and retry. Great when conflicts are rare. HTTP has the same idea with `ETag` and `If-Match` headers.
4. **Serializable isolation** plus retries, for complex invariants (write skew).

The lab reproduces the lost update with two connections and applies each fix.

## Replication and its surprises

Production databases replicate to **read replicas** for scaling and failover. Replication is usually **asynchronous**, so replicas lag behind the
primary by milliseconds to minutes. A user updates their profile (on the primary) and immediately reloads the page (from a replica): the old data is back.
"Read-your-writes" consistency has to be designed in (route that user's reads to the primary for a while, or wait for the replica to catch up).

For data engineering, replication lag matters when you extract data from a replica: your "latest" snapshot may be minutes old, and rows committed at the
same time on the primary might arrive in different extraction windows. Incremental loads need to account for it (13.1).

## OLTP vs OLAP

Here's the architectural split behind half of Part II.

**OLTP** (online transaction processing): the database behind an application. Many small, concurrent transactions that read and write a few rows by key:
"insert this order", "get this customer's cart", "decrement this stock". Needs low latency, high concurrency, strong consistency. Row-oriented storage with
B-tree indexes (PostgreSQL, MySQL, SQL Server, Oracle), normalized schemas (09.1).

**OLAP** (online analytical processing): the database behind reports, dashboards and ML training data. Fewer, huge queries that read millions or billions of
rows but only a few columns, and aggregate them: "revenue by country by month for three years". Needs scan throughput. Columnar storage with compression and
vectorized execution (BigQuery, Snowflake, Redshift, ClickHouse, DuckDB, Spark on Parquet), denormalized dimensional schemas (09.2).

| | OLTP | OLAP |
|---|---|---|
| Typical query | read/write a few rows by key | scan and aggregate millions of rows |
| Users | the application, thousands of concurrent requests | analysts, dashboards, pipelines, ML |
| Storage | row-oriented | column-oriented |
| Schema | normalized | denormalized (star schema) |
| Latency target | milliseconds | seconds to minutes |
| Data | current state | history |

**Why not run analytics on the production database?** Because a heavy analytical query scanning the orders table competes for CPU, memory and I/O with the
checkout flow, holds snapshots that bloat MVCC storage, and can take locks. I've seen a "quick query" from someone's notebook slow down a small shop's checkout page.
So companies copy data from OLTP systems into an OLAP system: that copy process (extract, load, transform) is the core of data engineering (Module 13),
done in batches or continuously with **change data capture** (CDC, 14.2), which reads the database's own write-ahead log.

The line is blurring (HTAP systems try to do both, and PostgreSQL extensions add columnar storage), but the workload difference is fundamental, and you'll
design around it for the foreseeable future.

## Things that will bite you

- **Read-modify-write races** in application code (lost updates).
- **Assuming serializable isolation** when your database defaults to read committed.
- **Long-running transactions** holding locks or old snapshots (a notebook with an open transaction left overnight).
- **Not retrying** transactions aborted by deadlock detection or serialization failures.
- **Replica lag** in read-after-write flows and in extractions.
- **Analytics on the OLTP primary.**
