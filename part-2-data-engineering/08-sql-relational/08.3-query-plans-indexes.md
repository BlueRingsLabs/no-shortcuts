# 08.3 Query plans, indexes and performance

*About 11 hours. Prerequisites: 08.1, 08.2, 07.1, 07.3. Lab: [`lab_08_3_query_plans.py`](labs/lab_08_3_query_plans.py).*

SQL is declarative: you say what you want, and the database decides how. Most of the time, that's a gift. Then one day a
query that took 200 milliseconds takes 40 minutes, nothing in the SQL changed, and you need to know what the database
decided and why. Or finance asks why the warehouse bill doubled, and the answer is one dashboard query scanning three
years of data every five minutes because nobody added a date filter.

This lesson opens the hood: how databases execute queries, how to read a query plan, what indexes actually are, and the
few rules that fix most slow queries. It's the "query performance tuning" line you'll see on almost every Data Engineer
job description, and it's also how you stop being the person who burns the cloud budget.

## From SQL to a plan

When you submit a query, the database:

1. **Parses** it and checks names and types.
2. **Rewrites** it logically (inlines views and CTEs, pushes filters down toward the tables, removes useless columns).
3. **Optimizes**: enumerates alternative physical plans (which table to read first, which join algorithm, whether to use an index) and
   estimates the cost of each using **statistics** about the data (row counts, number of distinct values, histograms, min/max per block).
   It picks the cheapest estimate.
4. **Executes** the plan: a tree of operators (scan, filter, join, aggregate, sort) that pass rows (or batches of rows, in columnar engines)
   to each other.

The optimizer is only as good as its **cardinality estimates** (how many rows each step will produce). Most catastrophically bad plans come from
estimates that are off by orders of magnitude: stale statistics after a big load, correlated columns the optimizer assumes are independent,
functions in predicates it can't estimate. When a plan is bad, first check whether the estimates are wrong. `ANALYZE table` refreshes statistics
in PostgreSQL and SQLite.

## Reading plans

`EXPLAIN` shows the plan the database *intends* to run. `EXPLAIN ANALYZE` actually runs the query and shows, per operator, the real row counts and
times next to the estimates. That comparison is the single most useful diagnostic in database performance work: find the operator where
"estimated 10 rows" meets "actual 4 million rows".

```sql
EXPLAIN ANALYZE
SELECT c.country, SUM(oi.quantity * oi.unit_price)
FROM orders o JOIN customers c USING (customer_id) JOIN order_items oi USING (order_id)
WHERE o.order_ts >= DATE '2025-01-01'
GROUP BY c.country;
```

Read it bottom-up (or innermost first): scans at the leaves, joins and aggregations above. Look for: full scans of large tables where you expected
a lookup, joins producing far more rows than their inputs (fan-out, 08.2), sorts or hash tables spilling to disk, and filters applied late instead of
early. The lab walks through real plans from SQLite and DuckDB.

## Scans, joins, aggregations: the physical operators

**Scans**: a full table scan reads everything. An **index scan** uses an index to find matching rows. In columnar engines, a scan reads only the
needed **columns** and can skip blocks using **zone maps** (min/max statistics per block): `WHERE order_ts >= '2025-01-01'` skips every block whose
maximum timestamp is earlier. Sorting or clustering data by a commonly filtered column makes those skips far more effective (11.2).

**Join algorithms**:

| Algorithm | How | Cost | Good when |
|---|---|---|---|
| Nested loop | for each outer row, scan (or index-lookup) the inner | $O(n \cdot m)$, or $O(n \log m)$ with an index on the inner key | small outer side, index on inner |
| Hash join | build a hash table on the smaller side, probe with the bigger | $O(n + m)$, memory for the build side | equality joins on big unsorted inputs (the analytics default) |
| Sort-merge join | sort both sides on the key, merge | $O(n \log n + m \log m)$, or $O(n + m)$ if already sorted | inputs already sorted, range conditions, huge inputs that must spill |

Distributed engines add a layer: to join two big tables they must **shuffle** both so that matching keys land on the same machine, or **broadcast**
the small table to every machine (12.2). Same algorithms, network on top.

**Aggregation**: hash aggregation (a hash table keyed by the group) or sort-based aggregation. High-cardinality `GROUP BY`s (millions of groups) can
exceed memory and spill.

## Indexes

An **index** is an auxiliary data structure that lets the database find rows by the value of some columns without scanning the whole table. In
row-oriented operational databases (PostgreSQL, MySQL, SQLite), the default index is a **B-tree** (07.1): a balanced, wide tree whose leaves hold the
indexed values in sorted order with pointers to the rows. Lookups are $O(\log n)$: three or four page reads for a billion rows.

Because the leaves are sorted, a B-tree supports equality (`=`), ranges (`<`, `BETWEEN`), prefix matches (`LIKE 'abc%'`, not `LIKE '%abc'`), and
`ORDER BY` on the indexed columns without a sort.

### Composite indexes and the leftmost prefix rule

An index on `(customer_id, order_ts)` is sorted by customer first, then by timestamp within each customer. It can serve:

- `WHERE customer_id = 42` (a prefix),
- `WHERE customer_id = 42 AND order_ts >= '2025-01-01'` (equality on the first column, range on the second: ideal),
- `WHERE customer_id = 42 ORDER BY order_ts DESC LIMIT 1` (the latest order of a customer, read directly from the index),

but not `WHERE order_ts >= '2025-01-01'` alone, because rows with that timestamp are scattered across all customers. **Column order matters: equality
columns first, then the range or sort column.** Get it backwards and the index is nearly useless for your query.

A **covering index** contains every column a query needs (in PostgreSQL, extra columns via `INCLUDE`), so the query never touches the table itself: an
"index-only scan".

### Sargable predicates

An index on `order_ts` is useless for `WHERE DATE(order_ts) = '2025-03-01'` or `WHERE EXTRACT(year FROM order_ts) = 2025`, because the database would
have to compute the function for every row to compare. Rewrite as a range on the raw column:

```sql
WHERE order_ts >= TIMESTAMP '2025-03-01' AND order_ts < TIMESTAMP '2025-03-02'
```

Same for `WHERE LOWER(email) = ...` (create an index on the expression, or store a normalized column), `WHERE price * 1.21 > 100` (move the arithmetic to
the constant side), and implicit type casts on the column. A predicate that can use an index is called **sargable** (Search ARGument ABLE, a
wonderfully ugly word).

### Indexes are not free

Every index must be updated on every insert, update and delete, takes disk and memory, and gives the optimizer more options to get wrong. On an
analytics table loaded in bulk, indexes may cost more than they save. On an operational table serving a web app, the right handful of indexes is the
difference between a working product and a timeout. Index for your **query patterns** (look at the slow query log), not "every column just in case".

Selectivity matters too: an index on `status` (four distinct values) rarely helps, because fetching 25% of the table through an index is slower than
scanning it sequentially (random I/O vs sequential I/O, 07.3). Optimizers know this and will ignore your index, correctly.

## Performance in analytical warehouses

Columnar engines (DuckDB, BigQuery, Snowflake, Redshift, ClickHouse, Spark on Parquet) mostly don't use B-trees. Their levers are different:

1. **Read fewer columns.** `SELECT *` on a wide table reads every column. In a columnar warehouse that bills by bytes scanned, `SELECT *` is literally
   money. Select what you need.
2. **Read fewer rows**: filter on **partition** columns (typically date) so whole partitions are skipped, and **cluster/sort** data by common filter
   columns so zone maps skip blocks (11.2).
3. **Filter early, aggregate early** (08.2): reduce data before joins.
4. **Avoid exploding joins and `COUNT(DISTINCT)` on huge cardinalities** (use approximate versions when exactness isn't required).
5. **Use the result of expensive computations**: materialize intermediate tables (13.3) instead of recomputing a heavy CTE in twenty dashboards.

## A tuning checklist

When a query is slow:

1. Get the plan with actual numbers (`EXPLAIN ANALYZE` or the warehouse's query profile).
2. Find where time and rows go. Compare estimated vs actual rows.
3. Common culprits, in my experience, in order of frequency: a missing filter (scanning all history), a fan-out join, a non-sargable predicate, a
   missing or wrongly ordered index (operational DBs), stale statistics, a sort or hash spilling to disk, skewed keys in a distributed join (12.2).
4. Fix one thing, measure again.

## Things that will bite you

- **Functions on indexed columns** in `WHERE`.
- **Wrong column order** in composite indexes.
- **`SELECT *`** in warehouses.
- **Stale statistics** after large loads.
- **Testing on small data.** Every plan is fast on 1,000 rows. Test with production-sized data or at least production-shaped statistics.
- **Over-indexing** write-heavy tables.

## Exercises

1. Which of these predicates can use an index on `orders(order_ts)`? (a) `order_ts > now() - INTERVAL 7 DAYS`, (b) `DATE_TRUNC('day', order_ts) =
   '2025-03-01'`, (c) `order_ts::DATE = '2025-03-01'`, (d) `order_ts BETWEEN '2025-03-01' AND '2025-03-31'`. Rewrite the ones that can't.
2. You frequently run `SELECT * FROM orders WHERE status = 'shipped' AND customer_id = ? ORDER BY order_ts DESC LIMIT 10`. Design an index.
3. A join between a 10-row table and a 100-million-row table with an index on the join key: which join algorithm do you expect, and why? What if neither
   side is indexed and both have 100 million rows?
4. An `EXPLAIN ANALYZE` shows a node with 12 estimated rows and 3.4 million actual rows feeding a nested loop join. What happened, and what are two ways to
   fix it?
5. Your BigQuery bill spikes. The culprit is a dashboard query `SELECT * FROM events WHERE user_id = @u`. The table is partitioned by `event_date` and
   has 30 columns. What's wrong and what would you change?

1. (a) and (d) can (the expression is on the constant side / a plain range). (b) and (c) can't: rewrite as `order_ts >= '2025-03-01' AND order_ts <

5. No partition filter, so it scans the whole table (every day, forever), and `SELECT *` reads all 30 columns. Add a date range filter on `event_date`,

- Markus Winand, *SQL Performance Explained* (use-the-index-luke.com). The best practical book on indexes, free online.
- Kleppmann, *Designing Data-Intensive Applications*, chapter 3 (storage and retrieval, B-trees vs LSM-trees, column storage).
