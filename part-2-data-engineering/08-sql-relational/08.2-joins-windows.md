# 08.2 Joins, aggregation and window functions

*About 12 hours. Prerequisites: 08.1. Lab: [`lab_08_2_joins_windows.py`](labs/lab_08_2_joins_windows.py).*

If I had to pick the one SQL skill that separates people who "know SQL" from people who can actually do analytics and
data engineering, it would be window functions. Latest row per user, running totals, sessionization, retention cohorts,
deduplication, top-N per group, time since the previous event: all of them are two or three lines with window functions,
and a nightmare of self-joins without them.

But first, joins, and specifically the join bug that has produced more wrong revenue numbers than any other bug I know.
I call it "the fan-out", and I'll show you exactly how it happens so you can smell it from across the room.

## Join types

| Join | Keeps |
|---|---|
| `INNER JOIN` | only rows with a match on both sides |
| `LEFT JOIN` | every row from the left; right columns are NULL where there's no match |
| `RIGHT JOIN` | the mirror image (rarely used: just swap the tables and use LEFT) |
| `FULL OUTER JOIN` | every row from both sides, NULLs where there's no match |
| `CROSS JOIN` | every combination (n × m rows); useful for generating grids, e.g. all days × all products |
| semi-join (`WHERE EXISTS`, `IN`) | left rows that have *at least one* match, without duplicating them |
| anti-join (`WHERE NOT EXISTS`, `LEFT JOIN ... WHERE right.key IS NULL`) | left rows with *no* match |

Notes that matter in practice:

- **`NULL` keys never match** (`NULL = NULL` is UNKNOWN, 08.1). Rows with NULL join keys disappear from inner joins and get no match in left
  joins. If you meant to match them, you need `IS NOT DISTINCT FROM` in the condition.
- **A `WHERE` condition on the right table turns a LEFT JOIN into an INNER JOIN**: `LEFT JOIN orders o ON ... WHERE o.status = 'delivered'` drops
  customers without orders, because their `o.status` is NULL. Put the condition in the `ON` clause if you want to keep them.
- **Join on keys with the same type.** Joining an integer ID to a string ID works in some databases (implicit casting, slowly, sometimes wrongly
  with leading zeros) and fails in others.

## The fan-out: why your revenue is inflated

A join's output has as many rows as there are **matching pairs**. When you join a table to another with a one-to-many relationship, each row on
the "one" side is repeated once per match. That's expected. The bug happens when you then aggregate a column that was *repeated*.

Classic example: you want, per customer, total revenue and number of page views. You join customers to order_items (one-to-many) and to events
(one-to-many) and aggregate:

```sql
-- WRONG
SELECT c.customer_id,
       SUM(oi.quantity * oi.unit_price) AS revenue,
       COUNT(e.event_id)                AS events
FROM customers c
JOIN orders o       ON o.customer_id = c.customer_id
JOIN order_items oi ON oi.order_id   = o.order_id
JOIN events e       ON e.customer_id = c.customer_id
GROUP BY c.customer_id;
```

A customer with 10 order lines and 30 events produces 10 × 30 = 300 joined rows. Revenue gets summed 30 times over and events counted 10 times over.
The query runs, the numbers look plausible for "big" customers, and the dashboard is wrong by a factor that varies per customer, which makes it
very hard to spot by eye.

The fix: **aggregate each one-to-many relation to the grain you want before joining.**

```sql
-- RIGHT
WITH rev AS (
    SELECT o.customer_id, SUM(oi.quantity * oi.unit_price) AS revenue
    FROM orders o JOIN order_items oi USING (order_id)
    GROUP BY o.customer_id
), ev AS (
    SELECT customer_id, COUNT(*) AS events FROM events GROUP BY customer_id
)
SELECT c.customer_id, COALESCE(rev.revenue, 0) AS revenue, COALESCE(ev.events, 0) AS events
FROM customers c
LEFT JOIN rev USING (customer_id)
LEFT JOIN ev  USING (customer_id);
```

Two habits that catch fan-outs before they reach a dashboard:

1. **Know the grain of every table and every intermediate result.** "One row per order line", "one row per customer per day". Write it in a comment.
   When a join changes the grain in a way you didn't intend, you have a bug.
2. **Count rows before and after joins.** If a join that should be one-to-one (enriching orders with customer attributes) changes the row count, a key
   you thought was unique isn't. Test uniqueness of join keys explicitly (dbt does this with `unique` tests, 13.3).

## Aggregation beyond GROUP BY

A few features that save a lot of code:

- **Conditional aggregation**: `COUNT(*) FILTER (WHERE status = 'returned')` (PostgreSQL, DuckDB) or the portable
  `SUM(CASE WHEN status = 'returned' THEN 1 ELSE 0 END)`. Pivot-like reports in one pass.
- **`COUNT(DISTINCT x)`**: exact but expensive on big data; `APPROX_COUNT_DISTINCT` uses HyperLogLog (07.1).
- **`GROUPING SETS`, `ROLLUP`, `CUBE`**: subtotals and grand totals in one query. `GROUP BY ROLLUP (country, channel)` gives per (country,
  channel), per country, and the grand total.
- **Percentiles**: `PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY x)` (standard) or `MEDIAN(x)`, `QUANTILE_CONT(x, 0.95)` (DuckDB). Remember
  07.4: latency is reported as percentiles, and 04.1: skewed data should be summarized by medians.

## Window functions

A window function computes a value for each row using a set of related rows (its **window**), **without collapsing rows** the way `GROUP BY` does.
Syntax:

```sql
function(...) OVER (
    PARTITION BY <columns>        -- which rows belong together (like GROUP BY, but rows are kept)
    ORDER BY <columns>            -- order within the partition
    ROWS BETWEEN <start> AND <end> -- the frame: which rows around the current one
)
```

### Ranking

`ROW_NUMBER()` (1, 2, 3, ... no ties), `RANK()` (ties share a rank, then skip: 1, 1, 3), `DENSE_RANK()` (no skipping: 1, 1, 2).

**Latest row per key**, the most common pattern in data engineering (deduplication, current state of a slowly changing record, the last known
address):

```sql
SELECT *
FROM (
    SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_ts DESC, order_id DESC) AS rn
    FROM orders o
) WHERE rn = 1;
```

Many engines support `QUALIFY` to filter on window results directly: `... QUALIFY ROW_NUMBER() OVER (...) = 1`. Note the tie-breaker (`order_id
DESC`): without it, two orders with the same timestamp make the result non-deterministic, and your "latest" row can change between runs. **Every
`ORDER BY` inside a window used for dedup must be a total order.**

**Top-N per group**: same pattern with `rn <= 3`, e.g. the three best-selling products per category.

### Offsets: LAG and LEAD

`LAG(x, k)` returns `x` from $k$ rows earlier in the partition, `LEAD` from later. Time since the previous order:

```sql
SELECT customer_id, order_ts,
       order_ts - LAG(order_ts) OVER (PARTITION BY customer_id ORDER BY order_ts) AS since_prev
FROM orders;
```

### Running aggregates and frames

With `ORDER BY`, aggregate functions become running aggregates. The **frame** says which rows are included:

```sql
SUM(revenue) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)   -- running total
AVG(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)           -- 7-day moving average
```

Warning: the default frame when you specify `ORDER BY` is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, which treats rows with equal `ORDER BY`
values as peers and includes all of them. With duplicate timestamps, a "running total" jumps by several rows at once. Specify `ROWS` explicitly when
you mean rows. And a 7-*row* moving average is only a 7-*day* average if there's exactly one row per day with no gaps: generate a calendar and left
join to it first, or use `RANGE BETWEEN INTERVAL 6 DAYS PRECEDING AND CURRENT ROW`.

### Sessionization

A **session** is a burst of activity separated from the next by a gap of inactivity (commonly 30 minutes). Web analytics, fraud detection and
feature engineering (22.1) all need it. With windows, it's three steps:

```sql
WITH flagged AS (
    SELECT *,
           CASE WHEN ts - LAG(ts) OVER (PARTITION BY customer_id ORDER BY ts, event_id) > INTERVAL 30 MINUTES
                  OR LAG(ts) OVER (PARTITION BY customer_id ORDER BY ts, event_id) IS NULL
                THEN 1 ELSE 0 END AS new_session
    FROM events
)
SELECT *,
       SUM(new_session) OVER (PARTITION BY customer_id ORDER BY ts, event_id
                              ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS session_number
FROM flagged;
```

Flag the rows that start a new session, then a running sum of the flags numbers the sessions. This "flag + running sum" trick solves a whole family of
**gaps-and-islands** problems: streaks of consecutive days, periods where a sensor was above a threshold, stretches of uninterrupted subscription.

### Cohort retention

The canonical product analytics query: group customers by the month of their first order (their cohort), then compute what fraction of each cohort
ordered again in each later month. It combines a `MIN(...) OVER (PARTITION BY customer_id)` to find the first order, date arithmetic to compute
"months since first order", and a conditional count. The lab builds it.

## Performance notes

Window functions sort each partition, so they cost roughly $O(n \log n)$. They're usually much faster than the equivalent self-join, which can be
quadratic. Several windows with the **same** `PARTITION BY ... ORDER BY` share one sort, so group them. On distributed engines (Spark, BigQuery), a
window with no `PARTITION BY` sends all the data to a single worker to be sorted: fine for a thousand rows, a disaster for a billion (12.2).

> **Scar tissue.** For a friend's small e-commerce site, as a freelance job, I built a revenue report that came out about 40% higher than
> what his accountant had. I defended it for a week. The query joined orders to order lines and then to payments, and orders with several
> payments (split payments, partial refunds) had every line duplicated once per payment. A fan-out join, the most boring bug in SQL, and
> comparing `COUNT(*)` before and after each join would have caught it in a minute. The accountant was right. Accountants are usually
> right about money. That's their whole job.

## Things that will bite you

- **Fan-outs.** Aggregate to the right grain before joining. Count rows after joins.
- **`WHERE` on the right side of a LEFT JOIN.**
- **Non-deterministic dedup** from ties in the window `ORDER BY`.
- **The default `RANGE` frame** with duplicate order values; row-based moving averages over gappy time series.
- **Unpartitioned windows on big data.**

1. ```sql
   WITH totals AS (
       SELECT o.order_id, o.customer_id, o.order_ts, SUM(oi.quantity * oi.unit_price) AS total
       FROM orders o JOIN order_items oi USING (order_id)
       WHERE o.status = 'delivered'
       GROUP BY o.order_id, o.customer_id, o.order_ts

   QUALIFY ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_ts DESC, order_id DESC) = 1;

   The filter on status happens *before* ranking, so "latest delivered" is what gets ranked.

2. ```sql
   WITH r AS (
       SELECT p.category, p.product_id, SUM(oi.quantity * oi.unit_price) AS revenue
       FROM order_items oi JOIN products p USING (product_id)
       GROUP BY p.category, p.product_id
   )
   SELECT * FROM r
   QUALIFY ROW_NUMBER() OVER (PARTITION BY category ORDER BY revenue DESC, product_id) <= 3;
   ```

3. ```sql
   WITH ranked AS (
       SELECT customer_id, order_ts, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_ts, order_id) AS rn
       FROM orders
   )
   SELECT customer_id,
          DATE_DIFF('day', MIN(order_ts) FILTER (WHERE rn = 1), MIN(order_ts) FILTER (WHERE rn = 2)) AS days_to_second
   FROM ranked GROUP BY customer_id;
   ```
