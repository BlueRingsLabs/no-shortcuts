# 37.2 KV cache, batching and serving engines

*About 9 hours. Prerequisites: 29.3 (the KV cache, GQA, FlashAttention), 33.1 (memory-bound decoding), 37.1. Lab: [`lab_37_2_kv_cache_serving.py`](labs/lab_37_2_kv_cache_serving.py).*

Training a model happens once. Serving it happens every time anyone sends a request, for as long as the model is in production, and
that's where most of the money in this industry goes. Serving an LLM well is a systems problem with unusual constraints: the work per request
is sequential (one token at a time), the memory per request grows while it runs, request lengths vary by a factor of a hundred, and users
notice latency in both the first token and every token after it. This lesson covers the ideas inside every serious serving engine (vLLM,
SGLang, TensorRT-LLM, TGI, llama.cpp) well enough to configure one, size the hardware and read its metrics.

## Prefill and decode

Generation has two phases with opposite characters:

- **Prefill**: process the whole prompt in one forward pass, computing and storing the keys and values of every prompt token. Many tokens at once: large matrix multiplies, **compute-bound**. It determines the **time to first token** (TTFT).
- **Decode**: generate one token per forward pass, each attending to everything before it. One token at a time per sequence: tiny matrix multiplies that read every weight and the whole cache from memory, **memory-bound** (33.1). It determines the **time per output token** (TPOT, or inter-token latency).

Almost every serving technique is about keeping decode from wasting the GPU.

## The KV cache

Without a cache, generating token $t$ recomputes keys and values for all $t - 1$ previous tokens: quadratic total cost. The **KV cache** stores each layer's keys and values as they're computed, so each decode step processes one new token and reads the rest (29.3). The lab's small GPT generates 100 tokens 2.6 times faster with the cache (on my CPU; timings vary by machine), with identical output; for long generations on large models the difference is far larger.

Its size, per sequence: $2 \times \text{layers} \times \text{KV heads} \times \text{head dim} \times \text{tokens} \times \text{bytes}$. Llama 3 8B: 128 KiB per token in bf16, so 32 concurrent sequences of 8,000 tokens need 34 GB of cache, twice the 16 GB of weights. For Llama 3 70B, the same load needs 86 GB. **At scale, the cache, not the weights, decides how many requests a GPU can hold**, which is why GQA (35.5), cache quantization (37.3), sliding-window layers and multi-head latent attention exist.

## Batching

A decode step for one sequence reads all the weights to do a sliver of arithmetic. For a batch of sequences, the weights are read once and used for all of them. On the lab's CPU, decode throughput goes from 1,500 tokens per second at batch 1 to 4,100 at 4, 12,100 at 16 and 23,300 at 64: almost linear at first, because the fixed per-step costs are shared. On GPUs the same curve continues into the hundreds of sequences, until the KV cache reads and the arithmetic catch up. **Throughput comes from batching; latency comes from not over-batching.** Every serving configuration is a choice on that tradeoff.

**Static batching** (collect a batch, run it to completion) wastes most of that. Requests have wildly different output lengths, and a static batch runs until its longest request finishes, with finished requests occupying slots. **Continuous batching** (Orca, Yu et al., 2022; iteration-level scheduling) re-forms the batch at every decode step: a finished request's slot is immediately given to a waiting one. The lab simulates 200 requests with output lengths between 10 and 500 tokens on 16 slots:

| | tokens/s | mean completion time | slot utilization |
|---|---|---|---|
| static | 318 | 83 s | 55% |
| continuous | 544 | 49 s | 93% |

Better throughput *and* better latency, which is rare. Every modern engine does this, and interleaves prefills of new requests with ongoing decodes (**chunked prefill** splits long prompts so they don't stall everyone else's decoding).

## Paged KV memory

A cache that must be contiguous per request forces you to reserve the maximum length up front. The lab's 1,000 requests with lengths up to 2,048 tokens would reserve 2,048,000 cache slots and use 1,033,008: half the memory wasted. **PagedAttention** (vLLM, Kwon et al., 2023) stores the cache in fixed-size blocks (16 tokens) allocated on demand and tracked with a block table, like an operating system's virtual memory: waste drops to 0.7% in the lab. More requests fit, so batches are larger, so throughput rises. Pages also make **sharing** cheap: requests with the same prefix can point at the same blocks.

## Prefix caching

Many requests share a long prefix: a system prompt, few-shot examples, a document being asked several questions, the history of a chat. **Prefix caching** keeps the KV blocks of recent prefixes and reuses them, skipping their prefill. In the lab, four questions after a 49-token system prompt need 230 tokens of prefill from scratch and 83 with the prefix cached (64% fewer), with identical outputs. On the lab's tiny model the wall-clock saving is hidden by per-call overhead; for a large model with a 2,000-token system prompt, it's most of the prefill cost and most of the time to first token. Hosted APIs bill cached input tokens at a large discount for exactly this reason. The practical rule: **put the stable part of your prompt first** and the variable part last, so the cache can hit (40.1).

## Speculative decoding

Decoding is memory-bound, so a forward pass over a few tokens costs about the same as over one. **Speculative decoding** (Leviathan et al., 2023; Chen et al., 2023) exploits that: a cheap **draft** proposes $k$ tokens, the big model scores all $k$ in one pass, and the longest prefix it agrees with is kept, plus one token of its own. For greedy decoding the output is identical to the big model's; for sampling, a rejection-sampling rule keeps the output distribution exactly the big model's.

The lab uses a draft that's almost free and almost always wrong: a trigram counter. Only 11% of its proposals are accepted, and it still cuts the big-model passes from 100 to 70, because every verification pass yields at least one token. A draft from the same model family (a 1B draft for a 70B target) is accepted 60% to 80% of the time, for speedups of 2 to 3 times. Variants skip the separate draft: **Medusa** adds extra prediction heads, **EAGLE** drafts from the target's own features, **lookahead** and **prompt lookup** decoding draft from n-grams of the prompt (very effective for editing and extraction tasks, where the output copies the input).

## Serving engines and their metrics

What to measure, per workload:

- **TTFT** (time to first token), **TPOT** (time per output token), and end-to-end latency, at percentiles (p50, p95, p99), not averages.
- **Throughput**: output tokens per second per GPU, at a given latency target. Quote both, or the number is meaningless.
- **Goodput**: requests per second that meet the latency targets.

Levers, in the order they usually matter: quantization of weights and cache (37.3), maximum batch size and scheduler settings, tensor parallelism across GPUs for large models (33.2), prefix caching, speculative decoding, chunked prefill, and **disaggregated serving** (separate GPU pools for prefill and decode, since they want different batch sizes). Benchmark with your real prompt and output length distributions: a configuration tuned on 100-token prompts can be wrong for 10,000-token ones.

Two operational notes. **Nondeterminism**: batched floating-point arithmetic isn't associative, so the same request can produce different tokens depending on what it was batched with, even at temperature 0. If you need reproducibility, you need batch-invariant kernels or a dedicated path. **Isolation**: a shared prefix cache means timing can reveal whether another user sent a given prefix recently; engines that serve mutually untrusted tenants should partition or salt their caches (44.1).

## Things that will bite you

- **Sizing GPUs by weights alone**, forgetting the KV cache.
- **Throughput numbers without a latency target** (or latency without load).
- **Static batching**, or a maximum batch size far below what memory allows.
- **Prompts with the variable part first**, defeating prefix caching.
- **Benchmarking with unrealistic lengths.**
- **Expecting bitwise determinism** from a batched server.
- **A shared prefix cache across tenants** without thinking about side channels.

## Exercises

1. Compute the KV cache per token in bf16 for a model with 40 layers, 8 KV heads and head dimension 128. How many 16k-token sequences fit in 40 GB of cache?
2. Why is prefill compute-bound and decode memory-bound?
3. In the lab's simulation, why does continuous batching improve both throughput and mean completion time?
4. A draft model's proposals are accepted with probability 0.7 each, independently, and $k = 4$. What's the expected number of tokens per big-model pass?
5. How does PagedAttention make prefix sharing cheap?
6. Your chatbot's p99 time to first token is 8 seconds while p50 is 0.4 seconds. What would you look at?

1. $2 \times 40 \times 8 \times 128 \times 2$ bytes $= 163{,}840$ bytes = 160 KiB per token. A 16k-token sequence: 2.5 GiB. 40 GB holds about 14 (15 with GB vs GiB rounding; plan for 14 with headroom).

2. Prefill processes many tokens per sequence in one pass: each weight read from memory is used for hundreds or thousands of multiply-adds (high arithmetic intensity), so arithmetic throughput is the limit. Decode processes one token per sequence per pass: each weight is used for one multiply-add per sequence in the batch, so the time is dominated by reading weights and cache from memory.

3. Static batching leaves finished requests' slots idle until the batch's longest request completes, so fewer tokens are produced per step (lower throughput), and new requests wait for the whole batch to finish before starting (longer completion times). Continuous batching refills slots immediately: more useful work per step, and requests start sooner.

4. The pass yields the accepted prefix plus one token. Expected accepted draft tokens: $\sum_{i=1}^{4} 0.7^i = 0.7 + 0.49 + 0.343 + 0.240 = 1.773$; plus the big model's own token: about 2.77 tokens per pass.

5. The cache is stored in fixed-size blocks referenced through a per-request block table. Two requests with the same prefix can have their tables point to the same physical blocks for that prefix (with reference counting and copy-on-write when one diverges), so the prefix's cache is computed and stored once.

6. Tail TTFT points to queuing or prefill contention: long prompts being prefilled in one piece and stalling other requests (enable chunked prefill), bursts exceeding capacity (queue length, autoscaling), prefix-cache misses for some request types, very long prompts themselves (the p99 requests may just be 30k-token prompts), and preemption or swapping when the cache fills. Break the latency down by prompt length and by queue time vs compute time.
