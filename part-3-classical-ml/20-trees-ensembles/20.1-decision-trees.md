# 20.1 Decision trees

*About 8 hours. Prerequisites: 06.1 (entropy), 07.1 (sorting, complexity), 16.2, 18.1. Lab: [`lab_20_1_decision_trees.py`](labs/lab_20_1_decision_trees.py).*

A decision tree is a flowchart learned from data: "is income above 42k? if yes, is tenure above 3 years? ...", and at the end of each path, a
prediction. It's the model a non-technical stakeholder can read, the one that needs no feature scaling and shrugs at mixed data types, and on
its own, frankly, a mediocre predictor: unstable, jagged, and prone to overfitting. So why does it get a whole lesson? Because the tree is the
building block of random forests and gradient boosting (20.2 to 20.4), which win most tabular-data competitions and run a large fraction of the
production ML in the world. Every property of those ensembles, good and bad, starts here.

## How a tree predicts

The tree recursively partitions the feature space into axis-aligned boxes. Each internal node tests one feature against a threshold ($x_j \le t$), each leaf holds
a constant prediction: the majority class (or class frequencies) for classification, the mean target for regression. A new point walks from the root to a leaf,
$O(\text{depth})$ comparisons.

## How a tree is grown

Finding the optimal tree is NP-hard. Everyone uses the **greedy** algorithm (CART, Breiman et al., 1984):

1. At the current node, for every feature $j$ and every candidate threshold $t$, compute how much splitting the node's data into $x_j \le t$ and $x_j > t$ reduces **impurity**.
2. Take the best split. Recurse on both children.
3. Stop when a stopping rule fires (below).

**Impurity** for a node with class proportions $p_k$:

- **Gini**: $G = 1 - \sum_k p_k^2$, the probability that two random draws from the node disagree.
- **Entropy**: $H = -\sum_k p_k\log_2 p_k$ (06.1). The impurity reduction is the **information gain**.
- **Regression**: variance of $y$ in the node (MSE); some libraries also offer MAE or Poisson deviance.

The split score is the parent's impurity minus the size-weighted impurity of the children. Gini and entropy almost always pick the same splits; Gini is slightly cheaper. It
genuinely doesn't matter much which you use.

**Efficiency.** For one feature, sort the node's values once; then sweep the threshold from left to right, moving one point at a time from the right child to the left, and
update the class counts (or sums and sums of squares) incrementally. Every candidate split is then $O(1)$, so a feature costs $O(n\log n)$ per node for the sort. Modern libraries
go further and **bin** each feature into ~256 histogram buckets once, up front, so finding a split costs $O(\text{bins})$ instead of $O(n)$ (LightGBM, XGBoost's `hist`, scikit-learn's
`HistGradientBoosting*`; 20.4). The lab implements the sorted-sweep version and reproduces scikit-learn's tree.

## Controlling complexity

Grown until every leaf is pure, a tree memorizes the training data (zero training error, high variance; 16.2). Two ways to stop it:

- **Pre-pruning** (stopping rules): `max_depth`, `min_samples_leaf`, `min_samples_split`, `max_leaf_nodes`, `min_impurity_decrease`. Simple and effective; `min_samples_leaf` is the one I tune first,
  because it directly controls how many examples back each prediction.
- **Post-pruning**: grow a big tree, then cut back. **Cost-complexity pruning** minimizes $R(T) + \alpha|T|$ (training error plus a penalty per leaf): as $\alpha$ grows, the weakest branches
  are collapsed one at a time, giving a nested sequence of subtrees. Pick $\alpha$ by cross-validation (`ccp_alpha` in scikit-learn; the lab walks the path).

## Properties, good and bad

Good:

- **No scaling needed.** A split only compares values within one feature, so any monotone transformation (log, standardization, rank) gives the identical tree. The lab checks it.
- **Mixed types, interactions and nonlinearity** come for free: a path through the tree is an interaction of all the features on it.
- **Robust to outliers in the features** (only the order matters) and to irrelevant features (they're rarely chosen).
- **Fast predictions**, and readable if small.

Bad:

- **High variance.** Change a few training points and the root split can change, and with it the entire tree below. The lab bootstraps the data and counts how many different
  root splits appear. This is the weakness 20.2 turns into a strength.
- **Axis-aligned boundaries.** A diagonal boundary ($x_1 > x_2$) needs a staircase of many splits. A linear model gets it with one coefficient.
- **No extrapolation.** Outside the training range, the prediction is the constant of the nearest leaf. A tree trained on prices from 2020 to 2024 predicts 2024-ish prices for 2030 forever.
  Trend-driven problems need a linear component or a transformed target (23.1).
- **Coarse, poorly calibrated probabilities** (leaf frequencies from few examples).
- **Greedy myopia**: a split that's useless alone but powerful combined with another (XOR, again) may never be chosen.

## Categorical features and missing values

**Categoricals**: one-hot encoding works but fragments a high-cardinality feature into many weak binary columns. Native handling is better: for a binary target (or regression),
sort the categories by their mean target, then the best split is one of the $K - 1$ splits along that order (a classic result, avoiding the $2^{K-1}$ subsets). LightGBM and
CatBoost do versions of this, with regularization to avoid overfitting rare categories (20.4).

**Missing values**: CART used surrogate splits (backup splits on correlated features). XGBoost and LightGBM learn a **default direction** at each split: missing values go to whichever
child reduces the loss more. scikit-learn's trees support missing values natively too. It's usually better than imputing, because "missing" is often informative (10.3).

## Importance, and a warning

Trees give a free **impurity-based feature importance**: the total impurity reduction from splits on each feature. It's biased: features with many possible split points
(continuous or high-cardinality ones) get more chances to reduce impurity by luck, so a random ID column can look important. Use **permutation importance** on held-out data
(22.3) instead. The lab plants a random high-cardinality feature and watches the impurity importance fall for it.

## Things that will bite you

- **Fully grown trees** evaluated on training data.
- **Impurity-based importance** taken at face value.
- **Extrapolating** with trees on trending data.
- **Reading a deep tree** as an explanation. A tree with 400 leaves isn't interpretable; it's just visible.
- **Assuming the tree structure is stable** enough to draw conclusions from a particular split.

## Exercises

1. A node has 60 positives and 40 negatives. Compute its Gini impurity and entropy. A split sends 50 positives and 10 negatives left, the rest right. Compute the Gini gain.
2. Why is a tree invariant to monotone transformations of the features? Is it invariant to monotone transformations of the target in regression?
3. Describe the $O(n\log n)$ algorithm for finding the best threshold on one feature for a regression tree with MSE. What running quantities do you keep?
4. Why would a tree need many splits to approximate the boundary $x_1 = x_2$? How many leaves for a good approximation on $[0, 1]^2$ to within 0.05?
5. Why does impurity-based importance favor high-cardinality features? What's the alternative?

5. A feature with many distinct values offers many candidate thresholds, so by chance alone one of them will reduce training impurity noticeably, especially deep in the tree where
