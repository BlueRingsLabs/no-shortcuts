# 20.4 XGBoost, LightGBM and CatBoost in the real world

*About 10 hours. Prerequisites: 20.3, 18.1 to 18.4. Lab: [`lab_20_4_gbdt_practice.py`](labs/lab_20_4_gbdt_practice.py).*

20.3 derived gradient boosting. This lesson is about using it for money: the three libraries that dominate, how they differ, how to feed them
categorical and missing data, how to tune and stop them, how to constrain them when a regulator is watching, and the traps I've watched people
walk into with them. If you work on tabular data, you'll spend more hours with these libraries than with any neural network framework, and the
difference between a default run and a careful one is often larger than the difference between the libraries.

## Three libraries, three sets of ideas

All three implement 20.3's second-order boosting with histogram-binned features. They differ in how they grow trees and handle categories.

**XGBoost** (Chen and Guestrin, 2016). The one that made gradient boosting fast and robust enough for everyone. **Level-wise** growth by default (split every node at a depth before
going deeper, controlled by `max_depth`), a sparsity-aware split finder that learns a **default direction for missing values**, the $\lambda$/$\gamma$ regularization from 20.3,
`hist` tree method as the default, good GPU support, native categorical support in recent versions (`enable_categorical=True`).

**LightGBM** (Ke et al., 2017, Microsoft). Built for speed on large data. **Leaf-wise** growth: always split the leaf with the largest gain, anywhere in the tree, controlled by
`num_leaves`. Reaches lower training loss with the same number of leaves, and overfits more easily on small data, so `min_child_samples` (or `min_data_in_leaf`) matters more. Two tricks
for scale: **GOSS** (keep the examples with large gradients, subsample the small ones) and **EFB** (bundle mutually exclusive sparse features into one). Native categorical splits
(sorting categories by gradient statistics, 20.1's trick).

**CatBoost** (Prokhorenkova et al., 2018, Yandex). Built around categorical features and a subtle leakage problem. Target statistics for categories (like target encoding) leak the
label if computed on the same rows (18.4), and boosting itself has a milder version of the same problem: the residuals used to fit tree $m$ were computed by a model that saw those
same rows. CatBoost's **ordered boosting** and **ordered target statistics** compute each row's quantities using only rows "before" it in a random permutation, like an online
learner. It also uses **oblivious (symmetric) trees**: the same split at every node of a level, which acts as a regularizer and makes prediction very fast. Often the best out of
the box on data with many categorical columns.

**scikit-learn's `HistGradientBoosting*`**: LightGBM-inspired, native missing values and categoricals, early stopping built in, and no extra dependency. For medium-sized data it's
often all you need, and it's what I use when I don't want another package in the image. One limit to know before it bites: native categoricals are capped at 255 levels
(one histogram bin each), so a 300-level merchant code gets an error, and you target-encode it instead (the lab does).

Which one? On most datasets, after tuning, the differences are small and dataset-dependent. Pick based on your data (lots of categoricals: CatBoost; huge data: LightGBM; GPU or
ecosystem needs: XGBoost), try a second one if the stakes justify it, and spend the rest of your time on features and validation, where the real gains are.

## The parameter map

| Concept | XGBoost | LightGBM | CatBoost | sklearn HistGB |
|---|---|---|---|---|
| Learning rate | `learning_rate` (`eta`) | `learning_rate` | `learning_rate` | `learning_rate` |
| Rounds | `n_estimators` | `n_estimators` | `iterations` | `max_iter` |
| Tree size | `max_depth` (level-wise) | `num_leaves` (leaf-wise), `max_depth` | `depth` (symmetric) | `max_leaf_nodes`, `max_depth` |
| Min leaf size | `min_child_weight` (Hessian sum) | `min_child_samples` | `min_data_in_leaf` | `min_samples_leaf` |
| Row subsampling | `subsample` | `bagging_fraction` + `bagging_freq` | `subsample` | (none) |
| Column subsampling | `colsample_bytree`, `_bylevel`, `_bynode` | `feature_fraction` | `rsm` | `max_features` |
| L2 on leaf values | `reg_lambda` | `lambda_l2` | `l2_leaf_reg` | `l2_regularization` |
| Min split gain | `gamma` | `min_gain_to_split` | (n/a) | (n/a) |
| Early stopping | `early_stopping_rounds` + eval set | `callbacks=[early_stopping(...)]` | `early_stopping_rounds` | `early_stopping=True` |
| Monotone constraints | `monotone_constraints` | `monotone_constraints` | `monotone_constraints` | `monotonic_cst` |

The names differ; the ideas are the same five: step size, tree size, leaf size, randomness, regularization.

## Categorical features

Options, from worst to best (usually):

1. **Integer codes as numbers**: category 7 is "between" 6 and 8, which is meaningless. Trees can still carve it up with enough splits, but inefficiently. Common by accident: a
   `category` column turned into codes somewhere in the pipeline.
2. **One-hot**: fine for low cardinality; for hundreds of levels it produces many sparse columns that each explain little, and trees need many splits to use them.
3. **Target encoding**, done out-of-fold with smoothing (18.4). Strong, and dangerous if done naively.
4. **Native categorical splits** (LightGBM, XGBoost, HistGB) or **CatBoost's ordered target statistics**. Usually the best, as long as you regularize rare categories (`min_data_per_group`,
   `cat_smooth` and friends in LightGBM).

The lab compares them on a feature with 300 levels.

## Missing values

All three learn a default direction for missing values at each split: missing goes wherever it helps the loss most. This is usually better than imputation, especially when
missingness is informative ("no credit history" is not "average credit history"). Don't impute by reflex. The lab shows the details: any *constant* fill (mean, −999) is a value a
tree can split off, so trees survive it; imputation with *varying* values (random draws, model-based imputers) erases the missingness signal; and a linear model needs an explicit missing
indicator to recover it.
Do make sure missing is *encoded* as missing (NaN), not as −1 or 0 or 9999, which the model would treat as real values (10.3).

## Constraints: when the model has to make sense

**Monotone constraints** force the prediction to be non-decreasing (or non-increasing) in a feature, holding the others fixed. In credit scoring, pricing and insurance, a model
where more income can lower the approval score won't survive a model review, regardless of its AUC, and sometimes it's a legal requirement. The constraint usually costs little accuracy
and often *improves* generalization, because the unconstrained model's non-monotone wiggles were fitting noise. The lab verifies monotonicity on a grid.

**Interaction constraints** limit which features may appear together in a tree (for regulatory explainability, or to encode known structure).

## Custom objectives

Because 20.3's machinery only needs the gradient and Hessian, any twice-differentiable loss is a few lines: return `grad, hess` per example. An asymmetric loss where
under-forecasting costs five times more than over-forecasting (stockouts vs holding cost) takes about four lines, and the lab shows the forecasts shifting up as they should.
(Check the Hessian is positive; if it's zero or negative somewhere, use a positive surrogate there.)

## Imbalance, probabilities, importance

- `scale_pos_weight` (or class weights) reweights positives. Same story as 18.4, with a twist: probabilities inflate, and because `min_child_weight` and the $\lambda$ shrinkage are measured in
  Hessian units, upweighting also *weakens the regularization*, so the ranking can get worse, not just stay the same. The lab's weighted model loses several AUC points. Prefer the
  unweighted model and a cost-based threshold; if you weight, retune the regularization and recalibrate.
- Boosted trees with log loss are usually reasonably calibrated, less so with heavy regularization, few rounds, or reweighting. Check a reliability diagram (18.3).
- **Built-in importance** comes in flavors that disagree: `weight`/`split` (how often a feature is used), `gain` (total loss reduction), `cover` (how many examples pass through). None of them
  is "the" importance. Use permutation importance on held-out data or SHAP values (22.3; TreeSHAP is exact and fast for tree ensembles).

## Production notes

- **Pin the library version**; model files are not always forward and backward compatible, and predictions can shift slightly between versions. Save in the library's native format (`.json`
  or `.ubj` for XGBoost, the text format for LightGBM, `.cbm` for CatBoost), not pickle.
- **Latency**: prediction cost is (number of trees) × (depth). Early stopping at a smaller learning rate gives more trees; balance accuracy against the latency budget. Compiling the ensemble
  (Treelite, ONNX, 49.3) or CatBoost's symmetric trees help.
- **Determinism**: set seeds and thread counts if you need bit-identical retrains (multithreaded histogram building can reorder floating point sums, 07.2).
- **Early stopping uses data**: the validation set used for stopping is part of training. Your test set must be separate (18.1).
- **Monitor feature distributions** (51.1): trees can't extrapolate, so a feature drifting beyond its training range silently gets the edge leaf's value.

> **Scar tissue.** In a class competition, a group of classmates topped the leaderboard with a gradient-boosted model whose most important
> feature was `row_id`. They'd copied the dataset from another course's repository, where it had been sorted by label before the IDs were
> assigned, so the ID was a near-perfect encoding of the answer, and the trees found it in the first split. The course's own test set had
> been drawn the same way, so the leaderboard agreed with them. Nobody had looked at the data before feeding it to XGBoost. Look at the
> feature importances, and distrust any feature that shouldn't mean anything.

## Things that will bite you

- **Early stopping on the test set.**
- **Categories as integer codes** by accident.
- **Sentinel values for missing** (−999, 0) instead of NaN.
- **Comparing libraries with default parameters** and declaring a winner.
- **`scale_pos_weight` probabilities** served to anyone who reads them as probabilities.
- **Trusting `feature_importances_`.**
- **Upgrading the library** in production without re-validating the saved model's predictions.

## Exercises

1. Why does leaf-wise growth (LightGBM) reach a lower training loss than level-wise growth with the same number of leaves? Why does it make `min_child_samples` more important?
2. Explain the "prediction shift" CatBoost's ordered boosting addresses. How is it related to naive target encoding (18.4)?
3. Write the gradient and Hessian for the asymmetric squared loss $\ell = w(y - F)^2$ with $w = 5$ if $y > F$ and $w = 1$ otherwise.
4. A credit model's partial dependence on income goes up, then briefly down between 80k and 90k, then up again. What would you do, and why might the fix improve test performance?
5. Your team saves XGBoost models with `pickle` and upgrades XGBoost from 1.7 to 3.x. What can go wrong, and what should the deployment process do?

<details>
<summary>Answers</summary>

1. Leaf-wise growth always spends the next split where the gain is largest, anywhere in the tree; level-wise growth must split every node at the current depth, including ones with small gains. With a fixed
   leaf budget, greedy-best-first reaches lower training loss. It also produces deep, narrow branches that can isolate a few examples, so a minimum leaf size is the main guard against fitting noise.

2. In standard boosting, the gradient for row $i$ at round $m$ is computed from a model that was trained on row $i$, so the residuals on training rows are systematically smaller than on new rows: the
   distribution of the model's outputs shifts between train and test. Naive target encoding is the same flaw applied to a feature: each row's encoding includes its own label. CatBoost fixes both by
   computing each row's statistics or residuals using only rows that precede it in a random order.

3. With $r = y - F$: for $r > 0$, $\ell = 5r^2$, gradient in $F$: $-10r$, Hessian $10$. For $r \le 0$, $\ell = r^2$, gradient $-2r$, Hessian $2$. (Both Hessians positive: a well-behaved objective.)

4. Add a monotone increasing constraint on income (if the business logic says more income can't mean more risk), retrain, and compare validation performance. The dip is most likely noise the
   unconstrained model fitted; forbidding it removes variance, so the constrained model often generalizes as well or better, and it passes model review.

5. Pickled models may fail to load, or load and behave differently, across major versions (internal formats, default parameters, and missing-value handling can change). Save models in the library's
   native format, pin versions in the serving image, and in CI load the model with the new version and compare predictions on a fixed reference dataset (50.1) before promoting it.
