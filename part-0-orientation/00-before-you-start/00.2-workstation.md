# 00.2 Your workstation: Linux, shell, Git, Python environments, Docker

*About 5 hours, most of it waiting for downloads. Prerequisites: a computer and admin rights on it.*

I've lost more hours in my life to broken environments than to actual bugs. CUDA version mismatches, a `pip
install` that silently upgraded numpy under another project, a Python that was secretly the system Python, a
Docker volume owned by root. None of that is interesting and none of it teaches you anything, so let's set the
machine up once, properly, and never think about it again. Well, "never". Until the next CUDA release.

## The operating system

Use Linux. If you're on Windows, use WSL2 with Ubuntu. If you're on a Mac, macOS is Unix enough for almost
everything in this course, but know that production runs on Linux, and some tools (GPU stuff, mostly) will
behave differently.

Why I'm so stubborn about this: every server you will ever deploy to runs Linux. Every container you build is
Linux. Every GPU cluster is Linux. If the first time you see `systemctl` is during an incident at 2 AM, you are
going to have a bad night.

On Windows:

```powershell
wsl --install -d Ubuntu-24.04
```

Reboot, open Ubuntu, create your user. Keep your code **inside** the Linux filesystem (`~/code/...`), not in
`/mnt/c/...`. File access across the boundary is painfully slow and you'll think Python is broken.

## The shell

You'll live in the terminal. Not because it's cool (it's a bit cool) but because it's scriptable, and anything
you do twice by clicking you'll eventually want to do a thousand times in a script.

The minimum you should be fluent in:

```bash
pwd; ls -la; cd -; mkdir -p a/b/c          # where am I, what's here, go back, make nested dirs
cp -r src dst; mv a b; rm -r dir           # rm has no trash can. Read the command before Enter.
cat f; less f; head -n 20 f; tail -f log   # look at files; tail -f follows a growing log
grep -rn "pattern" .                       # search recursively with line numbers
find . -name "*.py" -mtime -1              # Python files modified in the last day
wc -l data.csv                             # count lines (rows + header)
du -sh *; df -h                            # what is eating my disk
ps aux | grep python; kill -9 PID          # find and kill the process that ate my RAM
htop; nvidia-smi                           # what the CPU and the GPU are doing right now
export VAR=value; echo $VAR; env           # environment variables
chmod +x script.sh; ./script.sh            # make executable and run
ssh user@host; scp file user@host:path     # remote machines
curl -s https://api.example.com | jq .     # HTTP from the terminal, pretty-printed JSON
```

And pipes, which are the reason Unix won:

```bash
# The 10 most common values in column 3 of a CSV. No pandas required.
cut -d, -f3 data.csv | tail -n +2 | sort | uniq -c | sort -rn | head
```

If half of this is new to you, spend an evening with *The Linux Command Line* by William Shotts (free online).
It's the best investment in this whole module.

## Git

Everything you write in this course goes into Git. Not because I'll check (I won't), but because a portfolio
without history looks like it was copied, and because one day you'll delete something important and `git
reflog` will save your life.

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase true
```

The commands you need daily:

```bash
git status; git diff; git diff --staged     # what changed
git add -p                                  # stage hunk by hunk: read your own diff before committing
git commit -m "Explain why, not what"
git log --oneline --graph -20
git switch -c feature/x; git switch main
git fetch; git rebase origin/main           # replay your work on top of the latest main
git stash; git stash pop
git reflog                                  # the undo button nobody told you about
```

Two rules I learned the hard way:

1. **Never commit secrets.** No API keys, no passwords, no `.env` files, no database dumps. Git remembers
   forever, and bots scan public repositories for keys within minutes of a push. I know because I've run exactly
   that kind of scanner during security assessments, and the hit rate is depressing. Use a `.gitignore` from day one and a tool like `gitleaks` in a
   pre-commit hook.
2. **Never commit data or model weights** larger than a few MB. Git is not a storage system. We'll use proper
   tools for that in module 48.

## Python, done right

Here is the one rule: **never install anything into the system Python.** The system Python belongs to your
operating system. Break it, and you break things like your package manager.

I use [`uv`](https://docs.astral.sh/uv/) for everything now. It manages Python versions, virtual environments
and dependencies, and it's absurdly fast. Plain `python -m venv` plus `pip` also works, just slower.

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh   # read the script first if you're paranoid (you should be)
uv python install 3.11
cd ~/code/no-shortcuts
uv venv --python 3.11
source .venv/bin/activate
uv pip install -r requirements.txt
python -c "import numpy, torch; print(numpy.__version__, torch.__version__)"
```

For your own projects, go one step further and use a `pyproject.toml` with a lock file:

```bash
uv init my-project && cd my-project
uv add numpy pandas scikit-learn
uv add --dev pytest ruff
uv run pytest
```

The lock file (`uv.lock`) pins every transitive dependency to an exact version. Six months from now, `uv sync`
gives you the exact same environment. Without it, you'll get whatever versions happen to be newest that day,
and your code will break for reasons that have nothing to do with you.

**About conda:** it's fine, and in some GPU setups it's easier because it ships binary CUDA libraries. But mixing
conda and pip in the same environment is how people end up with three copies of numpy and a mysterious segfault.
If you use conda, use it for the environment and the heavy binaries, and be careful with pip on top.

## An editor

Use VS Code, PyCharm, Neovim, whatever. My only requirements:

- It runs your code with the virtual environment's Python, not the system one. Check the bottom bar in VS Code.
- It understands `# %%` cells, so you can run the labs cell by cell (VS Code and PyCharm both do).
- It has a linter and formatter. Install `ruff` and let it format on save. Arguing about code style is a waste
  of a life.
- It has a debugger you actually use. Breakpoints beat `print()` for anything non-trivial. I say this as a man
  who still uses `print()` for everything trivial.

## Docker

You need Docker from Part II onwards: to run databases, Kafka, Spark, and later to package your models.

```bash
# Ubuntu / WSL
sudo apt-get update && sudo apt-get install -y docker.io docker-compose-v2
sudo usermod -aG docker $USER    # log out and back in afterwards
docker run --rm hello-world
```

A word from the security side: being in the `docker` group is effectively root on that machine, because you can
mount the host filesystem into a container you control. On your laptop that's fine. On a shared server, it's a
privilege escalation path, and I've used it more than once during tests. Keep that in mind.

The five commands you need for now:

```bash
docker run --rm -it -p 5432:5432 -e POSTGRES_PASSWORD=dev postgres:16   # run something
docker ps; docker logs -f <id>                                          # what's running, what's it saying
docker exec -it <id> bash                                               # get a shell inside
docker compose up -d; docker compose down                               # multi-container setups
docker system prune                                                     # reclaim the 40 GB you didn't know you lost
```

We'll write Dockerfiles properly in module 49.

## GPUs, and what to do if you don't have one

You don't need a GPU for Parts 0 to III. Every lab in the course has a CPU-sized version that runs in minutes.

For Parts IV and V it gets more comfortable with one. Your options, from cheapest:

1. **Google Colab** or **Kaggle notebooks**: free GPUs with time limits. Good enough for every lab here. Upload
   the lab `.py` file, or convert it with `jupytext --to notebook`.
2. **Rent by the hour**: many providers rent a single consumer or datacenter GPU for well under a dollar an hour.
   Turn it off when you're done. People forget. The invoice doesn't.
3. **Your own card**: an NVIDIA card with at least 8 GB of VRAM (12-16 GB is much more comfortable) covers
   everything in this course, including fine-tuning small LLMs with QLoRA.

If you have a local NVIDIA card:

```bash
nvidia-smi                        # driver installed? which CUDA version does the driver support?
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```

If `nvidia-smi` works but torch says `False`, you installed a CPU-only torch wheel or one built for a CUDA version
your driver doesn't support. Go to pytorch.org, use the install selector, and install the matching wheel. This is
the single most common environment problem in deep learning. You're now warned, which means you'll still hit it,
but faster.

> **Scar tissue.** For a university group project I inherited the "working" model of a classmate who'd finished an online course and
> considered himself our group's ML expert. The notebook only ran on his laptop. The requirements file said `tensorflow`, `pandas`,
> `sklearn`. No versions. Two days later I had it running, and it gave different numbers from the ones in our draft report, because a

## Exercises

1. Create a fresh project with `uv init`, add `numpy` and `pytest`, write a function `mean(xs)` and one test for it,
   and run the test with `uv run pytest`. Commit the whole thing, including `uv.lock`.
2. Deliberately commit a fake secret (`API_KEY=sk-test-123`) to a throwaway repo. Then remove it in a second
   commit. Now find it again using only Git commands. What does this tell you about "I deleted it"?
3. Run a PostgreSQL container, connect to it with `psql`, create a table, insert a row, stop the container and
   start it again. Is your row still there? Why, or why not?

<details>
<summary>Answers</summary>

1. The point is the workflow, not the function. If `uv run pytest` works without activating anything, you've
   understood that `uv run` uses the project's environment automatically.
2. `git log -p` shows it, `git log -S "sk-test"` finds the exact commit that added it. Removing a secret in a later
   commit does nothing, it's still in history, and anyone who clones the repo gets it. The only real fix is to
   **rotate the secret** (revoke it and issue a new one). Rewriting history with `git filter-repo` helps, but if the
   repo was ever public, assume the key is already compromised.
3. With `docker run --rm` and no volume, the data is gone: the container's filesystem is thrown away when the
   container is removed. If you only stopped (`docker stop`) and restarted (`docker start`) the same container
   without `--rm`, the data survives. To keep data independently of the container, mount a volume:
   `-v pgdata:/var/lib/postgresql/data`. Containers are cattle, volumes are the farm.

</details>
