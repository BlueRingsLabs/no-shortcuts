# 55.4 Capstone D: a production RAG agent, attacked by you

*About 60 hours. Prerequisites: Part VI, and Capstone A for its data. Code to start from: `part-6-ai-engineering/_shared/`.*

The shop from Capstones A and B wants an assistant for its support team: ask it about an order, a customer's history, the returns
policy or a product, and it answers with sources, or does small things (look up a delivery, draft a reply, open a refund *request* for a
human to approve). Every vendor demo of this looks great. Yours has to survive real users, real documents that someone else wrote, and
you, spending a day trying to make it misbehave, then fixing what you found. The adversarial part is defensive: you test your own system,
with benign canaries, the way 44.2 showed.

## What to build

**1. A knowledge base** (41.3): write or generate 30 to 60 policy and product documents for the shop (returns, shipping by country,
warranty, care instructions, loyalty program), some deliberately contradictory or outdated, with dates and owners. Ingest them with
Capstone A's order and customer data as structured sources.

**2. Retrieval** (41.1 to 41.4): hybrid retrieval with metadata filters (country, validity dates), a reranker, an abstention threshold
tuned on your evaluation set, and access control: a support agent may see the customers and orders of their own queue, nothing else.

**3. Tools** (40.3, 42.2): an MCP server exposing `search_policies`, `get_order`, `get_customer_summary` (no raw personal data beyond what
support needs), `draft_reply` and `request_refund`. Arguments validated with schemas, scoped to the caller's permissions server-side,
idempotency keys on writes, and `request_refund` creating a *request* that a person approves, never a refund.

**4. The agent** (42.1, 42.3): a loop with a step budget, a token budget, loop detection and a clean "I can't do that" path. Decide
whether it should be an agent at all, or a workflow with one model call per step, and justify it with measurements.

**5. A gateway** (45.1): model routing (a small model first, a larger one on low confidence), retries with backoff, timeouts, a fallback
path, caching where safe (and not where it isn't: 45.1's semantic-cache results), cost per conversation tracked.

**6. An evaluation suite** (43.1): at least 150 cases across categories (policy questions, order lookups, multi-step tasks,
unanswerable questions, requests the assistant must refuse), with deterministic checks where possible and an LLM judge validated against
your own labels where not. Report pass rates with intervals, and the list of cases each change fixes and breaks.

**7. Tracing and monitoring** (43.2): every conversation traced (retrieval results, tool calls, tokens, latency, cost, model versions),
dashboards for quality proxies and cost, alerts on regressions.

**8. Adversarial testing of your own system** (44.1, 44.2). Build a test suite, with canaries, for the risks of the OWASP Top 10 for LLM
applications that apply to your design:
- **Indirect injection**: plant documents, ticket texts and customer-provided fields containing instructions that ask the assistant to
  do something harmless but detectable (include a canary string, call a tool it shouldn't need). Measure how often it complies, per
  channel (retrieved document, tool result, user field).
- **Data exposure**: canary personal data belonging to a customer outside the agent's queue. Measure whether any prompt gets it into a
  response or a log.
- **Excessive agency**: attempts to make the assistant call `request_refund` without a clear user request, or for another customer.
- **System prompt and configuration disclosure**, and **unbounded consumption** (long loops, huge outputs).

Then fix what you found with the layered defenses of 44.1 (privilege separation, quarantined processing of untrusted text, output
filtering, tool allowlists per context, human approval) and re-run the suite. Report the before and after, and what still gets through.
A defense that you can't measure isn't done.

## Deliverables

- The repository: ingestion, retrieval, MCP server, agent, gateway, evaluation suite, adversarial suite, dashboards; a README to run it
  all locally with a mock model (for tests) and with a real API or a local model.
- A design doc (47.1) with a threat model (44.2): assets, trust boundaries, who can put text into the system.
- The evaluation report and the adversarial test report, before and after fixes, with the remaining risks stated plainly.
- A runbook: how to roll back a prompt or model change, how to disable a tool in an incident, who gets paged.

## How it will be judged

| criterion | weight |
|---|---|
| evaluation: suite size and coverage, validated judge, fixed-and-broken lists, intervals | 25% |
| security: threat model, adversarial suite with canaries, measured defenses, honest residual risk | 25% |
| retrieval quality and abstention, measured | 15% |
| engineering: permissions server-side, idempotent tools, budgets, gateway, tracing | 25% |
| documentation: design doc, runbook | 10% |

The assistant that says "I don't know, here's who to ask" when it should scores higher than the one that always answers.
