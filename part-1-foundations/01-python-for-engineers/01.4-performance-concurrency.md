# 01.4 Performance, profiling and concurrency

*About 8 hours. Prerequisites: 01.1 to 01.3. Lab: [`lab_01_4_profiling_concurrency.py`](labs/lab_01_4_profiling_concurrency.py).*

Two classic ways to waste a week: optimizing code that wasn't slow, and parallelizing code that couldn't be
parallelized. Both come from the same place, which is guessing instead of measuring. I've watched people on a forum spend
weeks rewriting a data loader in a lower-level language to make training faster, only to find that training was waiting on a
single-threaded JSON parser in a completely different place. The rewrite was beautiful. The training time didn't
move.

This lesson is about measuring first, then choosing the right tool. And, because AI engineering is now mostly
about calling slow remote APIs, it's about concurrency: making a program do useful work while it waits.

## Rule zero: measure

The order of operations is always:

1. Make it correct (with tests, 01.2).
2. Measure where the time actually goes.
3. Fix the biggest thing. Measure again.
4. Stop when it's fast enough for the requirement. "Fast enough" is a number, write it down.

### Timing small things

```python
import timeit
timeit.timeit("sum(range(1000))", number=10_000) / 10_000     # seconds per call
```

In IPython or Jupyter, `%timeit sum(range(1000))` does the same with nicer output. For timing a block inside a
program, use `time.perf_counter()` (the `timer` context manager from 01.1), never `time.time()`, which can jump
when the system clock is adjusted.

### Profiling whole programs

`cProfile` tells you which functions the time goes into:

```bash
python -m cProfile -s cumulative train.py | head -30
```

or inside code:

```python
import cProfile, pstats

with cProfile.Profile() as prof:
    run_pipeline()
pstats.Stats(prof).sort_stats("cumulative").print_stats(15)
```

Read two columns: `tottime` (time spent inside the function itself) and `cumtime` (including everything it
calls). The hotspot is usually a function with a large `tottime` called a huge number of times.

Other tools worth knowing: `py-spy` (a sampling profiler that attaches to a *running* process without modifying it,
great for "why is production slow right now"), `line_profiler` (line-by-line timing of one function), and
`scalene` (CPU, memory and GPU in one report). For PyTorch, the built-in profiler (33.3).

### Memory

```python
import tracemalloc
tracemalloc.start()
data = build_features()
current, peak = tracemalloc.get_traced_memory()
print(f"peak {peak / 1e6:.1f} MB")
```

`tracemalloc` tracks Python allocations; NumPy arrays report their size with `.nbytes`. Peak memory matters more than
final memory: the process dies at the peak.

## Big-O and constants

Complexity is the first thing to check (07.1 covers it properly). A classic in data code:

```python
# O(n * m): for every event, scan the list of blocked users
blocked = load_blocked_users()          # a list with 100k entries
clean = [e for e in events if e.user_id not in blocked]

# O(n + m): a set lookup is O(1) on average
blocked = set(load_blocked_users())
clean = [e for e in events if e.user_id not in blocked]
```

With a million events that's the difference between a few hours and a fraction of a second. One character: `set(...)`.
Always ask: what am I searching in, and what's the lookup cost?

After complexity come constants: Python function call overhead, attribute lookups, object allocation. That's where
vectorization (01.3) wins, by moving the loop into compiled code. If you truly can't vectorize, you can compile the
loop with `numba` (`@numba.njit`), or write that one hot function in Cython or Rust. That's the last resort, not the
first.

## Concurrency vs parallelism

Two words people use interchangeably and shouldn't:

- **Concurrency** is *dealing* with many things at once: structuring a program so that while one task waits
  (for the network, for disk), another makes progress. One cook, several pots.
- **Parallelism** is *doing* many things at once: literally executing on several CPU cores at the same time.
  Several cooks.

Which one you need depends on what your program is waiting for:

| Your program is mostly... | It's called | Use |
|---|---|---|
| Waiting on network or disk (API calls, downloads, DB queries) | I/O-bound | threads or `asyncio` |
| Crunching numbers in pure Python | CPU-bound | processes (`multiprocessing`, `ProcessPoolExecutor`) |
| Crunching numbers in NumPy/PyTorch | CPU-bound, but in C | usually nothing: the library already uses all cores |

### The GIL

CPython has a Global Interpreter Lock: only one thread executes Python bytecode at a time. So threads don't
speed up pure-Python CPU work. But the GIL is **released** while a thread waits for I/O, and most C extensions
(NumPy, PyTorch, compression libraries) release it during heavy computations. That's why threads are perfect for
I/O-bound work and useless for pure-Python number crunching.

Python 3.13 introduced an experimental free-threaded build without the GIL, and it's maturing. Whether your
dependencies support it is another question. For now, assume the GIL exists and design accordingly.

### Threads for I/O

`concurrent.futures` is the easy, high-level API:

```python
from concurrent.futures import ThreadPoolExecutor
import urllib.request


def fetch(url: str) -> int:
    with urllib.request.urlopen(url, timeout=10) as r:
        return len(r.read())


with ThreadPoolExecutor(max_workers=16) as pool:
    sizes = list(pool.map(fetch, urls))
```

100 requests of 200 ms each: sequential, 20 seconds; with 16 threads, about 1.3 seconds.

### Processes for CPU

```python
from concurrent.futures import ProcessPoolExecutor


def simulate(seed: int) -> float:
    ...   # pure-Python Monte Carlo, CPU-heavy


if __name__ == "__main__":          # required: child processes re-import this module
    with ProcessPoolExecutor() as pool:
        results = list(pool.map(simulate, range(100)))
```

Processes have real costs: starting them takes time, and arguments and results are pickled and copied between
processes. Sending a 2 GB DataFrame to each worker is slower than doing the work in one process. Send small
things (a seed, a file path, a row range) and let each worker load its own data.

### asyncio for lots of concurrent I/O

When you have *many* concurrent I/O operations (hundreds or thousands of API calls, which is exactly what LLM
applications do), `asyncio` is lighter than threads:

```python
import asyncio


async def call_model(client, prompt: str, sem: asyncio.Semaphore) -> str:
    async with sem:                               # at most N requests in flight: respect rate limits
        resp = await client.post("/v1/generate", json={"prompt": prompt}, timeout=30)
        resp.raise_for_status()
        return resp.json()["text"]


async def main(prompts: list[str]) -> list[str]:
    sem = asyncio.Semaphore(10)
    async with httpx.AsyncClient(base_url=API_URL) as client:
        tasks = [call_model(client, p, sem) for p in prompts]
        return await asyncio.gather(*tasks)       # results come back in the same order as prompts


results = asyncio.run(main(prompts))
```

`async def` defines a coroutine; `await` is a point where the coroutine can pause and let others run. The whole
thing runs in one thread, switching between tasks whenever one is waiting. The `Semaphore` is the part people
forget: without it, `gather` fires all 10,000 requests at once, the API rate-limits you, and your retries make it
worse. Congratulations, you've launched a denial of service attack on your own vendor. We'll build this properly,
with retries and backoff, in 40.1.

The main rule of asyncio: **never call blocking code inside a coroutine** (`time.sleep`, `requests.get`, heavy
computation). It freezes the whole event loop, every task at once. Use `await asyncio.sleep`, async HTTP clients,
and `asyncio.to_thread(...)` for blocking calls you can't avoid.

### Races and shared state

As soon as threads share mutable state, you can get race conditions: two threads read a counter, both add one,
both write it back, and you've lost an increment. Prefer designs where workers don't share state at all: each
worker gets its input and returns its output, and the main thread combines results (that's what `pool.map` does).
When you must share, use a `threading.Lock` or a `queue.Queue`.

From the security side, races aren't just correctness bugs. "Time-of-check to time-of-use" races are a classic
vulnerability class: checking a permission or a file and then using it, with a gap in between that an attacker
can squeeze into. The mindset is the same: anything that can change between your check and your use, will.

> **Scar tissue.** For a Kaggle competition I once parallelized a feature pipeline with threads, watched all eight cores light up in
> `htop`, and felt very clever. The job got slower. The work was pure-Python string munging, so the threads spent their lives queueing for
> the GIL, and the cores were busy switching between them. Processes made it six times faster; vectorizing the string operations in Arrow
> made it forty times faster, on one thread. Profile first. I skipped that step because I was sure I knew where the time went. I did not.

## Things that will bite you

- Parallelizing before profiling. Your bottleneck may be one line.
- Using threads for pure-Python CPU work and concluding "Python can't parallelize".
- Nested parallelism: 8 processes each running NumPy with 8 BLAS threads on an 8-core machine means 64 threads
  fighting over 8 cores. Set `OMP_NUM_THREADS=1` in worker processes when you parallelize at the process level.
- Unbounded concurrency against external services: always cap it (semaphore, `max_workers`).
- Forgetting `if __name__ == "__main__":` with multiprocessing, which on some platforms spawns processes recursively.

## Exercises

1. A function processes 10,000 files. Each takes 50 ms to read from a network drive and 5 ms of NumPy work.
   Which concurrency tool would you use, and roughly how fast could it get?
2. Profile this and explain the result. Then fix it:

   ```python
   def dedupe(records):
       seen, out = [], []
       for r in records:
           if r["id"] not in seen:
               seen.append(r["id"])
               out.append(r)
       return out
   ```

3. Write an async function that calls a (simulated) API for 200 prompts with at most 20 concurrent calls, where
   each call takes a random 50-150 ms. Measure the total time and compare it with the sequential version and
   with the theoretical best.
4. Why would `ProcessPoolExecutor().map(train_one_fold, folds)` be slower than a plain loop if each fold receives the
   full 5 GB dataset as an argument?

<details>
<summary>Answers</summary>

1. It's I/O-bound (50 ms waiting vs 5 ms computing), so threads (or asyncio if the reader is async). NumPy releases the
   GIL during most computation, so the 5 ms part overlaps too. Sequential: 10,000 x 55 ms = 550 s. With 32 threads,
   bounded by the network drive's throughput, perhaps 20 to 30 s. The real ceiling is usually the storage system,
   not your code, and you find it by measuring at 8, 16, 32, 64 workers.

2. `r["id"] not in seen` on a list is O(len(seen)), so the loop is O(n²). The profiler shows almost all the time in
   that function with no expensive calls inside, a sign of a hot loop. Fix: `seen = set()` and `seen.add(...)`, which
   makes it O(n). If you need to keep the first occurrence, this is also correct; with pandas,
   `df.drop_duplicates("id")` does the same.

3. Sequential: about 200 x 100 ms = 20 s. With 20 concurrent: 200 / 20 = 10 "waves" of about 100 ms each, a bit more
   because of the random durations, so roughly 1.1 to 1.5 s. The theoretical best with unlimited concurrency is the
   slowest single call, about 150 ms. The lab does this.

4. Each task's arguments are pickled and sent to the worker process: 5 GB serialized, copied and deserialized per
   fold, plus the memory for each copy. Pass indices or a file path and have each worker load (or memory-map) the
   data itself. On Linux with the `fork` start method, workers can also inherit a global loaded before the pool
   was created, copy-on-write, but that's fragile and not portable.

</details>
