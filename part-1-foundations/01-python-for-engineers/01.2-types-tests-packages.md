# 01.2 Types, tests and packages: code other people can trust

*About 10 hours. Prerequisites: 01.1. Lab: [`lab_01_2_tested_package.py`](labs/lab_01_2_tested_package.py).*

There's a special kind of silence that follows finding out that a model you've been relying on for a month has
been wrong the whole time, and asking yourself "didn't I have tests for that?". I've been in that silence, alone, more than once.
Usually the answer is "we had tests, but they tested that the code ran, not that it was right".

ML code has a nasty property that normal software doesn't: **it fails silently**. A web service with a bug
usually throws an error. A feature pipeline with a bug produces numbers. Plausible numbers. The model trains on
them, the metrics look okay-ish, and nobody knows the numbers are wrong until the business does. So the
discipline of typing and testing matters *more* in data and ML work, not less. Which is ironic, since it's
exactly where people skip it the most.

## Type hints

Python is dynamically typed, and type hints don't change that at runtime. They're documentation that a tool
can check. That's already worth it.

```python
from collections.abc import Iterable, Sequence
from pathlib import Path


def load_ids(path: Path) -> list[int]:
    return [int(line) for line in path.read_text().splitlines() if line.strip()]


def mean(xs: Sequence[float]) -> float:
    if not xs:
        raise ValueError("mean of empty sequence")
    return sum(xs) / len(xs)


def top_k(scores: dict[str, float], k: int = 5) -> list[tuple[str, float]]:
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)[:k]


def find_user(users: Iterable[dict], user_id: int) -> dict | None:   # may return None: say so
    return next((u for u in users if u["id"] == user_id), None)
```

A few conventions that make hints useful rather than decorative:

- **Accept general types, return specific ones.** Take `Iterable` or `Sequence` as input (anything you can loop
  over or index), return `list` or `dict`. Callers get flexibility on the way in and precision on the way out.
- **Make `None` explicit.** `-> dict | None` forces whoever calls `find_user` to handle the missing case. A type
  checker will complain if they forget. This single habit eliminates a whole category of `'NoneType' object is not
  subscriptable` errors.
- **Don't fight the checker with `Any` everywhere.** `Any` switches checking off. Use it at boundaries (parsed
  JSON, for instance) and narrow it as soon as possible.

Run a type checker (`mypy` or `pyright`) in your editor and in CI:

```bash
uv add --dev mypy
uv run mypy src/
```

For arrays and tensors, type hints are weaker: `np.ndarray` says nothing about shape or dtype, which is where
most bugs live. Put shapes in docstrings and in assertions:

```python
def pairwise_sq_dists(a: np.ndarray, b: np.ndarray) -> np.ndarray:
    """Squared Euclidean distances.

    a: (n, d), b: (m, d)  ->  (n, m)
    """
    assert a.ndim == 2 and b.ndim == 2 and a.shape[1] == b.shape[1], (a.shape, b.shape)
    ...
```

That shape comment is the single most useful line of documentation in numerical code. I'd rather read a function
with shape comments and no docstring than the reverse.

## Tests with pytest

`pytest` is the standard. A test is a function whose name starts with `test_` in a file whose name starts with
`test_`, using plain `assert`:

```python
# tests/test_stats.py
import math
import pytest
from mypkg.stats import mean


def test_mean_simple():
    assert mean([1.0, 2.0, 3.0]) == 2.0


def test_mean_floats():
    assert math.isclose(mean([0.1, 0.2]), 0.15)     # never == for floats


def test_mean_empty_raises():
    with pytest.raises(ValueError, match="empty"):
        mean([])


@pytest.mark.parametrize("xs, expected", [
    ([5.0], 5.0),
    ([-1.0, 1.0], 0.0),
    ([1e308, 1e308], 1e308),        # overflow? sum() gives inf here. Does your function handle it?
])
def test_mean_cases(xs, expected):
    assert mean(xs) == pytest.approx(expected)
```

That third parametrized case is intentional. `sum([1e308, 1e308])` overflows to `inf`, so the naive mean returns
`inf`. Is that acceptable? Maybe, maybe not, but you should *know*, and a test is how you find out. Writing tests
is less about proving code correct and more about forcing yourself to think about the edges.

### What to test in data and ML code

The usual advice ("test every function") doesn't map cleanly onto ML code, so here's what I actually test:

1. **Pure transformations with known answers.** Feature functions, parsers, metric implementations. Hand-compute
   the expected output for a tiny input. If your F1 implementation disagrees with a calculation you did on paper
   for a 2x2 confusion matrix, one of you is wrong.
2. **Invariants.** Properties that must hold for *any* input: probabilities sum to 1, a normalizer outputs mean 0
   and std 1, a train/test split has no overlapping IDs, a pipeline output has the same number of rows as its
   input. These catch far more bugs than example-based tests.
3. **Shapes and dtypes.** A function returning `(n, 1)` instead of `(n,)` is the root of countless broadcasting
   disasters (01.3 will show you one).
4. **Edge cases.** Empty input, a single row, all-NaN columns, a category never seen in training, a string
   where a number was expected.
5. **Model-level smoke tests.** Can the model overfit 10 examples? (If it can't, the training code is broken.) Does
   the output change when the input changes? (If not, something is disconnected.) Is the output deterministic with
   a fixed seed? We'll build these properly in 26.5 and 50.1.

### Property-based testing

Invariants are best tested with **property-based testing**: instead of writing examples, you describe the
*kind* of input and a tool generates hundreds of them, including nasty ones you'd never think of, and shrinks
any failure to the minimal example. The Python library is `hypothesis`:

```python
from hypothesis import given, strategies as st


def standardize(xs: list[float]) -> list[float]:
    m = sum(xs) / len(xs)
    sd = (sum((x - m) ** 2 for x in xs) / len(xs)) ** 0.5
    return [(x - m) / sd for x in xs]


@given(st.lists(st.floats(-1e6, 1e6), min_size=2))
def test_standardize_has_zero_mean(xs):
    z = standardize(xs)
    assert abs(sum(z) / len(z)) < 1e-9
```

Run it and `hypothesis` finds, in about a second, the input `[0.0, 0.0]`: all values equal, standard deviation
zero, division by zero. Did you think of that? Constant columns show up in real datasets all the time (a sensor
that's stuck, a feature that's always null-filled with 0). The fix is a decision: raise, or return zeros, or add
an epsilon. The test forced you to make it.

It gets better. When I wrote the lab for this lesson, my "fixed" version checked `if sd < 1e-12` and returned
zeros. Hypothesis broke that too, in about a second, with three copies of `699051.2584180862`: the computed mean
is off by one unit in the last place, so the computed standard deviation is about `1e-10`, not zero, and the
function divided rounding noise by rounding noise and returned `-1.0` for every element. The fix is a threshold
*relative* to the size of the data. I left the whole story in the lab, because it's the best argument for
property-based testing I've got: it found a bug in code written by a person who was, at that exact moment, writing
a lesson about that family of bugs.

This is fuzzing, by the way, one of the oldest tricks in security testing: throw generated garbage at a
function until it breaks. Engineers who write parsers without fuzzing them are volunteering to be surprised.

### Fixtures

Fixtures give tests shared setup without globals:

```python
import numpy as np
import pytest


@pytest.fixture
def rng():
    return np.random.default_rng(42)            # each test gets a fresh, seeded generator


@pytest.fixture
def toy_dataset(rng):
    X = rng.normal(size=(100, 3))
    y = (X[:, 0] > 0).astype(int)
    return X, y


def test_split_no_overlap(toy_dataset):
    X, y = toy_dataset
    ...
```

`tmp_path` is a built-in fixture that gives each test its own temporary directory, perfect for testing code that
writes files.

## Packaging: `pyproject.toml` and the `src` layout

The moment your code is imported by more than one script, make it a package. The modern layout:

```
my-project/
├── pyproject.toml
├── uv.lock
├── README.md
├── src/
│   └── mypkg/
│       ├── __init__.py
│       ├── features.py
│       └── stats.py
└── tests/
    ├── test_features.py
    └── test_stats.py
```

Why `src/`? Because without it, running tests from the project root imports your package from the *working
directory*, not from the installed version. Everything passes locally, then fails in CI or in the Docker image
because a file wasn't included in the package. The `src` layout forces you to install the package (editable,
during development) and test what you'd actually ship.

A minimal `pyproject.toml`:

```toml
[project]
name = "mypkg"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
    "numpy>=1.26",
    "pandas>=2.1",
]

[dependency-groups]
dev = ["pytest>=8", "hypothesis>=6", "mypy>=1.10", "ruff>=0.5"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "S"]    # S = flake8-bandit: basic security lints

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-q"
```

Two notes on dependencies, one engineering and one security:

- **Libraries declare ranges, applications pin exact versions.** The `dependencies` list says what your code is
  compatible with (`numpy>=1.26`). The lock file (`uv.lock`) pins exactly what gets installed. Commit both.
- **Every dependency is attack surface.** Typosquatting (a malicious package named `reqeusts` or
  `scikit-learm`), compromised maintainer accounts and malicious post-install scripts are real and recurrent.
  Before adding a dependency, check that it's the package you think it is, that it's maintained, and that you
  actually need it. The lock file with hashes protects you from a package being swapped under you. We'll go deeper
  in 53.2.

## Linting and formatting

Use `ruff` for both. It's fast enough to run on every save:

```bash
uv run ruff check --fix .      # lint, auto-fix what's safe to fix
uv run ruff format .           # format (Black-compatible)
```

Put it, together with the tests and the type checker, in a pre-commit hook and in CI. Code review time should be
spent on logic, not on whitespace.

## Logging, not printing

`print` is for scripts you run once. Anything that runs unattended should log:

```python
import logging

log = logging.getLogger(__name__)       # one logger per module, named after it


def train(cfg):
    log.info("starting training with lr=%s batch=%s", cfg.lr, cfg.batch_size)
    ...
    log.warning("validation loss increased for %d epochs", patience)
```

And configure logging once, at the entry point:

```python
logging.basicConfig(level=logging.INFO,
                    format="%(asctime)s %(levelname)s %(name)s: %(message)s")
```

Use `%s` placeholders instead of f-strings in log calls: the string is only formatted if the message is actually
emitted, and structured-logging tools can group messages by their template. And **never log secrets or personal
data**. Logs get shipped to places with much weaker access control than your database. I have found API keys,
passwords and customer records in logs more times than I can count, and "it was only in the debug logs" has
never once been a good defense.

## Configuration

Hard-coded paths and hyperparameters scattered through the code are a reproducibility killer. Pick one approach:

- A frozen dataclass (01.1) populated from a YAML file or CLI arguments, logged at the start of every run.
- Environment variables for things that change per deployment (URLs, credentials), read once at startup.
  Secrets come from the environment or a secrets manager, never from the repository.

A small CLI with `argparse` (standard library) or `typer` makes a script reusable:

```python
import argparse


def main() -> None:
    p = argparse.ArgumentParser(description="Train the churn model")
    p.add_argument("--data", type=Path, required=True)
    p.add_argument("--lr", type=float, default=1e-3)
    p.add_argument("--seed", type=int, default=0)
    args = p.parse_args()
    ...


if __name__ == "__main__":
    main()
```

## Things that will bite you

- Tests that pass because they test nothing: `assert result` is true for any non-empty result, correct or not.
  Assert on *values*.
- Tests that depend on each other or on execution order, often through a shared global or a file on disk.
- Floating point equality in tests. Use `pytest.approx` or `np.testing.assert_allclose`, with tolerances you chose
  deliberately.
- Randomness in tests without a seed: a test that fails 1% of the time will fail in CI on the Friday before a
  release. Guaranteed.
- `pip install` without a lock file in your Docker image: the image you build next month is not the image you
  tested.

## Exercises

1. Add type hints to this function and find the bug using only reasoning (then confirm with mypy if you like):

   ```python
   def normalize_scores(scores, total=None):
       if total == 0:
           return scores
       return {k: v / total for k, v in scores.items()}
   ```

2. Write a property-based test for a function `train_test_split_ids(ids, test_frac, seed)` that returns two lists.
   List at least four properties that must hold for any input.

3. Here's a metric implementation. Write three example-based tests that would catch the bug, one of which uses a
   hand-computed confusion matrix:

   ```python
   def precision(y_true, y_pred):
       tp = sum(1 for t, p in zip(y_true, y_pred) if t == 1 and p == 1)
       fp = sum(1 for t, p in zip(y_true, y_pred) if t == 1 and p == 0)
       return tp / (tp + fp)
   ```

4. Why does the `src/` layout catch the bug "I forgot to include `data/schema.json` in the package", while the flat
   layout doesn't?

<details>
<summary>Answers</summary>

1. With hints: `def normalize_scores(scores: dict[str, float], total: float | None = None) -> dict[str, float]`.
   The bug: when `total` is `None` (the default!), `total == 0` is `False`, and then `v / None` raises
   `TypeError`. The author probably meant "if no total is given, use the sum of the scores". Once you write
   `float | None`, a type checker complains that you divide by something that might be `None`. That's the point
   of `Optional` in hints: it makes you handle the case.

   ```python
   def normalize_scores(scores: dict[str, float], total: float | None = None) -> dict[str, float]:
       if total is None:
           total = sum(scores.values())
       if total == 0:
           raise ValueError("cannot normalize scores that sum to zero")
       return {k: v / total for k, v in scores.items()}
   ```

2. For any list of unique IDs, any `test_frac` in (0, 1) and any seed: (a) the two lists are disjoint; (b) their
   union equals the input set, so nothing is lost or duplicated; (c) the test size is `round(test_frac * n)` or
   within 1 of it; (d) the same seed gives the same split (determinism); (e) the output doesn't depend on the
   order of the input IDs, if that's a requirement (it should be, otherwise re-reading the same data in a
   different order changes your test set). Property (e) is the one people forget, and it's the one that bites
   when a database query returns rows in a different order one day.

3. The bug: `fp` counts cases where `t == 1 and p == 0`, which are false *negatives*. False positives are
   `t == 0 and p == 1`. Tests:
   - `y_true=[0, 1], y_pred=[1, 1]`: TP=1, FP=1, precision 0.5. The buggy code gives 1.0.
   - `y_true=[1, 1], y_pred=[1, 0]`: TP=1, FP=0, precision 1.0. The buggy code gives 0.5.
   - All predictions negative: `y_pred=[0, 0]`. Precision is undefined (0/0). The buggy code may crash or not
     depending on labels; decide what you want (scikit-learn returns 0 with a warning, configurable with
     `zero_division`) and test that.
   Compare your function with `sklearn.metrics.precision_score` on random inputs: a "reference implementation"
   test is a great way to test metrics.

4. With `src/`, your tests import the *installed* package. If the package build doesn't include `schema.json`,
   the installed package doesn't have it, and the test that loads it fails, locally, before you ship. With the
   flat layout, Python imports the package directly from the source folder next to the tests, where the file
   exists, so the test passes and the missing file only shows up when someone installs the wheel.

</details>
