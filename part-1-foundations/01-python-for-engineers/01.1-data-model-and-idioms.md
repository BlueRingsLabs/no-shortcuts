# 01.1 Python's data model and the idioms that matter

*About 10 hours. Prerequisites: you can already write Python functions, loops and classes. Lab:

Most ML code I've reviewed in my life was written by people who learned Python from notebook tutorials. You can
tell immediately. Global variables everywhere, a 400-line cell called `main`, lists appended in loops for
things that should be generators, `except: pass` hiding the one error that mattered, and a class with a single
method called `run`. It works, in the sense that a car held together with tape works.

This lesson is not about syntax. You know the syntax. It's about how Python actually works underneath, because
once you understand the data model, a lot of "magic" in libraries like PyTorch, pandas and scikit-learn stops
being magic, and your own code starts looking like it was written by an engineer.

## Everything is an object, and names are just labels

In Python, variables don't contain values. Names *refer to* objects. This one sentence explains about a third of
the bugs beginners hit.

```python
a = [1, 2, 3]
b = a            # b is another label on the SAME list
b.append(4)
print(a)         # [1, 2, 3, 4]  <- surprise, if you thought b was a copy
print(a is b)    # True: same object
print(id(a) == id(b))  # True: same identity
```

Every object has an **identity** (`id()`, roughly its memory address), a **type**, and a **value**. `is` compares
identity, `==` compares value. Use `is` only for singletons like `None`: `if x is None`, never `if x == None`.

Mutable objects (lists, dicts, sets, numpy arrays, tensors) can change their value in place. Immutable ones
(ints, floats, strings, tuples, frozensets) can't: any "modification" creates a new object.

```python
x = 10
y = x
y += 1        # ints are immutable: y now points to a NEW int object, 11
print(x)      # 10

u = [10]
v = u
v += [11]     # lists are mutable: += modifies in place
print(u)      # [10, 11]
```

That last example is subtle: `+=` on a list calls `__iadd__`, which mutates. On a tuple it would create a new
tuple. Same operator, different behavior, because the *type* decides.

### The classic trap: mutable default arguments

```python
def add_item(item, bucket=[]):   # the default list is created ONCE, when the function is defined
    bucket.append(item)
    return bucket

add_item(1)   # [1]
add_item(2)   # [1, 2]  <- the same list, shared across calls
```

Default values are evaluated once, at definition time. The fix is the idiom you'll see everywhere:

```python
def add_item(item, bucket=None):
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket
```

I once spent a very long afternoon on a feature pipeline where a function with `cache={}` as a default was
quietly sharing state between what were supposed to be independent training runs. The results were
"reproducible", in the sense that they were reproducibly wrong. Learn this one now.

### Copies: shallow and deep

```python
import copy
config = {"layers": [64, 32], "lr": 1e-3}
shallow = dict(config)          # or config.copy()
deep = copy.deepcopy(config)
shallow["layers"].append(16)    # modifies the SAME inner list
print(config["layers"])         # [64, 32, 16]
deep["layers"].append(8)
print(config["layers"])         # [64, 32, 16]  <- deep copy is independent
```

A shallow copy copies the outer container but shares the inner objects. When you pass configs around in an
experiment framework, this matters. Numpy has the same distinction with *views* vs copies, which we'll see in
01.3, and PyTorch tensors too.

## The data model: dunder methods

Python's syntax is a thin layer over special methods, the "dunder" (double underscore) methods. When you write
`a + b`, Python calls `a.__add__(b)`. `len(x)` calls `x.__len__()`. `x[i]` calls `x.__getitem__(i)`. `for item
in x` calls `iter(x)`, which calls `x.__iter__()`. `with x:` calls `__enter__` and `__exit__`.

This is how numpy makes `a @ b` do matrix multiplication (`__matmul__`), how pandas makes `df["col"]` work
(`__getitem__`), and how PyTorch builds a computational graph when you write `loss = (y - y_hat) ** 2`: every
operator on a tensor is a dunder method that records what happened.

Let's build a tiny vector class to see it. This is also a preview of the autograd engine we'll write in 24.3.

```python
from __future__ import annotations
import math


class Vec:
    """A small immutable 2D/3D/nD vector. For learning, not for production (use numpy)."""

    __slots__ = ("_xs",)  # no per-instance __dict__: less memory, and typos in attribute names fail loudly

    def __init__(self, *xs: float) -> None:
        self._xs = tuple(float(x) for x in xs)

    # --- representation: what you see in the REPL and in logs
    def __repr__(self) -> str:
        return f"Vec{self._xs}"

    # --- container protocol
    def __len__(self) -> int:
        return len(self._xs)

    def __getitem__(self, i: int) -> float:
        return self._xs[i]

    def __iter__(self):
        return iter(self._xs)

    # --- arithmetic
    def __add__(self, other: Vec) -> Vec:
        self._check(other)
        return Vec(*(a + b for a, b in zip(self, other)))

    def __sub__(self, other: Vec) -> Vec:
        self._check(other)
        return Vec(*(a - b for a, b in zip(self, other)))

    def __mul__(self, k: float) -> Vec:          # v * 3
        return Vec(*(k * a for a in self))

    __rmul__ = __mul__                            # 3 * v  (Python tries int.__mul__ first, fails, then this)

    def __matmul__(self, other: Vec) -> float:    # v @ w  = dot product
        self._check(other)
        return sum(a * b for a, b in zip(self, other))

    def __abs__(self) -> float:                   # abs(v) = Euclidean norm
        return math.sqrt(self @ self)

    # --- comparison and hashing
    def __eq__(self, other: object) -> bool:
        return isinstance(other, Vec) and self._xs == other._xs

    def __hash__(self) -> int:                    # equal objects must have equal hashes
        return hash(self._xs)

    def __bool__(self) -> bool:                   # the zero vector is "falsy", like 0 and []
        return any(self._xs)

    def _check(self, other: Vec) -> None:
        if len(self) != len(other):
            raise ValueError(f"dimension mismatch: {len(self)} vs {len(other)}")
```

```python
v, w = Vec(1, 2), Vec(3, 4)
v + w          # Vec(4.0, 6.0)
3 * v          # Vec(3.0, 6.0)
v @ w          # 11.0
abs(w)         # 5.0
{v, Vec(1, 2)} # {Vec(1.0, 2.0)}  one element: equal and same hash
```

A few details worth noticing, because they're the kind of thing that separates "works" from "correct":

- `__rmul__` exists because `3 * v` first tries `int.__mul__(3, v)`, which returns `NotImplemented`, and then
  Python tries the reflected `v.__rmul__(3)`. This protocol is how `2 * tensor` works in PyTorch.
- If you define `__eq__`, you must define `__hash__` consistently or make the object unhashable. Two objects that
  compare equal must have the same hash, otherwise dicts and sets silently misbehave.
- `__repr__` should be unambiguous and ideally look like code that recreates the object. When you're debugging
  from logs at 3 AM, you'll thank yourself.
- `__slots__` makes attribute typos raise `AttributeError` instead of silently creating a new attribute. On
  classes you create millions of instances of, it also saves real memory.

## Iterators and generators

The iterator protocol is two methods: `__iter__` returns an iterator, and the iterator's `__next__` returns the
next item or raises `StopIteration`. A `for` loop is just:

```python
it = iter(collection)
while True:
    try:
        item = next(it)
    except StopIteration:
        break
    ...  # loop body
```

Generators are the easy way to write iterators. A function with `yield` returns a generator object; its body runs
lazily, pausing at each `yield`:

```python
def read_batches(path: str, batch_size: int):
    """Yield lists of lines from a file that may be far bigger than RAM."""
    batch = []
    with open(path) as f:
        for line in f:                 # file objects are themselves lazy iterators
            batch.append(line.rstrip("\n"))
            if len(batch) == batch_size:
                yield batch
                batch = []
    if batch:                          # don't forget the last, partial batch (classic off-by-one)
        yield batch
```

This processes a 50 GB log file with a few kilobytes of memory. This is exactly the pattern behind data loaders
in every deep learning framework, and behind streaming pipelines in Part II. When someone reads a whole file
into a list "because it's easier", they're writing code that works on their laptop and dies in production when
the file grows.

Generator expressions are the lazy version of list comprehensions:

```python
total = sum(len(line) for line in open("huge.log"))   # lazy: constant memory
lines = [line for line in open("huge.log")]            # eager: everything in RAM
```

And the `itertools` module is a toolbox you should know exists: `islice` (take the first n of an infinite
iterator), `chain` (concatenate iterables), `groupby` (group consecutive items), `product`, `combinations`,
`accumulate`, and since Python 3.12, `batched`.

```python
from itertools import islice, count
squares = (n * n for n in count())      # infinite, but lazy, so that's fine
list(islice(squares, 5))                # [0, 1, 4, 9, 16]
```

One warning: a generator can be consumed only once. Iterate over it a second time and you get nothing, silently.

```python
g = (x for x in range(3))
list(g)   # [0, 1, 2]
list(g)   # []  <- no error, just empty. Enjoy debugging that in a training loop.
```

## Context managers

Anything that must be cleaned up (files, locks, database connections, GPU memory, timers, temporary directories)
should be handled with `with`. The `__exit__` method runs even if an exception is raised inside the block.

```python
import time
from contextlib import contextmanager


@contextmanager
def timer(name: str):
    t0 = time.perf_counter()
    try:
        yield
    finally:                                 # runs on success AND on exception
        print(f"{name}: {time.perf_counter() - t0:.3f}s")


with timer("load"):
    data = [i ** 2 for i in range(1_000_000)]
```

You'll see this pattern everywhere in ML: `torch.no_grad()`, `torch.autocast(...)`, `mlflow.start_run()`,
`tempfile.TemporaryDirectory()`. They're all context managers that set something up and guarantee it's undone.

## Functions as objects: closures and decorators

Functions are objects. You can pass them around, return them, and store them in dicts. A **closure** is a
function that remembers variables from the scope where it was created:

```python
def make_scaler(mean: float, std: float):
    def scale(x: float) -> float:
        return (x - mean) / std        # mean and std are captured from the enclosing scope
    return scale

z = make_scaler(10.0, 2.0)
z(14.0)    # 2.0
```

A **decorator** is just a function that takes a function and returns a new one. `@decorator` above a `def` is
syntax sugar for `f = decorator(f)`:

```python
import functools
import time


def retry(times: int = 3, delay: float = 0.5, exceptions=(Exception,)):
    """Retry a flaky call (network, rate-limited API) with exponential backoff."""
    def decorator(fn):
        @functools.wraps(fn)                 # keep the original name and docstring
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return fn(*args, **kwargs)
                except exceptions:
                    if attempt == times - 1:
                        raise                # out of attempts: re-raise the real error
                    time.sleep(delay * 2 ** attempt)
        return wrapper
    return decorator


@retry(times=5, exceptions=(ConnectionError, TimeoutError))
def fetch_features(user_id: int) -> dict: ...
```

Note two engineering decisions there. First, it retries only on the exceptions you name. Retrying on *every*
exception means retrying on bugs, which just makes the bug slower. Second, after the last attempt it re-raises
instead of returning `None`. Silent failure is the worst kind. We'll use exactly this pattern when calling LLM
APIs in 40.1.

`functools` also gives you `lru_cache` / `cache` for memoization, `partial` for fixing arguments, and
`cached_property` for expensive attributes computed once.

## Dataclasses: stop writing boilerplate

For classes that are mostly data (configs, records, results), use `dataclasses`:

```python
from dataclasses import dataclass, field, asdict, replace


@dataclass(frozen=True)          # frozen: immutable and hashable, great for configs
class TrainConfig:
    lr: float = 1e-3
    batch_size: int = 64
    epochs: int = 10
    layers: tuple[int, ...] = (128, 64)
    tags: frozenset[str] = field(default_factory=frozenset)

    def __post_init__(self):
        if not (0 < self.lr < 1):
            raise ValueError(f"lr={self.lr} looks wrong")


cfg = TrainConfig(lr=3e-4)
asdict(cfg)                       # plain dict, easy to log to your experiment tracker
cfg2 = replace(cfg, batch_size=128)   # "modify" a frozen config by making a new one
```

You get `__init__`, `__repr__` and `__eq__` for free, plus validation in `__post_init__`. For configs that come
from outside your program (YAML files, API requests, LLM outputs), you want real validation with types coerced
and errors reported nicely; that's what `pydantic` is for, and we'll use it in Part VI.

## Errors: fail loudly, fail early

Exceptions are for exceptional situations, and the golden rule is: **never swallow an exception you don't
understand.**

```python
# Terrible. I have seen this in production code that handled money.
try:
    result = process(record)
except:
    pass

# Better: catch what you expect, handle it, log it, and let everything else crash.
import logging
log = logging.getLogger(__name__)

try:
    result = process(record)
except ValidationError as e:
    log.warning("skipping invalid record %s: %s", record.get("id"), e)
    result = None
```

A bare `except:` also catches `KeyboardInterrupt` and `SystemExit`, which means Ctrl+C won't stop your script.
If you must catch broadly, catch `Exception`, log it with `log.exception(...)` (which includes the traceback),
and think very hard about whether continuing is safe.

From the security side: error messages leak information. A stack trace returned to a user of your model API
tells an attacker your framework, library versions, file paths and sometimes chunks of data. Log the details
internally, return a generic error externally. We'll come back to this in 49.1.

## Idioms, briefly

These are small, but reviewers notice them:

```python
for i, x in enumerate(xs): ...                 # not: for i in range(len(xs))
for x, y in zip(xs, ys, strict=True): ...      # strict=True raises if lengths differ (3.10+). Use it.
counts = collections.Counter(words)            # not: a dict with manual +1
groups = collections.defaultdict(list)
first, *rest = items                           # unpacking
x = cfg.get("key", default)                    # not: cfg["key"] if "key" in cfg else default
if not items: ...                              # empty containers are falsy
path = pathlib.Path("data") / "raw" / "x.csv"  # not: string concatenation with "/"
f"{loss:.4f}"                                  # f-strings for formatting
```

`zip(..., strict=True)` deserves a special mention. The default `zip` stops silently at the shortest input. I've
seen features and labels zipped together where one list was one element shorter because of a filtering step,
shifting every label by one row. The model trained fine. It just learned garbage. `strict=True` turns that into
an immediate error.

> **Scar tissue.** A friend with a startup and two paying customers asked me, as a freelance favor, to find out why his recommendation API
> occasionally returned another user's recommendations. He'd already decided it was a race condition in the web server. It was `def
> build_features(row, cache={})`: a mutable default argument, created once when the module loaded and shared by every request the process
> ever served, added as a "harmless" optimization to skip a lookup. A week of theories, one line of Python. I now read default arguments
> the way I read `chmod 777`.

## Things that will bite you

- **Mutable defaults** and **shared references** (the `b = a` problem). Every framework has its version of this:
  numpy views, pandas chained assignment, PyTorch in-place operations on tensors needed for backward.
- **Exhausted generators** that silently yield nothing the second time.
- **Silent truncation** in `zip`. Use `strict=True`.
- **Floating point equality**: `0.1 + 0.2 == 0.3` is `False`. Use `math.isclose` or `np.allclose`. Module 07.2
  explains why.
- **Late binding in closures**: `[lambda: i for i in range(3)]` gives three functions that all return 2, because
  `i` is looked up when the lambda is *called*. Fix with a default argument: `lambda i=i: i`.

1. `[[1, 0, 0], [1, 0, 0], [1, 0, 0]]`. `[x] * 3` repeats the *reference* to the same inner list three times, so all
   rows are the same object. Correct version: `a = [[0] * 3 for _ in range(3)]`, which creates a new inner list
   per row. (The inner `[0] * 3` is fine because ints are immutable.)

2. One reasonable implementation:

   ```python
   def __neg__(self): return Vec(*(-a for a in self))
   def __truediv__(self, k): return Vec(*(a / k for a in self))
   def normalized(self):
       """Unit vector in the same direction. Raises ValueError for the zero vector,
       because it has no direction and returning zeros would silently hide a bug upstream."""
       n = abs(self)
       if n == 0:
           raise ValueError("cannot normalize the zero vector")
       return self / n
   ```

   Returning the zero vector unchanged is also defensible (some libraries do it, and some add a small epsilon
   to the norm), but then the caller must know. Whatever you pick, the docstring must say it. Silent choices
   are the ones that hurt.

3. ```python
   from collections import deque
   from itertools import islice

   def sliding_window(iterable, n):
       it = iter(iterable)
       window = deque(islice(it, n), maxlen=n)
       if len(window) == n:
           yield tuple(window)
       for x in it:
           window.append(x)          # maxlen drops the oldest element automatically
           yield tuple(window)
   ```

   Since Python 3.12 there's `itertools.pairwise` for n=2, and the itertools docs have this exact recipe.

4. ```python
   import random
   from contextlib import contextmanager

   @contextmanager
   def set_seed(seed):
       state = random.getstate()
       random.seed(seed)
       try:
           yield
       finally:
           random.setstate(state)
   ```

   Restoring the state means a block of code can be made deterministic without affecting the randomness of the
   rest of the program. That matters when, say, you want a reproducible data split inside a larger experiment
   whose other random choices should stay independent.

   with an idempotency key that the server uses to deduplicate. Payment APIs do exactly this. We'll see the same
