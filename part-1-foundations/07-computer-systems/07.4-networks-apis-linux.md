# 07.4 Networks, APIs and Linux processes

*About 9 hours. Prerequisites: 00.2, 01.4. Lab: [`lab_07_4_networks_processes.py`](labs/lab_07_4_networks_processes.py).*

Every model you deploy becomes a process on a Linux machine, listening on a network port, answering HTTP requests,
reading secrets from its environment, and getting killed and restarted by an orchestrator that doesn't care about your
feelings. Every data pipeline you build pulls from APIs that time out, rate-limit you and occasionally return HTML error
pages with a 200 status code. And every LLM application in Part VI is, mechanically, a program that makes a lot of HTTP
calls and has to survive them failing.

I've spent a lot of my career on the other side of these systems, looking for the open port nobody knew about, the debug
endpoint left enabled, the API that trusted whatever the client sent. So this lesson has two goals: give you the working
knowledge of networks, HTTP and processes that ML courses assume you already have, and give you the reflexes that keep
your services from becoming someone else's entry point.

## Networking, the ten-minute version

When your code calls `https://api.example.com/v1/predict`:

1. **DNS** resolves `api.example.com` to an IP address. (DNS failures and slow DNS are real causes of "the API is down" incidents. So is
   DNS caching with a stale IP after a migration.)
2. **TCP** opens a connection to that IP on port 443: a three-way handshake, one network round trip before any data flows. TCP gives you a
   reliable, ordered byte stream on top of an unreliable network.
3. **TLS** negotiates encryption: another round trip or so (TLS 1.3 reduced it), and certificate verification. This is where "certificate
   verify failed" errors come from. The fix is almost never to disable verification. I've found `verify=False` in production code
   more times than I'd like, usually with a comment like `# TODO fix later`. Later never comes, and now anyone on the network path can read and
   modify your traffic.
4. **HTTP** sends the request (method, path, headers, body) and reads the response (status, headers, body).

So a single request to a far-away server can cost several round trips before the first byte of the answer, which is why **connection reuse**
(keep-alive, connection pools) matters so much for latency: create one `requests.Session` or `httpx.Client` and reuse it, instead of calling
`requests.get` a thousand times.

Ports: a process listens on a port (8000, 443, 5432 for PostgreSQL, 6379 for Redis, 9092 for Kafka). **Binding to `0.0.0.0` means "accept connections
from anywhere"**; binding to `127.0.0.1` means "only from this machine". Half of the exposed databases and Jupyter servers I've found in security
assessments were somebody binding to `0.0.0.0` on a cloud VM with a permissive firewall, "just for testing".

## HTTP and REST

An HTTP request has a **method**, a **path**, **headers** and an optional **body**:

```
POST /v1/predict HTTP/1.1
Host: api.example.com
Authorization: Bearer <token>
Content-Type: application/json
Idempotency-Key: 7b1c...

{"features": [0.3, 1.2, 5.0]}
```

Methods and their semantics (which servers should respect and clients can rely on):

| Method | Meaning | Safe? | Idempotent? |
|---|---|---|---|
| GET | read a resource | yes | yes |
| POST | create / trigger an action | no | no |
| PUT | replace a resource | no | yes |
| PATCH | modify part of a resource | no | not necessarily |
| DELETE | delete a resource | no | yes |

**Idempotent** means doing it twice has the same effect as doing it once. It matters for retries (01.1): retrying a GET or a PUT is safe; retrying a
POST that charges money is not, unless the API supports an **idempotency key** that lets the server recognize and ignore the duplicate.

Status codes, the ones you'll handle:

- **2xx success**: 200 OK, 201 Created, 202 Accepted (queued for later), 204 No Content.
- **4xx client errors (your fault, don't retry blindly)**: 400 Bad Request, 401 Unauthorized (not authenticated), 403 Forbidden (authenticated but not
  allowed), 404 Not Found, 409 Conflict, 422 Unprocessable (validation failed), **429 Too Many Requests** (rate limited: retry, but *later*,
  respecting the `Retry-After` header).
- **5xx server errors (their fault, usually worth retrying with backoff)**: 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable,
  504 Gateway Timeout.

**REST** is a style of API design around resources and these methods (`GET /models/42`, `POST /models/42/predictions`). **JSON** is the usual body
format. Alternatives you'll meet: gRPC (binary, schema-first, faster, common between internal services and in model servers), WebSockets and
Server-Sent Events (for streaming, which is how LLM APIs stream tokens, 40.1).

### Calling APIs like a professional

The checklist I apply to every HTTP client I write or review:

1. **Always set a timeout.** The default in `requests` is to wait forever. One hung connection and your pipeline hangs with it.
2. **Retry only what's retryable** (connection errors, 429, 5xx), with **exponential backoff and jitter**, and a cap on attempts. Jitter (a random
   component in the delay) avoids the "thundering herd" where all clients retry at the same instant and knock the server over again.
3. **Respect rate limits** and cap your own concurrency (the semaphore from 01.4).
4. **Check the status code and validate the body.** Parse errors are errors.
5. **Reuse connections.**
6. **Log requests with their latency and status, never with their secrets.** Authorization headers and API keys in logs are one of the most common
   credential leaks there are.

### Latency is a distribution

A service doesn't have "a latency". It has a latency distribution, and it's usually heavy-tailed (04.1): most requests are fast, a few are very slow
(garbage collection pauses, cache misses, a slow disk, a noisy neighbour). You report **percentiles**: p50 (median), p95, p99. The mean is misleading
because the tail drags it.

The tail matters more than you'd think. If a page makes 20 backend calls in parallel and waits for all of them, and each has a 1% chance of being
slow, then $1 - 0.99^{20} \approx 18\%$ of page loads hit at least one slow call. Your p99 backend latency becomes the p82 of the user experience. Dean and
Barroso's "The Tail at Scale" is about exactly this, and about tricks like hedged requests (send a duplicate after a short delay, use whichever answer
comes first).

## Linux processes

A **process** is a running program with its own memory, a PID, an owner (user), environment variables, open file descriptors and a parent. Things to
know:

- **Environment variables** are how configuration and secrets reach your service in containers and orchestrators: `os.environ["DATABASE_URL"]`.
  Read them once at startup, validate them, fail fast if something required is missing. Remember that environment variables are visible to anyone
  who can read `/proc/<pid>/environ` as the same user, and they often end up in crash dumps and debug pages. A secrets manager is better for high-value
  secrets.
- **Signals** are how the system talks to processes. `SIGTERM` means "please shut down" (sent by `kill`, `docker stop`, Kubernetes before evicting a
  pod). `SIGINT` is Ctrl+C. `SIGKILL` (`kill -9`) can't be caught: the process just dies. A well-behaved service catches `SIGTERM`, stops accepting new
  work, finishes in-flight requests, flushes logs and exits within the grace period (30 seconds by default in Kubernetes). A training job should
  checkpoint on `SIGTERM`, especially on preemptible/spot instances (52.1), where that signal is your only warning.
- **Exit codes**: 0 means success, anything else is failure. Orchestrators (Airflow, Kubernetes, CI) decide what to do based on them. A script that
  catches every exception and exits 0 is lying to its orchestrator.
- **stdout and stderr**: in containers, log to stdout/stderr and let the platform collect it. Don't write log files inside containers.
- **File descriptors and limits**: every open file and socket uses one. "Too many open files" means a leak (not closing files or connections) or a limit
  that's too low (`ulimit -n`).
- **Users and permissions**: don't run services as root. In containers, set a non-root user (49.2). If an attacker gets code execution in your model server
  (and 53.2 will show you how easy that is with unsafe model files), the privileges of that process are what they get.

Useful commands, beyond 00.2: `ss -tlnp` (what's listening on which port, and which process), `lsof -p PID` (open files and sockets), `strace -p PID` (what
system calls a stuck process is making), `journalctl -u service` (systemd logs), `curl -v` (see the whole HTTP exchange, including TLS).

## A minimal model service, and what's wrong with it

To make this concrete, here's the kind of thing people write first:

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import json, pickle

model = pickle.load(open("model.pkl", "rb"))       # (1)

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))   # (2)
        pred = model.predict([body["features"]])[0]                               # (3)
        self.send_response(200)
        self.end_headers()
        self.wfile.write(json.dumps({"prediction": float(pred)}).encode())

HTTPServer(("0.0.0.0", 8000), Handler).serve_forever()                            # (4)
```

What I'd flag in a review: (1) unpickling a file is arbitrary code execution if anyone can replace it (53.2); (2) no size limit on the body (an attacker
sends 10 GB), no validation of the JSON, no error handling (a bad request crashes the handler and returns a stack trace); (3) no input validation (wrong
number of features, NaNs, strings); (4) listening on all interfaces, no authentication, no TLS, single-threaded, no health check, no graceful shutdown,
no logging, no timeouts. It works on the demo. It's also a small catalogue of findings. In 49.1 we'll build the production version with FastAPI, pydantic
validation, health endpoints and proper shutdown. The lab builds a small but less naive version so you can see each piece working.

## Exercises

1. A client makes requests to a server 150 ms away (round trip). Without connection reuse, each request needs TCP + TLS 1.3 handshakes (about 2 round
   trips) plus the request itself (1 round trip). How long do 100 sequential requests take with and without keep-alive?
2. Which of these should a client retry automatically: connection refused, 400, 401, 429, 500, 503, timeout on a POST that creates an order? For the ones
   you'd retry, how?
3. Your service's p50 is 20 ms and p99 is 900 ms. A page calls it 10 times in parallel. Roughly what fraction of page loads wait at least 900 ms?
4. Write the `SIGTERM` handling you'd want in a training script running on a spot instance.
5. List five things wrong with the minimal model service above and the fix for each.

<details>
<summary>Answers</summary>

1. Without keep-alive: 3 round trips per request × 150 ms × 100 = 45 s. With keep-alive: 2 round trips once, then 1 per request: 0.3 + 15 = 15.3 s.
   (With HTTP/2 multiplexing or concurrency, much less.)

2. Retry: connection refused (maybe the server is restarting, a few times with backoff), 429 (after `Retry-After`), 500, 503 (with exponential
   backoff and jitter). Don't retry: 400 (your request is wrong; fix it), 401 (credentials; maybe refresh a token once, then fail). The POST timeout is
   the dangerous one: the order may have been created. Only retry with an idempotency key the server honours; otherwise check whether it exists first.

3. $1 - 0.99^{10} \approx 9.6\%$ of page loads include at least one call at or above the p99.

4. Something like:

   ```python
   import signal, sys
   stop = False
   def on_term(signum, frame):
       global stop
       stop = True                      # don't do heavy work inside the handler
   signal.signal(signal.SIGTERM, on_term)

   for step in range(start_step, total_steps):
       train_step()
       if stop or step % 1000 == 0:
           save_checkpoint(step)        # atomically: write to a temp file, then rename
       if stop:
           sys.exit(0)                  # or a specific code your orchestrator understands
   ```

   Keep the handler minimal (set a flag), checkpoint at a safe point in the loop, write checkpoints atomically so a kill during the write doesn't
   corrupt the last good one, and make sure the checkpoint fits in the grace period.

5. Examples: unsafe pickle → use a safe format (skops, ONNX, safetensors) or verify integrity; no body size limit → reject large requests; no validation →
   schema validation (pydantic) returning 422; stack traces to clients → catch errors, log internally, return generic 500; `0.0.0.0` without auth → bind to
   localhost behind a gateway, add authentication; single-threaded blocking server → a proper ASGI/WSGI server with workers; no health checks or graceful
   shutdown → `/healthz` and `/readyz` endpoints and SIGTERM handling; no timeouts → server-side request timeouts.
