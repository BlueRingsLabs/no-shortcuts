## Complexity, in practice

Big-O describes how cost grows with input size $n$, ignoring constants. The classes that matter, with a feel for what they mean
at $n = 10^6$ and $n = 10^9$ (assuming roughly $10^8$ simple operations per second in a tight compiled loop, far fewer in Python):

| Complexity | Example | $n = 10^6$ | $n = 10^9$ |
|---|---|---|---|
| $O(1)$ | hash lookup | instant | instant |
| $O(\log n)$ | binary search, B-tree lookup | instant | instant |
| $O(n)$ | one pass over the data | ms | seconds |
| $O(n \log n)$ | sorting | tens of ms | tens of seconds to minutes |
| $O(n^2)$ | all pairs, naive dedup, nested loops | ~hours in Python | forget it |
| $O(2^n)$ | brute-force subsets | forget it | forget it |

The practical rules:

- **Anything quadratic in the number of rows is a bug** unless $n$ is small and will stay small. All-pairs similarity, joining a table
  to itself without keys, `for x in a: if x in some_list`. Quadratic algorithms work fine in the notebook with a sample of 10,000 rows and
  explode in production at 10 million.
- **Know the cost of your containers' operations.** In Python: `x in list` is $O(n)$, `x in set` and `x in dict` are $O(1)$ on average,
  `list.insert(0, x)` is $O(n)$ (use `collections.deque`), `list.pop()` from the end is $O(1)$, string concatenation in a loop is $O(n^2)$
  (use `"".join`).
- **Space complexity matters as much as time.** A $d \times d$ matrix for $d = 10^6$ features is $8 \times 10^{12}$ bytes. Some algorithms
  (all-pairs distances, full attention in 29.3) are limited by memory long before time.
- **Amortized analysis**: appending to a Python list or a dynamic array is $O(1)$ *amortized*: occasionally it copies everything to a bigger
  buffer, but on average each append is cheap. Same idea for hash table resizing.

## Hash tables

The most useful data structure in engineering. A hash function maps a key to an integer; the table uses it to jump directly to a slot.
Average $O(1)$ insert and lookup. Python's `dict` and `set`, database hash joins (08.3), Spark's shuffle partitioning (12.1), feature
hashing, caches, deduplication: all hash tables underneath.

Things worth knowing:

- **Collisions** (two keys, same slot) are handled by chaining or probing. Many collisions degrade lookups toward $O(n)$. Attackers know
  this: "hash flooding" sends many keys crafted to collide, turning a web server's parameter parsing into a quadratic CPU sink. That's why
  Python randomizes string hashes per process (`PYTHONHASHSEED`), and why hashing is also the reason `set` iteration order isn't stable
  across runs for strings. (The lab runner sets `PYTHONHASHSEED=0` so labs are reproducible.)
- **The hashing trick** (feature hashing): map high-cardinality categorical features (user IDs, words) into a fixed number of buckets
  with a hash, accepting a few collisions in exchange for bounded memory and no vocabulary to maintain. Vowpal Wabbit and many ad-tech
  systems are built on it.
- **Consistent hashing**: assign keys to servers so that adding or removing a server only moves a small fraction of keys. Used in
  distributed caches and databases.

## Heaps and top-k

A **binary heap** keeps the minimum (or maximum) at the top with $O(\log n)$ insert and pop. The killer application: **top-k**. To find the k
largest of $n$ items, keep a min-heap of size $k$; for each item, if it beats the heap's minimum, replace it. Cost $O(n \log k)$ instead of
$O(n \log n)$ for a full sort, and $O(k)$ memory, so it works on a stream.

```python
import heapq
top10 = heapq.nlargest(10, scores_iterable)        # O(n log k), streaming-friendly
```

With NumPy, `np.argpartition(scores, -k)[-k:]` does it in $O(n)$ (a partial quickselect), then sort only those $k$. Recommendation
services and vector search (41.2) do top-k millions of times per second; nobody sorts the whole catalogue.

## Sorting and searching

Sorting is $O(n \log n)$, and you'll almost never write one. What you need to know:

- **Binary search** on sorted data is $O(\log n)$: `bisect` in Python, `np.searchsorted` in NumPy (which you used for sampling from a
  categorical in 04.1). Sorted data enables range queries, merge joins, and fast lookups without a hash table.
- **External sorting**: when data doesn't fit in memory, sort chunks, write them to disk, then merge them with a heap. This is how databases
  and Spark sort terabytes.
- **Stability**: a stable sort keeps the original order of equal elements. Matters when you sort by multiple keys in sequence (and for
  reproducibility).

## Trees and graphs, briefly

- **B-trees** are what database indexes are made of (08.3): wide, shallow balanced trees optimized for disk pages. A lookup in a billion-row
  index touches 3 or 4 pages.
- **KD-trees and ball trees** partition space for nearest-neighbour search in low dimensions (19.1). They degrade in high dimensions (the
  curse again), which is why vector databases use graph-based indexes instead (HNSW, 41.2).
- **Graphs**: BFS finds shortest paths in unweighted graphs, DFS explores connectivity and detects cycles, topological sort orders a DAG. An
  orchestrator like Airflow (13.2) topologically sorts your pipeline to decide what runs first. An autograd engine (24.3) topologically sorts the
  computational graph to run backprop in the right order. Same algorithm, two very different places.

## Dynamic programming

When a problem decomposes into overlapping subproblems, solve each subproblem once and store the result. Three DP algorithms you'll meet in
this course:

- **Edit (Levenshtein) distance** between strings: minimum insertions, deletions and substitutions to turn one into the other. $O(mn)$ table.
  Fuzzy matching, deduplication of names and addresses (10.3), and the core of WER for speech recognition.
- **Viterbi**: the most likely sequence of hidden states in an HMM (34.2).
- **Bellman equations**: value iteration in reinforcement learning (46.2) is DP over states. Bellman *invented* the term "dynamic
  programming", and supposedly picked it partly because it sounded impressive to funding bureaucrats. Some things never change.

## Streaming algorithms: answers from data you can't keep

This is my favourite part, and the most underrated in data engineering courses. When data arrives as a stream too large to store (clickstreams,
network logs, events), you can still answer many questions *approximately*, in a single pass, with memory that doesn't grow with $n$.

**Reservoir sampling**: keep a uniform random sample of $k$ items from a stream of unknown length. Keep the first $k$. For the $i$-th item ($i > k$),
keep it with probability $k/i$, replacing a random item in the reservoir. Every item ends up in the sample with probability exactly $k/n$. Ten lines,
and it's how you sample from logs you can't count in advance.

**Bloom filter**: "have I seen this item before?" with no false negatives and a tunable false positive rate. A bit array of size $m$ and $h$ hash
functions; to add an item, set the $h$ bits it hashes to; to query, check whether all $h$ bits are set. The false positive rate is about
$(1 - e^{-hn/m})^h$. For 1% false positives you need only about 9.6 bits per item, *regardless of how big the items are*. Used to skip useless disk
reads in databases (every modern LSM-tree database), to check passwords against breach lists without storing them, and to avoid re-crawling URLs.

**Count-min sketch**: approximate frequency counts for a huge number of distinct items, in fixed memory. A $d \times w$ array of counters and $d$ hash
functions; to add an item, increment one counter per row; to estimate its count, take the minimum over its $d$ counters. It never underestimates,
and overestimates by at most $\epsilon N$ with probability $1 - \delta$ when $w = \lceil e/\epsilon\rceil$ and $d = \lceil\ln(1/\delta)\rceil$. Heavy
hitters, trending topics, DDoS source detection.

**HyperLogLog**: count distinct items (cardinality) of a stream with about 2% error using a couple of kilobytes. The trick: hash each item and record
the maximum number of leading zeros seen; seeing a hash with many leading zeros is evidence that you've seen many distinct items. BigQuery, Redis,
Presto and Spark all offer `APPROX_COUNT_DISTINCT` built on it, and they're orders of magnitude cheaper than exact `COUNT(DISTINCT ...)` on big data.

Knowing these exist is half the value. When somebody proposes storing every user ID of the last year to count unique visitors per day, you'll know
there's a better way.

## Things that will bite you

- **Quadratic behaviour hidden in innocent code**: `in` on lists, pandas `apply` with a lookup inside, self-joins without keys.
- **Sorting to get top-k.**
- **Exact answers when approximate ones are fine**, at 100x the cost. And the reverse: approximate answers where exactness matters (billing).
- **Non-deterministic hashing** across processes, breaking reproducibility of hashed features or partitioning. Use a stable hash (e.g. `hashlib`,
  MurmurHash with a fixed seed) for anything persisted.
