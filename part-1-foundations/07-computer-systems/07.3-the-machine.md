# 07.3 The machine: memory hierarchy, CPUs and GPUs

*About 9 hours. Prerequisites: 01.3, 01.4, 07.2. Lab: [`lab_07_3_the_machine.py`](labs/lab_07_3_the_machine.py).*

Here's a question that separates people who train models from people who understand what's happening when they train
models: *why is a layer normalization slower than a matrix multiplication that does a thousand times more arithmetic?*
The answer has nothing to do with math and everything to do with the machine. Modern processors are so fast at
arithmetic that most of the time they're sitting idle, waiting for data to arrive from memory. Understanding that single
fact explains FlashAttention (29.3), kernel fusion and `torch.compile` (33.3), why batch size matters for inference
throughput (37.2), why quantization speeds up LLM serving (37.3), and why your pandas `apply` is slow.

This lesson is the mental model of hardware you need as an ML engineer. Not how to design a chip, just enough to predict
what will be fast and what won't.

## The memory hierarchy

A processor doesn't compute on data in RAM directly. Data moves up a hierarchy of increasingly small, fast and expensive
memories:

| Level | Typical size | Typical latency | Rough bandwidth |
|---|---|---|---|
| CPU registers | a few KB | < 1 ns | |
| L1 cache | 32-64 KB per core | ~1 ns | ~TB/s per core |
| L2 cache | 0.5-2 MB per core | ~4 ns | |
| L3 cache | tens of MB shared | ~10-20 ns | |
| DRAM (RAM) | tens to hundreds of GB | ~80-100 ns | 50-100+ GB/s per socket |
| NVMe SSD | TBs | ~50-100 µs | a few GB/s |
| Network (same datacenter) | | ~0.5 ms round trip | 10-400 Gb/s |
| Network (cross-continent) | | ~100+ ms round trip | |

(These are orders of magnitude, not specs. They move every hardware generation. The *ratios* are what stay roughly constant: each level down is
about an order of magnitude slower.) Jeff Dean's "latency numbers every programmer should know" list is the famous version of this table. I'd
print it and tape it to your monitor, next to the sticky note with your Wi-Fi password.

Two principles make caches work, and your code should cooperate with them:

- **Spatial locality**: memory moves in **cache lines** of 64 bytes. Read one float and you get the 15 next to it for free. So traversing memory
  sequentially is fast, and jumping around is slow.
- **Temporal locality**: recently used data is likely still in cache. Reusing data while it's hot is fast; touching it once and coming back much
  later means fetching it from RAM again.

This is why the layout of arrays matters (01.3). NumPy arrays are **row-major** (C order) by default: elements of a row are adjacent in memory.
Walking along a row reads memory sequentially; walking down a column jumps by a whole row each step. (NumPy's own `sum(axis=0)` is clever
enough to reorder the work and add whole rows at a time, but a loop in *your* code that processes one column at a time pays the full price.
The lab measures both.) It's also
why columnar data formats (Parquet, 11.1) make analytics queries fast: reading one column of a table means reading one contiguous chunk, instead
of skipping through every row.

## Compute-bound vs memory-bound: arithmetic intensity

Every operation needs to (1) move data between memory and the processor, and (2) do arithmetic. Which one limits the speed? Define the
**arithmetic intensity** of an operation:

$$\text{AI} = \frac{\text{FLOPs performed}}{\text{bytes moved to/from memory}}$$

And every processor has a **machine balance**: peak FLOP/s divided by peak memory bandwidth. A modern datacenter GPU does on the order of
$10^{15}$ low-precision FLOP/s and moves about $3 \times 10^{12}$ bytes/s from its HBM memory: a balance of several hundred FLOPs per byte. A laptop
CPU might do $10^{12}$ FLOP/s with $10^{11}$ B/s of bandwidth, a balance around 10.

- If an operation's AI is **below** the machine balance, it's **memory-bound**: the arithmetic units wait for data. Speed = bandwidth × AI.
- If it's **above**, it's **compute-bound**: speed = peak FLOP/s.

This is the **roofline model**: plot achievable FLOP/s against arithmetic intensity, and you get a sloped line (bandwidth limit) that flattens into
a roof (compute limit).

Where do common operations fall?

- **Elementwise operations** (add, ReLU, GELU, scaling, dropout): 1 FLOP per element, reading 4 bytes and writing 4 bytes in float32. AI ≈ 0.125 to 0.25.
  Hopelessly memory-bound on every processor. Their cost is entirely the memory traffic.
- **Reductions and normalizations** (sum, softmax, LayerNorm): a few FLOPs per element, still memory-bound.
- **Matrix multiplication** of $n \times n$ matrices: $2n^3$ FLOPs, $3n^2$ numbers moved (in the ideal case). AI grows like $n$. Large matmuls are
  compute-bound, which is why GPUs are built around them and why they reach 60-80% of peak FLOP/s on big matmuls and 1% on elementwise ops.
- **Matrix-vector products** (batch size 1 inference of a linear layer): $2n^2$ FLOPs, $n^2$ weights read once. AI ≈ 1 for fp16. Memory-bound. This is
  **why LLM inference at small batch sizes is memory-bound**: generating each token reads every weight of the model from memory for a handful of
  FLOPs per weight. The speed of token generation is basically memory bandwidth divided by model size in bytes. Batching many users together
  (37.2) reuses each weight read for many tokens, and quantization (37.3) makes the weights smaller to read. Both attack the memory bottleneck, not the
  arithmetic.

And the answer to the opening question: LayerNorm is memory-bound, a big matmul is compute-bound. Both take time proportional to their *bottleneck*,
and the matmul's bottleneck (FLOPs, at hundreds of TFLOP/s) moves much faster than the LayerNorm's (bytes, at a few TB/s). Chains of small
memory-bound operations are why **kernel fusion** exists: instead of reading and writing the tensor from memory for each of five elementwise
operations, a fused kernel reads it once, does all five in registers, and writes it once. Five times less traffic, five times faster. That's most of
what `torch.compile` and handwritten kernels like FlashAttention buy you (33.3, 29.3).

## CPUs

A modern CPU has a handful to a few dozen cores, each able to run one or two threads, each with **SIMD** (single instruction, multiple data) units
that apply the same operation to a vector of 8 or 16 floats at once (AVX2, AVX-512, ARM NEON/SVE). Fast numerical code uses all three levels:
vectorization within a core, multiple cores, and caches. NumPy's BLAS does this for matmul; pure Python does none of it. That's the 100x from 01.3.

CPUs are optimized for **latency**: making one thread go as fast as possible, with big caches, branch prediction and out-of-order execution. They're
excellent for control-heavy code, data processing with irregular access, and small models. Classical ML (gradient boosting on tabular data, 20.4)
runs perfectly well on CPUs, and so does inference for small models.

## GPUs

A GPU is built for **throughput**: thousands of simple cores that run the same instructions on different data. The relevant structure (NVIDIA
terminology, other vendors have equivalents):

- **Streaming multiprocessors (SMs)**: the GPU has around a hundred of them. Each runs many threads.
- **Warps**: threads execute in groups of 32 in lockstep. If threads in a warp take different branches (`if` statements), both paths run one after the
  other ("divergence"). GPUs like uniform work.
- **Tensor cores**: specialized units that do small matrix multiply-accumulates in low precision (fp16, bf16, fp8, int8) extremely fast. Most of a
  modern GPU's advertised FLOPs come from them, which is why mixed precision (25.3) isn't optional for performance.
- **Memory hierarchy**: registers, a small fast on-chip **shared memory / L1** per SM (a few hundred KB), an L2 cache (tens of MB), and **HBM** (high
  bandwidth memory, tens of GB, a few TB/s). FlashAttention's whole trick is to compute attention in tiles that fit in on-chip shared memory, never writing
  the big attention matrix to HBM.
- **Host-device transfer**: the GPU sits across a PCIe or NVLink connection from the CPU. PCIe is far slower than HBM. Copying data back and forth every
  step (a `.cpu()` or `.item()` in the training loop, a data loader that can't keep up) stalls the GPU. `nvidia-smi` showing 30% utilization usually means
  the GPU is waiting for the data pipeline, not that it's too weak.

GPU programming model in one paragraph: you launch **kernels** (functions run by thousands of threads over a grid of blocks). Each kernel launch has a
fixed overhead of a few microseconds, so thousands of tiny kernels (typical of eager-mode PyTorch with small tensors) spend more time launching than
computing. CUDA graphs and compilation reduce that overhead. You don't need to write CUDA for this course; you need to recognize which of these
bottlenecks you're hitting, which is what profilers show you (33.3).

## Practical rules of thumb

- **Big matmuls good, small ops bad.** Batch work together. A batch size of 1 wastes most of a GPU.
- **Avoid data movement.** Keep data on the device, avoid synchronizing transfers (`.item()`, printing tensors) inside hot loops, and prefetch data on
  the CPU while the GPU computes.
- **Fuse memory-bound chains** (let the compiler do it).
- **Lower precision helps twice**: faster tensor cores and half the bytes to move.
- **Sequential access beats random access** everywhere: RAM, disk, network, columnar formats, embeddings tables.
- **Measure.** Profilers (01.4, 33.3), `nvidia-smi`, and back-of-the-envelope roofline estimates. If your estimate says an operation should take 1 ms and it
  takes 50, something other than the math is going on.

> **Scar tissue.** Me and a couple of my best friends pooled our money for a used GTX 1080 Ti to experiment with GANs, and put it in the
> oldest desktop any of us owned. The GPU sat at 12% utilization. We blamed the drivers for a week. It was the data loader: JPEG decoding
> and augmentation on a dual-core CPU from another decade, starving a card that could have eaten ten times more images per second.
> Preprocessing the dataset once to tensors on disk fixed that. The ending was worse: the old power supply had no 8-pin connector, someone
> had bought a cheap adapter, and one night the room smelled of melting plastic. The card survived. The adapter and our confidence did
> not.

## Exercises

1. A float32 elementwise addition of two arrays of $10^8$ elements on a machine with 50 GB/s of memory bandwidth. How long should it take, at best?
2. What's the arithmetic intensity (FLOPs per byte, float32) of multiplying two $4096 \times 4096$ matrices, assuming each input is read once and the output
   written once? Is it compute- or memory-bound on a machine with balance 10? And 300?
3. A 7-billion-parameter model in bfloat16 is served on a GPU with 3 TB/s of HBM bandwidth. Estimate the maximum tokens per second at batch size 1. What
   happens (roughly) at batch size 32?
4. Why is `[x[:, j].sum() for j in range(ncols)]` slower than `[x[i, :].sum() for i in range(nrows)]` for a large C-ordered square array, and why is
   `x.sum(axis=0)` nevertheless fast? What would you do if your code needed to process columns one at a time, often?
5. Your GPU shows 25% utilization during training. List three likely causes and how you'd check each.

<summary>Answers</summary>

1. Read 2 × 400 MB, write 400 MB: 1.2 GB. At 50 GB/s, about 24 ms. The $10^8$ FLOPs themselves would take a fraction of a millisecond. Memory-bound.

2. FLOPs $2 \times 4096^3 \approx 1.37 \times 10^{11}$. Bytes $3 \times 4096^2 \times 4 \approx 2.0 \times 10^8$. AI ≈ 683 FLOPs/byte. Compute-bound at balance 10 and also at 300.
   (Real implementations don't achieve the ideal "read once" but tile cleverly to get close.)

3. Each generated token reads all weights: $7 \times 10^9 \times 2$ bytes = 14 GB. At 3 TB/s: about 214 tokens/s, as an upper bound (plus KV cache reads,
   37.2). At batch size 32, the weights are read once per step for 32 sequences, so throughput rises toward 32x (~6,800 tokens/s total) until compute or
   the KV cache traffic becomes the bottleneck. Per-user speed stays about the same; total throughput jumps. That's the economics of LLM serving.

4. A row slice is contiguous: sequential access, full cache lines used. A column slice picks one element per row, jumping a full row stride each time,
   so each 64-byte cache line delivers one useful float out of sixteen. `x.sum(axis=0)` is fast because NumPy doesn't walk columns: it accumulates entire
   rows into a running result, which is contiguous access (a lesson in itself: good libraries reorder loops for you, your own loops don't get that
   favour). If you need to process columns one at a time, store the array transposed or in Fortran order (`np.asfortranarray`), or use a columnar format.

5. (a) Data loading can't keep up: check with the profiler, or time the loop with a dummy batch kept on the GPU; fix with more DataLoader workers, pinned memory,
   faster decoding, pre-processed data. (b) Too small a batch or model: tiny kernels and launch overhead; check kernel durations in the profiler; increase batch
   size or use CUDA graphs / compile. (c) Synchronization points (`.item()`, logging every step, CPU-side metric computation): look for gaps in the GPU timeline;
