# 24.3 Building an autograd engine

*About 12 hours. Prerequisites: 24.2, 07.1 (graphs, depth-first search), 01.3 (NumPy broadcasting). Lab: [`lab_24_3_autograd.py`](labs/lab_24_3_autograd.py).*

In 24.2 each layer had a hand-written `backward()`. That works for an MLP and becomes miserable for anything else: every new architecture means new
backward code, and every new backward is a new chance to be wrong. **Automatic differentiation** removes the chore: you write only the forward
computation, the engine records what you did, and it applies the chain rule for you. PyTorch, JAX and TensorFlow are, at their core, exactly this, plus
a very large amount of engineering for speed.

In this lesson you build one. First a **scalar** engine (each number is a node), which is small enough to hold in your head and makes the algorithm
completely transparent. Then a **tensor** engine (each node is a NumPy array), which is the real design and fast enough to train networks on. After this,
nothing `loss.backward()` does should surprise you, which is the point: the day it does something surprising is the day you'll need to know why.

(The scalar engine follows the spirit of Andrej Karpathy's *micrograd*, which I recommend watching him build. The tensor engine goes further, into broadcasting
and the numerical details that a real framework has to get right.)

## The design

Each value in the computation is a **node** that stores:

- `data`: its value (a float, or an array).
- `grad`: $\partial L / \partial(\text{this node})$, filled in by the backward pass, starting at zero.
- `parents`: the nodes it was computed from.
- `_backward`: a closure that, given this node's `grad`, **adds** the right contributions into the parents' `grad` (the VJP from 24.2's table).

Every operation (`+`, `*`, `matmul`, `exp`, `relu`, ...) creates a new node, links its parents, and attaches its `_backward`. Operator overloading makes this invisible: `c = a * b + a` builds the graph as a side effect
of computing the value. This is **define-by-run** (dynamic graphs): the graph is whatever Python actually executed, including loops and `if`s, which is why PyTorch feels like writing NumPy. The alternative,
**define-then-run** (static graphs: TensorFlow 1, and in a different sense JAX's tracing and `torch.compile`, 25.3), builds the graph first and then executes it, which allows whole-graph optimization.

## The backward pass

`L.backward()` must call each node's `_backward` only after every node that uses it has finished contributing to its gradient. That's a **reverse topological order** of the graph:

1. Depth-first search from $L$ to collect all nodes in topological order (a node after all of its parents).
2. Set `L.grad = 1`.
3. Walk the list in reverse, calling `_backward` on each node.

Because contributions are **added** into `grad`, a node used twice (24.2's `x * x`, or a weight shared across time steps in an RNN, 28.1) automatically receives the sum of its gradients. And because gradients
accumulate, running backward twice without resetting doubles them: the engine needs `zero_grad()`, exactly like PyTorch.

## From scalars to tensors

The scalar engine creates one Python object per number, so a single 256×256 matmul is 16 million node operations: correct and hopeless. A **tensor** engine makes each node an array and each `_backward` a
vectorized NumPy expression (24.2's VJP table). Three details make it correct:

- **Broadcasting.** If `a` has shape `(3,)` and `b` has shape `(4, 3)`, `a + b` broadcasts `a` across 4 rows. The gradient flowing back to `a` has shape `(4, 3)` and must be **summed back down** to `(3,)`. The engine needs
  an `unbroadcast(grad, shape)` helper that sums over the added and stretched axes. Getting this wrong is the most common bug in hand-rolled engines, and it's silent when shapes happen to line up.
- **Numerically stable primitives.** Composing `exp`, `sum` and `log` to build log-softmax works mathematically and overflows in practice (07.2). Real frameworks provide fused, stable ops (`log_softmax`, `logsumexp`,
  `cross_entropy` from logits) with their own hand-written, stable backward. The lab's engine does the same.
- **Not tracking what doesn't need gradients.** Inputs and targets don't need `grad`; evaluation doesn't need a graph at all. A `requires_grad` flag and a `no_grad` mode avoid building (and storing) graphs you'll never
  backpropagate through, which saves memory (24.2's activations) and time.

## What real frameworks add

Everything else in PyTorch's autograd is engineering on top of this core: GPU kernels for every op (25.3), in-place operation checks (the "a variable needed for gradient computation has been modified by an
inplace operation" error is the engine telling you that you overwrote something a `_backward` closure needed), views that share storage, custom `autograd.Function`s where you supply your own backward, higher-order
gradients (building a graph *of the backward pass*), gradient hooks, checkpointing, and compilers that fuse many small ops into one kernel. You'll use all of them; none of them changes the algorithm.

## Things that will bite you

- **Overwriting instead of accumulating** gradients in `_backward`.
- **Forgetting `unbroadcast`**, or summing over the wrong axes.
- **Recursion depth**: a recursive topological sort on a long graph (an RNN over 5,000 steps) blows Python's stack. Use an iterative DFS.
- **Composing unstable primitives** (`log(sum(exp(x)))`) instead of a fused stable op.
- **Building graphs during evaluation**, and wondering where the memory went.
- **Mutating a tensor** that a pending `_backward` still needs.

## Exercises

1. Write the `_backward` closures for `a / b`, `a ** n` (constant `n`), and `log(a)` in the scalar engine.
2. Why must the backward pass follow a reverse topological order? Construct a small graph where a naive order (for example, the order in which nodes were created, reversed per branch) gives a wrong gradient.
3. Write `unbroadcast(grad, shape)` for NumPy broadcasting rules, and test it on shapes `(4, 3) → (3,)`, `(4, 3) → (4, 1)`, `(2, 4, 3) → (1, 3)`.
4. Why is `logsumexp` implemented as $m + \log\sum e^{x - m}$ with $m = \max x$, and what's its gradient?
5. Your engine trains an MLP correctly but uses 10 times more memory than expected during evaluation. What's the likely cause and the fix?

<summary>Answers</summary>

1. `a / b`: `a.grad += out.grad / b.data`; `b.grad += -out.grad * a.data / b.data**2`. `a ** n`: `a.grad += out.grad * n * a.data**(n - 1)`. `log(a)`: `a.grad += out.grad / a.data`.

2. A node's `_backward` passes its own `grad` to its parents, so its `grad` must be complete, meaning every consumer of the node has already run its `_backward`. Reverse topological order guarantees that. Counterexample:
   $b = 2a$, $c = a + b$, $L = c$. If $a$'s `_backward` would run before $b$'s (say you process $a$ as soon as $c$ is done), $a$ gets only $\partial L/\partial c \cdot 1 = 1$ from $c$ directly, and misses the path through $b$ (another 2), which arrives
   after $a$ was already "finished". The correct gradient is 3.

3. Sum over leading axes that `shape` doesn't have, then over axes where `shape` has size 1 and `grad` doesn't, keeping dimensions:
   `while grad.ndim > len(shape): grad = grad.sum(0)`; then `for i, s in enumerate(shape): if s == 1 and grad.shape[i] != 1: grad = grad.sum(i, keepdims=True)`. Results: `(4,3) → (3,)` sums axis 0; `(4,3) → (4,1)` sums axis 1
   keeping it; `(2,4,3) → (1,3)` sums axis 0 (the extra leading one), then axis 0 again with keepdims (size 1 in the target).

4. Subtracting the max makes every exponent at most 0, so nothing overflows, and at least one term is $e^0 = 1$, so the sum can't underflow to 0 and the log is finite (07.2). The gradient of $\text{logsumexp}(x)$ is $\text{softmax}(x)$.

5. The engine builds a graph during evaluation (every op records parents and closures, keeping all intermediate arrays alive until the output is freed). Evaluation doesn't need gradients: add a `no_grad` mode
   that computes values without recording parents or closures (PyTorch's `torch.no_grad()` / `torch.inference_mode()`), and use it for evaluation.
