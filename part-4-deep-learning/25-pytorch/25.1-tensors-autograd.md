# 25.1 Tensors and autograd

*About 8 hours. Prerequisites: 01.3 (NumPy, broadcasting, strides), 24.3 (you built an autograd engine), 07.2 (floating point). Lab: [`lab_25_1_tensors_autograd.py`](labs/lab_25_1_tensors_autograd.py).*

You've built your own autograd engine, so PyTorch holds no secrets at the level of the algorithm. What it has is a large surface of behavior that's
*almost* like NumPy and almost like your engine, and the differences are where the bugs are: a view that silently shares memory, a `.grad` that
quietly accumulates, a dtype that isn't the one you think, an in-place operation that breaks the backward pass. This lesson goes through tensors and
autograd with those differences in mind. Nothing here is advanced; all of it will cost you an afternoon at some point if you don't know it.

## Tensors

A `torch.Tensor` is an n-dimensional array with a **dtype**, a **device** (CPU, CUDA GPU, Apple's MPS), a **shape**, and **strides**. Most of NumPy carries over: creation (`torch.zeros`, `torch.randn`,
`torch.arange`), elementwise math, reductions, broadcasting (01.3's rules exactly), indexing, `@` for matmul, `einsum`.

Differences that matter:

- **Default float is float32**, NumPy's is float64. `torch.from_numpy(np_array)` keeps float64, so a model in float32 meeting a float64 input fails with a dtype error or, worse, promotes silently. Pick a
  dtype policy and convert at the boundary.
- **Integer tensors** from `torch.tensor([1, 2])` are int64; dividing with `/` gives floats, with `//` integers. Class labels must be `long` for `cross_entropy`.
- **Devices must match.** Every tensor in an operation must be on the same device; moving is explicit (`.to(device)`), and moving data between CPU and GPU in the inner loop is the classic silent slowdown (25.3).
- **`torch.from_numpy` and `.numpy()` share memory** with the NumPy array (on CPU). Modify one, the other changes. Useful for zero-copy, dangerous by surprise.
- `.item()` extracts a Python number from a one-element tensor, and on a GPU it **forces a synchronization**. Calling it every step to log the loss is a common, invisible slowdown.

## Views, strides and copies

A tensor is a pointer into a block of memory plus strides: how many elements to skip to move one step along each dimension (01.3). Many operations return **views** that share memory with the original,
just with different shape and strides: slicing, `view`, `transpose`/`permute`, `expand`, `squeeze`/`unsqueeze`, `narrow`. Others return **copies**: advanced (integer or boolean) indexing, `repeat`, `clone`,
most arithmetic.

- A view of a transposed tensor is **non-contiguous** (its elements aren't in row-major order in memory). `view` requires compatible strides and fails on it; `reshape` returns a view when it can and copies when it
  must; `.contiguous()` makes a copy in standard layout. Some kernels are much faster on contiguous inputs.
- **`expand` vs `repeat`**: `expand` broadcasts a size-1 dimension with stride 0, using no extra memory; `repeat` materializes copies. Writing into an expanded tensor writes the same memory many times; don't.
- Changing a view changes the original. That's the point of views, and also a source of bugs when a function modifies its input "just a slice".

## In-place operations

Methods with a trailing underscore (`add_`, `mul_`, `zero_`, `clamp_`) and indexed assignment (`x[mask] = 0`) modify a tensor in place. They save memory, and they interact badly with autograd: if a value that a
backward function needs (24.3's closures kept references to their inputs) has been overwritten, PyTorch notices via a version counter and raises the famous error ("one of the variables needed for gradient
computation has been modified by an inplace operation"). The fix is almost always to use the out-of-place version. The lab provokes it.

## Autograd, as PyTorch does it

Everything from 24.3, with PyTorch's names:

- Tensors created by you with `requires_grad=True` are **leaves**; results of operations on them get a `grad_fn` (the node's backward) and form the graph. `nn.Parameter`s are leaves with `requires_grad=True`.
- `loss.backward()` walks the graph in reverse topological order and **accumulates** $\partial\text{loss}/\partial\text{leaf}$ into each leaf's `.grad`. Only leaves keep `.grad` by default (intermediates can with `retain_grad()`).
- **Accumulation is the reason for `zero_grad()`** (the module's self-check): `.grad` is added to, never overwritten, so gradients from the previous step would be mixed into this one. Zero them (or set to `None`, the
  default in `optimizer.zero_grad()`, which saves memory and a kernel launch) before each backward. The accumulation is also a feature: call backward on several micro-batches before one optimizer step and you've
  simulated a larger batch (**gradient accumulation**, 25.2).
- After `backward()` the graph is **freed** to save memory. Calling backward through it again raises an error unless you passed `retain_graph=True` (needed when two losses share part of a graph, or for some
  higher-order tricks).
- `backward()` on a **non-scalar** tensor needs a `gradient` argument: the vector in the vector-Jacobian product (24.2). `y.backward(v)` computes $v^\top J$.
- `torch.autograd.grad(outputs, inputs)` returns gradients instead of accumulating them into `.grad`, and with `create_graph=True` builds a graph of the backward pass for higher-order derivatives (gradient penalties, 31.2).
- **Stopping gradients**: `x.detach()` returns a tensor sharing data but cut from the graph; `with torch.no_grad():` records nothing (for evaluation, and for manual parameter updates); `torch.inference_mode()` is a
  stricter, faster version for pure inference.

## Extending autograd

- A **custom `torch.autograd.Function`** defines `forward` and `backward` explicitly: for a numerically stable formula (the lab writes a stable softplus), an operation from another library, or a deliberately "wrong"
  gradient like the **straight-through estimator** (round in the forward pass, pretend it was the identity in the backward, used in quantization, 37.3). Verify it with `torch.autograd.gradcheck` in float64 (24.2's check,
  built in).
- **Hooks** (`tensor.register_hook`, module hooks) let you inspect or modify gradients as they flow: debugging vanishing gradients, gradient clipping per tensor.
- **`torch.func`** (formerly functorch) gives JAX-style function transforms: `grad`, `vmap` (vectorize over a batch dimension), `jacrev`/`jacfwd`, composable. **Per-example gradients** (for differential privacy or
  influence analysis) are one `vmap(grad(...))`, which the lab compares with a slow loop.

## Things that will bite you

- **float64 NumPy data meeting a float32 model.**
- **Forgetting `zero_grad()`**, or calling it after `backward()` instead of before.
- **In-place operations** on tensors autograd needs.
- **Views modified** through a function that "only touched a slice".
- **`.item()` or `.cpu()` inside the training loop** on a GPU.
- **`from_numpy` memory sharing** when you meant a copy.
- **`.view` on a non-contiguous tensor** (use `reshape`, and understand why it may copy).
- **Evaluation without `no_grad`**: memory for a graph nobody will use.

## Exercises

1. What does `loss.backward()` do to `.grad`, and why do you call `zero_grad()`? When is *not* zeroing between two backward calls exactly what you want?
2. For `x = torch.arange(12.).reshape(3, 4)`, give the strides of `x`, `x.T`, `x[:, 1:3]` and `x[:, None, :].expand(3, 5, 4)`. Which of them are contiguous?
3. Why does `b = a.exp(); b.add_(1); b.sum().backward()` fail, while `b = a * 2; b.add_(1); b.sum().backward()` works?
4. Write a custom `autograd.Function` for the straight-through estimator of `round`. What does gradcheck say about it, and why is that expected?
5. You need the gradient of the loss for each of the 256 examples in a batch separately. Describe the slow way and the `torch.func` way.

<summary>Answers</summary>

1. It computes $\partial\text{loss}/\partial p$ for every leaf $p$ that requires grad and **adds** it into `p.grad`. Without zeroing, the next step's gradient is added to this step's, so the optimizer uses a sum over steps. Not zeroing
   is what you want for gradient accumulation: several forward/backward passes over micro-batches, then one optimizer step, then zero (scaling each micro-batch loss by 1/number of micro-batches so the sum is a mean).

2. `x`: (4, 1), contiguous. `x.T`: (1, 4), not contiguous. `x[:, 1:3]`: (4, 1) with an offset of 1 and shape (3, 2), not contiguous (rows aren't adjacent in memory). The expanded tensor: (4, 0, 1): stride 0 on the new
   dimension, not contiguous, and no extra memory.

3. The backward of `exp` needs its output $e^a$ (the derivative is $e^a$), and `add_` overwrote that output in place, bumping its version counter, so autograd refuses. The backward of `a * 2` only needs the constant 2,
   not the output, so modifying the output doesn't break anything.

4. `forward(ctx, x): return x.round()`; `backward(ctx, g): return g`. `gradcheck` fails: the true derivative of round is 0 almost everywhere, and the finite differences see that, while the function claims 1. That's expected: the
   straight-through estimator is a deliberate, useful lie that lets gradients flow through a discrete operation, not a correct derivative.

5. Slow: loop over the 256 examples, compute each loss, call `torch.autograd.grad` for each (256 backward passes, each small, lots of Python overhead). With `torch.func`: write the loss for one example as a function of
   the parameters, then `vmap(grad(loss_fn), in_dims=(None, 0, 0))(params, X, y)` computes all 256 gradients in one vectorized pass.
