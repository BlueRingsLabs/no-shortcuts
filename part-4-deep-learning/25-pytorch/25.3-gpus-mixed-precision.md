# 25.3 GPUs, mixed precision and reproducibility

*About 8 hours. Prerequisites: 07.2 (floating point), 07.3 (the memory hierarchy, why GPUs), 25.1, 25.2. Lab: [`lab_25_3_precision_reproducibility.py`](labs/lab_25_3_precision_reproducibility.py).*

A GPU can do tens to hundreds of trillions of floating-point operations per second, and a surprising number of training runs use a small fraction of that,
because the data arrives late, the host keeps forcing synchronizations, or everything runs in a precision twice as expensive as it needs to be. This
lesson covers the practical side: moving work to the GPU without stalling it, using **mixed precision** without destroying your gradients, **compiling**
models, fitting them in memory, and making runs **reproducible** enough to trust a comparison. Module 33 goes deeper into GPU performance and multi-GPU
training.

The lab runs on a CPU (the course's labs must run anywhere), so it demonstrates the *numerics*, which behave the same on every device. Where something
only makes sense on a GPU, the lab checks for one and says so.

## Using the GPU without stalling it

- **Device-agnostic code**: `device = torch.device("cuda" if torch.cuda.is_available() else "cpu")` (or `"mps"` on Apple silicon), then `model.to(device)` and `batch.to(device)`. Everything in an operation must be on the same device.
- **Execution is asynchronous.** Python queues kernels and moves on; the GPU runs them later. That's why GPU training can be fast from Python, and it has consequences:
  - **Timing** needs `torch.cuda.synchronize()` before reading the clock (or CUDA events), or you measure how fast Python enqueues work.
  - **Synchronizing operations** stall the pipeline: `.item()`, `.cpu()`, `.numpy()`, printing a tensor, Python `if` on a tensor value, some indexing with boolean masks. One `.item()` per step to log the loss can cost more than
    you'd believe. Accumulate on the device and synchronize every N steps.
- **Feeding the GPU**: data loading in worker processes (25.2), `pin_memory=True` and `.to(device, non_blocking=True)` so host-to-device copies overlap with compute. If GPU utilization is low, the loader is the usual suspect.
- **Batch size** matters for throughput: small batches can't fill a GPU. But the right batch size is an optimization question too (26.2), not only a hardware one.

## Where the memory goes

For a model with $P$ parameters trained with Adam in float32: parameters $4P$ bytes, gradients $4P$, Adam's two moment estimates $8P$: **16 bytes per parameter** before a single activation is stored. A 1-billion-parameter model
needs 16 GB just for that. Then the **activations** (24.2), which scale with batch size, sequence length and depth, and often dominate. When you run out of memory (`CUDA out of memory`), the options in order of
cost: smaller batch plus **gradient accumulation** (25.1), **mixed precision** (halves activations), **activation checkpointing** (recompute instead of store, 33.1), and sharding the optimizer and parameters across
GPUs (FSDP/ZeRO, 33.2).

## Mixed precision

Two 16-bit formats (07.2):

| Format | Exponent bits | Mantissa bits | Max | Smallest normal | Relative precision |
|---|---|---|---|---|---|
| float32 | 8 | 23 | $3.4 \times 10^{38}$ | $1.2 \times 10^{-38}$ | $\sim 10^{-7}$ |
| float16 | 5 | 10 | 65,504 | $6.1 \times 10^{-5}$ | $\sim 10^{-3}$ |
| bfloat16 | 8 | 7 | $3.4 \times 10^{38}$ | $1.2 \times 10^{-38}$ | $\sim 10^{-2}$ |

Half precision halves memory and bandwidth and runs on tensor cores at many times the float32 rate. The costs: **float16 has a tiny range** (gradients below $6 \times 10^{-5}$ lose precision, below about $3 \times 10^{-8}$ they become zero; activations
above 65,504 become `inf`); **bfloat16 has float32's range but only 2 to 3 significant digits**.

**Mixed precision training** (Micikevicius et al., 2018) gets the speed without the damage:

- Keep a **float32 master copy** of the weights; the optimizer updates it (small updates to large weights would vanish in 16 bits).
- Run the **matmuls and convolutions** in 16 bits (that's where the time is), and keep **reductions, softmax, normalization and the loss** in float32 (that's where precision matters). `torch.autocast` does this
  selection per operation automatically.
- With **float16**, use **loss scaling**: multiply the loss by a large factor (say $2^{16}$) before backward so small gradients stay representable, then divide the gradients by the same factor before the optimizer step,
  skipping steps where an `inf` appears and lowering the scale. `torch.amp.GradScaler` automates it. The lab shows gradients vanishing to zero in float16 and surviving with scaling.
- With **bfloat16** (on hardware that supports it: recent NVIDIA GPUs, TPUs, recent CPUs) the range is float32's, so **no loss scaling is needed**. It's the default choice for training today, including for large language models.

Also: **TF32** on NVIDIA Ampere and later runs float32 matmuls with a 10-bit mantissa internally (`torch.backends.cuda.matmul.allow_tf32`, or `torch.set_float32_matmul_precision("high")`). A free speedup for most training, worth
knowing about when you see small numerical differences between machines.

The lab also shows the classic low-precision trap outside neural networks: **accumulating** a long sum in 16 bits stops increasing once the running total is large relative to the addends (07.2), which is why
hardware accumulates 16-bit products in 32 bits.

## `torch.compile`

PyTorch executes operations one at a time (eager mode, 24.3's design). Each small elementwise operation reads its input from memory and writes its output back; for chains of elementwise ops, memory traffic, not arithmetic,
is the bottleneck (07.3). `torch.compile(model)` captures the computation graph (TorchDynamo), and compiles it (TorchInductor) into **fused** kernels that keep intermediate values in registers, often giving 1.3 to 2× speedups
on training and more on some inference workloads, with one line of code. Costs: compilation time on the first call (seconds to minutes), **recompilation** when input shapes or Python-level control flow change (pad to a few
fixed shapes, or mark dimensions as dynamic), and harder debugging (run eager first). The lab compiles a chain of elementwise operations on the CPU and times it, if a compiler is available.

## Reproducibility

Deep learning runs are nondeterministic by default, from several independent sources:

- **Random seeds**: initialization, data shuffling, dropout, augmentation. Seed Python's `random`, NumPy and torch (and the DataLoader's generator and workers, 25.2).
- **Floating-point summation order**: addition isn't associative in floating point (07.2), and parallel reductions (atomics on GPUs, thread scheduling on CPUs) add in varying orders. The lab sums the same
  numbers in different orders and gets different float32 results. `torch.use_deterministic_algorithms(True)` (plus `CUBLAS_WORKSPACE_CONFIG` on CUDA, and `torch.backends.cudnn.benchmark = False`) selects deterministic kernels
  where they exist and raises an error where they don't, at some cost in speed.
- **Hardware and software versions**: a different GPU, driver, library version or thread count can change the results, even with everything seeded.

So be realistic about what reproducibility means. **Bitwise** reproducibility on the same machine and software is achievable and worth it for debugging (25.2's resumed run). **Across** machines, aim for **statistical**
reproducibility: the result holds across several seeds (18.4's seed variance), and you report the spread. A result that only appears with seed 42 isn't a result.

> **Scar tissue.** The most time I've lost to a single error message was `libcudnn.so.8: cannot open shared object file`, on the
> university's GPU server, a machine shared by three research groups, each of which had installed CUDA by hand, in a different place, for
> a different version, next to a system Python so old it still thought 2.6 was a fine idea. My container had PyTorch built for one CUDA
> version, the driver supported another, and `LD_LIBRARY_PATH` pointed at whichever had been installed last. Two days. The fix was a base
> image that ships its own CUDA runtime, and never touching the host's libraries again.

## Things that will bite you

- **`.item()` in the training loop** and other hidden synchronizations.
- **Timing GPU code** without synchronizing.
- **float16 without loss scaling**: gradients silently round to zero.
- **Doing the loss or softmax in float16** by hand, outside autocast.
- **Blaming the model** for low GPU utilization that's actually the data loader.
- **Recompilation storms** with `torch.compile` on variable input shapes.
- **Comparing two runs** that differ by less than the seed-to-seed variation.

## Exercises

1. Estimate the memory needed to train a 7-billion-parameter model with AdamW in mixed precision (bf16 activations and weights for compute, fp32 master weights and optimizer states), excluding activations.
2. A gradient has magnitude $10^{-7}$. What happens to it in float16, in bfloat16, and in float16 with a loss scale of $2^{16}$?
3. Why doesn't bfloat16 need loss scaling, and what does it give up compared with float16?
4. Your training step takes 80 ms and you add `print(loss.item())` to every step; now it takes 95 ms. Why, and what should you do instead?
5. Two runs with identical code, data and seeds give validation accuracies 91.2% and 91.5% on different GPUs. Is something broken? What would you check before concluding one configuration is better than another?

1. Per parameter: fp32 master weights 4 bytes, fp32 Adam moments 8 bytes, bf16 working weights 2 bytes, gradients 2 bytes (bf16; 4 if kept in fp32): about 16 to 18 bytes. $7 \times 10^9 \times 16 \approx 112$ GB, before activations. It doesn't fit on one
   80 GB GPU, which is why optimizer-state sharding (33.2), 8-bit optimizers, or parameter-efficient fine-tuning (38.2) exist.

2. float16: $10^{-7}$ is a subnormal and rounds to $2 \times 2^{-24} \approx 1.19 \times 10^{-7}$: about one significant bit, a 19% error, and anything below about $3 \times 10^{-8}$ becomes exactly zero. bfloat16:
   representable (same exponent range as float32), with about 3 significant digits. float16 with scale $2^{16}$: about $6.6 \times 10^{-3}$, comfortably representable with full float16 precision; unscaling happens in
   float32 before the update.

3. bfloat16 has float32's 8 exponent bits, so its range covers the same tiny and huge values as float32; small gradients don't underflow. It pays with a 7-bit mantissa (vs float16's 10), so each value is less precise (about 2 to 3
   decimal digits), which mixed precision tolerates because sensitive operations and the master weights stay in float32.

4. `.item()` forces the CPU to wait for the GPU to finish all queued work and copy the value back, so the CPU can no longer run ahead enqueueing the next step's kernels; the pipeline drains every step. Accumulate the
   loss on the device (`running += loss.detach()`) and call `.item()` every $N$ steps.

5. Not necessarily broken: different GPUs (and library versions) use different kernels and reduction orders, so floating-point results differ and training trajectories diverge. Check the seed-to-seed spread on one machine first; if
   0.3 points is within it, the runs agree. To compare configurations, run several seeds of each (on the same hardware), and compare means with the spread (18.1, 18.4).
