# 25.2 Modules, data loading and the training loop

*About 9 hours. Prerequisites: 25.1, 18.1, 22.1 (pipelines), 07.4 (processes). Lab: [`lab_25_2_training_loop.py`](labs/lab_25_2_training_loop.py).*

Every deep learning project has the same skeleton: a model, a way to feed it data, a loop that trains it, a loop that evaluates it, and checkpoints so a
crash at hour 30 doesn't cost you 30 hours. The skeleton is short, and nearly every line of it has a known way to be subtly wrong: parameters the
optimizer never sees, dropout left on during evaluation, a validation metric averaged incorrectly, a resumed run that isn't the run you stopped,
data workers that all produce the same "random" augmentation. This lesson builds the skeleton properly, once, so you can reuse it for the rest of the course.

I'd recommend writing your own training loop for a while before adopting a framework like PyTorch Lightning or Hugging Face Accelerate. They're good,
and they're much easier to debug when you know what they're doing for you.

## `nn.Module`

A module is a class with parameters and a `forward` method:

```python
class MLP(nn.Module):
    def __init__(self, sizes, p_drop=0.1):
        super().__init__()
        self.layers = nn.ModuleList(nn.Linear(a, b) for a, b in zip(sizes[:-1], sizes[1:]))
        self.drop = nn.Dropout(p_drop)

    def forward(self, x):
        for layer in self.layers[:-1]:
            x = self.drop(torch.relu(layer(x)))
        return self.layers[-1](x)          # logits: the loss applies the softmax (17.4)
```

What the base class does for you, and how to break it:

- **Registration.** Assigning an `nn.Module` or `nn.Parameter` as an attribute registers it, so `parameters()`, `state_dict()`, `.to(device)` and `zero_grad()` find it. A **plain Python list** of layers is *not*
  registered: the layers work in `forward`, but the optimizer never sees their parameters and they never train. Use `nn.ModuleList` / `nn.ModuleDict`. The lab shows the list version silently not learning.
- **Buffers** (`register_buffer`) are state that isn't trained but must be saved and moved with the model: BatchNorm's running statistics (26.4), fixed positional encodings.
- **Modes.** `model.train()` and `model.eval()` switch the behavior of dropout (off in eval) and batch normalization (running statistics in eval). They don't disable gradients; that's `torch.no_grad()`. Forgetting
  `eval()` makes evaluation noisy and wrong; forgetting `train()` after an evaluation makes training silently lose its regularization.
- **`state_dict()`** is a dictionary of named tensors (parameters and buffers). Save that, not the pickled model object: pickles break when the class's code moves or changes.

## Data: `Dataset` and `DataLoader`

A **map-style `Dataset`** has `__len__` and `__getitem__(i)` returning one example. A **`DataLoader`** wraps it and handles the rest:

- **Batching** with a **`collate_fn`** that stacks examples into tensors. The default stacks same-shaped tensors; variable-length data (sentences, time series of different lengths) needs a custom collate that **pads**
  to the batch's maximum length and returns a mask or the lengths (28.1, 29.1). The lab writes one.
- **Shuffling** each epoch for training (not for evaluation), reproducibly with a seeded `generator`.
- **Parallel loading** with `num_workers` separate processes (07.4), so decoding images or tokenizing text doesn't starve the GPU. `pin_memory=True` speeds host-to-GPU copies; `persistent_workers=True` avoids re-spawning workers
  every epoch.
- **Worker seeding.** Each worker is a forked copy of the main process, *including any random generator your dataset holds*. PyTorch reseeds each worker's torch RNG (and, since version 1.9, NumPy's legacy global
  RNG), but a `np.random.default_rng(...)` created in the dataset's `__init__` is copied into every worker in the same state, so all workers produce the **same "random" augmentations**. Silent, and
  common. Fix it in a `worker_init_fn` that reseeds the generator from `torch.utils.data.get_worker_info().seed`, or draw randomness from torch. The lab reproduces the bug and the fix. (Older code
  using the global `np.random` had the same bug before 1.9, which is why you'll find `worker_init_fn` boilerplate everywhere.)
- **Iterable-style datasets** (`IterableDataset`) for streams and data too large to index: shards read sequentially, with care that each worker reads different shards.

For real projects, the data pipeline is often the bottleneck. If GPU utilization is low, profile the loader first (33.3).

## The training loop

```python
for epoch in range(epochs):
    model.train()
    for xb, yb in train_loader:
        xb, yb = xb.to(device, non_blocking=True), yb.to(device, non_blocking=True)
        optimizer.zero_grad(set_to_none=True)
        loss = loss_fn(model(xb), yb)
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)   # optional, cheap insurance
        optimizer.step()
        scheduler.step()                                                   # if the schedule is per step (26.2)
    val = evaluate(model, val_loader)
    save_checkpoint(...) ; maybe_stop_early(...)
```

And the evaluation loop:

```python
@torch.no_grad()
def evaluate(model, loader):
    model.eval()
    total_loss, total_correct, n = 0.0, 0, 0
    for xb, yb in loader:
        logits = model(xb)
        total_loss += loss_fn(logits, yb, reduction="sum").item()          # sum, then divide once
        total_correct += (logits.argmax(1) == yb).sum().item()
        n += len(yb)
    return total_loss / n, total_correct / n
```

Details that matter:

- **Aggregate metrics over examples, not batches.** Averaging per-batch means is wrong when the last batch is smaller (and badly wrong with `drop_last=False` and tiny final batches). Sum, then divide by the count. The lab
  measures the error.
- **Gradient accumulation** (25.1) for effective batch sizes larger than memory allows: divide the loss by the number of micro-batches, step every $k$ micro-batches.
- **Gradient clipping** by global norm guards against rare exploding steps (RNNs, 28.1; transformers early in training). Log the norm before clipping; it's one of the best health signals you have (26.5).
- **Early stopping** (26.3): track the best validation metric, stop after a patience window, restore the best weights.
- **Log** the training loss per step, validation metrics per epoch, the learning rate, and the gradient norm. An experiment tracker (48.1) makes comparisons possible.

## Checkpoints that actually resume

A checkpoint for resuming training needs **everything that determines the future of the run**: model `state_dict`, optimizer `state_dict` (Adam's moment estimates, 26.1), scheduler state, epoch and step counters,
the best validation score so far, and the **RNG states** (Python, NumPy, torch CPU and CUDA) if you want bit-identical continuation, plus the data order (the sampler's generator state). Save atomically (write to a
temporary file, then rename) so a crash during saving doesn't destroy your last good checkpoint. The lab stops a run in the middle, resumes from the checkpoint, and gets exactly the same final weights as an
uninterrupted run. Separately, keep the **best** checkpoint by validation score for deployment, which needs only the model weights (and the preprocessing, 22.1).

> **Scar tissue.** I've dragged my own projects through TensorFlow 0.x graphs and sessions, then 1.x, then 2.x with eager execution, and
> finally to PyTorch, and the bug I remember best happened in the easy part. My data loader used four workers, each forked with the same
> NumPy random state, so the "random" augmentations came in identical groups of four. The model trained fine and generalized a bit worse,
> which is the kind of bug that never gets found. Seed every library's random state per worker in `worker_init_fn`, and check that two
> workers produce different augmentations.

## Things that will bite you

- **Layers in a Python list** instead of `nn.ModuleList`.
- **`eval()` forgotten** at evaluation, or **`train()` forgotten** after it.
- **Averaging batch averages.**
- **Shuffled validation data** and non-deterministic evaluation (harmless for the metric, confusing for debugging).
- **Identical augmentations** across workers from a NumPy generator created in `__init__`.
- **Checkpoints without optimizer state**: the resumed run restarts Adam's moments from zero and the loss jumps.
- **Pickling the whole model** instead of saving the `state_dict`.
- **`loss.item()`** every step on a GPU (25.1), for logging you look at every 100 steps.

## Exercises

1. Why are parameters of layers stored in a plain Python list invisible to `model.parameters()`? What happens during training?
2. A validation set of 1,000 examples is evaluated in batches of 64. The model is perfect on the first 960 and wrong on the last 40. Compute the accuracy by averaging batch accuracies and by counting.
3. Write a `collate_fn` for sequences of different lengths that returns a padded tensor, a lengths tensor, and the labels.
4. List everything a checkpoint must contain to resume an AdamW run with a cosine schedule and random data augmentation *exactly*.
5. Dropout is active and BatchNorm is in training mode during your "evaluation". What happens to (a) the reported metrics and (b) the model?

<details>
<summary>Answers</summary>

1. `nn.Module.__setattr__` registers attributes that are `Module`s or `Parameter`s; a list is neither, so its contents aren't registered as submodules. `parameters()` doesn't return them, the optimizer never updates them, `.to(device)`
   doesn't move them (device errors on GPU), and `state_dict()` doesn't save them. On CPU the model runs but those layers stay at their random initialization forever.

2. Batches: 15 full batches of 64 (960 examples, all correct: accuracy 1 each) and a last batch of 40 (all wrong: 0). Mean of batch accuracies: $15/16 = 0.9375$. Counting: $960/1000 = 0.96$. The batch average weights the last
   40 examples as if they were 64.

3. `def collate(batch): seqs, labels = zip(*batch); lengths = torch.tensor([len(s) for s in seqs]); padded = torch.nn.utils.rnn.pad_sequence(seqs, batch_first=True, padding_value=0); return padded, lengths, torch.tensor(labels)`.
   (Also return a mask `torch.arange(padded.shape[1])[None] < lengths[:, None]` if the model needs one.)

4. Model state_dict; optimizer state_dict (AdamW's first and second moments and step counts); scheduler state_dict (its step counter); epoch and global step; best validation metric and early-stopping counter; RNG states for
   Python `random`, NumPy, torch CPU and every CUDA device; the data sampler's generator state (or the epoch number and seed that determine the shuffling); and the configuration/hyperparameters so you know what you're resuming.

5. (a) Metrics are noisy (dropout randomly drops units) and biased (BatchNorm uses the evaluation batch's statistics instead of the population's), usually worse and depending on batch size and order. (b) BatchNorm's running
   statistics are *updated* with the evaluation data, so evaluation changes the model; with `no_grad` the weights don't change, but the buffers do.
