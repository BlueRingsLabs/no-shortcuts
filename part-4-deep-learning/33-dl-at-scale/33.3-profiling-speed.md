# 33.3 Profiling and making it fast

*About 8 hours. Prerequisites: 33.1 (compute, memory and overhead), 25.2 (DataLoader), 25.3 (mixed precision, torch.compile). Lab: [`lab_33_3_profiling.py`](labs/lab_33_3_profiling.py).*

Performance work has one rule that everyone agrees with and almost nobody follows: **measure before you change anything**. I wrote this
lesson's lab to demonstrate a slow training loop whose obvious villain was a per-sample Python preprocessing function. Then I ran the
profiler, as the lesson tells you to, and it said the preprocessing was 7% of the time. Fixing it first moved throughput by between −9% and +15% across my runs, which is run-to-run noise. I kept
that in, because it's the most useful thing in the lab: your intuition about where the time goes is a hypothesis, and usually a wrong one.

This lesson is the method: benchmark correctly, find which of three regimes you're in, and apply the fixes that address that regime, in order
of payoff.

## Benchmark correctly first

- **Warm up.** The first iterations pay for memory allocation, cuDNN algorithm search, lazy initialization and, with `torch.compile`, compilation. The lab's first forward-backward pass takes twice as long as the later ones.
- **Synchronize on GPUs.** CUDA kernels run asynchronously; `time.time()` after a GPU call measures how long it took to *launch* the work. Call `torch.cuda.synchronize()` before reading the clock, or use CUDA events. (And note that a stray `.item()` or `print(loss)` in the loop also synchronizes, which is why it makes loops slower on GPUs: the CPU stops queuing work while it waits.)
- **Repeat and take the median**; report the variance. `torch.utils.benchmark.Timer` does this for small snippets.
- **Measure the thing you care about**: end-to-end training throughput (samples or tokens per second) and MFU (33.1), not the speed of one kernel in isolation.

## The three regimes

Horace He's framing: every step of a deep learning program is dominated by one of

1. **Compute**: time spent in big matrix multiplies. The good regime: you're using what you paid for. Improve it with lower precision (bf16, fp8) and tensor cores.
2. **Memory bandwidth**: time spent moving data for operations with little arithmetic per byte (elementwise ops, normalizations, softmax: 33.1's roofline). Improve it with **fusion**: fewer passes over memory.
3. **Overhead**: time spent in Python, in the framework's dispatcher, launching kernels, or waiting for data. The GPU sits idle between tiny kernels. Improve it with larger batches, fewer and bigger operations, CUDA graphs, compilation, and a data pipeline that keeps up.

The same fix helps one regime and does nothing for another; a profiler tells you which you're in.

## The profiler

`torch.profiler` records every operator (and, on GPUs, every kernel and memory copy), with self time and total time, call counts, shapes and memory. Label your own regions with `record_function("data")`, and export a trace to view the timeline in Perfetto or TensorBoard, where idle gaps on the GPU are immediately visible. On GPUs, **Nsight Systems** gives the whole-system view (CPU threads, kernels, NCCL communication, data loading); **Nsight Compute** analyzes individual kernels.

What to look for:

- **Top operations by self time**: is it matmuls (compute) or a long tail of small ops (bandwidth and overhead)?
- **Gaps on the GPU timeline**: the GPU waiting for the CPU (overhead) or for data (the input pipeline).
- **Many tiny kernels**: the signature of overhead. Tens of microseconds each, thousands per step.
- **Memory copies between CPU and GPU** in the middle of the step: something is moving data every iteration that shouldn't.

In the lab, the profiler's top operations for the slow loop are `mm` and `addmm`, and the labeled regions say 93% of the time is in forward, backward and the optimizer step, 7% in data preparation. So the model's arithmetic, in float64, is the first target.

## The fixes, roughly in order of payoff

The lab applies them one at a time to the same model, measuring samples per second:

| change | throughput | vs baseline |
|---|---|---|
| baseline: per-sample Python preprocessing, float64, batch 16, hand-written LayerNorm and GELU | 2,500 | 1.0× |
| + batched preprocessing | 2,540 | 1.0× |
| + float32 | 3,820 | 1.5× |
| + batch 256 | 17,500 | 7.0× |
| + built-in fused LayerNorm and GELU | 27,100 | 10.8× |
| hand-written layers + `torch.compile` instead | 25,900 | 10.3× |

(Numbers from my run on a 4-core CPU, each the median of three timed windows. Yours will differ, and not only in size: batch 256 bought 7× here and 2.8× on a 2-core cloud runner, because batch 16 is limited by Python overhead on one core and batch 256 by matrix multiplies that use every core. My first version of the lab asserted "at least 3×", calibrated without noticing on a 4-core machine, and it passed or failed depending on which machine CI happened to get. The ordering shouldn't change.) In general:

1. **Precision.** fp32 instead of an accidental fp64 (a NumPy array converted without a dtype is float64), and on GPUs **bf16 autocast** (25.3), which moves the matmuls onto tensor cores: often 2× to 3× by itself.
2. **Batch size and shapes.** Bigger batches amortize per-step overhead and give matmuls enough work; dimensions that are multiples of 8 or 64 map better onto tensor cores (the vocabulary size of 50,257 was padded to 50,304 in nanoGPT for a measurable speedup).
3. **The input pipeline.** `DataLoader` with `num_workers > 0`, `pin_memory=True`, and `persistent_workers=True` so the next batches are prepared while the model trains; preprocessing done once offline rather than every epoch; fast formats (Parquet, 11.1; WebDataset shards; memory-mapped token arrays). In the lab, with loading costing 1 ms per sample, three workers cut an epoch from 1.38 s to 0.59 s. Here the preprocessing fix mattered; in the table above it barely registered. Same fix, different bottleneck.
4. **Fusion.** Use the built-in fused operations (`F.layer_norm`, `F.scaled_dot_product_attention`, fused AdamW with `fused=True`) rather than composing them from primitives, and **`torch.compile`**, which traces the model and generates fused kernels (Triton on GPUs, C++ on CPUs) for chains of elementwise and reduction operations. In the lab, compiling the hand-written layers closes part of the gap to the built-in ones (between a third and all of it, across my runs). Compilation costs time on the first steps (37 s here on a cold cache, about 2 s once compiled kernels are cached) and recompiles when shapes change, so pad to a few fixed shapes or mark dimensions as dynamic.
5. **Overhead removal on GPUs**: CUDA graphs (`torch.compile(mode="reduce-overhead")`) replay a whole step's kernels with one launch; avoid `.item()`, `.cpu()` and Python-side logic on tensor values inside the step.
6. **Memory to spend on speed**: after activation checkpointing (33.1) has made room, spend it on a larger batch; conversely, don't checkpoint if you have memory to spare.
7. **Distributed efficiency** (33.2): overlap communication with computation, bucket sizes, and the right parallelism for the interconnect.

What *not* to do first: rewrite the model in a custom CUDA kernel. Write custom kernels (Triton makes it reasonable) only when the profiler shows a specific operation dominating after all of the above, and it isn't already fused by someone else.

## GPU memory problems

- **Out of memory**: reduce the micro-batch and use gradient accumulation; activation checkpointing; bf16; check for tensors kept alive by accident (a list of losses that holds their graphs: append `loss.item()` or `loss.detach()`).
- **Fragmentation**: memory is free but not contiguous. `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` helps; so do fixed shapes.
- **The memory snapshot tool** (`torch.cuda.memory._record_memory_history` and the visualizer) shows what's allocated where and when.

## Things that will bite you

- **Optimizing before profiling.** My lab, for one.
- **Timing GPU code without synchronizing.**
- **Timing the first iteration**, including compilation and allocation.
- **Accidental float64**, from NumPy.
- **`.item()` and prints inside the training step** on GPUs.
- **`num_workers=0`** with expensive loading, or workers without `persistent_workers` on small epochs.
- **Recompilation** on every new sequence length.
- **Micro-benchmarks** that don't reflect the real training step.

## Exercises

1. Why does `time.time()` around a CUDA matmul report a time that's too small, and how do you fix it?
2. A profile shows thousands of kernels of about 10 µs each, with gaps between them. Which regime is this, and what would you try?
3. Why do fused operations help memory-bound workloads but not compute-bound ones?
4. The lab's batched preprocessing fix barely changed throughput. Describe a situation where the same fix would have been the most important one.
5. Your training loop keeps `losses.append(loss)` for logging and memory grows every step until it runs out. Why?
6. After adding `torch.compile`, the first epoch is slower than before and later ones are faster, except on the last batch of each epoch, which is slow again. What's happening?

<details>
<summary>Answers</summary>

1. CUDA operations are queued asynchronously: the call returns once the kernel is launched, before it runs, so the host clock measures launch time. Call `torch.cuda.synchronize()` before starting and before stopping the timer (or use `torch.cuda.Event(enable_timing=True)` pairs), after warm-up, and repeat.

2. Overhead-bound: the GPU spends much of its time idle waiting for the CPU to launch the next small kernel. Try larger batches (more work per kernel), fusion (`torch.compile`, built-in fused ops) to reduce the number of kernels, CUDA graphs to remove launch overhead, and removing Python-side logic and syncs in the step.

3. Memory-bound operations spend their time reading and writing memory; fusing several of them into one kernel reads the inputs once and writes the output once, removing the intermediate round-trips to memory, so time drops roughly with the number of passes removed. Compute-bound operations (large matmuls) are limited by arithmetic throughput, and fusing them with neighbors saves memory traffic that wasn't the bottleneck.

4. When the model is cheap relative to preprocessing: a small model, or expensive per-sample work (image decoding and augmentation, tokenization, feature computation). With a large batch and fast compute, per-sample Python work dominates and the GPU waits for data; batching or moving preprocessing to DataLoader workers (or offline) is then the biggest win. The profiler's labeled regions would show data preparation as the majority of step time.

5. `loss` is a tensor attached to its computation graph; keeping it alive keeps every intermediate activation of that step alive for the backward pass that will never happen. Memory grows by one step's activations per iteration. Append `loss.item()` (a Python float; syncs on GPU, so maybe only every N steps) or `loss.detach()`.

6. The first steps include compilation, and `torch.compile` compiles for the shapes it sees. The last batch of an epoch is smaller (the dataset size isn't a multiple of the batch size), so it triggers a recompile for a new shape (and possibly again for the next epoch's). Use `drop_last=True`, pad the last batch, or mark the batch dimension as dynamic.
