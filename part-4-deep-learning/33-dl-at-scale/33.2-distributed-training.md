# 33.2 Distributed training: DDP, FSDP, tensor and pipeline parallelism

*About 12 hours. Prerequisites: 33.1 (memory and FLOP accounting), 25.2 (training loops), 26.1 (Adam's state), 29.2 (the transformer block). Lab: [`lab_33_2_distributed.py`](labs/lab_33_2_distributed.py).*

You go distributed for one of two reasons: the job takes too long on one GPU, or it doesn't fit on one GPU. They lead to different
techniques, and mixing them up is expensive. Data parallelism fixes "too slow" and does nothing for "doesn't fit". Sharding fixes "doesn't
fit" at a communication cost. Tensor and pipeline parallelism split the model itself, when even the sharded pieces are too big or the
communication is too slow. Every large model is trained with some combination, and the combination is chosen by exactly the arithmetic of
33.1 plus one more resource: the bandwidth between GPUs.

The lab runs real `torch.distributed` code with two CPU processes standing in for two GPUs, and checks each technique against a single process,
because the defining property of all of them is that **the math doesn't change**: same gradients, same parameters, different placement.

## Collective operations

Distributed training is built from a few **collectives**, implemented on GPUs by NCCL (and on CPUs by gloo, which the lab uses):

- **All-reduce**: every rank contributes a tensor; every rank gets the sum (or mean).
- **Reduce-scatter**: every rank gets one shard of the sum.
- **All-gather**: every rank contributes a shard; every rank gets the concatenation.
- **Broadcast**, **all-to-all** (for mixture-of-experts routing), and point-to-point **send/recv** (for pipelines).

An all-reduce is a reduce-scatter followed by an all-gather. Implemented as a **ring**, each rank sends and receives $2\frac{p-1}{p}$ times the tensor size, nearly independent of the number of ranks $p$: that's why data parallelism scales. The cost model everyone uses is **alpha-beta**: time $= \alpha + \text{bytes}/\beta$, a fixed latency plus bandwidth. The lab measures it over gloo on one machine: small messages take a few hundred microseconds whatever their size, and large ones approach the transport's bandwidth.
The lesson for code: many small collectives are dominated by latency, so frameworks **bucket** them.

## Data parallelism

Every rank holds a full copy of the model, processes a different slice of the batch, and the gradients are **averaged** across ranks before the optimizer step, so all copies stay identical. With equal-size slices and a mean loss, the averaged gradient is exactly the full-batch gradient: the lab's two half-batches, all-reduced, match one process on the whole batch to $4 \times 10^{-9}$.

**DDP** (`DistributedDataParallel`, Li et al., 2020) does the same thing efficiently: gradients are grouped into buckets, and each bucket's all-reduce starts as soon as its gradients are computed, overlapping communication with the rest of the backward pass. Practicalities:

- Launch with `torchrun --nproc_per_node=8 train.py`; each process gets a rank and a GPU.
- Shard the data with `DistributedSampler` and call `set_epoch(epoch)`, or every epoch sees the same order (25.2).
- **The global batch grows** with the number of GPUs. Keep it fixed with gradient accumulation, or scale the learning rate (the linear scaling rule with warmup, Goyal et al., 2017, works up to a point, 26.2).
- **BatchNorm** statistics are per rank unless you use `SyncBatchNorm`; with small per-GPU batches it matters.
- Every rank must call every collective in the same order. A rank that skips one (an `if rank == 0:` around a forward pass, a data-dependent branch) makes the others wait forever: **the classic hang**.

Data parallelism does nothing for memory: every rank holds all 16 bytes per parameter (33.1).

## Sharding: ZeRO and FSDP

**ZeRO** (Rajbhandari et al., 2020) removes the redundancy. With $p$ data-parallel ranks, each one keeps only a $1/p$ shard of:

- **Stage 1**: the optimizer state (Adam's $m$ and $v$, the fp32 master weights). Each rank updates only its shard of the parameters, then an all-gather distributes the updated values. The lab implements it by hand in twenty lines: after three Adam steps the parameters match PyTorch's unsharded Adam, fed the same averaged gradients, to $3 \times 10^{-8}$, with half the optimizer state per rank.
- **Stage 2**: also the gradients (reduce-scatter instead of all-reduce: each rank receives only the gradient shard it needs).
- **Stage 3**: also the parameters. Each layer's full weights are all-gathered just before its forward pass and freed after, and again for the backward pass.

Stage 3 is **FSDP** in PyTorch (`fully_shard`, "FSDP2"). Model-state memory per GPU becomes $16N/p$ bytes: a 70B model's 1.1 TB spread over 64 GPUs is 17.5 GB each. The cost is communication, about 1.5 times DDP's volume (an all-gather in the forward pass, another in the backward pass, and a reduce-scatter of gradients), hidden by prefetching the next layer's parameters while the current one computes.
The lab runs FSDP2 across two processes: its gradients match a single process on the full batch to $2 \times 10^{-8}$, and after three Adam steps its parameters match unsharded Adam on the same gradients exactly, with each rank storing half.

Choices within FSDP: the **wrapping unit** (usually one transformer block: smaller units mean less memory, more and smaller collectives), **hybrid sharding** (shard within a node, replicate across nodes, to keep the heavy traffic on fast links), and **CPU offload** of optimizer state (ZeRO-Offload), which fits bigger models on fewer GPUs at a large speed cost.

## Tensor parallelism

When one layer's computation is too large, or FSDP's all-gathers are too slow, split the matrices themselves. **Megatron-LM** (Shoeybi et al., 2019) splits a transformer's MLP so that it needs one all-reduce: the first matrix is split **by columns** (each rank computes some of the hidden units, and GELU applies elementwise, so no communication is needed yet), the second **by rows** (each rank computes a partial sum of the output), and an all-reduce adds the partial sums. Attention splits the same way by heads. The lab's two-rank version matches the full MLP to $7 \times 10^{-7}$, with each rank holding half the weights.

The cost: two all-reduces of activations per transformer layer in the forward pass (and two in the backward), in the critical path. That needs NVLink-class bandwidth, so tensor parallelism stays **within a node** (typically 8 GPUs). **Sequence parallelism** extends it to the LayerNorm and dropout regions, splitting along the sequence to save activation memory.

## Pipeline parallelism

Split the model **by layers** into stages on different GPUs; activations flow forward from stage to stage and gradients flow back. Communication is point-to-point and small (one activation tensor per micro-batch), so it tolerates slower links: pipelines cross nodes.

The problem is the **bubble**. Stage 4 can't start until stages 1 to 3 have processed the first input, and during the backward pass the reverse. Splitting the batch into $m$ **micro-batches** (GPipe, Huang et al., 2019) keeps stages busier: with $p$ stages, the idle fraction is $\frac{p-1}{m+p-1}$. The lab draws the schedule for 4 stages: 4 micro-batches waste 43% of the time, 16 micro-batches 16%.
**1F1B** schedules (PipeDream) interleave forward and backward passes to cap activation memory, and **interleaved** schedules (several smaller stages per GPU) shrink the bubble further; zero-bubble schedules split the backward pass to fill the gaps.

## Other dimensions

- **Context (sequence) parallelism**: split very long sequences across GPUs, with ring attention passing key/value blocks around (29.3's online softmax, distributed).
- **Expert parallelism**: in mixture-of-experts models (35.5), experts live on different GPUs and tokens are routed to them with all-to-all communication.

## Putting it together

Large runs combine them, **3D (or 4D, 5D) parallelism**: tensor parallelism within a node, pipeline parallelism across nodes, and data parallelism (FSDP or ZeRO-1) across the replicas that result, plus context and expert parallelism for long sequences and MoE. Llama 3 405B, for example, trained on up to 16,000 H100s with 8-way tensor, 16-way pipeline, up to 16-way context parallelism and FSDP-style data parallelism over the rest.

The decision procedure for everyone else:

1. It fits on one GPU and is fast enough: don't distribute.
2. It fits, but is too slow: **DDP**.
3. The model state doesn't fit (33.1's 16 bytes per parameter): **FSDP**. With LoRA (38.2) or 8-bit optimizers, check first whether it would fit without it.
4. FSDP's communication dominates, or single layers are too large: add **tensor parallelism** within nodes.
5. Hundreds of GPUs across many nodes: add **pipeline parallelism**, and read the Megatron and TorchTitan documentation, because you're now in the business of distributed systems.

## Operating it

- **Failures are normal at scale.** Llama 3's pretraining saw 466 job interruptions in 54 days, most from hardware. Checkpoint often, with **sharded** checkpoints (each rank writes its own part) and asynchronous writes; test restoring them; automate restarts.
- **Stragglers**: one slow GPU or link sets the pace for every synchronous step. Monitor per-rank step times.
- **Hangs**: mismatched collectives, one rank crashed, a deadlock in data loading. Set collective timeouts, and use `NCCL_DEBUG=INFO` and `TORCH_DISTRIBUTED_DEBUG=DETAIL` when they happen.
- **Reproducibility**: collective reductions aren't bitwise deterministic across different world sizes (floating-point addition order changes), so a run on 64 GPUs won't match 8 bit-for-bit. The lab's differences of $10^{-9}$ to $10^{-6}$ are this effect. Adam magnifies it: it divides each coordinate by that coordinate's own running scale, so where a gradient is about $10^{-8}$, rounding noise of the same size changes the step by a visible fraction of the learning rate. That's why the lab compares the sharded optimizers against Adam fed the *same* gradients: comparing against a separately computed full-batch run, as the first version of this lab did, passed on one CPU and failed on another.
- **Security**: the rendezvous endpoint (`MASTER_ADDR:MASTER_PORT`) and the collective transport have no authentication. On a shared or reachable network, anything that can connect can join or disrupt the job. Keep training traffic on isolated networks. Load checkpoints with `torch.load(..., weights_only=True)` or safetensors, since a pickled checkpoint is code (53.2). And remember that a cluster of GPUs with outbound internet access is an attractive thing to compromise.

> **Scar tissue.** The first time I got an allocation of eight GPUs on the university cluster, my distributed job hung at the end of the
> first epoch: every GPU at 100% utilization, no progress, no error, and my allocation hours draining. The dataset didn't divide evenly
> across eight ranks, one rank got one batch fewer, and it skipped the final all-reduce the others were waiting on. A collective blocks
> until every rank arrives, and busy-waiting looks exactly like working. `drop_last`, a `DistributedSampler` with padding, and a timeout
> on the process group. And a healthy suspicion of GPUs at exactly 100%.

## Things that will bite you

- **DDP for a model that doesn't fit**, or FSDP for one that does (paying communication for nothing).
- **Forgetting `set_epoch`** on the distributed sampler.
- **Rank-conditional code around collectives**: hangs.
- **The global batch size** silently multiplied by the number of GPUs.
- **Tensor parallelism across nodes**.
- **Too few micro-batches** in a pipeline.
- **Untested checkpoint restores**, discovered after the first node failure.
- **Unauthenticated rendezvous** on a reachable network; `torch.load` on untrusted checkpoints.

## Exercises

1. Show that averaging the gradients of $p$ equal-size shards of a batch (with mean loss per shard) gives the full-batch gradient.
2. A 13B model is trained with Adam in mixed precision on 16 GPUs of 80 GB. Compute the model-state memory per GPU with DDP, ZeRO-1, ZeRO-2 and ZeRO-3/FSDP. Which ones fit (before activations)?
3. In ring all-reduce, how many bytes does each rank send for a tensor of $S$ bytes and $p$ ranks? What happens as $p$ grows?
4. Why does Megatron split the first MLP matrix by columns and the second by rows, rather than the other way around?
5. With 8 pipeline stages, how many micro-batches do you need to keep the bubble under 10%?
6. Your 64-GPU run hangs at step 1 after you add evaluation code. What's the most likely cause?

1. With shards $B_1, \dots, B_p$ of size $b$ and total batch size $pb$: full-batch gradient $\frac{1}{pb}\sum_{i \in B}\nabla\ell_i = \frac1p\sum_{k=1}^p\frac1b\sum_{i \in B_k}\nabla\ell_i$, the mean of the per-shard mean gradients. (With unequal shard sizes you'd need a weighted mean.)

ZeRO-1: $26 + 26 + 156/16 = 61.75$ GB: fits, with little room for activations. ZeRO-2: $26 + (26 + 156)/16 = 37.4$ GB: fits. ZeRO-3/FSDP: $208/16 = 13$ GB: fits comfortably (plus temporarily gathered layers).

3. Reduce-scatter then all-gather, each moving $\frac{p-1}{p}S$ per rank: $2\frac{p-1}{p}S$ in total, approaching $2S$ as $p$ grows. The volume per rank is nearly constant, but the number of steps ($2(p-1)$) grows, so latency ($\alpha$) terms grow linearly with $p$; for large $p$, tree or hierarchical algorithms help.

4. Splitting the first matrix by columns gives each rank a complete subset of hidden units, so the elementwise GELU can be applied locally without communication. The second matrix split by rows then consumes exactly that rank's hidden units and produces a partial sum of the output, which one all-reduce completes. The other way around, the first product would produce partial sums, which would need an all-reduce *before* the nonlinearity (GELU of a sum isn't the sum of GELUs), adding a second communication.

5. $(p - 1)/(m + p - 1) < 0.1$ with $p = 8$: $7 < 0.1(m + 7)$, so $m > 63$: 64 micro-batches (in practice, interleaved schedules reach the same with fewer).

6. Collectives called unevenly: for example evaluation (or checkpoint saving, or logging that calls a collective such as a metric all-reduce) inside `if rank == 0:`, so rank 0 enters a forward pass whose FSDP all-gathers the other ranks never join, or the other ranks reach the next training collective while rank 0 is elsewhere. Every rank must execute the same sequence of collectives; run evaluation on all ranks (sharded) or on an unsharded copy outside the distributed path.
