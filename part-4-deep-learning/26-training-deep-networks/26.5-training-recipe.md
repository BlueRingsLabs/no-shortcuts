# 26.5 A recipe for training and debugging neural networks

*About 7 hours. Prerequisites: 25.1 to 25.3, 26.1 to 26.4, 18.4. Lab: [`lab_26_5_debugging.py`](labs/lab_26_5_debugging.py).*

Neural network bugs rarely crash. A wrong transpose, a softmax applied twice, labels misaligned by one row, an optimizer that never sees half the
parameters: the code runs, the loss goes down a bit, the accuracy is disappointing, and you spend a week tuning hyperparameters on a broken model.
Andrej Karpathy put it well in his "recipe" essay: neural net training fails *silently*. The defense isn't cleverness; it's a fixed sequence of cheap
checks that each rule out a class of bugs, done in order, before you believe any number. This lesson is my version of that sequence, and the lab plants
a bug for each check to catch.

I've watched talented people skip these steps because they felt beneath them. Don't. They take an hour, and I have never regretted doing them.

## The recipe

**1. Look at the data.** Before any model: print raw examples, plot them, look at label distributions, duplicates, corrupted files, weird lengths, the class balance, how labels were produced. Look at what the model will actually
receive, *after* the data pipeline (decoded, augmented, normalized, batched), not the raw files. A surprising fraction of "model problems" are visible in thirty seconds of looking at a batch.

**2. Build the skeleton with a dumb baseline.** A full train/evaluate loop (25.2) with the simplest possible model (logistic regression, a tiny MLP) and the evaluation you'll use at the end (Module 18). Fix seeds. Get a number. Everything later is
compared with it.

**3. Check the loss at initialization.** With a sensibly initialized final layer, the model's initial predictions are close to uniform, so the cross-entropy at step 0 should be about $\ln K$ for $K$ classes (2.30 for 10), and a regression loss
should be about the variance of the targets. If it's much larger, the output layer is initialized too large, or the targets are scaled wrong. Better: initialize the output bias to the class log-priors (or the target mean) so
step 0 already predicts the base rate.

**4. Check that the model uses its input.** Train (briefly) with all inputs set to zero. The loss should be clearly worse than with real inputs. If it isn't, the input isn't reaching the model: a detached tensor, a wrong column, a
bug in the data loader.

**5. Overfit a single batch.** Take one small batch (say 16 examples) and train on it alone, with the regularization off. The loss should go to (nearly) zero and the predictions should match the labels. If it can't memorize 16
examples, nothing downstream matters: something is broken in the model, the loss, the optimizer or the gradient flow. This is the single most valuable check on this list.

**6. Check for batch mixing with gradients.** Examples in a batch should be independent (except through BatchNorm in training mode). Compute the loss of example $i$ only, backpropagate to the *inputs*, and check that the gradient on example
$j \neq i$ is exactly zero. A nonzero gradient means an operation mixes examples: a `view` or `reshape` that should have been a `permute`, a reduction over the wrong axis. These bugs produce models that train (badly) and never
error.

**7. Now scale up and overfit the training set.** Make the model big enough to reach low training loss (26.3's memorization); if it can't, fix underfitting first (capacity, learning rate, 26.2's range test, normalization, 26.4).

**8. Then regularize** (26.3), watching the validation curve, and **then tune** (22.2), starting with the learning rate and its schedule.

**9. Squeeze last**: ensembles, test-time augmentation, longer training, bigger models, and the hyperparameters that matter least.

## Where silent bugs live

| Where | Bug | How it shows | Check that catches it |
|---|---|---|---|
| Data | labels misaligned with inputs (shuffled separately, off by one after a join) | model learns little; can still overfit one batch | look at examples with labels; baseline performance |
| Data | train and eval normalized differently | good validation loss, bad production | run training rows through the eval pipeline |
| Data | augmentation that changes the label | a ceiling on accuracy | look at augmented batches |
| Model | `view` instead of `permute`, wrong reduction axis | trains, underperforms | batch-mixing gradient check (6) |
| Model | softmax before `cross_entropy` (which expects logits) | slow training, tiny gradients | loss at init looks fine; gradient norms small; read the loss docs |
| Model | layers not registered (25.2) | part of the model frozen | count trainable parameters |
| Model | `train()`/`eval()` modes wrong | noisy or wrong evaluation | evaluate twice, compare |
| Loss | wrong reduction, mismatched class weights, `ignore_index` not set for padding | wrong scale, padding learned as a class | loss at init (3) |
| Optimizer | `zero_grad` missing or misplaced | erratic, exploding steps | gradient norm log |
| Optimizer | learning rate far off | flat or exploding loss | range test (26.2), overfit one batch (5) |
| Numerics | `log(0)`, overflow in float16, division by a zero std | NaN after N steps | anomaly detection, a NaN check in the loop |
| Infrastructure | data loader bottleneck | slow, GPU mostly idle | profile (33.3) |

When a NaN appears, `torch.autograd.set_detect_anomaly(True)` makes the backward pass report which forward operation produced it (slow; use it only while hunting). A cheap permanent guard: check `torch.isfinite(loss)` every
step and stop with a useful error, saving the batch that caused it.

## What to log, always

Training loss (per step, smoothed), validation loss and metrics (per epoch), the learning rate, the gradient norm (before clipping), the update-to-weight ratio for a few layers (26.2), throughput (examples per second), and a few
predictions on fixed examples you can look at. An experiment tracker (48.1) keeps these comparable across runs. Most "why did this run fail?" questions are answered by one of these curves.

> **Scar tissue.** A model I was training on my home GPU went to NaN at step 312, every time, with any seed. I spent a day on the data,
> convinced one sample was corrupt. It was the learning rate: no warmup, Adam's second-moment estimates are unreliable in the first few
> hundred steps, the effective step sizes were erratic, and one attention layer's logits blew through fp16's range. Logging the gradient
> norm per step would have shown it climbing for fifty steps before the crash. Now every training loop I write logs it from the first
> line.

## Things that will bite you

- **Skipping the single-batch overfit.**
- **Tuning hyperparameters on a model with a bug.**
- **Trusting a number you haven't compared with a dumb baseline.**
- **Changing several things at once**, then not knowing which one helped.
- **Evaluating on a pipeline different from training's** (normalization, tokenization, image resizing).
- **Believing a single run** (26.2, 18.4's seed variance).

## Exercises

1. What should the initial cross-entropy be for a 1,000-class classifier with a well-initialized output layer? What does an initial loss of 40 suggest?
2. Your model can't overfit a batch of 16 examples. List four things to check, in order.
3. Write the batch-mixing check in PyTorch for a model that maps `(batch, features)` to `(batch, classes)`.
4. A model's validation accuracy is excellent in your notebook and poor in the production service, with identical weights. Where do you look first?
5. The loss becomes NaN at step 12,000. Describe how you'd find the cause.

<summary>Answers</summary>

1. $\ln 1000 \approx 6.91$. A loss of 40 means the initial logits are huge (the output layer's weights or inputs are badly scaled), so the model starts out confidently wrong. Scale down the output layer's initialization (or zero it) and check
   the input normalization.

2. (a) The loss goes down at all with a larger and a smaller learning rate (learning rate or optimizer problem); (b) all parameters are registered and receive nonzero gradients (`requires_grad`, `ModuleList`, zero_grad placement); (c) the loss
   function receives what it expects (logits vs probabilities, label dtype and range, reduction); (d) the model can represent the mapping at all (capacity, no accidental bottleneck or detached tensor), and regularization (dropout, weight decay,
   augmentation) is off for the test.

3. `x = torch.randn(8, d, requires_grad=True); out = model(x); out[3].sum().backward(); mask = torch.ones(8, dtype=bool); mask[3] = False; assert (x.grad[mask] == 0).all()` (in `eval()` mode, so BatchNorm doesn't legitimately mix examples).

4. The preprocessing: production must apply exactly the same transformations (normalization constants, tokenizer and its version, image resizing and color order, feature computation, 22.1's training-serving skew). Then the model mode
   (`eval()`), dtype and device differences, and the input distribution itself (51.1).

5. Keep the checkpoint and the data order so you can reproduce it; add a finiteness check that saves the offending batch and stops; rerun from the last checkpoint before step 12,000 with `set_detect_anomaly(True)` to find the operation; inspect the
   batch (extreme values, empty sequences, division by zero), the gradient norm history (a growing trend suggests instability: lower the learning rate, add clipping or warmup), and the precision (float16 overflow, 25.3).
